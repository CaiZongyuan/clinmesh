# 病历修订区优先与签署历史折叠回顾

Status: implemented

## 问题与目标

医生在“病历记录”中签署一次病历后，当前页面先完整铺开“签署历史”，再显示“修订病历版本”表单。多次修订会使历史正文持续堆叠，医生必须越过已完成内容才能继续编辑，页面主次不清，也不便快速回顾各版本。

目标是将当前编辑或修订区域放在前面，已完成的签署历史统一放在其下方，按明确顺序排列，并支持逐条折叠、展开回顾。

## 范围

- 门诊医生“病历记录”页的已签署文书与修订表单，覆盖共享 standalone Web 和 DSH React Surface 入口。
- 历史范围为当前就诊已有的首次签署版本与后续签署修订版本。
- 调整区域顺序、历史条目的摘要与折叠交互，沿用现有病历字段、签署及修订合同。

## 用户故事

1. 作为医生，我希望签署后优先看到当前可修改的区域，以便继续补充和修订。
2. 作为医生，我希望在修改区域下方按版本顺序回顾已完成病历，并按需展开某个版本，以便查看当时的完整记录。

## 验收条件

- [x] A1：存在签署版本且允许修订时，“修订病历版本”表单位于“签署历史”之前；历史正文不会排在修订表单上方。
- [x] A2：历史完整保留首次签署与全部后续修订；按确定的版本顺序排列，刷新及新增修订后保持一致，不重复、不遗漏。
- [x] A3：每条历史均可独立折叠、展开；收起时仍显示版本号、签署时间和展开状态，最新版本有明确标识，存在修订原因时可在摘要中识别。
- [x] A4：展开后可阅读该版本完整病历字段与修订原因；不同版本内容保持各自签署时的原文，支持同时展开多条以便回顾。
- [x] A5：折叠或展开历史不会提交修订、清空未提交的表单输入，或将旧版本内容写回当前修订表单；修订仍以最新签署版本为基础。
- [x] A6：修订成功后，新版本进入历史列表，旧版本继续保留，修订区仍在前；成功与失败反馈保持可见且不重复铺开历史正文。
- [x] A7：尚未签署时保留现有草稿编辑入口，不出现空的历史容器；没有修订权限时仍可按权限只读回顾历史，不显示可提交的修订表单。
- [x] A8：长病历、多版本与 DSH 窄分屏下，摘要和正文可读，展开控件可用键盘操作，并向辅助技术表达展开状态；切换病例不串用历史或展开状态。

## 设计决定

当前修改区在上，已完成签署历史在下，历史有序并可折叠展开。共享实现位于 `apps/web/src/app/doctor/clinical-document-page.tsx`。

历史按版本号由新到旧排列（V3 → V2 → V1），每条默认收起，允许多条同时展开；最新版本具有明确标识。折叠状态只属于当前病例的页面视图，刷新或切换病例后全部收起。

签署件不可覆盖，修订仅从最新版本创建新文书，详见[系统架构](../architecture/fhir-and-commands.md#53-资源映射)。完整病历字段及签署保护沿用[病历字段规格](2026-10-14-clinical-document-fields.md)。

## 测试策略

实施时在现有医生工作台组件测试中覆盖区域顺序、多个版本的排序与完整性、独立折叠、表单未提交内容保护及只读入口。沿用 `apps/web/e2e/consultation-signing.spec.ts` 的真实签署与修订旅程，使用 Playwright 验证首次签署、多次修订、刷新、历史展开和窄视口布局；新增修订后逐条核对历史正文。

共享页面在 React 18 DSH 和 React 19 standalone Web 下验证折叠交互与现有修订确认弹窗；不使用仅在 React 19 可用的 API。

## 范围外

跨就诊历史病历聚合、版本差异比较、恢复旧版本、删除历史、改变签署或完诊状态机、修改接口及持久化格式、Mobile 页面改造。

## 依赖与风险

无外部能力依赖。现有签署测试直接断言已签署正文可见，折叠后应先明确展开目标版本再断言内容，保留原有业务保护断言。
