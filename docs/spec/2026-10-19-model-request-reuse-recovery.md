# 同输入建议复用、患者回答去重与模型任务阶段恢复

Status: implemented

## 问题与目标

基线审计发现，同正文病历另存会推进草稿版本并使五类诊疗建议失效；同一待回答问题的重叠请求会分别调用模型，虽然最终只保存一份回答；建议任务的核验请求失败或关停恢复会重新执行已经成功的生成。三个问题及对照条件由[离线动态复现](../research/2026-10-19-agent-model-call-lifecycle.md#七三个风险的离线动态复现)保存证据。

目标是保留病历保存与临床安全边界，让同输入建议复用、同题并发生成合并、成功步骤持久复用，并用跨重启的请求次数限制约束自动继续；范围限于上述三个问题。当前机制由[临床业务流程](../architecture/clinical-workflows.md#81-门诊闭环)与[存储合同](../architecture/storage.md#模型执行恢复)拥有，本规格保留正式需求与验收条件。[模型调用停用、预算与用量监控](2026-10-19-model-usage-control.md)继续拥有全系统停用、Token 与金额额度、用量账本和仪表盘。

## 范围

- 五类诊疗建议的输入有效性、资料与目录筛选、候选生成、分批核验、有限恢复，以及 Web/DSH 的人工恢复操作。
- 患者回答的提问重发、补答重试、在途共享、持久尝试状态、关停处理与同键回放。
- 上述链路通过 DSH 桥或直连 Provider 发出的每次实际模型请求；运行时状态、次数和成功步骤保存到现有 SQLite 持久边界。
- 保留现有岗位授权、Workspace/Epoch 隔离、共享 Command、幂等输入冲突检查、预期版本、审计、临床核验及采纳保护。

## 用户故事

1. 作为医生，我希望保存完全相同的病历后继续使用已有建议，也保留正常的保存版本与审计。
2. 作为医生，我希望同一个待回答问题的重复提交等待同一份回答，连接重发不会悄悄启动另一轮生成。
3. 作为医生，我希望核验技术失败后仅恢复未完成步骤；需要人工处理时能区分继续原任务与重新生成。
4. 作为开发协作者，我希望用合成模型、临时数据库和少量受控请求证明调用次数与恢复边界。

## 验收条件

- [x] A1：同文保存继续推进草稿版本并记录审计；全部临床输入及来源相同时，五类建议的有效性、generation 和已成功步骤保持不变。既有空建议复现的调用数在同文另存及后续自动请求后仍为 5；无保存重复请求继续复用。
- [x] A2：正文按结构化字段精确比较，不合并空白、标点或同义改写；仅草稿保存版本与保存时间不属于临床变化。来源、报告、诊疗状态、适用目录或指南发生有效变化仍使旧结果失效；独立的保存、签署与采纳版本检查继续生效。
- [x] A3：同文保存不取消在途建议；实际临床输入、代次或授权失效时，旧任务尽力取消，后续筛选、生成、核验、纠错或重发不再开始。提交与采纳重新验证当前有效性，旧结果不能覆盖新任务。
- [x] A4：同一待回答医生轮次的 ask、ask 重发和补答重试共享一次在途生成，后来请求等待同一结果；各请求分别完成授权、输入冲突检查和自身回执。其他轮次的同文问题不合并。
- [x] A5：相同 ask/retry 幂等键只恢复或回放原尝试：执行中等待原截止时间，成功返回已存回答，失败或未知返回原状态，均不新增推理。回答保存后响应丢失，以及完成后的串行回放，仍复用已保存回答。
- [x] A6：患者回答开始后的 30 秒期限不因新增等待者延长；单个或全部页面离开不取消已经接受的问题。runtime 关停主动取消并收束执行；医生问题保留，持久状态区分执行中、成功、失败和未知，重启不自动补答。
- [x] A7：人工明确补答使用新 retry 意图与新幂等键；原尝试已终止且问题仍待答时，采用当前模型。原尝试仍执行时仍加入原尝试；同一人工重试意图的传输重发不重新生成。
- [x] A8：建议任务按稳定的阶段与批次持久保存成功结果，包括必要的资料筛选、目录筛选、候选生成及各核验批次；后段技术失败或重启后，在符合自动或人工恢复条件时只恢复未完成单元，成功生成不重复，已成功的核验批次也不重做。
- [x] A9：每个建议阶段批次含首次最多 3 次实际请求，同一 generation 的全部批次合计最多 4 次额外请求。限流重发、格式纠错、技术故障重试和人工继续共用持久计数，重启及 outbox 重新领取不清零；并发派发不能超额。
- [x] A10：不同正常批次分别有一次首次请求，不能靠换批次 ID、重新分组、重建计划或调度 attempt 获得新首次额度。任一次数上限耗尽即停止新派发，并如实显示原因；普通自动请求不能通过新建 generation 绕过限制。
- [x] A11：明确的可恢复技术失败允许在剩余额度内自动恢复失败单元；合法的核验否定正常结束，不重做候选直至通过。请求发出后因关停、超时、断流等未取得完整终态，按结果未知处理，保留次数占用并停止自动重发；此前成功步骤保留。
- [x] A12：“继续原任务”保留原 generation、模型、成功步骤与剩余额度，只处理未完成单元；未知请求只有本次人工明确继续才允许再次派发。次数耗尽、输入或授权失效时不能继续；同一继续意图的重发不再次开放派发。
- [x] A13：“重新生成”是明确的人工操作，按当前资料与当前模型开启新 generation 和新次数额度。普通 `refresh:false` 请求遇到同输入失败、未知或耗尽状态只返回原状态。重新生成命令的传输重发不创建多个任务，旧结果不能覆盖新 generation。
- [x] A14：新持久状态、恢复数据、接口和工具响应在边界验证；旧成功回答与回执保持可重放。指纹策略升级不把可验证为同输入的旧成功建议直接变成自动重算；缺少执行证据的旧在途任务按未知处理，不能默认为未派发。
- [x] A15：从真实 Web 入口验证保存后五类自动准备的调用数不增长，验证同题等待、失败与未知反馈，以及继续原任务、次数耗尽和重新生成。DSH 共享入口保持相同行为；涉及的公开 Operation/CLI 恢复合同、运行时 Skill 与示例漂移测试同步更新。

## 设计决定

### 输入与安全边界

建议采用规范化的临床输入指纹，草稿版本与保存时间留在保存记录及审计中。模型侧的草稿证据标签也使用稳定名称，避免指纹忽略变化但实际提示词仍因保存时间而变。完整来源及其有效性参与失效判断，不仅比较最终筛选出的片段；不新增跨历史任务的语义相似缓存。

成功结果不因当前模型设置变化而自动刷新。任务内自动恢复及“继续原任务”沿用原绑定；人工新补答或“重新生成”采用当前模型。每次实际派发前与结果提交时，检查该任务的输入、代次及受信授权；这些检查独立于用于保存、签署和采纳的资源 CAS。

旧成功建议的升级兼容基于其已保存的原始输入快照，验证旧指纹与结果归属后，再分别规范化原快照和当前输入。只有规范化结果确实相同才复用，不能无条件把旧结果绑定到当前指纹，也不能改写历史回执或审计来伪造一致。覆盖升级前已经发生同文保存的情况；损坏或不一致快照不能被迁移为有效结果。

### 患者回答与请求身份

在途共享按受信 Workspace/Epoch、Encounter 与待回答医生轮次协调，不按问题正文或单个 HTTP 幂等键去重。共享项持有生成与已保存回答，不复用首个调用者整份 HTTP 回执或审计身份。每个 ask/retry 意图持久关联其尝试，解决仅有内存 Promise 在失败、关停或重启后无法阻止同键重新推理的问题。

先查询已保存回答，再解释尝试状态。失败、取消或未知的原意图保持终态，只有明确人工新 retry 才能建立新尝试；生成中的新 retry 加入已有执行，并继续关联它的原截止时间和结果。运行时正常关闭要等待患者回答执行收束，不能仅清理内存映射。

### 阶段恢复与派发计数

候选只在全部必要核验完成后成为可采纳建议。私有成功步骤记录可以保存恢复所需候选及核验结论，不能因此提前发布未核验候选。恢复绑定确切输入、generation、原模型、候选与核验批次依赖、处理策略版本；不同输入或候选的核验结论不互用。

阶段计划在依赖确定后持久保存唯一批次身份及内容哈希，受现有历史、目录与候选数量边界约束。预算检查在每次 Provider 外部派发前通过短事务原子预占，覆盖 Provider 内部重发和格式修复；网络等待始终在事务外。只有计划内首次请求是正常额度，其余派发消耗单元及 generation 的额外额度。outbox attempt 是调度次数，不能代替模型请求次数。

已派发或无法证明未派发的中断请求保留次数占用与未知状态；保存预占与外部执行之间的崩溃窗口采取相同保守解释。完整成功结果一旦持久化便不重做；外部结果无法查询时不承诺跨崩溃只推理一次。单次模型与任务的现有时间配置保持；本次新增次数限制不以重新开始计时获得额外次数。

非平凡取舍及兼容要求见[请求复用与持久恢复决策](../decisions/implemented/architecture/2026-10-19-model-request-reuse-recovery.md)。

## 测试策略

模型传输全部由合成 Provider 或 `DshModelProvider` 的受控 fetch 拦截，数据库使用独立临时 SQLite。通过少量请求及调度屏障验证重叠、不同批次、并发预占、响应丢失、关停和重启，不执行真实模型或压测。将既有[诊断用例](../../apps/server/tests/agent-usage-risks-reproduction.test.ts)的风险断言转为修复后的合同，并保留无保存重复请求和回答完成后串行重放两个对照。

Server 测试拥有完整矩阵：同输入与真实输入变化、ask 与 retry 重叠、同键异文拒绝、失败或未知回放、人工新模型、每一层额外请求的共享计数、并发时最后一个额度、每个成功步骤的持久化、多个核验批次局部失败、旧任务迁移和迟到结果。DSH 与直连 Provider 均验证实际派发前的限制，不能只在 `completeJson` 外层计一次。核验不通过与请求技术失败分别验证。

Playwright 使用真实 Hono listener、生产 Web 入口、合成模型与临时数据库观察自动 POST、模型派发次数和公开业务状态。共享视图和 DSH wiring 按[测试策略](../testing.md#用户界面验证)补充对应合同；新增对话框时覆盖 React 18/19。文档阶段只运行文档检查；实施后的代码验证按实际 diff 运行受影响的最小集合，跨包接口或持久化发布路径变化再按仓库要求扩大检查。

## 范围外

- 全局停用、Token 或金额额度、价格映射、完整逐次用量账本、仪表盘，以及 DSH 原生会话和宿主内部请求拦截。
- 修改自动记录或病历质控的核验责任、一般聊天来源采集范围、其他 Agent 的临床触发条件。
- 改变同文保存的版本语义、删除必要临床核验、按同义文本跨问题或跨病例缓存回答。
- 多服务端进程写同一个 SQLite、分布式锁、供应商结果查询或外部推理 exactly-once 承诺。
- GitHub 写入、提交、发布、真实模型开发验证或压测执行。

## 依赖与风险

现有模型桥只有路由解析与生成，没有可依赖的生成幂等或结果查询能力。取消、失败和未知请求不等于零消耗；本规格限制 ClinMesh 可观察的实际派发次数，不代表成功推理次数或费用额度，也不声称覆盖 Provider 或宿主内部不可见重试。

同键失败回放会有意改变既有测试中的再次生成行为，必须同步公开恢复合同和客户端明确重试入口。持久尝试与步骤数据需要可恢复迁移；旧输入无法安全验证时不得假装命中，新策略也不能通过重建任务隐式重置次数。
