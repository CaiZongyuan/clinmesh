# 门诊与住院共享收款交易内核

Status: implemented

执行追踪：[Issue #342](https://github.com/CaiZongyuan/clinmesh/issues/342)，实施切片为 [#354](https://github.com/CaiZongyuan/clinmesh/issues/354)、[#355](https://github.com/CaiZongyuan/clinmesh/issues/355) 和 [#356](https://github.com/CaiZongyuan/clinmesh/issues/356)。本规格承接 [#225](https://github.com/CaiZongyuan/clinmesh/issues/225) 转出的共享收款范围（原 A01），C01–C11 的验收入口与适用边界见[验收证据](#验收证据)；规格状态不替代 GitHub 执行票的交付与结案状态。

## 问题与目标

门诊和住院分别维护收款尝试、确认和结果恢复，会使共同规则重复并产生分叉。本规格统一收款交易内核和交易存储，由两端分别拥有业务入账及资金用途分配规则，保持现有收费、医保、首次结算及归档后调整的业务含义。当前机制归[收款存储与事务](../architecture/storage.md#门诊收款记录)，职责理由归[支付与住院职责边界决策](../decisions/implemented/architecture/2026-10-21-payment-inpatient-drg-boundaries.md)。

## 范围

- 统一门诊账单、住院预交金及补缴的收款尝试、结果确认、支付方式记录和原尝试查询恢复，保留部分及组合支付。首次与后续补收使用同一交易内核，并保留各自业务用途。
- 使用共同交易模型及统一交易存储，保留 Workspace、Epoch、患者、就诊、账单、费用、渠道尝试、原交易与 Command 回执之间的关联；成功、拒付和结果未知具有一致含义。
- 门诊负责费用关联、应收与结清判断及收费后的业务放行；住院负责预交金入账与抵扣、补缴、首次结算及后续调整。各自保留业务门禁、预览及收费页面，原交易退款继续使用既有退款 owner。
- 每笔资金绑定原就诊及用途，同一患者的不同门诊或住院不自动合并余额或跨就诊抵扣。
- 当前开发阶段不迁移旧合成历史交易，按[开发数据切换](#开发数据切换)重建受影响的合成就诊运行链并保留可复用资产；切换后新交易的持久化、重启恢复和引用完整性继续验收。

## 用户故事

1. 作为收费员，我希望两类就诊采用一致的收款结果和恢复规则，避免重复收款或把未知结果当成完成。
2. 作为收费员，我希望资金分配、预交金抵扣和剩余应收能够回查原就诊、账单及交易，后续退款仍引用原款。
3. 作为护士，我希望首次住院结算只根据确定资金结果完成，查询恢复后可继续清床。
4. 作为开发维护者，我希望统一交易模型能在保留患者库及参考资产的前提下切换，并从岗位入口重新建立合成就诊，以验证新的收款与入账链路。

## 验收条件

- [x] C01：门诊和住院实际通过同一交易内核创建尝试、确认结果和查询恢复，使用统一交易存储；共同状态及恢复规则不在两端各自维护。门诊费用分配与住院预交金使用、抵扣及结算规则分别由业务 owner 执行。
- [x] C02：两端分别完成部分及组合支付，支付方式及金额组成可核对；门诊分配到原费用，住院预交金抵扣、补缴、未分配余额与已使用金额可从公开接口核对，均关联原就诊、账单、费用和交易，不重复保存另一套可编辑资金余额。
- [x] C03：成功、拒付和结果未知分别可见；未知时查询原尝试取得确定结果，重试或重复结果不新增收款或分配。确定失败后按当前预览恢复，不复用过期余额。
- [x] C04：相同幂等键并发或重放返回同一结果，不同载荷被拒绝；不同键竞争不能突破各自业务允许的应收或补缴约束，也不重复分配或抵扣，冲突有明确恢复路径。预交金仍按住院既有规则办理，不把本次重构解释为新增应收上限政策。
- [x] C05：所需住院资金未知时，首次财务完成与清床继续被阻断；查询原尝试成功后可继续。后续财务调整不倒退已发生的首次结算、出区、清床或归档事实。
- [x] C06：原交易引用、可退余额及未知退款预占仍由既有退款 owner 核对；统一收款不重复记录退款或待遇分摊。
- [x] C07：完成开发数据切换后，可通过原岗位入口重新建立受影响的合成就诊；保留资产的身份、来源及内容完整，旧运行意图不能在新数据世代重放。新模型的成功交易、未决尝试、退款引用和回执跨重启可读、可恢复，原交易与分配关系不被覆盖；不要求读取或恢复被舍弃的旧合成历史交易。
- [x] C08：岗位、病区、Workspace 和 Epoch 隔离继续有效，越权被拒绝，正式动作及其恢复保留审计。
- [x] C09：同一患者不同次门诊、不同次住院及门诊与住院之间的资金保持原就诊和用途绑定；恢复、分配及退款不能改绑另一就诊，也不隐式形成通用钱包。
- [x] C10：本地交易事实、业务入账或分配、预览消费、Command 回执、审计及相关 outbox 在同一 Command 事务提交；故障注入验证部分写入回滚，重放或恢复后只出现一次有效收款及业务入账。本地事务原子性不被扩大表述为外部支付渠道能够随数据库回滚。
- [x] C11：门诊收费和住院财务的现有页面分别接入共享内核，预览、审阅确认、三类结果和原尝试恢复在原业务入口可用；首期不增加统一交易工作台。

## 设计决定

共享交易内核拥有交易身份、金额与支付方式事实、原始结果及追加查询结果；业务 owner 拥有应收计算、资金用途分配、预交金使用和业务放行。Payment Tender 表达付款方式组成，Payment Allocation 表达原就诊内的费用或结算用途关联，术语归[领域词汇](../../CONTEXT.md#费用与医保)。

共同交易内核在现有 Server 内由业务 Command 调用，沿用受信上下文、幂等、预期版本、事务和审计机制；调用共享内核不把门诊和住院的公开动作合并为任意交易写入口。原 `RefundLedger` 接入统一原款引用和支付方式事实，继续拥有退款余额、未知占用及原交易恢复；不重写退款状态机。

门诊收费和住院财务保留各自岗位入口，接入统一交易结果与恢复机制；必要合同变化同步其对应业务接口、CLI/Catalog 和运行时 Skill。职责及真实取舍见[支付与住院职责边界决策](../decisions/implemented/architecture/2026-10-21-payment-inpatient-drg-boundaries.md)，门诊分配、住院用途和一次性切换分别由对应 implemented Note 保存独有理由。

### 开发数据切换

本次模型切换允许舍弃旧合成历史交易，并重建受旧支付结构影响的合成就诊运行链，包括本院患者及就诊物化、临床进度、费用、收退款、预交金、首次结算、后续调整、病案冻结及关联运行回执。这些病例通过岗位流程重新建立运行事实，不将原已结算或已放行的进度留在缺少资金依据的新模型中，也不为被舍弃的旧交易保留两套格式适配。

切换保留患者来源 Profile/Revision、Case、Persona、可复用来源病史及检查结果、账号与成员关系、岗位及目录配置、独立 Reference SQLite 和 Guideline SQLite。保留来源、配置、场景安装和模型用量等持久 owner 的 Command 回执及 effects，重放不能重新安装或覆盖原资产。其他跨 Epoch 状态，例如号码发行权威、模型用量及额度、独立保留的审计，继续按各自 owner 合同保留；本次旧合成交易舍弃范围不包含这些数据。

患者库资产与运行记录位于同一 operational SQLite，切换须按保留清单处理并验证身份、数量及内容完整，不能以删除整个业务库代替关联运行链重建。现有 Epoch reset 会保留旧世代，不直接完成旧 schema 转换；明确的一次性开发切换步骤、失败诊断和恢复路径归[部署指南](../deployment.md#共享收款的一次性开发切换)，详细保留及校验合同归[存储与事务](../architecture/storage.md#共享收款的一次性开发切换)。新运行世代继续拒绝旧 Command 意图和迟到回调，正常启动及岗位操作不隐式清空业务数据。

切换验收使用含旧交易、关联运行事实和保留资产的合成临时库，验证重建范围及保留边界；不承担旧交易数据保真迁移。切换后以新交易覆盖成功、未知、拒付、退款及重启恢复，不将本次允许重建推广为后续升级可默认丢弃数据。

## 测试策略

主矩阵通过公开 HIS Query/Command、真实临时文件 SQLite 和确定性合成支付渠道验证。沿用 `outpatient-workflow-http.test.ts`、`inpatient-payments-http.test.ts` 及 PCI 联合账本的有效业务证据，并为共享内核及统一存储补两类业务的分配、三种结果、原尝试恢复、幂等、独立数据库连接竞争和新交易重启断言；从公开交易、账单和回执核对唯一性，不用各端旧成功路径代替共享实现验收。

共享内核的 Interface 是共同状态转换与故障断言的直接测试入口；两端公开 Command 验证各自业务入账、用途隔离和门禁。故障注入覆盖交易结果写入与业务入账之间的回滚；同患者多就诊矩阵覆盖来源改绑及跨就诊资金复用拒绝。开发切换另用非空合成旧库核对保留资产、运行链重建、新世代隔离及切换失败可诊断，不要求迁移旧交易。

Web 仅补两端实际收款入口及恢复接线，按现有测试策略覆盖真实岗位页面和 React 18/19 Surface 合同；不新增统一工作台。CLI/Catalog 或运行时 Skill 合同若变化，在同一 diff 同步 owner、示例漂移和恢复合同。全部使用合成 Provider 和临时业务库，真实模型及压测另行取得当次运行授权。

## 范围外

- 改动患者医保待遇算法、DRG 分组、临床状态机或病案归档规则。
- 新增成本数据 owner、完整医院成本核算、财政票据或真实支付/医保渠道。
- 重写既有退款 owner，或以恢复床位、解档、覆盖历史账目处理资金差异。
- 患者通用钱包、跨就诊转款或自动抵扣，以及统一交易查询和异常处理工作台。
- 旧合成历史交易的数据迁移或旧格式读取兼容，以及通过整库删除清理患者库和其他保留资产。

## 依赖与风险

既有门诊、住院、退款、医保和归档后更正继续拥有各自业务规则；共同交易内核不接管这些状态。首次财务门禁与后续调整必须分别表达，交易来源及用途不能被公共模型抹平。

开发切换会舍弃受影响的旧合成就诊运行链，相关病例需重新执行岗位流程；患者库、配置和其他保留资产的丢失不属于允许的切换结果。新模型产生后的未知尝试及原回执须持久保留并可恢复，切换例外不能替代正常业务的资金安全和审计要求。
