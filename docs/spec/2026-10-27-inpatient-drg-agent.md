# PCI 住院 DRG Agent 与耗材建议

Status: implemented

本规格拥有首期 PCI 住院 Agent 的产品范围、围手术期耗材建议、持续跟进和病例用量展示要求。首期使用明确标识的有限合成仿真范围，当前行为见[临床流程合同](../architecture/clinical-workflows.md)。既有分组、计价、患者医保及医院核定由[支付与 DRG 规格](2026-10-15-drg-prescription-budget.md)拥有。

## 问题与目标

需要将既有实际耗材登记、费用推演和 DRG 分组贯通为术前具体耗材建议、术中逐笔使用与后续建议更新、术后差异跟进。医生需要在同一次住院内看清建议依据、实际执行与费用变化，以及尚待处理的问题。

首期以 PCI 为主线，由医生开启该次住院的 DRG 跟进。任务覆盖在院评估、术前、术中、术后及出院前核查，持续到病案归档并完成交接。关闭或切走病例页面后，任务在授权有效期间继续；界面明确展示模型调用及用量，不能让后台工作成为不可见的消费。

## 范围

- 医生确定治疗方向和术式；Agent 在该方案内建议本院具体耗材产品、规格、预计数量和备选项，并解释依据及费用影响。医生可以修改和确认建议，正式临床与账务操作继续经过对应岗位审阅。
- 选型所需关键临床参数由医生根据已有检查结果手工填写并确认，保留测量对象、部位、单位及可追溯依据；未知项保留未知。首期不增加报告自动提取或影像像素分析。
- 在医生认可、临床适用且器械兼容的候选中，优先推荐预计费用较低的方案。费用按本院收费定义及数量计算，采购成本、医院完整成本和利润不由该排序推断。
- 术中由手术团队人工逐笔确认实际耗材使用；Agent 随记录更新后续建议和费用预估。实际使用、已确认计划与新建议分别表达，既有使用事实和历史依据保留。
- 术后核对计划与实际耗材、记录与计费的一致性，更新 DRG 和已有后续治疗计划的费用评估；差异形成待办，由对应岗位处理后重新核查。
- 关键记录变化触发自动跟进，普通更新在病例内展示，需要人核实或决定时提醒。归档交接后结束本轮自动跟进，首期不增加医保办阶段的 Agent。
- 在病例内展示本次住院 DRG 任务的模型用量摘要及明细入口，复用现有用量账本和管理页面，补齐住院任务、阶段及权限关联。

## 用户故事

1. 作为住院医生，我希望主动开启某次住院的 DRG 跟进，在离开页面后仍保留有效任务，并在回来时看到最新结果、待办及用量。
2. 作为术者，我希望依据已确认的临床参数比较可用耗材，术中实际使用变化后获得更新的后续建议，而不是覆盖原计划或已发生事实。
3. 作为处理差异的岗位人员，我希望看到问题、原始依据和当前处理状态，核实或更正后能够确认问题是否解决。
4. 作为病例负责人，我希望看清模型何时被调用、为什么调用、在哪个阶段消耗多少 token，以及哪些费用或用量尚不完整。

## 验收条件

- [x] A1：医生从当前获授权的住院病例开启跟进；同一意图的重复提交、刷新或重启不重复创建有效任务，也不重跑仍有效且已成功的分析。结果未知的请求保留待核查状态，不自动重发。任务可显式停止，失权后不再发起分析。
- [x] A2：关键临床参数来自医生确认并保留依据；缺少必要参数、单位不明或相互矛盾时，明确列出缺项，不从目录规格、病例底稿或目标费用反推患者信息。
- [x] A3：耗材建议引用本院可用产品及版本、适用与兼容依据、预计数量依据和费用口径；先核对临床条件，再在医生认可的候选中按预计费用比较。缺价不能当零价，未核验候选不能因便宜而成为确定推荐。
- [x] A4：术中可连续登记同一次手术的实际耗材使用；单笔使用不提前完成手术。部分使用预留、额外使用、替换及记录更正均可追溯，完成手术后不重复记费或重复计算预留。
- [x] A5：实际使用更新后，已发生部分如实保留，后续建议和费用投影按最新依据更新；临床依据、用途或计划变化使受影响旧建议立即标为需重评。未完成新核验时，不把旧建议显示为当前有效。
- [x] A6：术后分别展示计划与实际差异、记录与计费疑点及阶段性 DRG 结果。耗材数量增加不直接提高病组；实际诊断、操作及所选规则决定分组，归档结果保持冻结。
- [x] A7：同一问题按相同依据去重，待办可区分待核实、处理中、已解决及经人工判断无需处理；处理后通过最新业务事实复查。仅关闭提示或模型自行声明不能证明正式更正已经完成。
- [x] A8：离开页面后任务仍按其病例与岗位授权运行；患者切换、授权撤销、转科及责任变化不能让旧任务越权读取或写入。旧任务的迟到结果不能覆盖其他病例或更新后的建议。
- [x] A9：病案归档并完成交接后停止本轮自动分析，保留结果、用量及未解决待办的处理归属。AI 待办本身不新增出院门禁，既有临床、财务及归档条件继续执行；交接不把未解决问题自动标为已解决。
- [x] A10：已发生正式收费净额严格大于当前有效 DRG 支付参考额的 3 倍时，显示非阻断的特例单议提醒；等于 3 倍不触发。缺少有效正参考额、分组或参数时说明无法判断，不以零值代替。
- [x] A11：特例提醒说明本次住院诊疗结束后由医保办人工评估申请；不自动判定医保资格、不控制 5% 申报比例、不修改分组或核定金额，也不预测协商补付。
- [x] A12：病例用量摘要只归集本次住院 DRG 跟进产生的实际模型请求，可查看阶段、触发原因、模型、输入／输出 token、估算费用和结果状态；不混入同患者其他次就诊或未归属本任务的调用。
- [x] A13：生成、必要核验、格式纠错及重试按实际派发分别计量，同一请求经 Server 与 bridge 转发不重复入账。规则检查、后台等待及有效结果复用显示本次未调用模型，不制造用量或虚构节省量。
- [x] A14：已知用量、未返回用量、进行中请求和估算费用分别表达；缺价格、缺汇率或失败后未取得计量时不显示为零费用。缓存与推理 token 按服务商口径作为相应分项，不重复计入总量。
- [x] A15：关闭页面、重启或任务结束不清零已发生用量；按既有留存合同说明可查范围。住院任务摘要和明细都经过该病例的读取授权，不能仅凭工作区汇总权限下钻其他患者。
- [x] A16：额度或计量能力不足时，显示模型分析尚未完成及具体原因，保留规则结果、待办和有效的既有证据；不以停用模型为由把未经复查的建议标为有效。不得通过重建任务、隐藏重试或换病例标识绕过既有控制。

## 设计决定

### 病例任务与阶段

跟进由医生在当前病例中主动开启一次；诊断、医嘱、实际操作、耗材使用和相关费用等依据变化后自动跟进。任务只覆盖所授权的这次住院，临床与费用事实继续由现有业务模块拥有。后台任务保存问题、依据引用和处理进度，不建立可独立编辑的第二套病历或费用账。

归档后只完成既有结果汇总和待办交接，不因后续财务更正或医保核定恢复临床分析。授权中止早于交接时，保留待交接信息由有效岗位接手，不能为完成交接而延长失效授权。

术前依据不足时只提供有依据的候选与缺项说明，不要求填造尚未取得的测量。术中取得并确认新信息后再更新具体建议。手术结束后的分组和费用评估仍是住院过程中的阶段结果，不能提前冒充出院或医保最终核定。

正式诊断、术式和治疗方向由医生确认；耗材建议、参数录入及待办操作沿用相应岗位边界。术中登记、记录更正与预留分次消耗统一由手术 owner 执行；逐笔使用与完成手术是独立动作，不将一次性完成接口逐件调用。后台任务的权限与页面临时上下文分别管理，方案与取舍见[持续跟进决策](../decisions/implemented/architecture/2026-10-27-inpatient-drg-agent.md)。

实施优先扩展现有住院、手术、计费、DRG、模型执行与用量模块。新增职责集中在病例跟进、住院耗材建议和差异待办；不新建分组引擎、费用账、模型账本或后台调度框架。直接复用与需要适配的边界由[模块复用方案](../decisions/implemented/architecture/2026-10-27-inpatient-drg-agent.md#复用现有模块)说明。

### 推荐依据与费用口径

医生手工确认参数不等于产品适用与兼容规则已经完备。推荐必须能够追溯患者参数、治疗计划、具体产品版本及所使用的规则；数量有独立依据，不能以达到某个 DRG 差额为目标倒推用量。当前数据及缺口见[PCI 耗材依据研究](../research/2026-10-27-pci-material-recommendation-evidence.md)。

首期继续使用合成病例及明确标识的院内演示参数。固定合成规格、价格或病例设定不能宣称为真实临床推荐金标准；来源缺口和适用范围必须显式呈现。费用较低只描述相同已满足临床要求前提下的预计收费比较，不替代采购成本、全成本、真实收入或利润核算。

### 模型用量展示

在住院病例的 DRG 跟进区域展示累计实际请求次数、已知输入和输出 token、已知总用量、估算费用及进行中／计量未知状态；提供展开明细入口。明细可按术前、术中、术后及其他住院核查阶段定位，说明触发原因、调用时间、模型、结果及本次用量。一次分析可能包含多次实际请求，业务事件数、分析次数和模型请求数不能互换。

用量由服务端已记录的派发与服务商返回值形成，不由模型自己报告估计。仅执行规则或复用已有结果时，标明本次没有新增模型请求；不根据假设的完整分析量宣称节省了多少 token。费用沿用既有配置与估算身份，显示已知部分及不完整原因，不把未计量或未覆盖的调用写成零。

病例摘要与明细共同遵守本次住院读取权限，并关联当前任务和实际调用阶段；既有总用量页、额度、价表、核对及留存继续由[模型用量规格](2026-10-19-model-usage-control.md)拥有。只统计能够归属本任务的调用；DSH 原生聊天、压缩或其他插件调用未纳入时说明覆盖范围，不把病例摘要称为整个宿主或账号的完整账单。

### 自动分析与 token 控制

关键记录变化触发的是重新核对相关依据，不要求每条记录都独立调用大模型。费用计算、分组规则、阈值比较及待办状态读取复用确定性业务能力；生成建议和语义核查保留必要模型分析及验证。合并触发、复用成功结果和有界恢复不得削减已确认的核查内容或掩盖过期建议。

新任务须接入现有逐次调用账本与适用控制。模型调用的具体触发、输入范围和恢复边界在实施设计中列明并以请求次数验证；不预设每例 token 或人民币保证值，不新增未经确认的每病例预算配置。现有生产入口的有限 token／金额能力限制由[用量查询合同](../architecture/security-and-reliability.md#模型用量查询)拥有；监控、请求次数限制和可信金额硬上限分别验证，不用合成适配器通过代替真实入口能力。

### 特例单议提醒

本规格采用已发生正式收费净额与当前有效 DRG 医院支付参考比较，包含正式收费的合法冲正，排除未执行计划、备用预留及草稿。提醒绑定本次住院、分组及参数版本；收费或有效参考变化后重新判断，过期依据不能继续作为当前提醒。

3 倍是首期产品提醒门槛，不是已核实的跨地区医保准入标准。特例单议的政策与支付边界继续见[支付与 DRG 规格](2026-10-15-drg-prescription-budget.md#特例单议边界)；本功能不承担申请、审核、评议、协商或补付流程。

主业务验证沿用公开 HIS Query／Command 入口，复用已有 PCI 病例准备、角色会话、真实 HTTP 和临时 SQLite；界面与模型派发检查复用各自现有测试工具，只补主业务结果无法证明的交互、实际请求及计量行为。

新增验收由[住院 Agent 联合 HTTP 旅程](../../apps/server/tests/inpatient-drg-agent-http.test.ts)串联同次住院的三阶段模型分析、逐笔更正、岗位复查与归档交接；[候选依据](../../apps/server/tests/inpatient-pci-selection-http.test.ts)、[后台规则](../../apps/server/tests/inpatient-drg-followup-http.test.ts)、[手术事实](../../apps/server/tests/inpatient-surgery-http.test.ts)和[任务用量](../../apps/server/tests/model-usage-inpatient-task-http.test.ts)分别覆盖独立边界及失败路径。Web E2E 与 React 18／19 Surface 合同验证对应真实岗位入口。

复用测试基础不改变旧测试证明的合同。既有 PCI 支付联合旅程保留不调用模型的断言；新增 Agent 旅程使用受控模型边界并补充独立推荐样例。浏览器 fixture 的有限合成分组用于验证页面接线，不能替代 PCI 固定规则的分组对照；不为复用而削减旧断言或把新功能通过归因于旧测试结果。

采用合成 Provider、受控模型响应和临时 SQLite，在公开 HIS Query／Command、Agent 授权与模型派发边界验证同一病例的完整行为。主要场景包括正常 PCI、临时增加或替换耗材、部分预留转实际使用、缺少参数或价格、相关临床依据变化、错误记录更正、超 3 倍及恰好 3 倍、失权、页面关闭、重启和归档交接。推荐正确性需要独立的人工核对样例，不能从当前推荐算法生成期望值。

用少量受控请求断言无关刷新及同依据复用不新增模型派发，关键依据变化会使旧结果失效；生成、核验与重试逐次计量，Server／bridge 不重复计账，失败和未知用量不会归零。用已知合成计量及价格核对病例累计与明细一致、阶段和触发归属、权限、部分未知、配置缺失、拒绝及恢复；不以减少必要核验换取更低调用次数。

Web 与 DSH Surface 从真实住院入口验证主动开启、阶段建议、逐笔耗材使用、待办处理及病例用量展示；共享交互与审阅遵循 React 18／19 合同。新增 Agent／CLI 能力时同步对应 Catalog、运行时 Skill 和命令示例验证。真实模型开发验证和压测仍需要针对本次运行的明确许可，本规格不提供该许可。

| T2 | 医生开启或停止当前住院后台跟进；离开页面后仍更新规则分组与费用，正确显示 3 倍提醒及失权状态 | 无 | A1、A8、A10、A11；归档停止基础 |
| T3 | 基于已确认参数生成、修改并审阅术前具体耗材建议；依据变化后旧建议失效；首次模型调用即计量并受控恢复 | T1、T2 | A3、术前 A5、A13、A16 |
| T4 | 同一次 PCI 手术逐笔登记实际耗材、分次消耗预留及更正，并更新后续建议；完成手术不重复计费 | T3 | A4、术中 A5、A6 的实际执行依据 |
| T5 | 术后完成计划／实际、记录／费用核查和阶段性 DRG／后续治疗费用重评，跟进差异待办并完成归档交接 | T4 | A6、A7、A9，后续阶段的 A8、A13、A16 |
| T6 | 医生查看本次住院模型用量摘要、阶段和触发明细，正确表达已知／未知及估算费用，并保持权限与累计一致 | T3 | A12、A14、A15及 A13 的展示对账 |

T1 的临床参数和证据归本次住院或手术计划，后台任务只引用其身份与版本，因此 T1 不依赖 T2 的任务 ID。T2 先形成可观察的规则跟进，不把无模型调用包装为完成了模型分析；T3 再接入首条模型流程，统一承担任务／阶段身份、实际尝试计量、住院查询授权和留存关联。T4、T5 与 T6 消费同一合同，不能各自创建派发或用量账本。

T1 与 T2 可并行；T3 完成后，T4 与 T6 可并行。T6 使用 T3 已产生的真实受控模型请求独立验收，不要求预先伪造术中或术后用量；T4、T5 完成后的实际阶段计量在父任务联合验收中核对。

父任务在同一集成版本串联六票，从手工开启、参数确认、术前建议、术中增补／更正、术后待办到归档交接，并同时核对本次住院各阶段模型用量。父任务拥有整体证据汇总，不额外拆出只有测试的横向票；完整交付采用一个集成 PR，叶子通过不等于整项完成。

既有支付、分组、规则启用及从零 PCI 旅程已由[联合验收 #279](https://github.com/CaiZongyuan/clinmesh/issues/279)、[规则启用 #319](https://github.com/CaiZongyuan/clinmesh/issues/319)、[病例准备入口 #320](https://github.com/CaiZongyuan/clinmesh/issues/320)及[从零旅程 #321](https://github.com/CaiZongyuan/clinmesh/issues/321)交付。实施前采用包含这些交付的共同基线，不为旧能力重复建票；它们的旧证据不替代本规格新增行为的验收。

## 范围外

- 首期扩展到所有手术类型，或由 Agent 自主改变治疗方向和术式。
- 扫码、手术设备采集、从报告自动提取关键选型参数及影像像素分析。
- Agent 自动修改正式诊断、病案、医嘱、费用或核定金额。
- 病案归档后的医保办 Agent、特例单议全流程及协商补付预测。
- 全院供应链、采购优化、全成本利润优化，以及未经验证的真实临床推荐能力声明。
- 通用多 Agent 编排平台、整个 DSH 宿主的完整费用控制或未经确认的每病例预算设置。

## 依赖与风险

- PCI 选型使用有版本的有限合成依据及独立正反对照，当前范围由[选型依据决策](../decisions/implemented/architecture/2026-10-27-pci-selection-evidence.md)说明；这些声明不构成真实产品 IFU 或完整临床金标准，范围之外维持待核实。
- 逐笔使用、部分预留与追加更正共同维护临床和共享账务不变量，具体合同见[手术决策](../decisions/implemented/architecture/2026-10-27-inpatient-surgery-material-events.md)；完成手术不重复收费，不覆盖原使用记录。
- Page Context 与医院工具仍受页面、病例及短期授权约束；病例后台任务独立持有绑定，每次重新核验授权、责任及归档状态，不能延长旧页面权限。
- 用量账中的 DRG 功能、任务、阶段及留存汇总共同约束病例归属；摘要、明细和人工核对不能借工作区汇总权限扩大患者读取范围，详见[用量查询合同](../architecture/security-and-reliability.md#模型用量查询)。
- 当前生产模型入口存在可信计量上界不足的限制；实际 token、费用和完整覆盖仍需按适配器与真实用量证据核对，未取得证据前不承诺每例消耗或费用上限。
