# 检验检查两阶段工作台与统一分类

Status: approved

## 问题与目标

医生接诊页目前在同一个“检验检查”分区中依次展示检验、放射检查和病理会诊。检验申请编辑与结果并排，申请列表、各份完整报告和历史版本连续展开。未开立时缺少直接检索项目的工作区；开立项目增多后，申请跟踪和报告阅读被放在较长的内容流中。

目标是按当前分类是否已有申请组织界面：未开立时直接搜索并选择本院项目，开立后集中跟踪申请和阅读选中报告。检验、放射检查和病理会诊使用统一分类入口，各自保留原有目录、表单、权限和业务规则。布局采用已确认的 V3 交互预览；正式行为以本文和现有业务合同为准。

## 范围

- 医生接诊页内的“检验检查”分区，包括标准就诊流程中的目录搜索、申请草稿、正式开立、申请列表、状态反馈和报告详情。
- standalone Web 与 DSH Surface 复用的真实页面。保留病例横幅、外层诊疗页签、候诊列表、宿主左右分屏和手动全屏合同。
- 内部通过“检验 / 放射检查 / 病理会诊”切换分类，展示该分类的申请数量，查询、选择、草稿和报告均属于当前病例与对应分类。
- 接通真实 Query、Command 和现有表单验证，复用 `packages/ui` 的组件、主题、字号与中英文文案。
- 保留旧病例兼容入口与已完诊病例的报告读取、已获授权的纠错入口；不将缺少独立申请状态的旧数据伪装为新流程。

## 用户故事

1. 作为医生，我希望未开立检查时直接看到可搜索的本院目录，以便立即选择项目。
2. 作为医生，我希望按检验、放射检查和病理会诊切换上下文，以便使用对应目录和申请表单。
3. 作为医生，我希望明确选择项目后就地查看申请信息与适用条件，以便准确填写后正式开立。
4. 作为医生，我希望开立成功后自动进入申请管理，以便跟踪执行状态和追加项目。
5. 作为医生，我希望选中申请后阅读当前完整报告，以便把异常指标、报告结论和已阅状态联系起来。
6. 作为医生，我希望按需查看历史版本、取消、重试和更正，以便沿用已有恢复与纠错流程。
7. 作为医生，我希望切换分类或病例时保留各自已有事实与草稿，以便不会把表单或报告带入错误上下文。
8. 作为键盘用户或在 DSH 窄分栏中工作的医生，我希望搜索、选择、提交和返回操作始终可达。

## 验收条件

- [ ] “检验检查”分区以统一分类入口承接三类项目，选中态与各类申请数量清晰；不再依次铺开三套完整页面。
- [ ] 当前分类没有已签发申请记录且允许编辑时，默认直接加载项目目录、搜索和申请信息区，不需先点击按钮打开搜索弹窗，也不显示空的申请列表与报告阅读布局。
- [ ] 目录支持现有搜索与分页。首次进入没有默认选中的项目；搜索无匹配、目录加载、读取失败及重试具有可用反馈，重试成功回到目录搜索。
- [ ] 明确选择项目后，在同一工作区显示该类别已有的必要字段与项目元信息。检验保留真实指征选项、标本、报告结构、TAT 和已有计价表示；放射保留检查指征、部位和检查方式；病理保留送检的既往手术与会诊目的。
- [ ] 草稿加载、保存、删除、验证和错误反馈保持既有合同。正式开立前仍执行现有保存与 Command 校验；无选择、输入无效、保存或开立进行中、平台或岗位无权时不能提交。
- [ ] 当前分类首次开立成功后自动进入“申请列表 + 选中申请详情”，默认显示新申请的真实状态；尚未取得报告时不展示模拟结果。开立失败不切换阶段，保留可恢复的表单。
- [ ] 当前分类已有申请记录时直接进入申请管理，并保留追加入口；追加使用当前分类的项目选择与申请表单，成功后新增申请可见，原有申请和报告不丢失。
- [ ] 分类之间不混用目录、项目 ID、指征、病理来源、草稿、申请或报告。某分类有申请、另一分类无申请时，各分类按自己的记录进入相应阶段。
- [ ] 申请列表可以搜索并筛选全部、待阅及进行中，状态、失败与可用动作紧邻申请。取消后保留记录；生成失败的重试资格继续由现有业务规则决定。
- [ ] 报告区默认只展开选中申请的当前报告，展示结论、报告时间、版本和已阅状态。检验保留完整指标、结果、单位、参考范围和解释标记，并支持切换全部指标与仅异常；正常指标不过度使用醒目的徽章。
- [ ] 报告历史默认收起，展开后可读完整旧版本及已有修订原因。确认已阅作用于当前正式报告，成功后申请与待阅计数同步更新；最后一份待阅确认后仍可返回列表或切回全部申请。
- [ ] 放射阅片、病理阅片、报告更正和历史版本等已有能力在对应详情中可达，不以通用检验指标表替代其报告结构或阅读门禁。
- [ ] 不适用或本院未开展的项目按现有返回事实呈现原因并限制开立。病理没有符合条件的既往乳腺手术时保留来源条件提示，不提供虚构来源；不把预览样例的禁用状态硬编码到所有病例。
- [ ] 未接诊、只读或已完诊状态保留现有授权边界；缺少写权限时不会因进入目录阶段出现可用的写入控件，已获授权的纠错入口继续按现有规则工作。
- [ ] 切换分类、病例、页面刷新和报告自动返回后，阶段从真实申请状态恢复；旧响应、保存中的草稿和迟到任务不会覆盖另一病例或分类的当前内容。
- [ ] 原有医生页面 Tools 能读取真实表单和当前事实，导航、准备开立、人工审阅和正式提交仍可用；布局或分类切换不导致工具丢失、错误绑定、越权或超过宿主工具数量限制。
- [ ] 中文、英文、亮暗主题及三档字号下保持可读。1280px 桌面与 390px 窄屏的搜索、目录分页、表单、追加弹窗、申请列表和报告末尾操作完整可达，页面不出现非预期横向溢出；表格仅在自身容器中滚动。
- [ ] 控件具有正确的分类名称与可访问名称，键盘可完成选择和开立；弹窗关闭后返回触发器，重绘、错误恢复和筛选为空时保留明确的焦点与返回路径。

## 设计决定

阶段由当前病例、当前分类的已签发申请记录派生，不增加服务端阶段字段。已保存的草稿仍属于目录与申请编辑阶段；已签发的申请包含执行中、已报告、已阅、失败和已取消记录，筛选为空不代表回到未开立阶段。

| 当前分类的状态 | 默认工作区 | 主要动作 |
| --- | --- | --- |
| 没有已签发记录，具有编辑权限 | 直接加载目录搜索，桌面目录与申请信息并排，窄屏可顺序操作 | 明确选择、填写必要信息、正式开立 |
| 已有申请记录 | 紧凑申请列表与选中申请详情 | 跟踪、阅读、已阅、追加及已有恢复动作 |
| 没有记录，缺少写权限 | 只读空状态或现有不可用提示 | 不开放开立 |

统一入口只收敛展示与导航，不合并三类业务模型。检验继续使用本院 Hospital Laboratory Service 及其现有指征与报告定义；放射使用现有本院服务与自由文本检查指征；病理使用现有会诊服务、受限的来源手术和会诊目的。每次开立一个项目，不新增购物车、多选批量提交或跨类别通用写命令。

三类草稿和正式动作复用已有 Query、Command、版本检查、幂等、审计和人工确认。TanStack Query 继续拥有服务端事实；分类、搜索、选中申请和历史展开属于视图状态，不建立第二套申请或报告缓存。目录不新增 Case Truth、模型或结果生成能力字段。

读到已保存草稿时恢复其实际项目和输入；从目录选择的新输入不覆盖其他分类的已保存草稿。追加复用当前类别的表单与选择逻辑。阶段切换以正式 Command 成功和已提交状态为依据，不能由点击、草稿保存或预览提案触发。

当前报告优先，异常结果提供克制的语义色和文字标记，完整指标仍是默认内容；历史版本渐进展开。现有放射和病理阅读器继续拥有阅片与报告的交互，页面不新增影像或切片生成、下载与标注能力。

正式组件遵循 [UI 设计合同](../ui/design.md)，预览产物按 [交互预览规则](../agent-development.md#交互预览)保留。原型中的合成数据、内存提交、模拟报告返回与预览状态选择器不进入正式页面，原型验证不替代真实入口、权限、持久化或审计证据。

## 测试策略

优先在现有医生工作台的公开渲染与交互入口验证，复用 `apps/web/src/app/role-workspaces.test.tsx`、目录选择测试和现有 Agent 页面工具测试，不为私有布局函数建立测试接口。对阶段切换、分类隔离和状态恢复采用 TDD，测试断言可见目录、表单、申请、报告与实际调用的现有操作。

关键回归包含无申请与已保存草稿、首次开立成功与失败、同类追加、另一分类无申请、目录分页与失败恢复、无选中项目、不同类别输入校验、病理来源缺失、只读、取消记录保留、报告自动返回、最后一份待阅确认、报告更正与旧版本，以及病例切换后的迟到读取或保存。验证人工操作与页面 Tool 使用相同的已解析输入和业务入口。

通过 Playwright 从 standalone Web 和 DSH Surface 的真实入口验证完整的“进入目录 → 搜索 → 选择 → 开立 → 跟踪 → 报告到达 → 确认已阅”旅程，并验证追加及分类切换。共享弹窗按现有 React 18／19 浏览器合同覆盖；布局检查使用 1280px 与 390px、长中英文、亮暗主题和三档字号，确认滚动分区、报告末尾动作、焦点恢复和宿主分屏行为。

沿用已有 Server、Command 与报告生命周期回归，不放宽临床、预期版本、授权、幂等、审计和阅读门禁断言。全部验证使用合成数据；影像与病理能力通过文字快照、公开元信息和聚合统计验证，Agent 不读取像素或包含像素的截图，见 [测试策略](../testing.md#用户界面验证)。

实施后运行覆盖改动的相关测试、类型检查、lint、Web 与 DSH 构建；文档与现有设计合同同步后运行对应文档检查。跨包合同、发布路径或测试策略变化时按根 `AGENTS.md` 扩大验证并补充对应 Agent Note，复用仍然有效的成功证据。

## 范围外

- 新增检验、放射或病理项目、院内服务发布能力、计价政策、标本采集或其他 HIS 岗位。
- 修改请求和报告生命周期、临床适用规则、FHIR R5 合同、HTTP／CLI schema、SQLite 字段或权限边界。
- 批量开立、购物车、跨类别通用申请模型、趋势图、PDF 导出和自动诊断解释。
- 实施医生 Agent 的项目推荐或建议采纳；该能力由 [#179](https://github.com/CaiZongyuan/clinmesh/issues/179) 追踪，本需求只保留现有页面 Tools 和人工审阅合同。
- 重做病例头部、外层导航、DSH 聊天、候诊列表、设置、Mobile 或未实际开发的 Desktop 入口。
- 在正式 Web 中加入长期 mock 展示站、方案切换器或模拟业务状态。

## 依赖与风险

现有检验目录与检验、放射、病理 Query／Command 已提供所需业务能力，没有已知外部前置阻塞。三类表单字段、草稿语义、报告结构和适用条件不同；统一布局必须适配现有接口，不能复制原型的通用内存提交作为业务实现。

页面 Tools 和自动报告刷新依赖真实病例、岗位及页面上下文绑定，分类与阶段切换可能影响工具发布和选中项，需覆盖迟到响应、报告修订与恢复入口。病理来源和放射可用性按当前病例及服务端事实确定，不按演示样例推断。

检验检查页面与 #179 涉及同一工作区，实施时核对该任务的实际集成状态并保留其已有入口；当前没有将 Agent 推荐列为本需求的前置依赖。界面阶段和目录状态与现有设计文档可能存在描述差异，正式交付时更新各自 owner 文档，不把本规格当作已实现状态。
