# 门诊住院共享目录与冠心病 PCI 演示闭环

Status: approved

## 问题与目标

门诊与住院已有诊断参考库、院内药品及检验服务目录的共享基础，但住院药品启用依赖少量固定示例配置，检验住院价目及部分项目资料不完整。医生的本次用量也被限定为目录中预先列出的值，混淆了产品基础资料与本次医嘱的归属。

目标是复用药品、检验和诊断主数据，补齐住院使用所需的资料与程序接入。首批覆盖一例无复杂并发症、非急诊的冠心病患者：入院检查，经医生评估需要介入治疗，冠脉造影并植入一枚支架，术后用药、稳定出院、费用结清、病案归档，最后显示 DRG 分组和明确标注为演示计算的模拟支付金额。

本规格拥有目录共享、医生用量录入、缺项展示、首例资料补齐及必要页面接入的增量要求。既有业务状态、权限及事务沿用[临床流程](../architecture/clinical-workflows.md)、[存储与事务](../architecture/storage.md)和[住院规格](2026-10-20-inpatient-closed-loop.md)。

资金、患者医保待遇、DRG 机制和归档后财务更正的完整要求继续由[门诊住院共享支付与 DRG 一体化正式规格](https://github.com/CaiZongyuan/clinmesh/blob/e322fef689b009cc0175931b4070b8713c8dedff/docs/spec/2026-10-15-drg-prescription-budget.md)拥有，由 [#225](https://github.com/CaiZongyuan/clinmesh/issues/225) 及其 [#279 联合验收](https://github.com/CaiZongyuan/clinmesh/issues/279)追踪。本次复用这些能力，新增本例接入及页面验收，不替代原规格的完整验收，也不据此关闭原任务。既有 DRG 设计理由见[仿真链决策](../decisions/implemented/feature/2026-10-23-drg-inpatient-simulation-chain.md)。

## 范围

### 共用主数据，分别声明使用范围

- 诊断共用既有参考库及来源版本；住院主次诊断、逐项入院病情和确认修订归本次住院。
- 药品共用具体产品身份、厂家、剂型、规格、包装、已确认单位及价格。住院另声明适用范围、执行和计费所需的配置；不得按同名药合并不同产品。
- 检验共用已发布的院内项目、组合与子项、标本、结果类型、单位和参考范围；住院补齐适用范围、开展条件及收费定义。
- 目录变更采用明确版本。已开立医嘱、实际实施、报告及费用保留原冻结快照，各次就诊的正式事实分别保存。

### 医生填写本次用量

- 医生在本次医嘱中填写每次剂量和频次，常用用法只作可修改的建议。具体每次用量不作为药品目录启用前必须填写的固定枚举。
- 产品规格、最小制剂单位、包装与发药/收费单位的关系属于主数据。只有有明确依据或明确标记的合成换算关系时才自动换算，不从药名、模糊规格或未知价格分母猜算。
- 输入必须能够支持本例所需的开立、排程、发药、给药与计费；单位不匹配、数量非法或无法换算时说明具体原因。发药时继续检查实际批次、数量及有效期。
- 继续保留角色权限、过敏及本例已声明的有界用药规则，不能通过取消校验、填零或随意固定用量使流程通过。

### 显示待补项目

- 住院检索同时呈现共享目录中已可用的项目及尚未具备住院条件的候选项目，提供搜索和分页。
- 候选项目显示具体缺项，例如规格、发药/计价单位、单位换算、院内价格或开展条件。尚未满足相应开立条件的条目不能作为可执行项目提交。
- 医生尚未填写本次剂量，应在开医嘱表单中提示，不标记为产品目录基础资料缺失。
- 单条项目缺项不使其他完整项目不可用；区分待补、停用、加载失败和查询无结果。

### 首批病例、资料与演示补数

- 准备固定且可追溯的合成病例底稿，具备本例所需的身份、诊断、检查依据及合成来源绑定，使用户可以从入院开始通过页面完成流程。
- 首批只配齐该例实际需要的药品、检查、术式、支架及其他冠脉耗材，以及对应库存、执行、费用和病案资料。临床事实通过既有正式动作产生，不用孤立数据行冒充已完成诊疗。
- 优先复用门诊已有完整资料及已确认规则；确实缺失的产品资料、单位、价格、库存和规则可用明确标记的合成院内数据补齐。
- 原始来源及其缺项保留；合成补充与来源事实分别存储。沿用已确认表价及其口径；来源价格分母不明时保留原报价，演示收费另明确声明单位和模拟身份，不把猜测写回原始资料。
- 用户提供的 r3 目录及价格包作为固定参考输入，保留编码体系、版本、来源和使用边界。医保药品条目不能冒充具体厂家规格产品，医保版编码不能无依据地覆盖临床版。
- 使用有版本和可解释依据的规则包完成本例分组；为实际目标 PCI 病组补齐独立标记的合成支付参数。缺规则或参数时明确报告，不编造病组或以零额冒充成功核定。
- 安装或准备过程幂等，保留已有目录配置、患者、业务事实与历史回执；不会因重新启动自动执行诊疗、收费、归档或重置已有业务。

### 页面与岗位

复用现有正式业务页面及共享 Web/DSH 入口，补齐本例必要的搜索、用量录入、缺项说明、DRG 结果及医保办模拟核定入口。用户能按职责切换登记、住院医生、护士、药师、收费、病案和医保岗位完成对应操作，后端权限与页面入口一致。既有检验执行及报告内核继续复用，不复制状态机。

## 用户故事

1. 作为住院医生，我希望检索到与门诊同源的项目，知道哪些可用、哪些缺资料，并自行填写本次用量。
2. 作为住院医生，我希望本次合法剂量和频次由我填写，常用用法作为可修改建议，避免被旧示例的固定用量限制。
3. 作为目录使用者，我希望未配齐的候选项目仍可检索，并看到具体缺项，以便区分资料缺失、停用和系统查询失败。
4. 作为登记岗位，我希望已有可追溯的合成病例及入院依据，使我能从住院登记开始操作本例。
5. 作为药师，我希望药品规格、发药单位、换算和有效批次明确，按实际发药数量扣减库存并形成可追溯费用。
6. 作为病区护士，我希望按本次医嘱校对、给药和执行，数量与单位清楚，重复操作不会重复生成临床或费用事实。
7. 作为住院医生，我希望实际检查、冠脉造影、单枚支架实施和耗材使用形成正式记录，供后续诊疗、费用与病案使用。
8. 作为收费岗位，我希望实际费用、预交金和补退资金可以核对，在费用结清后按既有门禁收口。
9. 作为病案岗位，我希望首页引用本次正式诊断、实际主要操作和费用，审核后形成不随目录或规则更新漂移的归档快照。
10. 作为医保岗位，我希望看到有版本和解释依据的冻结 DRG 分组，按合成支付参数完成模拟核定，且保留职责权限。
11. 作为资料维护者，我希望来源字段和合成补充分别保存，重复准备不会覆盖已有配置、患者、业务及历史单据。
12. 作为演示使用者，我希望通过各岗位页面把同一例冠心病患者从入院操作到归档和 DRG 模拟核定，金额及事实可追溯。

## 验收条件

- [ ] A1：药品、检验和诊断按统一主数据身份与来源版本供两端使用；本例所需条目在住院端可检索并开立。
- [ ] A2：医生可填写本次合法用量及频次，不受旧固定用量枚举限制；规格、单位、换算、非法数量及发药库存检查仍有效。
- [ ] A3：未满足住院条件的候选项目可检索，显示具体缺项；不能绕过服务端检查提交，且不影响其他完整项目。
- [ ] A4：来源原文和原有空值保留，合成补充独立标注；已确认价格不被启动覆盖，缺价不当作零价。
- [ ] A5：重复安装或准备不重复新增本例、不覆盖正在进行的业务，不重做诊疗及收费；旧目录、医嘱、报告和回执继续可读取。
- [ ] A6：本例通过岗位页面完成登记入科、诊断医嘱、药师发药、护士执行、检查报告、造影与实际支架实施，实际耗材与费用可逐项追溯。
- [ ] A7：出院结清、补退资金及费用账一致；首页来自本次正式诊断、实际操作和费用，审核归档后冻结，主要操作选择明确。
- [ ] A8：显示本例预分组与归档冻结分组，保留规则版本和解释；医保岗位按固定版本合成参数生成模拟支付金额，越岗访问被拒绝。
- [ ] A9：覆盖缺资料、停用、查询/加载失败、库存不足、旧版本、重复操作与关键失败恢复，不因演示需要跳过校验或放宽超时、重试预算。
- [ ] A10：正常页面可完成整链验收；仅有后台接口成功或静态原型展示不算完成。

## 设计决定

首批完整启用一例冠心病 PCI 所需项目，共享机制覆盖药品、检验和诊断；不把所有参考条目一律声明为住院已开展。已确认允许补合成院内数据，已有表价保留。病例采用无复杂并发症的择期单枚支架路径，验收终点为结清、归档、DRG 分组和模拟支付。未补项目显示原因，用量由医生在本次医嘱中填写。

在不改变上述要求的前提下，复用已有数据发布、院内目录、共享 Command、检查内核、费用账及归档机制。具体数据模型、接口兼容与非平凡取舍在实施前核对现有调用者，必要时更新既有或新增 Agent Note。

## 测试策略

先在现有公共 HTTP/Command 与浏览器入口为目标行为建立有效失败回归，再实现最少必要变更。合成 Provider、受控响应与临时数据库验证目录共享和缺项、医生用量、换算、批次发药、逐项计费、幂等、版本及归档冻结。按改动覆盖旧数据和旧回执读取。

主要验收边界为既有业务 HTTP/Command 和真实岗位页面。目录及病例准备通过现有公开准备入口执行，并以公共查询回读验证；测试验证可观察的检索、拒绝原因、临床事实、费用与冻结结果，不依赖私有函数结构。

Playwright 从真实岗位页面验证完整病例及关键失败路径；修改 DSH 共享表单或对话框时覆盖 React 18/19 合同。运行覆盖完整 diff 的类型、静态、文档与项目必需检查，并完成同一固定快照的 Standards/Spec 双轴审查。真实模型、压测及正式运行库变更仍按对应明确授权执行，需求批准不代替逐次许可。

## 范围外

本轮不逐项完成全院全部目录住院化，不建设通用临床规则平台、设备采集或全院供应链；不重做原规格的完整患者医保待遇及归档后财务更正，不接真实医保结算平台，不提供真实医院收入、全成本或盈亏结论。沿用现有页面风格，不将用户原工作区的未提交原型及其他 WIP 自动纳入交付。

## 依赖与风险

- 当前 r3 包属于离线参考候选，部分报价的分母、规格、适用期及编码对应关系不完整；数据补充须保持来源与演示边界。
- 正常启动的可执行 DRG 规则包装载及 PCI 病组支付参数仍需接入；仅下载离线资料不构成可分组和可核定。
- 现有住院医嘱以有界频次及用量结构实现；自由录入、执行排程和库存/收费换算的接口两侧必须一起核对，不能只修改前端输入框。
- 若核查发现首例所必需、但现有合同不能表达的新实质性分支，先澄清受影响部分，不静默缩减验收范围。
