# 诊疗建议读取复用指南检索结果

Status: approved

## 问题与目标

门诊医生在诊断、检验检查、处方之间切换页签，每选完一项，以及切换岗位时，都要等待数秒。

在本地合成数据副本上实测，每次读取诊疗建议（`GET /api/his/v1/doctor/cases/{caseId}/recommendations/{kind}`）耗时 1.3–1.5 秒，而队列、病例详情和质控只需 2–20 毫秒。合成测试库的指南很少，同一接口只需 60–120 毫秒，因此测试中没有暴露。

原因有三层：

- 每次读取都完整执行一次指南检索（`GuidelineCorpus.search`），只为计算输入指纹和 `stale`。检索包括全文段落查询、逐份指南重算完整性哈希和段落统计。
- 病例和指南库都没变时，检索结果每次相同；5 类建议使用同一段检索文本。
- 指南库读取是同步的，检索期间服务端处理不了其他请求。建议处于 `pending` 时前端每秒轮询，诊断、检验、处方三类同时轮询会让服务端满载。浏览器实测此时其他请求排队后需要 2.6–3.7 秒，切换岗位的请求同样排在后面。

目标：病例和指南库都没变时，重复读取建议不再重新检索，轮询、切页签和切岗位不再排队等待。

## 范围

- 服务端指南库检索结果的进程内复用。当前唯一调用方是门诊诊疗建议服务（`DoctorRecommendationsService`），复用实现在 `GuidelineCorpus.search` 内部，不改调用方。
- 检索结果只在检索文本和指南库内容都不变时复用。另一个进程导入、更新或标记损坏指南后，下一次检索必须反映变化。

## 用户故事

1. 作为门诊医生，我希望建议生成期间在诊断、检验检查、处方页签之间切换时页面立即响应，以便不用等后台检索。
2. 作为门诊医生，我希望开具一项诊断、检验或处方后很快能继续操作下一项，以便连续完成接诊。
3. 作为门诊医生，我希望病例没变时反复打开同一类建议不再卡顿，以便随时回看建议依据。
4. 作为演示操作者，我希望在门诊医生、收费、药房等岗位之间切换时立即进入新岗位，以便顺畅演示完整流程。
5. 作为门诊医生，我希望病例资料变化后建议照常标记为待更新，以便不会误用旧建议。
6. 作为部署维护者，我希望另一个进程导入或更新指南后服务端无需重启就使用新内容，以便指南同步立即生效。
7. 作为部署维护者，我希望被标记损坏的指南在下一次检索中立即停用，以便错误原文不会成为建议依据。
8. 作为部署维护者，我希望服务端长时间运行时内存占用不随接诊病例数增长，以便演示环境稳定。

## 验收条件

- [ ] 检索文本和指南库都不变时，同一 `GuidelineCorpus` 实例再次检索不再查询指南库，返回结果与首次检索一致。
- [ ] 检索文本变化时（病例资料变化），重新检索并返回新结果；建议的 `stale` 与输入指纹判定与现行为一致。
- [ ] 另一个连接在同一指南库文件上导入新指南后，服务端下一次检索包含新指南，无需重启。
- [ ] 另一个连接把某份指南标记为完整性损坏后，服务端下一次检索不再使用它，并照常列入 `inactiveSources`。
- [ ] 缓存条目有上限，长时间运行不会随病例数量无限增长。
- [ ] 在本地合成数据的只读副本上，同一病例连续读取 5 类建议，除首次外每次在 50 毫秒内返回；PR 记录修复前后的耗时。
- [ ] 在同一副本上停留门诊诊疗页、建议处于 `pending` 轮询时，病例详情等其他请求在 100 毫秒内返回，不再排队数秒。

## 设计决定

- 采用整次检索结果复用（方案一）。缓存键为检索文本加指南库版本，命中时直接返回上次结果。
- 指南库版本由 SQLite `PRAGMA data_version`（感知其他连接提交）和本连接写入计数（`total_changes()`）组成，不依赖逐个写入方法手工清缓存。
- 缓存只存在于进程内存，按最近使用保留有限条目，不持久化、不跨进程共享。
- 病例变化后的首次检索仍完整执行一次（约 1.4 秒），5 类建议共用这次结果。是否进一步按指南库版本单独缓存完整性哈希与段落统计，待本修复实测后再决定。
- 前端轮询间隔、触发条件和建议生成流程不变。

## 测试策略

- 只测公共行为：检索结果、失效时机和条目上限；不断言缓存内部结构。唯一的切入点是指南库检索接口（`GuidelineCorpus.search`）。
- `apps/server/tests/guideline-corpus.test.ts`，沿用该文件"写入实例 + 同一文件的只读实例"的既有写法：
  - 同一文本重复检索时不再查询指南库（观察数据库语句准备次数），结果深度相等；
  - 另一个可写 `GuidelineCorpus` 实例在同一文件导入指南后，只读实例下一次检索包含新指南；
  - 另一实例标记完整性损坏后，只读实例下一次检索排除该指南；
  - 超过上限后最早条目被淘汰。
- 现有 `doctor-guideline-corpus-http.test.ts` 和诊疗建议相关测试保持通过，用于确认检索结果与 `stale` 判定不变。
- 性能证据：用进程内计时脚本和浏览器请求追踪，在本地合成数据的只读副本上记录修复前后的读取耗时和轮询期间的排队情况。脚本不纳入仓库，不接模型，不修改原数据库。

## 范围外

- 病例变化后首次检索的提速（单独缓存完整性哈希与段落统计，或改写检索查询）。
- 前端轮询频率、质控每 1.5 秒轮询及建议生成逻辑的调整。
- 门诊与窗口岗位界面细节修整、住院界面重做，分别由各自规格负责。

## 依赖与风险

- 依赖 better-sqlite3 只读连接在 WAL 模式下能通过 `data_version` 感知其他进程的提交；由跨实例测试验证。
- 性能验收依赖本地合成数据副本中较大的指南库；CI 中的合成指南库无法复现修复前的耗时，自动测试只验证复用与失效语义。
