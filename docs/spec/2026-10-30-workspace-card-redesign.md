# 工作台扁平卡片重构（门诊与住院）

Status: approved

## 问题与目标

现状审计（[UI/UX 现状审计](../research/2026-10-29-ui-ux-current-state-audit.md)）发现了以下问题：

- 浅色状态色对比度不足。
- 同类页面各自实现，观感和行为不一致。
- ClinMesh 的靛紫主色与 DSH 宿主的中性主按钮、蓝色业务色并存，整屏不像一个产品。
- 住院线入口分散。阶段工作台把办不了的环节也摆在页签上，点进去才提示由别的岗位办理。
- 住院界面充斥系统用语，例如冻结、正式事实、推演、尚应收、出区。
- Agent 的草稿和正式值外观相同；`.propose` 动作用弹窗打断当前工作。
- 住院页面的 Agent 读不到当前患者，助手也只会用医生的口吻回复。

目标：所有岗位改用同一套扁平卡片工作台。

- 整屏视觉与 DSH 宿主一致。
- 每个岗位只看到要办的事，并且清楚下一步是什么、卡在哪里。
- 界面和助手都使用岗位的日常用语。
- Agent 只填草稿或准备操作，正式提交由人在原位确认。

业务能力、服务端合同和门禁保持不变；住院 Agent 能力的补充除外。

## 方案概述

使用者打开任一岗位，看到的页面结构都一样：

1. 页头：页面名、当前患者、助手状态和人物菜单。
2. 流程线：显示病例走到了哪个岗位。
3. 画布，从左到右三部分：
   - 左边：可收起的队列。
   - 中间：患者卡和本岗位的分区页签。
   - 右边：做决定时需要看的只读资料。
4. 底部操作栏：告诉使用者下一步按什么、现在为什么按不了。

助手在对话区里帮忙查询、填写或准备操作。它填过的字段带虚线框和「助手」标记。需要提交时，页面在原位出现确认框，由使用者决定采用或不采用。

设计依据是用户确认过的两份可交互原型：

- 门诊原型：挂号员、分诊护士、门诊医生、收费员、药师。
- 住院原型：住院医生、病区护士、收费员。采用 W1 分组页签和基准风格，不加特色层；住院文案和助手话术按实际岗位用语改写。

已确认的原型取舍和无原型页面的功能规划统一记录在本规格中，实施与验收以本规格为准。原型只用于视觉对照，不是实现代码；发现未记录的差异时，先确认并更新同一份规格。

## 范围

- **平台：** standalone Web 与 DSH Surface 两端。Desktop 消费同一套 token，但不单独验收；Mobile 不在范围内。
- **共用外壳：** 覆盖全部岗位页面，包括语义 token、页头、流程线、队列卡、患者卡、内容卡、右栏、底部操作栏、原位确认、助手草稿标记和响应式布局。
- **门诊五个岗位（有原型）：** 挂号员、分诊护士、门诊医生、收费员、药师。
- **住院三个岗位（有原型）：** 住院医生、病区护士、收费员的住院部分。
- **无原型、按规划执行的七处：** 住院登记（挂号员的住院部分）、住院药房、病案、医保核定、退费、模拟数据（管理员）、设置。
- **住院 Agent 能力：** 住院页面上下文加入当前患者和环节，新增「准备、等你确认」类工具，助手人设按岗位回复。
- **界面文案：**
  - 住院界面和助手话术按实际岗位用语改写。
  - 门诊按门诊原型的文案改写。
  - 英文文案同步使用对应的术语。

## 用户故事

### 所有岗位

1. 作为任一岗位人员，我希望页面只显示本岗位要办的事和必须看的只读资料，以便不被办不了的环节打断。
2. 作为任一岗位人员，我希望底部操作栏一直告诉我下一步按什么、为什么现在按不了，以便不用猜禁用原因。
3. 作为任一岗位人员，我希望不可逆的提交先给我一条说明后果的确认条，以便不会误操作，也不被模态框打断。
4. 作为任一岗位人员，我希望流程线标出病例现在走到哪个岗位，以便知道前后环节是否就绪。
5. 作为任一岗位人员，我希望能收起队列，让主区占满，以便在分屏时有足够的空间办理当前患者。
6. 作为任一岗位人员，我希望页签放不下时自动收进「更多」，并且当前页签始终可见，以便窄屏也不丢位置。
7. 作为在 DSH 中工作的人员，我希望 ClinMesh 与宿主的颜色、字体、主按钮和明暗模式一致，以便整屏像一个产品。
8. 作为 standalone Web 使用者，我希望看到与 DSH 内相同的配色和组件，以便两端的操作习惯一致。
9. 作为视力较弱或在强光下工作的人员，我希望文字和状态色有足够对比度，并且字号三档偏好继续生效，以便看清关键信息。
10. 作为习惯用键盘的人员，我希望页签能用方向键切换，原位确认出现时焦点落在确认按钮上，以便不离开键盘也能完成操作。
11. 作为任一岗位人员，我希望读取失败时卡片写明哪项失败并提供重试，列表为空时说明原因和去哪里处理，以便自己恢复工作。

### 助手

12. 作为使用助手的人员，我希望一眼看出哪些字段是助手填的，我改过之后标记自动消失，以便区分我的输入和助手的草稿。
13. 作为使用助手的人员，我希望助手准备好的操作出现在对应的行内或底部操作栏，「不采用」和「确认」并排，以便在原位决定。
14. 作为使用助手的人员，我希望同一时间只有一个待确认项，助手被中止时确认框自动消失，以便不会确认过期的操作。
15. 作为使用助手的人员，我希望助手回复先说结论，用我这个岗位的用词，需要我确认时说清楚按哪个按钮，以便快速行动。
16. 作为护士或收费员，我希望助手按床号称呼患者；作为医生，我希望助手按姓名称呼患者，以便和平时的交班习惯一致。
17. 作为任一岗位人员，我希望助手不替我做必须本人确认的事，例如知情同意书，并用一句话说明由谁办理，以便责任清楚。

### 门诊

18. 作为挂号员，我希望在队列卡里切换待挂号、检索和建档，选中病例后填写科室、号别和地点，以便一处完成挂号。
19. 作为挂号员，我希望今日挂号列表里的门诊号可以复制，复制失败时有提示，以便告知患者或交给其他岗位。
20. 作为分诊护士，我希望体征输入框直接显示可录入范围，超出时在原位报错，以便当场改正。
21. 作为分诊护士，我希望底部写明还差哪些字段，以便不用逐项找。
22. 作为门诊医生，我希望在五个分区之间自由切换，每个页签显示状态和待办数，以便不按固定顺序也能完成就诊。
23. 作为门诊医生，我希望右栏的完诊清单写明每项对应哪个分区并可以跳转，点「完诊」时先列出缺少的项，以便一次补齐。
24. 作为门诊医生，我希望质控疑点和诊疗建议仍留在右栏，以便签署和确认前参考。
25. 作为门诊收费员，我希望按类别和状态筛选费用，组合最多三种收款方式，先预览再确认，结果未知时能查询原支付结果，以便不重复收款。
26. 作为门诊药师，我希望先审核再发药，批次默认选最早到期的，库存不够时可以部分发药，以便按规范发药。

### 住院

27. 作为病区护士，我希望队列里新入院的患者置顶，每床显示「轮到你 n 项」，以便交班后知道先去哪床。
28. 作为病区护士，我希望打开患者时直接落在有待办的环节，环节头写明「轮到你：…」，以便先处理到时间的给药和校对。
29. 作为病区护士，我希望给药未到时间时写明「08:00 可给药」，办理出院受阻时写明差几条医嘱、等谁处理，以便知道该找谁。
30. 作为住院医生，我希望只看到能办的环节，只读环节收进「更多」，以便少点无用的页签。
31. 作为住院医生，我希望右栏临床提醒写清在等谁，「开始手术」旁边直接列出还差的项和负责人，以便术前不遗漏。
32. 作为住院医生，我希望 DRG 预分组用「按当前诊断和手术」「如按计划手术」这样的说法，以便不用理解系统口径。
33. 作为住院收费员，我希望门诊和住院收费在同一个队列卡里切换，队列按待结算、在院、待入科分组，以便不在外层页签之间来回跳。
34. 作为住院收费员，我希望金额写成「需补交」「无需补退」，确认收款和确认结算前都有说明后果的确认条，以便能直接念给家属听。
35. 作为病区护士，我希望助手能帮我备好医嘱校对，由我在医嘱行确认，以便少点几下又不失去把关。
36. 作为住院医生，我希望助手能帮我备好报告「已阅」，由我逐份确认，以便查房后快速处理报告。
37. 作为住院收费员，我希望助手能填好补交金额，并生成收款和结算预览，确认仍由我操作，以便窗口办理更快。

### 无原型的页面

39. 作为药师，我希望住院发药放在队列卡的「住院」侧，审核、批次、数量的样式与门诊一致，以便不用切换操作习惯。

41. 作为医保办人员，我希望只有一个核定队列，只列已归档的病案，按「审阅模拟核定 → 提交模拟核定」办理，以便不被无关表格干扰。
42. 作为收费员，我希望退款只在有已缴费用时作为一张卡片出现，按「预览退款 → 确认退款」办理，以便账单区不堆叠面板。

## 验收条件

### 共用外壳与视觉

- [ ] 语义 token 来自 DSH 宿主变量：浅灰画布配白色卡片，卡片有圆角和淡边框，没有常驻阴影和渐变。主按钮使用中性色（浅色模式近黑、深色模式近白）。蓝色只表示交互、焦点、选中和 Agent 参与。字体使用系统字体栈。standalone Web 使用相同取值作为回退，不再使用靛紫主色。
- [ ] 浅色和深色两套主题都成立。DSH 中只跟随宿主的明暗，不提供本地主题入口。正文文字的对比度达到 4.5:1，状态色和非文本边界达到 3:1。
- [ ] 字号：正文和输入为 14px，表格与数据区为 13px。字号三档偏好继续生效，只缩放语义字号。日期、时间、金额和检验值使用等宽数字。
- [ ] 页头只放这些内容：页面名、当前患者、助手状态摘要、全屏按钮、人物菜单。岗位切换只在右上角人物菜单里，菜单分为门诊、住院、系统三组。
- [ ] 页头下方有一条流程线。门诊依次为挂号 → 分诊 → 接诊 → 缴费 → 发药；住院依次为住院登记 → 入科分床 → 在院诊疗 → 办理出院 → 结算 → 清床 → 病案归档 → 医保核定。流程线标出当前病例所在环节；队列开关放在流程线最左端。收起队列时整列移除，不留细条。
- [ ] 画布从左到右依次为：队列卡（可收起）、主区（患者卡、页签和内容卡）、右栏（只放做决定需要的只读资料）。没有只读资料的页面不设右栏，主区占满。
- [ ] 底部操作栏只在有主操作，或刚完成一个操作时出现。左边显示关键数字，中间显示禁用原因或「还差：…」，右边只放一个主按钮。完成后显示「已完成 …」和可以接着做的下一步。
- [ ] 不可逆的提交（确认收款、确认结算、确认完诊、提交支付、确认发药）先把操作栏变成确认条，说明后果，并提供「返回」和「确认」，不弹出模态框。
- [ ] 布局按 ClinMesh 内容容器的宽度切换，不按视口宽度：
  - 900px 以上：三栏。
  - 600–900px：队列与主区两栏，右栏移到主区下方。
  - 600px 以下：单栏，队列变成顶部的横向条。
  - 宽屏 944、分屏 720、窄屏 400 三档下都不出现横向页面滚动，标签文字不折行挤压。
- [ ] 页签放不下时，排在后面的页签自动收进「更多」，当前页签始终可见。展开「更多」后页签换行显示，宽度变化时重新测量。

### Agent 草稿与原位确认

- [ ] Agent 通过 `*.draft.set` 填写的字段显示虚线框和「助手」标记，人工修改后变回实线并去掉标记。
- [ ] Agent 的 `.propose` 动作不再弹出 AlertDialog：
  - 针对某一行的操作（校对、确认已阅、确认诊断）显示为该行内的确认框。
  - 针对整页的操作（挂号、分诊、开具处方、收款、发药）显示为底部操作栏的助手确认条。
  - 两种形式都并排提供「不采用」和确认按钮。
- [ ] 原位确认保留现有审阅合同，只改变呈现位置：
  - 同一时间只有一个待确认项。
  - 需要「已核对」勾选的请求，必须勾选后才能确认。
  - 请求被中止、或页面卸载时，确认框消失，调用方收到拒绝。
  - 批准和拒绝都是静态的，不播放 Agent 动效。
- [ ] Agent 执行非 proposal 动作时，工作区的环绕柔光改用蓝色交互色；系统开启减弱动效时，不播放柔光。
- [ ] DSH 对话区仍是唯一的模型对话位置，ClinMesh 页面内不另做聊天区。

### 门诊

- [ ] **挂号员。**
  - 队列卡顶部分为待挂号、检索、建档三个分段。
  - 主区：选中病例后显示患者卡和挂号信息（科室、号别及价格、就诊地点）。就诊日期显示为仿真日期，只读。
  - 右栏：今日挂号列表，门诊号可以复制；复制失败时显示提示。
  - 确认挂号后生成 `CM-OP-…` 门诊号，病例进入待分诊。
  - 队列卡顶部的「门诊 / 住院」切换替代原来的外层页签。住院部分见下文的无原型页面。
- [ ] **分诊护士。**
  - 队列分为待分诊、已分诊两个页签，去掉服务端恒为空的「异常」页签。
  - 主区：主诉，六项体征，以及四级分级的单选芯片。
  - 体征输入框显示可录入范围，超出范围时在原位报错，并写明范围。
  - 体征卡片标题说明「默认值不是测量结果」。
  - 右栏显示风险信息。
  - 操作栏写明还差哪些字段。
- [ ] **门诊医生。**
  - 五个分区保留 `doctorCaseSectionSchema` 的枚举值和 Agent 参数；界面的显示顺序沿用当前页面：问诊记录、病历记录、检验检查、诊断、处方，不按枚举声明顺序排列。
  - 分区页签可以任意切换，每个页签显示状态图标和待办数。
  - 患者卡有「完诊 n/7」按钮。
  - 右栏显示完诊清单，七项都写明对应的分区名，点击可跳转。生命体征放在完诊清单下方。
  - 现有的质控开放疑点和诊疗建议继续保留在右栏，改用新的卡片样式。
  - 点击完诊时，如果有未完成项，操作栏列出缺少的项，并给出「前往〈第一个缺项的分区〉」；全部满足时，操作栏变成确认条。
  - 原来的完诊 Dialog 不再使用。
  - 已完诊的病例为只读，服务端允许的纠错入口继续保留。
- [ ] **收费员（门诊）。**
  - 队列卡顶部是「门诊 / 住院」切换，下面依次是类别筛选（检验、放射、病理、药品）和 2×2 网格的状态筛选（待缴、已缴、已拒绝、结果未知）。
  - 主区：账单表格中挂号费只读，并注明「不在这里收取」。收款最多支持三种方式组合，金额填错时在原位报错。
  - 预览之后才能确认支付。支付拒绝时可以重新填写；结果未知时，主操作变为「查询原支付结果」。
  - 右栏显示支付尝试记录。
- [ ] **药师（门诊）。**
  - 队列分为待发药、已发药两个页签，去掉恒为空的「异常」页签。
  - 先审核，再发药。审核意见为空时不能审核通过。
  - 发药时批次默认选最早到期的，下拉选项显示库存和有效期。发药数量超过批次库存时在原位报错；允许部分发药，剩余数量留在待发药里。
  - 过敏只提示，不阻止审核或发药。

### 住院（有原型的岗位）

- [ ] **患者卡与环节页签。**
  - 患者卡显示：住院号、行政状态、姓名、性别年龄、住院第 N 天（从入科日算）、病区床位、预交金、累计费用。只有收费员显示「需补交」这个大号金额。
  - 环节页签按岗位收敛：
    - 住院医生：诊断医嘱、检查检验、手术、DRG 预分组、出院、病案；入科和费用收进「更多」。
    - 病区护士：入科、诊断医嘱、检查检验、手术、出院；费用和病案收进「更多」，不显示 DRG 预分组。
    - 收费员：费用、出院；入科收进「更多」。
  - 本次住院没有发生的环节移进「更多」，并标注「未发生」。本岗位读不到的环节不显示。页签多于 3 个时，按「入院｜在院｜出院｜病案」分组显示。
  - 转科交接只在多病区环境出现，住院医生和病区护士按现有权限读取。
- [ ] **环节头与落点。**
  - 每个环节头显示办理顺序，本岗位那一步加粗。
  - 有待办时写「轮到你：…」；没有待办时，写这个环节在等谁。
  - 打开患者时，默认落在本岗位第一个有待办的环节；没有待办时，落在岗位默认环节。
- [ ] **病区护士。**
  - 队列：待接诊置顶，每个床位显示「轮到你 n 项」，空床显示床位费。召回窗口和出院后病历放在列表底部。
  - 医嘱：可以逐条校对；按需执行和停嘱需要先填理由。给药未到计划时间时，写明「〈时间〉后可给药」。
  - 检查检验：可以校对并送检。
  - 手术：术前核对需要先填核对说明。
  - 出院：办理出区受阻时，写明还差几条医嘱、几次给药，以及下一步由谁处理。
  - 右栏显示已出的检查检验结果，带参考范围。
- [ ] **住院医生。**
  - 右栏为临床提醒，只写平台已有的事实，并说清在等谁；没有提醒时写「目前没有提醒」。
  - 「开始手术」旁边直接列出还差的项及负责人，不靠悬停提示。
  - DRG 预分组、耗材建议和自动跟进使用新文案，规则不变。
- [ ] **收费员（住院）。**
  - 队列按待结算、在院、待入科分组。
  - 出院补交的流程：可以留空，按全额记为现金 → 预览收款 → 确认收款 → 预览结算 → 确认结算 → 等护士清床。固定的是本次结算预览的金额，不锁定业务账目；账目变化后旧预览不能用于结算，需要明确重新预览，不自动替换已审阅的金额。

### 无原型的页面（按规划执行）

- [ ] **住院登记。** 放在挂号员页面队列卡的「住院」侧。主区是住院登记表（入院途径、患者来源、住院证、入院病区、预交金）和在册列表，门诊转住院与直接入院走同一个表单。
- [ ] **住院药房。** 放在药师页面队列卡的「住院」侧。主区是住院发药队列，样式与门诊发药一致，包括审核、批次和数量。
- [ ] **病案。**
  - 队列：全部、待整理、审核通过、已归档，行可以点击切换。
  - 主区：病案环节显示基本信息、住院过程、正式诊断与实际操作、病案费用、审核与归档记录。
  - 右栏：DRG 复核。
  - 病区和床位显示名称，不显示 ID。
- [ ] **医保核定。** 只保留核定队列一个入口，只列已归档的病案，去掉下方的住院表格。主区显示归档冻结的分组、复核说明和历史核定。主操作依次为「审阅模拟核定」→「提交模拟核定」。
- [ ] **退费。** 「费用更正与退款」改为当前费用下面的一张内容卡，只在有已缴费用时出现。操作依次为「预览退款」→「确认退款」。
- [ ] **模拟数据。**
  - 改为两个页签：演示准备、患者库。
  - 演示准备：虚拟时间、重置数据、生成患者、PCI 演示准备、影像和病理准备。
  - 患者库：搜索与翻页、患者详情、患者档案、开始门诊就诊、本次病例真值、来源历史。
  - 列表、详情、开始就诊等操作失败时，按实际失败的操作写错误文案。
- [ ] **设置。** 换成新外壳和卡片样式，导航与功能不变。

### 住院 Agent 能力

- [ ] 住院页面的 Agent 上下文包含当前患者和当前环节，替代现在的 `inpatient: []`。
- [ ] 新增以下 Agent 工具，均遵循窄 schema、受信 context binding、幂等键、预期版本与完整审计：
  - `inpatient.stage.select`：切换环节，只做导航。
  - 护士医嘱校对：准备后等护士确认。
  - 医生报告确认已阅：准备后等医生确认，沿用人工入口的报告可用和显示门禁；影像尚未实际显示时不能通过 Agent 确认已阅，不因新增工具绕过阅片要求。
  - 收费员出区补缴：可以填写收款草稿，也可以生成收款预览。
  - 收费员结算：可以生成结算预览，只预览，不结算。
- [ ] 下列操作不提供 Agent 入口，由人工完成：
  - 直接提交校对、给药、收款、结算。
  - 替医生确认知情同意。
- [ ] Agent 工具变化要同步更新 Operation Catalog、对应的 `clinmesh-*` Skill 和命令示例漂移测试。

### 状态与回归

- [ ] 每张内容卡都覆盖以下状态：
  - 加载中：使用 Skeleton，不整页闪烁。
  - 读取失败：写明哪项失败，并提供重试。
  - 空列表：写明为什么是空的，以及去哪里处理。
  - 无权限：不显示该环节或入口，不显示「请由其他岗位办理」的空壳。
- [ ] 以下既有门禁全部不回归：
  - 门诊：挂号 → 分诊 → 接诊 → 缴费 → 发药的状态机；完诊清单；处方开具后不可修改、未发药前可撤回；支付结果未知时阻止重复收款。
  - 住院：校对 → 发药 → 给药；手术四步门禁；未出院处理不能结算；未结算不能清床；归档冻结。
- [ ] 所有交互控件都有可访问名称，装饰图标设 `aria-hidden`，键盘焦点使用 `ring` token 且不被裁切。页签支持方向键切换。原位确认出现时焦点移到确认按钮，确认框关闭后焦点回到原位置。

## 设计决定

### 交互与视觉

- **视觉方向：** 扁平卡片加基准风格。住院日程、床头卡、品牌色、签名格等特色层都比较过，已否决。
- **token 来源：** DSH `preserve` 模式下，中性色、主按钮和文字色从宿主 `--dsw-*` 变量派生，并给出回退值。交互蓝和医疗状态色由 ClinMesh 自己定义：宿主的成功色、警告色和浅色业务蓝作为文字时对比度不足（见 [DSH 宿主研究](../research/2026-10-29-dsh-host-design-language.md#21-颜色-token011-rc2-取值)）。不改用 `shell: 'surface'`。
- **主题合并：** 现有的「基线青绿」和「靛紫」两套主题合并为一套。
- **[UI 设计合同](../ui/design.md) 随实现改写：**
  - 「页面分区不做浮动 Card」改为扁平卡片合同。
  - 门诊医生的 1080 / 720 断点改为 900 / 600。
  - 窄屏下建议栈从抽屉改为右栏移到主区下方。
  - 住院工作台、色彩与主题、Agent 柔光等章节同步更新。
- **门诊结构：** 沿用现有结构，只做界面细化；五个分区的枚举和 Agent 工具的分区参数不变。
- **住院结构：** 沿用患者列表加阶段工作台（见[住院阶段工作台](../decisions/implemented/architecture/2026-10-21-inpatient-stage-workspace.md)），阶段导航改为按岗位收敛的分组页签。药师和医保办不进入阶段工作台。
- **「门诊 / 住院」切换：** 挂号、收费、药房的切换从页面外层页签移到队列卡顶部的分段控件。
- **界面称呼：** 面向使用者的界面和话术称「助手」，工程文档、代码和工具名继续使用 Agent。

### 模块与接口

- **语义 token：** UI 包的样式表仍是 token 的唯一 owner。DSH Surface 的样式构建继续把作用域改写到 ClinMesh 根节点；浅色和深色仍由根节点的 `dark` 类切换，DSH 中只跟随宿主的明暗。
- **业务组合组件：** 队列卡、患者卡、内容卡、右栏卡、底部操作栏、分组页签放在 Web 应用内部，供各岗位工作台共用。目前只有 Web 一个消费者，按包规则不进入共享 views 包。底部操作栏的输入只有四项：关键数字、原因文本、主操作、语气（普通、受阻、完成、确认、助手）。
- **原位确认：**
  - `AgentReviewProvider` 保留 `request()` 与 `cancel()` 合同。
  - 请求新增一个可选锚点，用来标识对应的行。
  - 有锚点、并且该行已挂载时，确认框显示在行内；其他情况显示在当前页面的操作栏。
  - 原有的 AlertDialog 呈现方式删除。
  - 「已核对」勾选、单一待确认项、中止和卸载时拒绝、决策闸门（decision gate）都保持现有行为。
- **完诊：** 继续使用现有的完诊预览数据，改由医生工作台的操作栏呈现阻断项和确认条，不再打开完诊 Dialog。
- **门诊医生控制器拆分：** `DoctorCaseController`（约 4,000 行）先按五个分区和外壳拆分，外部行为和 Agent 工具合同不变，再替换界面。
- **住院环节页签：** 由一个纯函数根据岗位、住院状态和现有的 `mayRead` 规则，推导每个环节的类别：
  - 可办理的环节：主页签。
  - 只读或本次未发生的环节：收进「更多」。
  - 不可读的环节：隐藏。

  默认落点取本岗位第一个有待办的环节。待办由现有住院查询（住院概要、临床、手术）在前端聚合，不新增聚合端点。
- **视图状态：** 队列收起、当前页签、「更多」展开属于客户端视图状态，归 Zustand；服务端数据仍归 TanStack Query，不在两处重复保存。
- **住院 Agent：**
  - 服务端上下文规则为住院视图声明当前住院和环节两个字段。
  - 合同包的工具登记表新增住院工具，类别为 ui-only、draft-only 或 human-review，并按岗位授权。
  - 工具输入 schema 与现有门诊工具同构：页面绑定、幂等键、预期版本。
  - 前端工具处理放在一个独立模块里，住院工作台一行接入。propose 类工具通过 `AgentReviewProvider` 发起人工确认，确认后调用现有 Command。
  - 如果涉及 Agent-facing CLI 合同，同一 diff 更新 Operation Catalog、住院 Skill 和漂移测试。
- **助手人设：** 只改 DSH 业务 preset 的人设前缀，加入按岗位的用词和话术规则，保留现有的安全与恢复规则。
- **文案：** 沿用现有的 `t(中文, 英文)` 写法，不引入新的文案机制；中文按术语表改写，英文同步改为对应术语。

## 测试策略

### 测试切入点

只使用三个测试切入点，都有现成先例，不新建测试工具。

1. **Web 端到端（主切入点）：**
   - 运行在 Playwright `web` project，使用真实 HTTP 服务、合成数据和真实 Web 入口。
   - 按岗位走完整流程：门诊挂号 → 分诊 → 接诊 → 缴费 → 发药；住院校对 → 发药 → 给药 → 出院 → 结算 → 清床。另外覆盖病案归档、医保核定和退费。
   - 验证内容：布局、文案、门禁、助手草稿标记、原位确认、空状态、错误状态和门禁拒绝；报告已阅的 Agent 确认保留人工入口的显示门禁，结算预览后账目变化须拒绝旧预览并允许重新预览。
   - 可参照的先例：`inpatient-bench.spec.ts`、`billing-payments.spec.ts`、`doctor-checklist.spec.ts`。
2. **DSH Surface 浏览器合同：**
   - 运行在 Playwright `contracts` project，覆盖 React 18 / 19 和 ShadowRoot。
   - 验证原位确认的批准、拒绝、勾选、中止、卸载、单一待确认项和焦点去向。
   - 验证 token 能否从宿主变量派生，以及浅色、深色是否正确。
   - 验证内容容器在 944 / 720 / 400 宽度下的布局，以及「更多」收纳。
   - 可参照的先例：`agent-feedback.browser.test.ts`、`borders.browser.test.ts`、`font-size.browser.test.ts`。
3. **服务端 HTTP：** 只针对新增的住院 Agent 工具和住院页面上下文，覆盖 schema 拒绝、幂等重放、版本冲突、越权岗位和审计记录。可参照的先例：`agent-context-http.test.ts`。

### 好测试的标准

- 只断言使用者或调用方能观察到的结果，例如可访问名称、可见文字、按钮是否可用、接口响应和审计记录；不断言组件内部状态或类名。
- 门禁类断言只能改定位方式，不能放宽条件。
- 不给待办推导、页签收纳这类内部函数单独写单测，由端到端测试从可见页签和环节头覆盖，避免测试锁死实现细节。
- 迁移现有测试时，旧的 AlertDialog 审阅断言转到 Surface 浏览器合同；按文案定位的断言随新文案更新。

### 其他检查

- 住院界面文案禁用词扫描：扫描住院界面的中文文案，出现规格列出的系统用语时失败。
- 助手人设：沿用现有的 `business-preset.test.ts`。
- 只使用合成 Provider 和临时数据库，不调用真实模型。
- 截图证据：用 Playwright 从真实入口截取每个岗位 × 944 / 720 / 400 × 浅色、深色。截图不包含影像和病理像素。
- 必跑检查：
  - `pnpm verify:boundaries`、`pnpm typecheck`、`pnpm lint`、`pnpm test:unit`、`pnpm test:browser`、`pnpm test:e2e`。`test:unit` 必须包含新增住院 Agent 的服务端 HTTP 测试和助手人设测试。
  - `pnpm --filter @clinmesh/dsh-web build`，并通过 verify-artifact 体积关卡。
  - `pnpm verify:docs`、`pnpm docs:check`；修改 Agent Note 时加跑 `pnpm verify:agent-notes`。
  - 本次涉及跨包接口，最终集成还须按[测试策略](../testing.md#检查命令)运行 `pnpm check`。该命令包含 `perf:ci`，必须先取得用户针对当次压测的明确许可；未获许可时先完成可独立执行的常规检查，并如实保留完整集成检查未完成的状态。

## 范围外

- 业务能力、Command、FHIR 合同和授权的变更（「住院 Agent 能力」所列的除外）。
- 岗位之间的交接通知（需要新的通知能力）；挂号费的收取入口；退款与医保的 Agent 工具。
- 问诊录音、病历质控、放射和病理详情页的结构重做。这些页面只换样式。
- `shell: 'surface'` 品牌模式；DSH 宿主区域内的导航行改为模仿宿主样式。
- Desktop 单独验收、Mobile UI。
- 未提交的 `inpatient-prototype.tsx` 原型路由，不纳入本次交付。

## 依赖与风险

- **DSH 产物体积：** 现状审计记录产物已超出 5,000,000 字节预算。本次改造不新增依赖，样式整合后要实测体积；超出时先处理预算问题，再合入。
- **`DoctorCaseController` 体量：** 约 4,000 行，需要先拆分再改界面，否则风险集中在一个文件。
- **测试定位：** 约 3,400 处测试按角色名或文案定位，文案改写后要批量更新。
- **新增住院 Agent 工具：** 涉及合同包、服务端和前端三处，可以作为独立切片验收。
- **工作区现状：** 主工作区有用户未提交的改动。实施在独立分支和仓库外 worktree 中进行，不覆盖这些改动。
- **术语依据：** 住院术语依据常见的临床说法，没有对照真实医院的 HIS 核对。上线前最好请护士和收费员各看一遍术语表。
