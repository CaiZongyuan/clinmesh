# 门诊号按日期持久发号与一致展示

Status: approved

## 问题与目标

现有门诊号包含就诊日期，但按 Workspace、Epoch 和当日现存挂号记录推导流水，不能保留已删除号码的发行高水位，也不能保证跨 Epoch 的可见号码不同。医生患者横幅将 `patient.identifier` 标为“门诊号”，而挂号记录和分诊队列使用独立的 `registrationNumber`，同一就诊在不同入口展示的号码含义不一致。

目标是保留号码中的日期信息，按业务日期持久发号，使迁移后成功发行的门诊号在同一权威数据库历史内不复用，并让挂号、分诊和医生工作台展示本次就诊的同一个号码。日期帮助识别和划分编号空间，唯一性由受事务保护的持久流水及数据库约束共同保证。

## 范围

- 普通挂号和合成病例开始就诊的共享挂号 Command，以及门诊号在 Registration 与 Encounter.identifier 之间的原子保存。
- 同一权威数据库内跨 Workspace、Epoch 的按日发行状态、存量初始化、删除、重启、产品内 reset、日期回拨和备份恢复边界。
- 挂号记录、分诊队列和详情、医生队列和病例详情，以及独立 Web 与 DSH 共享患者横幅中的号码查询、展示和复制。
- 保留内部 UUIDv7、患者级标识、既有幂等回执、授权、审计和 Workspace/Epoch 数据隔离。当前归属见[领域词汇](../../CONTEXT.md)、[存储与事务](../architecture/storage.md)与[临床业务流程](../architecture/clinical-workflows.md)。

## 用户故事

1. 作为挂号员，我希望号码保留就诊日期，并在重启、删除或重置后继续安全发号，不因历史号码复用导致混淆或挂号失败。
2. 作为分诊员或医生，我希望各工作台显示本次就诊的真实门诊号，并能复制完整号码核对同一次就诊。
3. 作为医生，我希望患者号和门诊号含义清楚，号码与主诉在窄窗口中仍可阅读和核对。

## 验收条件

- [ ] A1：新门诊号使用 `CM-OP-YYYYMMDD-流水号`，例如 `CM-OP-20261020-000123`；日期来自已校验的就诊业务日期，流水从 1 开始，至少六位，超过六位自然增长，不截断、取模或回绕。排序使用业务日期和数值流水，不依赖变长字符串的字典序。
- [ ] A2：同一业务日期在同一权威数据库内共用持久发行高水位，跨所有 Workspace 和 Epoch 分配不同的新号；进入新日期使用该日期的序列。删除中间号、最高号或全部挂号业务行、关闭重开数据库以及产品内 reset 后，原日期的新流水仍大于该日期此前已提交发行值；虚拟日期回拨时继续该日期已有高水位。
- [ ] A3：普通挂号与合成病例开始都通过同一个发号边界执行；发行状态、Registration、Encounter.identifier、业务关联和 Command 回执在同一写事务中提交。事务失败时一起回滚，提交前不向外返回成功号码；同一幂等键重发返回原事实和原号码，不再次分配。
- [ ] A4：两个受控连接或并发公开请求不会得到重复号码；保留适用的数据库唯一约束和有界锁等待。序列缺失、损坏、耗尽或编号容量超过安全整数合同的情况返回可识别的受控错误，不按当前业务行数、现存最大值或默认初值自动重建发行状态。
- [ ] A5：同一患者再次挂号时，患者级标识保持不变，新就诊取得新门诊号；本次就诊内的首诊、检查、复诊、签署及完诊不更换门诊号。医生与分诊读取的号码和挂号记录、Encounter.identifier 中的对应号码一致。
- [ ] A6：迁移跨全部 Workspace、Epoch 和日期初始化可靠高水位，完整保留已有门诊号、患者标识及内部 ID。当前最大存量号码只是历史高水位的下界；历史删除造成上界无法确认时，迁移报告受控失败并保留数据，不能将猜测值当作已确认历史。既有跨作用域重复号保持原值，新发行保证不扩展这些重复。
- [ ] A7：挂号和分诊读模型、医生队列与病例详情提供明确的 `registrationNumber`；页面的“门诊号”读取该字段，不读取 `patient.identifier` 或以患者号补缺。兼容历史病例确实缺少挂号号时如实显示“未记录”；正在加载或读取失败时不沿用上一病例的号码，也不伪装成成功取得号码。
- [ ] A8：挂号记录、分诊和医生工作台均能核对完整门诊号，并支持复制完整原值；复制失败时不给出成功反馈。医生横幅使用等宽数字，号码与主诉有明确标签和阅读空间，窄窗口可换行；不只展示无法唯一核对的尾四位。患者标识需要展示时明确标为“患者号”，病例切换后复制目标随当前病例更新。
- [ ] A9：新旧格式的完整号码均可通过现有授权内查询找到对应记录；编号跨 Workspace 发行不扩大查询权限，其他 Workspace、旧 Epoch 及越权病例仍按既有权限规则隔离。
- [ ] A10：一致备份及恢复核验覆盖发行高水位；受控恢复旧备份时必须保全并恢复不低于此前已发行范围的可信高水位。受控恢复或克隆流程无法证明高水位与单发行权威时，不启用发号并报告受控错误；不要求应用自动识别任意文件复制，不宣称本地计数器可独自保证任意备份回退或独立克隆后的全历史不重复。

## 设计决定

门诊号识别本次就诊，当前挂号号与其使用同一个业务值；患者级标识识别患者，候诊序号属于岗位队列，三者不互相替代。门诊号继续投影到 Encounter.identifier，内部逻辑 ID 保持现有 UUID 合同。

使用按业务日期维护的独立持久计数器，作用域不包含 Workspace 或 Epoch；计数器不随业务删除、reset 或日期变化清理。日期沿用已校验的就诊业务日期与 Virtual Time 合同，真实接收和提交时间独立保存。六位是最小显示宽度，允许断号，不回填历史空洞，也不追求无间隙流水。

迁移是发行前置条件：盘点存量和可信历史证据，初始化所有已知日期；迁移后的新日期可以受控建立初始序列，已建立日期的发行状态缺失时必须失败，不能把损坏误判为首次使用。采用能区分首次建立与历史丢失的持久记录和完整性校验，具体 schema 在实施时确定。

号码取值由服务端的当前就诊读模型统一投影，前端不从患者号、可见记录数量或日期拼接重建。主诉正文选择与质控由[医生主诉任务](https://github.com/CaiZongyuan/clinmesh/issues/252)独立维护；本项只处理同一横幅内的号码语义和阅读布局，实施时协调共享文件。

实施时将发行状态、初始化与恢复完整性方案记录为 Agent Note，并更新存储、FHIR/Command 和实际受影响的 UI 合同；本规格描述目标，不把尚未实施的发号行为写成当前系统事实。

## 测试策略

通过公开 HIS HTTP 入口和 file-backed SQLite 验证普通挂号与合成病例开始，覆盖历史断号、删除最高号及全删业务行、跨六位增长、跨 Workspace/Epoch、日期变化与回拨、同键重试、事务失败和两个真实连接竞争。关闭重开数据库以及产品内 reset 必须使用持久库；迁移样本覆盖已有格式、跨作用域重复号、历史高水位证据缺失，以及序列缺失和损坏，断言失败不丢数据、不自动重建。备份恢复测试验证发行状态被保全，受控恢复或克隆流程在旧快照未保全高水位、单发行权威未确认时不启用发号。

以挂号与分诊工作台、`apps/web/src/app/doctor/patient-summary.test.tsx` 及医生控制器为前端测试入口，使用患者号与门诊号明显不同的合成数据，验证真实取值、缺失、加载和失败、病例切换、完整复制与窄宽度阅读。按[用户界面验证](../testing.md#用户界面验证)从真实 Web 和 DSH 共享入口执行 Playwright 回归，并覆盖共享代码的 React 18/19 与 ShadowRoot 合同。

文档阶段运行对应文档检查；实施阶段先运行覆盖变更的最小回归，再按跨包接口与协议变化执行 `pnpm check`。若 Agent-facing CLI 的 schema、错误或恢复合同受影响，同步其 owning Operation Catalog、产品 Skill 和示例漂移测试。

## 范围外

- 重编号历史挂号、改写患者来源标识、替换内部 UUID、统一处方或其他业务编号。
- 新建候诊叫号系统、将门诊号后缀作为排队顺序，或新增预约、退号、Mobile 功能。
- 主诉同步、分诊差异质控、病历正文自动保存和医生工作台整体改版。
- 保证流水无间隙，或在没有外部高水位证据的任意旧备份恢复和独立双写克隆中继续承诺全历史唯一。

## 依赖与风险

无已知外部平台实施阻塞。迁移前需核对实际存量与可信发行历史，已有业务表无法证明此前删除过哪些号码；证据不足按 A6 失败并保留数据。按日初始化与损坏识别、受控恢复前高水位保全和发行权威核验必须作为实施完整性设计的一部分，不能以运行时自动重建代替。

跨 Workspace 共用发号器只共享编号分配，不共享患者或就诊读取权限。主诉同步任务和医生工作台改版可能同时修改横幅与病例合同，实施前协调基线、字段归属和最终集成验证。
