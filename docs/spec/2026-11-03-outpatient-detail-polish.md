# 门诊与窗口岗位界面细节修整

Status: approved

## 问题与目标

用户复审主线门诊各岗位，并在收费、药房有数据时逐页巡检，发现结构已定但细节粗糙：

- 五个开具窗口（诊断、药品、检验、放射、病理）各自实现，排版、按钮和不可选原因写法不一致。检验详情与开具住院证两个弹窗内容贴边，根因是共享对话框容器没有内边距。
- 问诊记录页标题与计数重复，对话外层多一圈边框，输入区看起来像禁用。
- 医生队列"在诊 / 待诊 / 完诊"页签切换时宽度跳动：完诊没有计数，页签由 48px 变成 59px。
- 分诊头部占用过高，露出 SYN 开头的原始患者编号。
- 收费左栏叠了三层切换（门诊/住院、四类费用、四种缴费状态），药房左栏叠了两层。
- 门诊收费账单两张表重复，露出原费用 UUID 和 FHIR 引用。抬头 ¥68 与费用合计 ¥88 口径不一。缴清后仍显示挂号未收 ¥20。费用更正表单常驻。
- 门诊药房审核前就能改批次和数量。发完药后主区只剩空占位。已发药详情用禁用下拉框展示批次。
- Surface 宽 826px 时，收费和药房的队列不收起，门诊账单表格被横向裁切。
- 药品建议里，国家目录药品的频次显示"频次待核对"，实际是医生已填写的自由文本。

目标：在不改变门诊结构和业务流程的前提下，统一这些细节，去掉原始编号和开发腔文案，消除金额与状态矛盾。

## 范围

适用门诊医生、分诊护士、门诊收费员、门诊药师，覆盖 standalone Web 和 DSH Surface，浅色和深色主题，以及 1101px、826px 两档 Surface 宽度。

1. 开具窗口：诊断、药品、检验、放射、病理五个开具窗口和开具住院证弹窗。
2. 检验详情弹窗和开具住院证弹窗的内边距。
3. 问诊记录页。
4. 门诊医生队列页签。
5. 分诊头部。
6. 收费左栏和门诊账单。
7. 药房左栏和门诊药房流程。
8. 药品建议的频次显示。

## 用户故事

1. 作为门诊医生，我希望五个开具窗口布局一致，以便换一类项目时不用重新找按钮。
2. 作为门诊医生，我希望开具窗口左栏一屏能看到更多候选项目，以便少翻页。
3. 作为门诊医生，我希望在右栏看到选中项目的详情和填写项，以便确认后再加入。
4. 作为门诊医生，我希望不可选的项目直接写明原因（如"本院当前未开展""未配置门诊价格"），以便知道为什么点不了。
5. 作为门诊医生，我希望还没选项目时主按钮明显不可点，并在底部提示下一步，以便知道还差什么。
6. 作为门诊医生，我希望检验详情和开具住院证弹窗的内容不贴边，以便阅读。
7. 作为门诊医生，我希望问诊记录页直接展示对话，没有重复的标题和多余的边框，以便专注问诊。
8. 作为门诊医生，我希望问诊输入区一看就能输入，以便不会误以为被禁用。
9. 作为门诊医生，我希望切换"在诊 / 待诊 / 完诊"时页签不跳动，每个页签都有计数，以便快速比较各队列人数。
10. 作为分诊护士，我希望分诊头部只占一行，以便把空间留给体征录入。
11. 作为分诊护士，我希望头部不显示原始系统编号，风险标识与患者信息同行，以便一眼看清。
12. 作为收费员，我希望左栏只有一层切换，其余筛选放在列表头，以便快速定位待缴项目。
13. 作为收费员，我希望门诊账单只有一张费用表，不出现原始编号和 FHIR 引用，以便核对费用。
14. 作为收费员，我希望抬头金额与费用合计一致，以便不用自己核算差额。
15. 作为收费员，我希望挂号费标明已在挂号处收取，缴清后不再显示未收，以便不误收。
16. 作为收费员，我希望费用更正、医保待遇和支付尝试记录默认收起，以便主流程只剩收款。
17. 作为收费员，我希望付款方式区域紧凑，以便一屏完成收款。
18. 作为药师，我希望先审核处方，审核通过后才能选择批次和数量，以便符合审核在前、调配在后的顺序。
19. 作为药师，我希望发药后主区继续显示刚完成的处方，以便确认结果后再处理下一位。
20. 作为药师，我希望已发药的批次用只读文字展示，以便不误以为还能修改。
21. 作为在窄 Surface 中工作的收费员或药师，我希望 826px 宽时账单和处方不被横向裁切，以便看全金额和数量。
22. 作为门诊医生，我希望药品建议直接显示我填写的频次，以便不用再核对一遍。
23. 作为使用深色主题的用户，我希望以上变化在浅色和深色下都清晰可读。

## 验收条件

### 开具窗口

- [ ] 诊断、药品、检验、放射、病理五个开具窗口使用同一两栏布局：左栏为搜索和候选列表，右栏为选中项目的详情与填写项，底部为提示文字和主按钮。
- [ ] 左栏行距比现状更紧，在 1101px 宽、窗口高度 `min(720px, 视口高度 − 40px)` 下，诊断一屏至少显示 12 行，检验至少显示 11 行。
- [ ] 主按钮文案沿用现有动作：加入诊断、加入处方、加入检验、加入放射检查、加入病理会诊、开具住院证。
- [ ] 不可选的候选行在行内显示原因，原因文字来自现有不可用判定，不新增判定规则。
- [ ] 未选项目时，主按钮以虚线框表示不可点，与提交中状态区分，底部提示写明下一步。
- [ ] 826px 宽时两栏仍可用，内容不被裁切；容器过窄时右栏移到左栏下方。
- [ ] 窗口内的现有 Agent 目录标识保持不变，Agent 工具照常定位各类开具窗口。

### 弹窗内边距

- [ ] 检验详情弹窗和开具住院证弹窗的内容与边框之间有内边距，与其他对话框一致。
- [ ] 修复落在共享对话框容器的一处，已有对话框不出现双重内边距。

### 问诊记录

- [ ] 去掉页内重复的标题和计数行。
- [ ] 对话直接展示在页面卡片内，没有嵌套边框；每条消息的时间与说话人同行。
- [ ] 输入区默认是可输入外观，只有真正不可用时才显示禁用样式。

### 医生队列页签

- [ ] "在诊 / 待诊 / 完诊"三个页签等宽，各自显示计数，切换时宽度不变。

### 分诊头部

- [ ] 分诊头部在 1101px 宽下只占一行：患者姓名、性别年龄、门诊号和风险标识同行。
- [ ] 不显示 SYN 开头的原始患者编号。
- [ ] 头部的体征摘要不显示参考区间线。

### 收费

- [ ] 左栏只保留缴费状态一层分段页签。门诊/住院和费用类别移到列表头，改为下拉筛选，计数跟随当前筛选。
- [ ] 门诊账单只有一张费用表，不显示原费用 UUID 和 FHIR 引用。
- [ ] 抬头应收金额与费用表合计使用同一口径。
- [ ] 挂号费标为"已在挂号处收取"，不计入本页待收；缴清后不显示任何挂号未收金额。
- [ ] 费用更正、医保待遇和支付尝试记录默认收起，展开后功能不变。
- [ ] 826px 宽时费用表在卡片内完整显示，不出现横向裁切。

### 药房

- [ ] 左栏只保留"待发 / 已发"一层分段页签，门诊/住院移到列表头筛选。
- [ ] 处方待审核时只显示审核操作，批次和数量不可编辑；审核通过后才出现批次和数量。
- [ ] 发药成功后，主区停留在刚完成的处方，展示只读结果，并在操作栏提供下一位。
- [ ] 已发药处方的批次以只读文字展示。不显示发药时间，因为现有队列合同没有这个字段。
- [ ] 826px 宽时处方明细完整显示，不出现横向裁切。

### 药品建议频次

- [ ] 频次不是本院受控代码（QD、BID、PRN）时，显示医生填写的原文，不再显示"频次待核对"。频次为空时仍显示"待补充"。
- [ ] 国家目录药品的剂量和频次继续使用自由文本输入，本院药品继续使用下拉。

### 通用

- [ ] 以上岗位在 standalone Web 和 DSH Surface、浅色和深色主题、1101px 和 826px 宽度下逐项截图，无重叠、无裁切。
- [ ] 界面上不出现原始 UUID、FHIR 引用和开发腔文案。

## 设计决定

- 开具窗口采用两栏布局（原型 `2026-11-03-order-dialogs` 中的"两栏"方案），左右栏比例约 5:6，左栏行距收紧以容纳更多条目。五个窗口共用一个布局组件；各类项目的检索、可用性判定和提交逻辑保持原样。
- 弹窗贴边从共享对话框容器修复，不在单个弹窗里补内边距。
- 国家目录药品的频次保持自由文本，只修正显示：非受控代码显示原文。
- 收费和药房的门诊/住院切换改为列表头筛选，延续 2026-10-29 已定的"挂号、收费、药房去掉外层门诊/住院页签"方向。
- 挂号费在挂号处收取，门诊收费页只做说明，不再作为未收项。
- 药房保持"审核 → 调配发药"顺序，界面按状态逐步展开，不改变审核和发药命令。
- 不新增或修改服务端合同。现有合同缺少的信息（如发药时间）不展示，不编造。
- Surface 小于 800px 时队列的收起规则沿用[外壳规格](2026-11-02-dsh-shell-feedback-redesign.md)；826px 下的裁切通过表格自适应解决，不改变队列断点。

## 测试策略

- 只验证公开可观察行为：可见文字、可用状态、布局约束和截图，不断言组件内部结构。
- Web E2E（`apps/web/e2e`，Playwright）是主切入点，沿用现有 fixture 和写法：
  - 开具窗口：`diagnosis-prescription.spec.ts`、`investigation-billing.spec.ts` 的开具流程，断言两栏、主按钮文案、不可选原因和未选状态；
  - 收费：`billing-payments.spec.ts` 断言单张费用表、无原始编号、金额口径一致、挂号费说明、折叠区和 826px 不裁切；
  - 药房：`pharmacy-card.spec.ts` 断言审核前不可编辑批次、发药后停留结果、只读批次；
  - 队列页签、分诊头部和问诊记录在现有医生、分诊旅程中补充断言。
- DSH Surface 浏览器合同（`apps/dsh-web/src/client/*.browser.test.ts`）：两栏开具窗口和对话框容器内边距纳入 React 18/19 ShadowRoot 双版本测试，沿用 `workspace-card.browser.test.ts` 的写法。
- 频次显示用现有建议组件单元测试覆盖受控代码、自由文本和空值三种情况。
- 交付前按岗位、宽度和主题截图，与开具窗口原型逐项对照。

## 范围外

- 住院各岗位（住院收费、住院药房、住院登记等）的界面重做，由住院规格负责。
- 诊疗建议读取延迟，由[诊疗建议读取延迟 Issue](https://github.com/CaiZongyuan/clinmesh/issues/385) 链接的规格负责。
- 国家目录药品频次改为受控下拉。
- 服务端合同变化，包括为药房队列新增发药人和发药时间。
- 门诊结构、流程步骤和岗位划分。

## 依赖与风险

- 开具窗口原型保存在被忽略的 `.prototypes/`，worktree 中需按[开发环境](../memory/development-environment.md)软链接后才能对照；验收以本规格条目为准。
- 五个开具窗口共用布局后，各窗口原有的键盘焦点、Agent 目录定位和提交恢复行为需要逐个回归。
