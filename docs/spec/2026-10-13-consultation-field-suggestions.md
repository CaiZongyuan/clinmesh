# 问诊自动记录建议与病历字段集成

Status: draft

## 问题与目标

当前病历记录和问诊记录页面都在正文上方显示独立的“问诊自动记录”提示块，病历页还在该块中集中列出全部自动内容、来源与核对按钮。医生需要在提示块和实际字段之间来回对照，记录增多时提示块不断拉长，挤占病历编辑和问诊空间。

目标是将自动整理结果集成到对应的病历字段内，让医生在阅读、编辑该字段时直接选择是否应用。自动生成建议与医生确认后的病历正文应清晰区分，建议不能混入输入框的真实值。

## 范围

覆盖医生病历记录与问诊记录的共享 Web/DSH Surface 入口。字段内建议首先适用于现有自动整理支持的主诉、现病史和既往史；用药及过敏自述仍归入相关病史字段。本需求不扩展模型的临床内容生成范围。

移除两页正文上方的大块自动记录面板。全局整理状态、暂停、恢复、历史补录与失败重试以紧凑方式整合到现有页头；具体建议、来源查看及应用、忽略、撤销入口归属相应病历字段，不再集中堆在表单外。

## 用户故事

1. 作为医生，我希望在对应病历框内看到自动整理的建议，直接判断是否应用，无需回到页面顶部对照。
2. 作为医生，我希望自动建议先供我选择，未应用时保留当前病历正文；查看来源后可逐项应用或忽略。
3. 作为医生，我希望病历编辑和问诊对话拥有足够空间，自动记录状态与控制入口简洁且容易找到。

## 验收条件

- [ ] A1：病历页和问诊页正文上方不再出现独立的大块自动记录面板或跨字段建议列表；现有页头提供紧凑状态和全局控制入口。
- [ ] A2：建议出现在所属字段的同一视觉容器内，与字段标题、编辑框和操作形成一体；主诉、现病史、既往史各自只展示自己的建议，医生无需离开当前字段进行选择。
- [ ] A3：新提取的新增、补充和更正均先成为待应用建议。生成成功、轮询、刷新或打开页面都不会在医生应用前改变草稿正文；已经应用的内容发生后续更新时，也需重新展示建议并等待选择。
- [ ] A4：每条待应用建议提供“应用”“忽略”和“查看来源”。应用仅改变对应字段的有效目标范围，保留其他字段和无关人工内容；忽略不修改正文，同一来源的重复处理不能恢复已忽略建议，新证据可形成新建议。
- [ ] A5：字段内可区分当前正文、待应用内容和已经应用的内容。替换或冲突建议展示被影响的当前内容与拟应用内容；失效目标不能继续应用，须提示重新核对。
- [ ] A6：来源入口展示支撑该建议的全部必要患者原话、轮次、相关医生问题与引用定位；来源内容保持完整，关闭来源后能继续在原字段操作。
- [ ] A7：目标字段有未保存编辑时，沿用先保存再应用的保护规则，给出就地提示；其他字段的未保存输入不因应用或刷新丢失。版本冲突保留人工输入与建议，重新读取后允许再次核对。
- [ ] A8：已应用建议在所属字段提供来源与局部撤销入口。撤销保留之后的无关新增；目标已经人工改写时保留正文并进入核对，不直接覆盖。原有自动写入的历史内容仍可查看、核对和撤销，不自动清空或重新写入。
- [ ] A9：没有建议的字段保持普通编辑体验，不预留大型空面板；建议较多或原文较长时可展开查看历史和细节，默认不堆积已忽略、被替代或已撤销的历史列表。
- [ ] A10：整理中、暂停、待补录、失败和重试状态仍可观察与操作；模型失败不阻断问诊或删除建议。应用中防止重复提交，失败在相应字段反馈并保留可恢复内容；无编辑权限或签署准备期间禁用写操作，仍允许合法的只读来源查看。
- [ ] A11：建议及应用、忽略、撤销事实由服务端持久化，保存、刷新、切换病例、重连和服务重启后保持一致；患者、Encounter、Workspace/Epoch 隔离与现有幂等、版本和审计规则继续有效。
- [ ] A12：签署前摘要准确包含尚未应用的建议和未整理回答，沿用现有人工核对与签署协议；签署准备和已签署文书不被迟到结果或建议操作修改。
- [ ] A13：窄 DSH 分屏、长建议、中英文和应用字号变化下，编辑框、字段操作与问诊输入区可见且可到达；按钮支持键盘访问，来源弹窗在 React 18/19 与 ShadowRoot 内正常打开、关闭并返回焦点。

## 设计决定

字段容器拥有该字段的建议与人工选择，页头只承载整理状态和全局控制。建议不得通过 placeholder、隐藏默认值或未经确认的输入框正文模拟已经应用。默认优先展示仍需处理的内容，来源细节与历史按需展开。

“是否应用”暂按所有新提取内容先确认再写入理解，因此这是对现有自动合并行为的调整。当前实现会直接应用无冲突新增及未被人工改写的自动片段更新；既有行为与追踪边界由[自动记录规格](2026-10-08-consultation-auto-record.md)、[病史总结与患者自述溯源](2026-10-12-consultation-agent-summary-sources.md)和[系统架构](../architecture.md#81-门诊闭环)拥有。本规格尚为 draft；若最终确认仅搬迁核对界面、保留无冲突自动写入，应先修订 A3 及相关验收，再进入实施。

继续复用已保存问诊、病史总结、来源校验、Query、共享 Command、持久任务和审计。应用和忽略是服务端事实，不能仅由浏览器维护；未保存输入保护继续沿用现有规则。建议布局、待应用增量的应用语义与多轮更新归属在实施前细化，非平凡流程及协议取舍由 Agent Note 记录。

## 测试策略

通过公开问诊 HTTP、病例 Query 与 file-backed SQLite 验证：提取后仅有建议，点击应用后才改变对应草稿范围；覆盖新增、相关补充、更正、人工冲突、忽略后重放、重复应用、并发编辑、撤销、旧数据、重启和签署。仅替换外部模型边界，不以按钮回调或浏览器本地状态作为持久化证据。

Playwright 从真实病历和问诊入口验证字段归属、页头紧凑布局、应用与忽略、来源返回、未保存编辑保护、空状态、长内容、失败恢复和窄窗口操作可达性。涉及来源弹窗的 Surface 合同覆盖 React 18/19 与 ShadowRoot；从实际 DSH 入口用合成问诊验证完整旅程。常规 CI 不依赖真实模型凭据或付费调用。

## 范围外

自动诊断、检查检验推荐、处方推荐、全病历内容生成、正式过敏记录写入、自动签署，以及 Mobile 入口改造。医生补充来源与全病历整理由 [Issue #177](https://github.com/CaiZongyuan/clinmesh/issues/177) 单独追踪。本次仅登记需求，不实施业务代码或改变现有病例数据。

## 依赖与风险

自动记录、病史总结和来源核对基础已合入 main，无需等待其他功能票。当前审阅接受操作主要处理有目标的替换建议；新增内容改为待应用后，必须验证无替换目标的新增建议也有完整的应用路径，不能只隐藏顶部面板或禁用自动写入。

尚需确定最终确认模式、字段内默认密度与展开方式，以及多轮待应用建议的合并和失效规则。历史已应用内容不得被升级操作重写。若改变 schema、HTTP 或 Agent-facing CLI 合同，须同步 owning Operation Catalog、对应运行时 Skill 与命令示例漂移测试。
