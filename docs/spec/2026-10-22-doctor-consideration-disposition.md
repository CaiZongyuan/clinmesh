# 诊疗建议待核实思路的已核实与忽略

Status: implemented

## 问题与目标

医生工作台"依据与说明"当前是纯文本陈列：思路的支持/反对/待核实事项逐字渲染模型输出，其中引用的证据 id 以原始 `evidence:<哈希>` 示人；患者自述和历史记录整段铺开、多处重复；"待核实思路"没有任何处理动作，每轮生成原样重现，无法表达"医生已核实完毕"或"不再关注"。本需求让思路从文案变成可清零的工作项，并把证据呈现收敛为人读、可展开的来源。

思路本身仍是只读推断：已核实/忽略不是采纳按钮，不创建任何临床草稿或正式事实；[2026-10-13 规格](2026-10-13-doctor-guideline-recommendations.md)的 E1、R9、R23 边界继续生效。

## 范围

- 医生工作台三类建议（检验、放射、病理、诊断）"依据与说明"弹窗中的待核实思路：每条提供"已核实""忽略"两个动作，状态持久化；处方类无思路通道的现有约束不变。
- 已处理思路在弹窗内收起的"已处理"区可查看（标题与状态），可撤销恢复到待核实列表。
- 弹窗叙事质量：叙述文本中的证据 id 引用渲染为对应证据 label；病例证据块（患者自述、历史记录等）默认折叠为来源摘要行，展开显示全文；指南条款链接保持现状。
- 可采纳建议（items）的确认/开具交互不改动，仅以既有测试与构造状态验证其继续成立。
- 入口覆盖 standalone Web 与 DSH surface（同一源码，React 18/19 双版本合同）。

## 用户故事

1. 作为医生，我希望每条待核实思路能标记"已核实"或"忽略"，处理后不再每轮重复出现，以便把待办真正清零。
2. 作为医生，我希望点错了能在"已处理"区撤销，以便误操作可恢复。
3. 作为医生，我希望看到证据来源名而不是哈希，患者原话默认收起，以便快速读懂依据而不被大段文字淹没。

## 验收条件

- [x] C1：弹窗叙述文本（结论、支持信息、反对信息、待核实事项）中出现的证据 id 以对应证据 label 呈现；无法匹配的文本原样展示，不出现裸 `evidence:<哈希>`。
- [x] C2：items 与思路引用的病例证据块默认折叠，摘要行含证据 label（问诊轮附时间摘要，历史条目附条数摘要）；展开显示现有 `EvidenceContent` 内容。同一证据被多条思路引用时不重复铺开全文。
- [x] C3：每条待核实思路提供"已核实""忽略"动作；执行后该条从待核实列表消失并入"已处理"，状态存服务端；同一病例后续刷新或重新生成中，归一化标题相同的思路不再出现在待核实列表，顶部"另有 N 项待核实思路"计数同步排除。
- [x] C4："已处理"区默认收起，列出已核实/忽略的标题与状态，提供撤销；撤销后该思路回到待核实列表。
- [x] C5：已核实/忽略/撤销不创建诊断、申请、处方或病历内容，不改变 encounter 版本，不触发建议重新生成；items 的确认与开具流程不变。
- [x] C6：旧持久化建议状态（无处置字段）兼容读取，未处理思路展示与现状一致。
- [x] C7：Web 与 DSH（React 18/19 双版本）真实入口上动作、折叠、撤销可用；键盘可达且 aria 标注完整。

## 设计决定

- 处置状态存储在独立 SQLite 表，主键（actor_id, case_id, kind, label_key）；`label_key` 为思路标题归一化文本（trim 并压缩连续空白）。字面匹配：重新生成后标题相同的思路视为同一条；标题不同视为新思路如实展示，不做语义模糊匹配。
- 处置不写入 `doctor_recommendation_state` 持久 JSON；读取与生成响应按当前 actor 统一合并出可选字段 `considerationDispositions`（label_key、status、label 快照），旧行自然兼容。
- 契约新增 `POST .../recommendations/:kind/considerations/disposition`，入参 `{ label, status: 'verified' | 'dismissed' | 'clear' }`；`clear` 删除处置记录即撤销。upsert 天然幂等，走既有医生病例授权，不要求 encounter 版本。kind 契约与迁移 CHECK 均排除 prescription（处方类无思路通道）。
- 生成管线（提示词、核验、降级、outbox）零改动；处置只在读取与展示层生效。取舍详见 [Agent Note](../decisions/implemented/feature/2026-10-22-doctor-consideration-disposition.md)。
- 生成失败、pending、stale 状态下处置数据照常返回，但动作仅对当前可见思路提供。

## 测试策略

- 服务端沿用现有 HTTP + file-backed SQLite 模式（`doctor-consideration-disposition.test.ts`）：set/clear/读回合并、归一化 upsert、kind 隔离、重启保留、授权拒绝、prescription kind 拒绝。旧状态兼容由既有 Web 组件全套用例固定（其 state fixture 均为无处置字段的旧形状，经同一 strict schema 读取）。
- Web 组件测试（`doctor-recommendations.test.tsx`）：哈希→label、折叠与去重铺开、动作与消失、计数排除、已处理区与撤销、键盘与 aria。
- DSH 相关浏览器合同按 diff 影响运行既有用例；完整交付 diff 运行 typecheck、lint 与相关回归。

## 范围外

- 指南语料覆盖、院内目录内容、建议生成与核验逻辑（"口腔病例只产出思路"的根因，另立任务处理）。
- 病历质控条目（待补充/待核实）的展示与闭环。
- 思路与正式诊断/申请的自动关联、自动打勾。
- 可采纳建议的确认/开具交互改造。

## 依赖与风险

无外部阻塞。标题字面匹配意味着模型换一种措辞重提同一方向时会作为新思路出现，这是已确认的如实行为；处置数量有界（每 kind 最多等于历史思路数），不构成存储风险。
