# PR 按影响范围检查与主线全量并行验证

Status: approved

## 问题与目标

主 CI 在 PR 和主线 push 时均运行完整检查，并将单元/集成测试、浏览器合同、Web E2E 和其他检查串行执行。局部改动也承担全量测试的等待成本。目标是让 PR 根据可以证明的影响范围选择检查，将选中的独立检查组并行运行；合并后对主线保留完整验证。

提速通过减少无关检查和缩短串行等待实现，保留已确认的行为、错误路径、安全边界、React 18/19 覆盖及原有断言和超时。定向检查不保证每种改动都比全量更小，影响范围过广或无法可靠判断时执行全量。

## 范围

沿用主 CI 的现有触发入口：PR 创建、更新或重新打开，以及 `main`、`master` 的 push。其他 Actions 工作流保持各自的触发条件与职责。

| PR 改动 | 必需检查范围 |
| --- | --- |
| 只有普通说明文档 | 文档链接、Agent Note 格式及文档站构建等适用检查 |
| 只有已有独立测试入口，可同时包含普通文档 | 变更文件内的全部测试、所属包及实际测试入口的类型检查、lint；文档变化追加文档检查 |
| 普通页面、样式、UI 组件 | 受影响的前端组件测试和消费者类型/构建检查，完整浏览器合同与 Web E2E；可省略没有受到影响的整套服务端单元测试 |
| 普通服务端业务代码 | 服务端测试及受影响的 HTTP、CLI、DSH、浏览器/E2E 等实际消费者合同；无法证明集合完整或影响过广时全量 |
| 共享接口、数据库、权限、宿主桥接、依赖、CI/构建配置，或其他无法识别的改动 | 全量 |

`main`、`master` push 固定选择全量，不因合并前的 PR 检查成功而减少检查项目。

## 用户故事

1. 作为开发者，我希望文档和独立测试修改只运行必要检查，以便更早获得结果。
2. 作为修改普通业务代码的开发者，我希望 CI 检查实际受影响的模块及其消费者，而不是只检查改过的测试文件。
3. 作为审查者，我希望看到本轮选择了哪些检查以及选择理由，并确认没有把无法判断的改动误当成无影响。
4. 作为维护者，我希望独立检查并行执行、主线继续全量验证，并由同一个最终结果明确表示整体成功或失败。

## 验收条件

- [ ] A1：PR 的检查选择绑定本次事件和实际检出的候选合并结果，比较完整改动集合；不只读取最后一个提交，也不读取后来更新的另一个 PR head。
- [ ] A2：只有普通文档变化时，运行适用的文档检查，不启动无关业务测试。运行时 Skills、提示词、Agent 规则、代码生成或构建配置不因扩展名为 Markdown 而被当成普通文档。
- [ ] A3：独立测试修改运行所有变更测试文件的完整用例，不仅选择改动行或某个成功用例；浏览器合同继续覆盖文件内的 React 18/19。共享 fixture、setup、辅助代码，以及新增、删除或重命名测试入口不进入这条快速路径。
- [ ] A4：定向测试保留所属包的类型和 lint 检查；Web E2E 等未被包级 tsconfig 覆盖的入口有相应类型检查。入口不存在、无法选择或实际发现零个应运行测试时，不报告定向验证成功。
- [ ] A5：至少支持普通前端生产代码的定向路径，保留 Web/DSH 的直接源码消费者、前端组件测试、完整浏览器合同和 Web E2E；不能把它收缩成“只有测试文件变化才定向”。前端路径省略服务端整套 Vitest 时，浏览器和 E2E 内的真实 HTTP、临时 SQLite 接线仍保留。
- [ ] A6：服务端定向选择覆盖真实消费者，不能仅依赖 package.json、静态 import 或 HTTP 路径字符串猜测完整影响范围。没有可靠边界的服务端变更明确回退全量；不承诺自动为每个业务文件找到最小测试集。
- [ ] A7：共享 contracts/core、数据库及迁移、鉴权与受信上下文、宿主桥接/Proof 等协议边界、依赖锁、workspace、CI/测试/构建配置、子模块以及其他未知路径触发全量。DSH 包不能整体视为纯前端。
- [ ] A8：主线 push 总是运行与现有 `pnpm check`、`pnpm check:mobile` 等价的完整检查集合，包括包边界、类型、lint、所有单元/集成测试、两个 Playwright 项目、现有短性能预算、文档、构建与 Mobile 校验。
- [ ] A9：选中的单元/集成、浏览器合同、Web E2E 与基础检查等独立组在不同 runner 上并行执行，使用同一提交快照。保留测试、临时数据库、端口和产物隔离，不以同一台机器盲目增加 worker 数量代替并行分组。
- [ ] A10：最终必需结果继续命名为 `verify`。计划生成失败、必需组失败或取消、必需组意外跳过、结果缺失或无法解释时，`verify` 失败；只有被计划明确排除的组可以跳过。
- [ ] A11：差异读取不完整、事件与提交不匹配、空改动集合、未知状态、无法解释的跨模块组合等情况选择全量；不能静默成功或直接跳过整个主 CI。
- [ ] A12：文件名及事件数据经过验证，只作为参数或数据使用，不拼接成任意 shell 命令。保持最小 GitHub 权限，不为检查分流引入凭证写入或仓库管理权限。
- [ ] A13：Actions 能看到实际选择的检查组、回退原因、执行结果和耗时。用真实运行确认重型检查组时间重叠，记录与既有可比运行的差异；不把“约33分钟缩至20分钟”的估算作为已经交付或固定墙钟门槛。
- [ ] A14：实施交付同步测试策略 owner，并记录测试分流及并行的 Agent Note；所有未通过、未运行与尚缺的验证证据如实披露。

## 设计决定

检查选择与并行调度分开：先决定本次必须执行的检查，再启动对应组，最后汇总完整结果。主线保留全量复检，PR 定向检查保留失败关闭的全量兜底。

普通文档与独立测试使用窄范围识别；普通业务代码依据可审查的模块边界和实际消费者选择检查。允许先支持有明确证据的前端路径，其他生产代码在不能证明影响集合完整时回退全量。这种回退属于正常选择结果，不把所有路径伪装成已经具备精准筛选能力。

现有 Web 与 DSH Surface 存在直接源码引用，浏览器合同和 Web E2E 会动态构建真实 UI、启动真实 Server；因此生产前端变化保留完整的两个 Playwright 项目，不能只依赖静态导入图省掉上层回归。服务端的共同 Runtime 会使影响集合较广，定向范围可以接近或等于全量。

并行组覆盖原完整检查集合，基础检查可包含类型、lint、包边界、文档、构建、适用的 Mobile 与现有短性能预算；分组不改变各项检查的语义。不新增测试结果跨轮复用，不把主线复检替换成缓存成功状态。

正式要求由本文件拥有，Issue 仅追踪实施。具体文件/目录选择规则、执行命令与回退条件由实施测试和当前测试策略共同约束，新增映射必须有对应回归证据。

## 测试策略

使用现有 Vitest、Playwright、Node/Git 能力及合成数据，围绕三个公开边界验证：

1. 检查选择：用合成 PR 事件及临时 Git 提交/合并，覆盖文档、已有测试、普通前端、服务端保守回退、关键路径、混合改动、新增/删除/重命名、损坏或缺失差异、base/head/checkout 不匹配和主线全量。
2. 执行入口：在进程边界记录实际 runner 与参数，验证完整文件选择、React 版本保留、类型覆盖、零测试失败、任一子命令失败立即传播；不通过启动真实模型或负载来测试分流脚本。
3. 工作流汇总：覆盖计划失败、必需组失败/取消/意外跳过/结果缺失、允许跳过非必需组，以及全部必需组成功的路径；实际 GitHub Actions 证明并行关系与 `verify` 结果绑定本次提交。

首次改造本身涉及 CI 配置，必须验证完整检查集合。保留现有短 count/storage 预算门禁；持续负载、饱和度或真实模型验证仍需用户针对具体运行另行许可，不能从本规格或 Issue 推导许可。

## 范围外

- 删除合并后的主线全量 CI、修改其他工作流触发策略、自动合并或自动标记 PR ready。
- 降低断言、扩大超时、自动重试掩盖失败、减少既有安全/错误/平台合同。
- 建立覆盖全部 HTTP 和动态加载语义的通用依赖图系统，或为了每条路径都提速而猜测影响范围。
- 提升 runner 规格、付费缓存平台、增加第三方依赖或拆分大量执行票。
- GitHub 分支保护的管理员设置。该事项与 CI 输出兼容，但不由本规格宣告已经生效。

## 依赖与风险

当前 CI 与安装依赖足以实施分组和定向入口，无需新增测试框架。实际并行能力受 GitHub runner 排队与账号并发限制影响，缩短等待时间可能增加总 runner 用量，必须分别报告。

动态 UI 构建、跨包相对导入和 HTTP 调用不能由单一静态依赖工具完整表达；选择范围不可靠时的全量兜底是质量边界。分流实现自身的改动也必须选择全量，避免检查策略自我漏检。

将 `verify` 设置为强制合并条件需要仓库管理权限。既有身份未具备该权限；工作流实施可以独立推进，但不能把 `verify` 显示成功或失败等同于 GitHub 已强制拦截合并。
