# 多项业务集中办理与连续操作减负

Status: approved

## 问题与目标

医生为同一患者开多项检查或医嘱时，需要反复打开选择界面、填写并单项确认；护士校对、送检和住院药房发药也存在重复提交。门诊处方、诊断已有整组提交能力，但目录单项添加后关闭；手术耗材也已有整台提交，但仍需从下拉框逐项加入，连续录入繁琐。门诊收费的账单虽能汇总展示，收款仍绑定单个收费项目。

目标是在保留每项业务核对、实际执行事实和交易恢复边界的前提下，让同一患者的多项同类业务集中选择、编辑和确认；需要逐项阅读或办理的任务使用连续队列减少往返。事实来源见[重复逐项操作盘点](../research/2026-11-09-batch-action-inventory.md)，当前业务合同见[临床业务流程](../architecture/clinical-workflows.md)。

## 范围

全部纳入总需求，后续按可独立验收的纵向切片拆票。适用当前 Web、Desktop 和复用工作区的 DSH Surface；Mobile 不在本轮范围。

| 编号 | 场景 | 目标与必须保留的区别 |
| --- | --- | --- |
| S01 | 住院检查检验开立 | 连续选择多项，保留各项适应证、指征等信息，再集中开立。 |
| S02 | 门诊手动检查草稿 | 检验、放射、病理均纳入，解除每类只能保留一个手动草稿的限制；保留现有 AI 建议与手动项目共同待开的能力。 |
| S03 | 住院医嘱开立 | 改为弹窗内连续添加、多条待开医嘱和一次确认；每条保留药品或护理治疗项目、长期或临时、用法、剂量、频次等业务信息。 |
| S04 | 护士新医嘱校对与停嘱核对 | 多选、集中核对；新医嘱校对与停嘱核对是两种独立动作。 |
| S05 | 护士送检 | 多选同患者符合条件的申请并集中送检，保留各项标本、前置条件与状态校验。 |
| S06 | 门诊处方添加药品 | 改善多药连续选择与编辑；现有整张处方统一开具能力继续使用。 |
| S07 | 门诊诊断添加 | 改善多诊断连续选择与编辑，保留唯一主诊断等约束。 |
| S08 | 手术耗材录入 | 改善多耗材选择与用量、预留关联的连续编辑；整台手术仍作为现有提交单元。 |
| S09 | 住院药房发药 | 同患者多执行单集中核对和发药，逐单保留药品、批次、数量及执行时间。 |
| S10 | 门诊多项目收费 | 同患者同次就诊的多收费项目合并预览与收款，明确费用分配、结果不明与退款恢复边界。 |
| S11 | 报告阅读与已阅确认 | 一个窗口内连续阅读多份，再集中确认已阅；未打开或未满足显示条件的报告不能选中，不将未读报告直接标为已阅。 |
| S12 | 停嘱、取消申请与失败重试 | 同动作多选集中处理；需要理由时统一填写并允许逐项修改，保留逐项状态校验和恢复。 |
| S13 | 给药、健康教育与 PRN | 逐项核对实际情况后集中保存记录，不默认全选；PRN逐项提供发起理由，发起不等于已经给药。 |
| S14 | 剩余预留释放 | 在已有多选统一提交能力上改善全选、清空及状态反馈。 |
| S15 | 术后耗材更正与手工预留维护 | 纳入连续办理优化，保留逐笔实际用量、更正及库存关联。 |
| S16 | 病案审核归档与医保核定 | 跨患者采用连续办理队列，成功后点“下一份”切换；每份仍分别核对与提交，失败留在当前病例。 |
| S17 | 患者库开始就诊 | 跨患者采用连续办理队列，逐患者确认开始就诊，成功后显式选择下一位，不自动办理。 |
| S18 | 选择与结果反馈 | 当前页全选可办理项目、清空选择、跨页保留明确勾选的项目，始终显示待处理清单和数量；每项展示问题、结果与恢复入口。 |

## 用户故事

1. 作为住院医生，我希望一次添加多项检查和医嘱并核对清单，以便减少反复打开表单和逐项开立。
2. 作为门诊医生，我希望手动准备多个检查项目，并连续添加药品和诊断，以便集中核对后提交。
3. 作为病区护士，我希望分别集中校对新医嘱、核对停嘱和送检，以便减少重复确认且保留每项核对信息。
4. 作为住院药师，我希望集中核对同患者的多条待发药执行单，以便在每项药品与数量明确后完成发药。
5. 作为收费员，我希望同次就诊的多个待收费项目能合并收取，以便患者不必反复支付，并能准确追溯每项费用。
6. 作为手术耗材操作人员，我希望连续选择和维护多项耗材，以便减少逐次寻找项目且保留实际用量与预留关系。
7. 作为报告阅读者和实际执行记录者，我希望连续办理多项任务，以便减少页面往返而不省略实际阅读和执行核对。
8. 作为病案、医保和患者库操作人员，我希望办理后方便进入下一个病例，以便减少重复定位并保持患者边界。
9. 作为任一操作人员，我希望看到逐项处理结果，以便修正失败项目而不重复办理已经成功的项目。

## 验收条件

### 已确认的共同边界

- [ ] 同一批次只包含同一患者、同一次就诊或住院、同一种动作；不能将开立、送检、停嘱、发药或收费混为一次提交。
- [ ] 跨患者的病案审核、医保核定和开始就诊使用连续队列，分别提交各病例，不能跨患者集中写入。
- [ ] 提交前发现漏填或不符合条件时，标明具体项目和原因；用户修正或移除问题项目后才能提交。
- [ ] 提交后的非资金逐项动作若部分失败，逐项展示结果并保留成功项；恢复只处理明确失败且仍可操作的项目，不能重复办理成功项。
- [ ] 资金操作按单笔收款完整结果处理，不把临床项目的部分成功规则直接用于收款。
- [ ] 目录选择支持在弹窗内连续添加，添加一项后弹窗保持打开；待提交清单可逐项编辑并集中确认。
- [ ] 住院医嘱页面提供“开立医嘱”入口，目录选择、剂量、频次等填写移入弹窗，不保留一套并行的页面内开立表单。
- [ ] 检验、放射、病理各自在类别内部批量开立，不提供跨类别一次总签发；病理每项分别填写送检手术和目的。
- [ ] 未提交清单在关闭弹窗、切页、切患者及刷新后可恢复；回到原患者只展示该账号、岗位、患者和就诊绑定的草稿，退出登录后清除。
- [ ] “清空草稿”明确提示丢弃并由用户确认；提交成功的项目移出草稿，失败项目及其已填内容保留。
- [ ] 门诊合并收费按所选项目各自当前剩余应收一次收齐，预览逐项金额及总额；未选项目继续待缴，原有单项目分次收款能力保留。
- [ ] 合并收款成功后，各费用可以追溯本次原交易中的对应金额；退款仍按原费用、原成功交易和可退额度办理，不借退款撤销已发生的临床事实。
- [ ] 报告在同一窗口连续查看，最后一次确认选中报告已阅；未打开的报告不可选，放射或病理未满足既有显示条件时仍不可确认。
- [ ] 给药、健康教育等实际执行记录须逐项明确核对实际情况后才可选中并集中保存，不提供默认全选或无条件一键完成；未发生的动作不生成已完成事实。
- [ ] PRN 按项记录发起理由并集中发起，不将发起结果写成已给药。
- [ ] 需要理由的同类动作可填写共同理由并为个别项目覆盖；提交预览明确每项最终理由，保留原动作的理由必填和权限规则。
- [ ] 有全选功能的待办理清单只全选当前页中可办理的项目，不隐式选择未展示页面；翻页、搜索或筛选后保留用户已明确选中的项目，并持续展示完整已选清单与数量。
- [ ] “清空选择”只取消勾选，不删除草稿或已保存记录；“移除项目”“清空草稿”与取消选择明确区分。
- [ ] 报告全选只包括当前页已打开且满足显示条件的项目；实际执行记录不提供绕过逐项事实核对的全选。
- [ ] 跨患者办理成功后提供标明目标患者的“下一份”或“下一位”入口，用户点击才切换；失败时停留原病例，队列为空时明确提示，不自动审核、核定或开始下一患者的就诊。

### 目录与开立

- [ ] S01：同一类别的至少两个住院检查项目可以在一个弹窗内连续加入、分别修改指征、移除和选择，然后通过一次明确确认完成开立；成功结果回到各自独立申请和状态。
- [ ] S02：门诊检验、放射和病理各能同时保留多个手动草稿，不再要求开具或删除上一条后才能加下一条；手动和 AI 项目共用一份待开清单与正式入口。
- [ ] S02：只提交手动项目不依赖模型可用；包含 AI 项目时逐项保留资料指纹、准备代次、过期核验和人工修改保护。过期或不完整项目在提交前被标明，不以静默转为人工项目绕过核验。
- [ ] S03：住院药品和护理治疗医嘱可在开立弹窗连续添加并逐项填写现有业务字段；长期、临时与 PRN 等原有约束继续有效，开立不自动形成给药或教育事实。
- [ ] S06：在同一窗口连续加入两种完整药品后，一次开具形成同一张完整处方；药品包装、剂量、频次、疗程、数量及当前药品适用与库存规则均可核对。任一处方行不合法时不形成半张处方。
- [ ] S07：在同一窗口连续加入多个诊断，清单内设置和修改主次；正式确认仍形成完整诊断组，不允许出现两个主诊断或半组提交。
- [ ] S08：同一手术连续选择多种耗材，逐项编辑实际数量与预留关联，沿用整台手术的预览、核实及提交边界；任一不合法项目不产生半台手术或部分用量入账。
- [ ] 所有目录继续支持原有搜索、分页、包装或规格选择及不可用原因；不默认选择搜索结果首项，不因加入新项覆盖其他待办的人工修改。
- [ ] 原有处方、诊断和耗材等业务数量上限保留且在界面可见。新集中操作的公开数量上限须明确、有界；超过时明确阻止并保留输入，不静默截断项目或暗中分批提交。

### 护理、停嘱与库存

- [ ] S04：新医嘱校对清单展示每项药品或服务、用法、剂量、频次及时效；停嘱核对清单展示原医嘱、停嘱理由、当前状态及待执行任务影响。两类动作分别选择、分别确认。
- [ ] S05：护士可集中送检同患者多条符合条件的申请；每项说明申请类别、标本或前置条件、当前状态，尚不满足条件的项不可选择并给出原因。开立成功不自动代表送检完成。
- [ ] S09：同患者多条待发药执行单集中展示药品、批次、数量和执行时点；每项必须满足原有医嘱有效性、执行状态和库存条件。库存或状态变化发生冲突时，逐项报告结果，重试不重复扣库存或形成重复发药。
- [ ] S12：住院医嘱及出院前停嘱、门诊与住院可取消申请、可重试申请分别支持同动作集中处理；需要理由时共同理由及逐项覆盖可核对，不将“取消申请”直接显示成“退款成功”。
- [ ] S12：停嘱继续冻结后续任务、发药和给药，护士核停继续按原状态处理待执行任务；不自动退回已有库存、删除既有执行或撤销已发生费用。
- [ ] S13：给药、健康教育和 PRN 分别构成独立动作；清单逐项保留当前记录所需事实与理由，不暗中统一有差异的实际情况。提交前未明确核对的项不进入保存范围。
- [ ] S14：完成手术时，可对当前页符合条件的剩余预留全选和清空，并沿用一次预览及统一释放，不误作尚未具备的批量提交。
- [ ] S15：术后耗材更正和手工预留维护可在同一患者、同一手术内连续准备同类多条操作并集中核对，分别保留原记录、实际数量、理由及库存关联；漏记新耗材仍由 #406 的独立需求拥有。

### 资金、阅读与连续队列

- [ ] S10：门诊合并预览可以包含同次就诊内不同现有可收款类别的费用，每项显示原项目、净应收、已付或覆盖金额、剩余待付和本次收取金额；总额等于各选中项目待付之和。原来不可收取的费用类别不因此新增收款权限。
- [ ] S10：确认只执行一笔具有多项冻结费用分配的收款，不循环原有单项目收款按钮；保留现有支付方式组合与整数分规则。成功、拒付和结果不明分别作用于该整笔尝试，不产生“某付款方式成功、某方式失败”的新状态。
- [ ] S10：确认前费用金额、版本、医保覆盖、选择范围或支付方式变化使旧预览不可继续使用，须重新预览。任一关联费用有未决收款或退款时不发新资金操作。
- [ ] S10：支付响应丢失、结果不明、刷新或服务重启后查询同一原交易；恢复不产生新收款，相关费用在查明前保持资金阻断，确定后按各自资金和临床条件放行，不重复执行检查或发药。
- [ ] S10：原单费用分次收款与历史交易仍可办理和恢复；旧历史不被重写为新合并交易。
- [ ] S10：退回合并收款中的某一项时，明确选择原交易中的该项费用分配，同时受原交易未退总额、该项未退金额及该费用冲减依据限制。未知退款继续预占额度，退款渠道和原尝试恢复沿用既有合同；不能把同一笔总款对每项都重复退款。
- [ ] S11：阅读窗口可切换同患者同次就诊的报告并持续显示待确认清单，关闭、重开或刷新后，不把丢失的展示上下文当作影像或病理已经显示成功；报告修订或版本改变须重新查看后确认。
- [ ] S16–S17：成功后从当前队列进入明确的下一病例，下一目标失去资格时刷新队列并说明；当前病例的失败、未完成资金恢复和待保存事实不因切换而归属下一患者。

### 状态与恢复

- [ ] 空列表说明没有当前可办理项目；加载中不允许使用未完成的数据提交；加载失败提供重试并保留已有输入，不能把未加载误作无项目。
- [ ] 无权限、只读、就诊结束或状态变化的项目显示具体不可操作原因；服务端再次校验，不能仅靠按钮禁用保护。
- [ ] 提交中阻止重复点击；提交前保留原意图与幂等标识，响应丢失时查询原回执或原操作结果，不以新标识直接重试。
- [ ] 独立项目发生确定的部分成功时，结果摘要和逐项结果一致，成功项不可再次执行；确定失败项保留原输入并在修正后重新核对，结果不明项独立显示恢复入口。
- [ ] 诊断组、整张处方和整台手术内部失败时整体不生效，表单完整保留供修改；每个独立检查或医嘱内部的状态、费用、审计也作为一个完整单元生效。
- [ ] 目录、临床状态、库存或费用在选中后变化时明确显示冲突及需重新核对的项；不静默跳过、使用旧值或扩大选择范围。
- [ ] 键盘、长中文项目名、窄容器、缩放与长清单下可完成选择、编辑和提交；弹窗具备清楚标题、选中数量、焦点与独立滚动，不因 Surface 宿主宽度造成按钮或必填项不可达。

## 设计决定

取舍理由见[按业务单元集中办理与连续队列提案](../decisions/proposed/feature/2026-11-09-batch-action-boundaries.md)。

1. 全量场景纳入同一总需求，随后使用 `to-spec`、`to-tickets` 流程形成完整规格和执行票；创建需求和 Issue 不构成业务代码实施授权。
2. 批次边界为同患者、同次就诊或住院、同动作。跨患者办理使用逐病例连续队列。
3. 独立检查、单条医嘱等逐项动作采用提交前集中检查、提交后逐项报告结果的恢复方式；已经成功的项目保留，不随失败项目重复执行。诊断组、整张处方、整台手术内部仍整体提交或回滚；资金按整笔收款结果处理。
4. 目录选择采用弹窗内连续添加、待提交清单逐项编辑和集中确认；住院医嘱的页面内开立表单移入弹窗。
5. 检验、放射和病理各自在类别内部批量开立，不跨类别总签发；病理每项仍需关联送检手术与会诊目的。合并收费可跨这些类别选择同次就诊的费用。
6. 未提交草稿按账号、岗位、患者和就诊隔离；关闭弹窗、切页、切患者和刷新后保留，退出登录清除。清空需确认；成功项目移出，失败项目保留。已发出的操作不能当作尚未提交草稿再次执行，响应结果不明时沿用原操作恢复。
7. 合并收费只收齐选中项目的当前剩余应收；不提供跨项目任意不足额收款分摊。现有单项目分次收款保留。费用金额或余额变化须重新预览；结果不明时查询原支付，不对关联费用另发新收款，退款受各费用在原交易中的对应金额及既有退款合同约束。
8. 报告采用连续阅读后集中确认。打开报告只产生可参与确认的阅读上下文，不自动写入已阅事实；最终仍由医生明确选择和确认。报告修订、版本或患者上下文变化后须重新满足阅读与显示条件。
9. 实际执行记录采用逐项核对后集中保存，不默认选择未核对项；PRN发起与实际给药继续分离。需要理由的同动作支持共同理由与逐项覆盖，未要求理由的现有动作不因此新增无关必填项。
10. 跨患者队列成功后由用户点击标明目标患者的下一项入口才切换；失败留在当前病例，不自动提交下一患者。
11. 有全选功能的清单只选当前页中符合条件的项目，跨页和筛选保留明确选择并展示完整清单。实际执行事实须逐项核对，不能通过全选绕过。
12. 复用现有每项业务 Command 内核与状态流；集中操作不能绕过权限、状态、预期版本、幂等或审计。门诊同类独立检查由旧的整批原子保证转为逐项结果和恢复；这项变更明确接替[原诊疗建议规格 R17](2026-10-13-doctor-guideline-recommendations.md#自动准备与待开具清单)中独立检查的整批回滚要求，诊断组与整张处方的原子保证保留。既有[共享开单布局](../decisions/implemented/architecture/2026-11-03-shared-order-composer.md)继续拥有布局边界，不把业务草稿和提交状态放入布局组件。

## 测试策略

采用现有公开入口作为已确认的测试 seam，不为批量功能新增仅供测试调用的内部捷径。正式执行遵循[测试策略](../testing.md)。

| seam | 主要断言 |
| --- | --- |
| 公开 HTTP 与真实临时 SQLite | 同患者、同就诊、同动作及权限边界；独立项目部分成功与逐项结果；处方、诊断组、整台手术整体回滚；目录、库存、版本冲突；幂等重放和原回执恢复；审计及费用不重复。 |
| 资金公开预览、确认、查询与退款 | 多费用冻结分配、整笔成功或拒付、未知阻断、响应丢失及重启恢复；费用变化导致预览失效；单费用旧记录兼容；每项与整笔可退上限、预占及原渠道恢复。 |
| Playwright 真实岗位工作区 | 每个纵向切片通过真实目录连续添加、清单修改、明确确认与业务回读；草稿刷新及患者隔离、当前页全选、跨页保留、共同理由覆盖、部分失败恢复和下一病例显式切换。 |
| React 18/19、ShadowRoot 对话框合同 | 长中文、窄容器、缩放、键盘、焦点、独立滚动和输入保留；确认住院医嘱旧页面内表单已撤除。 |
| 报告与实际执行公开动作 | 未查看或显示未成功时拒绝已阅，报告改版后重新核对；给药、教育逐项实际事实及 PRN理由，不能因批量发起自动形成完成事实。 |

只测试外部行为，不逐函数复述实现。每个切片至少包含两个项目的成功例子、一个与该动作相关的失败或冲突例子，以及重试不重复生效的回读；现有 HTTP 回归、开单组件测试和 PCI 多岗位旅程提供事实与测试先例。涉及协议、CLI或Agent入口变化时按现有目录同步 owner 和漂移断言，不为了人类界面新增任意批处理工具。

仅使用合成数据、受控 Provider 和隔离数据库。放射与病理沿用显示成功后才能确认的合同；Agent 只读取文字与聚合状态，不读取影像或切片像素。正式实现须对照既有原型和真实渲染核对，本轮没有生成或接受新的批量交互原型。演示媒体在用户要求交付时按对应切片录制，并绑定实际提交；旧录像不是新功能的验收证据。

## 范围外

- 本阶段不修改业务代码、不执行实际业务批次或真实资金操作。
- 跨患者集中写入、跨就诊合并以及跨动作的一键总提交。
- 将尚未阅读的报告或尚未发生的给药、教育等事实直接标为完成。
- 术后漏记耗材的新登记能力由 [Issue #406](https://github.com/CaiZongyuan/clinmesh/issues/406) 追踪；本需求只处理相关录入和维护的重复操作，不扩展漏记补登记的要求。
- 调整尚未明确的既有临床与业务数量上限、扩展独立 Mobile 功能或创建不存在的技师岗位工作台。

## 依赖与风险

- 门诊合并收款会改变当前交易只关联单个费用、退款可从原交易推导唯一费用的假设，必须同步更新存储、预览、收款、恢复、退款及执行放行边界，不允许只循环现有 UI。
- 批量入口不能被误当成每项都已经读取或实际执行；实现和验收须分别验证报告、给药、教育与 PRN 的事实边界。
- 诊断组、处方、整台手术等现有整体业务单元不能因界面多选被拆成不一致的部分成功状态。每个独立检查或医嘱内部的状态、费用及审计仍须整体生效。
- 既有门诊建议确认对同类多项检查采用整体原子提交。新的独立检查逐项结果须明确与该合同的兼容方式，并更新对应协议和回归断言；不能直接声称沿用原事务而同时改变原子性。
- GitHub 执行票须引用本规格；只有已审阅拆票且没有未完成前置票的执行票使用 `ready-for-agent`，其余保留明确的依赖与状态。规格批准和 Issue 创建均不构成产品代码实施授权。

### 执行准备

- 需求范围、业务例外和测试 seam 已确认；产品代码实施仍须另获明确授权。
- 按 `to-tickets` 审阅下列纵向切片及真实阻塞关系后创建执行票；票号和远端关系以 GitHub 回读为准，不预设每票一个 PR。

## 执行切片

本节为待审阅的拆票方案；不新增上文之外的业务范围。每票同时完成该场景所需的界面、共享业务能力、状态与恢复验证，适用的共同规则（S18）随每票验收，不单独建立横向“批量框架”票。代码共享或文件相邻本身不构成阻塞；共同改动由实施时的归属和集成安排解决。

### 每票完成时的可见交付

每张执行票完成后，用户须能在该票对应的真实岗位入口看到并操作表中列明的变化。存在前置票时，在已包含前置成果的版本上独立演示本票新增行为，不要求等待其余无关执行票；总 Issue 只跟踪整体交付，不单独承诺新界面。

- [ ] 明确本票完成后可见的变化，以及本票尚未交付的后续能力；不能把只完成代码、接口或自动测试视作可见交付完成。
- [ ] 提供可运行的分支或提交、对应体验入口和复现步骤，并验证实际运行版本已加载该提交；需要业务数据时准备可复用的合成演示数据，用户无需手工构造前置状态。
- [ ] 通过真实界面完成本票的代表操作并回读结果；提供简短的前后变化说明及相应实机对比证据。布局变化可用对比截图，连续操作用短录屏；沿用仍有效的既有证据，不默认重拍整套项目视频。
- [ ] T19 的可见交付明确限定为多项目选择、余额合计及合并预览，集中收款、查询恢复与退款由 T20 完成；T20 不把仅有预览宣称为资金流程完成。
- [ ] 每票可见验收与合并、发布分别处理；提供该票可运行版本不代表已获自动合并或上线授权。
