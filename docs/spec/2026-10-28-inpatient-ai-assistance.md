# PCI 住院 AI 辅助：患者准备、耗材预计与分组核对

Status: approved

执行追踪：[父任务 #344](https://github.com/CaiZongyuan/clinmesh/issues/344)，四张原生子任务及其前置见下文。

本规格拥有本轮流程简化的目标与验收，不替代[PCI 住院 DRG Agent 规格](2026-10-27-inpatient-drg-agent.md)。既有持续跟进、逐笔实际耗材、差异待办和用量展示由原规格拥有；本轮复用其能力，只交付下述增量。规格及拆分已批准；发布规格与任务不等于业务实施、合并或真实模型运行授权。

## 问题与目标

固定 PCI 演示仍需操作者照手册填写患者扮演档案；耗材计划和预留需要重复选择、逐项填写；实际用量变化时难以在同一处核实并处理原预留。医生还要自行跨页面解释正式分组、计划推演和记录缺项。

目标是在原住院页面得到完整待入院患者、自动准备可修改的预计耗材、一次确认预留、按真实用量统一处理差异，并直接看见三类分组记录核对。明确遗漏自动提示，需要解释时再调用 AI。

## 范围

- 固定合成 PCI 患者一键就绪，仍由登记员办理入院、护士接诊分床；一般动态病例维持原生成方式。
- 首版耗材预计覆盖冠脉造影／PCI，按实际选择的手术区分方案。保存计划后自动预计一次；医生修改清单并统一确认一次形成预留。
- 刷新复用服务端结果，资料变化提示更新；显式重新预计保留人工编辑，将新结果作为候选差异供核对。
- 完成手术时直接核实真实最终用量，处理增加、减少、未用和新增项；与已有术中逐笔记录兼容。
- 现有住院页面展示提醒、清单及解释／修改／确认入口；无需先手工开启持续跟进任务，右侧聊天留待后续。
- AI 不可用或资料不足时说明原因，可从有效院内方案带入或人工补充，原诊疗不以模型成功作为门禁。

三类分组核对为：

1. 已有实际 PCI，而病案首页仍选择造影等其他主操作：展示两份记录供核对，不直接判错或代改主操作。
2. 正式分组与计划推演不同：展示各自实际依据。固定黄金病例可出现实际 FM59、计划 FM39，结果由规则引擎读取，不硬编码到其他病例。
3. 分组记录缺项／编码不兼容与支付参数缺失分别说明：病组已算出但缺支付参数时，明确“分组成功，金额暂不可估”。

## 用户故事

1. 作为演示操作者，我希望点击准备固定 PCI 病例后获得资料完整、待入院的患者，以免照手册填写九个档案字段。
2. 作为登记员和护士，我希望患者仍经过入院登记和接诊分床，以便演示原有多岗位流程。
3. 作为再次准备演示的操作者，我希望复用已有资料并保留人工修订，以免覆盖正在使用的患者来源。
4. 作为住院医生，我希望保存造影／PCI 计划后自动看到预计耗材，以免从空表单逐项录入。
5. 作为医生，我希望已有正式资料自动带入、缺少的参数逐项说明，以免重复抄写或把未知当作已知。
6. 作为医生，我希望看见材料身份、规格、数量、理由、金额和来源，以便判断是否可确认。
7. 作为医生，我希望调整清单后只确认一次，以免逐项操作或留下半份预留。
8. 作为医生，我希望刷新和重新登录后保留预计及手改内容，以免重复生成和丢失工作稿。
9. 作为医生，我希望资料变化后收到更新提示，新建议保留为待核对差异，以免覆盖人工判断。
10. 作为手术记录者，我希望核实真实最终用量并一处处理原预留差异，以免跨页释放和重填。
11. 作为已有术中记录的医生，我希望系统只补记与真实最终用量的差异，以免把已收费材料再记一次。
12. 作为医生，我希望明确哪些预留由本次处理，以免误动另一手术或未选材料。
13. 作为医生，我希望 AI 失败时仍能使用有效院内方案或人工路径，以便继续诊疗。
14. 作为核对 DRG 的医生，我希望直接看见三类确定性差异，再按需打开来源与解释，以便通过原审阅入口核实。
15. 作为病例负责人，我希望模型只读有权资料且不自动修改正式事实，以便保留诊疗与账务责任边界。

## 验收条件

- [ ] B1：首次准备后，患者资料、有效 Patient Persona 及选用状态就绪；无需手填九字段或另选首个修订，可沿既有来源绑定入口直接住院。准备不代办入院或分床。
- [ ] B2：重复准备复用原来源及有效资料，不覆盖人工修订、已开始就诊或历史绑定；保持一次消费、Epoch 重放和原操作恢复。
- [ ] B3：固定准备不调用模型，不产生本院正式诊断、检查报告、医嘱、实际手术、耗材使用或收费；患者自述只含其可知内容。
- [x] B4：造影／PCI 计划成功保存后自动准备一次本计划的 AI 预计，模型参与候选材料和预计数量的准备。刷新复用；关键依据变化提示更新，显式重新预计保留人工编辑和候选差异，不把四项各一件当作所有患者的默认答案。
- [x] B5：预计展示可解析的院内目录身份、规格、单位、数量、目录单价、金额、理由和待核实项。生成中、失败、缺目录、缺参数、无依据建议及依据变化分别表达；未经适用／兼容及数量依据核对的具体项不能直接确认为预留，院内方案带入也须核对。
- [x] B6：医生可调整清单并统一审阅一次；多项预留在一个共享 Command 内全部成功或全部回滚。再次确认明确处理被取代的原预留，不能叠加同一批计划金额。生成、查看或重算不创建预留、库存移动、实际使用或费用，草稿、有效预留和正式费用分开展示。
- [ ] B7：完成手术记录带入本计划原预留和已有实际使用；医生核实真实最终用量，在同一处处理增加、减少、未用和新增。确认后只对尚未发生或需要更正的差异记账，实际事实、所选预留处理、费用及审计一起成功或回滚；不影响其他手术及未选预留。
- [ ] B8：多条同材料预留等歧义须显式核对；可读取原目录版本及冻结价格，目录变化展示并重新审阅，不按材料名称猜版本或静默换价。原预计、实际、更正和费用关系可追溯，预留与实际不重复归集。最终零用量不新增零使用／零收费；已有使用须沿追加更正冲正，不能删改历史。
- [ ] B9：患者、岗位、Workspace/Epoch、计划、临床依据或目录变化时，旧结果不能错误应用；晚到结果不能覆盖人工编辑，提交核对受信版本并沿原意图恢复。
- [ ] B10：模型只使用当前岗位可见事实和允许的目录／方案，不读取 Case Truth、隐藏作者底稿或目标病组答案；身份、单位、价格、金额和分组由确定性业务规则处理。
- [ ] B11：正式 DRG 只消费已确认诊断及实际操作，计划只参与推演；医院支付参考、患者医保待遇和正式费用口径保持分离。
- [ ] B12：失败、取消、失效、重复请求、丢回执和冲突具有可理解状态与恢复入口；未知结果先查原尝试／回执，不自动重试业务写入或重复计费。有效方案／人工路径可继续，沿用目录与业务校验。
- [ ] B13：三类核对无需先开启持续跟进，随当前正式事实自动展示，包含来源和原页面入口；加载／读取失败不得冒充无遗漏。确定性查询不调用模型，解释按需调用且有效结果复用；AI 不可用仍可见规则结果，依据变化使旧解释失效。
- [ ] B14：同样包含 PCI 的病例可因主操作及其他正式事实不同得到不同病组；核对和解释不自动把 PCI 设为主操作，不补写并发症、不标记报告已阅，也不通过预留改变病组。

## 设计决定

### 来源准备与材料依据

固定演示使用版本化合成档案，通过共享准备事务生成并选用首个有效 Persona；保留不可变修订、人工修订优先及一次消费。患者自述不包含尚未发生的本院治疗事实。

材料预计复用现有住院耗材建议、目录与模型执行能力，自动带入有权且已确认的正式资料。复用 PCI 有限合成依据时标明适用范围；造影方案、数量依据及独立正反样例在预计切片补齐，不追溯扩大原材料票。缺少部位、测量、单位或兼容依据时保留缺项，不从作者底稿或目标费用补答案。合成证据只证明有限演示范围，不宣称真实临床金标准。

### 预计、确认与恢复

计划保存成功留下单次预计意图，复用现有持久化派发与恢复，不能依赖页面挂载触发模型。自动单次预计与主动持续跟进是不同产品动作；无需先点开启跟进，也不因此隐式开启长期病例任务。历史计划缺预计时由明确操作补建，Query 不产生写入。

服务端分别保存生成快照与医生工作稿，绑定本次住院、计划、临床依据及目录／方案版本。新生成只提供候选差异，编辑使用预期版本；取消、失权、Epoch 变化或迟到结果不得更新错误对象。生成和按需解释从首次派发即复用已有授权、用量和未知尝试恢复，不另建模型账本。

整批确认及同计划预留调整由共享 Command 原子完成，不循环单项请求伪装事务。预留继续只影响费用推演，不锁库存、不等于正式收费。详细取舍见[固定准备与预计／实际边界提案](../decisions/proposed/architecture/2026-10-28-inpatient-ai-preparation.md)。

### 真实用量与分组核对

实际差额沿现有手术材料事件、部分预留消耗和追加更正合同扩展；尚无逐笔使用时也可直接输入真实最终用量。已有事件按净实际量计算本次增量／更正，完成手术不能重记整份用量。仅处理明确选定的预留，未选项保留并说明；若既有完成合同自动清理其他剩余项，本切片须显式调整输入和校验，不能静默释放。

读取提供原预留身份、版本、数量、材料目录版本、单位、冻结价格和消费／更正关系。旧记录只从已有持久化事实解析，不用当前目录反推历史；价格依据变化须重新审阅。新增项沿有效目录计价，历史不回写。

核对复用同一分组与推演能力，无需活动跟进任务；已有后台待办可消费相同结构化规则结果，避免第二套判定。模型解释仅整理当前问题与依据，不执行临床更正。服务端状态由 TanStack Query 管理，不复制到客户端状态库。

已交付的耗材预计接口与恢复合同见[临床流程](../architecture/clinical-workflows.md#手术计划的单次耗材预计)。其余切片的公开接口／CLI 合同变化在实施时同步 owning Operation Catalog、对应运行时 Skill 和命令示例漂移测试。

## 范围外

- 重新实现持续跟进、术中逐笔记录、差异待办或病例用量看板；这些由原规格和 PR #339 负责，现有能力必须保留兼容。
- 扩展所有术式、检查药品草稿、出院助手、聊天入口、影像像素分析或通用多 Agent 平台。
- AI 自主改变术式、诊断、主操作、分组、医保资格、支付核定或收费。
- 全院库存／采购、全成本利润优化或真实临床推荐能力保证。

## 依赖与风险

- 原六票已通过[PR #339](https://github.com/CaiZongyuan/clinmesh/pull/339)集成主线，本轮沿已集成的候选、模型建议、材料事件和复查合同扩展；原范围与验收仍由[原规格](2026-10-27-inpatient-drg-agent.md)拥有。
- 自动单次预计必须适配原先依赖活动跟进任务的模型执行／计量合同，避免隐式创建长期授权或重复调度。服务端持久化结果不等于后台持续分析。
- 最终用量与逐笔事件共存涉及历史收费及剩余预留，必须基于净实际事实追加差异并原子完成；不能覆盖事件历史或释放未明确选择的材料。
- 固定 Persona 的首个修订自动选用会部分改变原人工首录取舍；实施时更新当前 owner 及双向决策引用，继续保留隐藏事实隔离。
