# PCI 黄金病例的演示环境与从零岗位流程

Status: approved

本规格补充[门诊住院共享支付与 DRG 一体化](2026-10-15-drg-prescription-budget.md)的实际演示交付，执行父任务为 [Issue #225](https://github.com/CaiZongyuan/clinmesh/issues/225)。原规格继续拥有支付、待遇、分组、归档与财务更正的业务合同；本文件只拥有部署就绪、固定病例页面起点和从零岗位演示的新增验收条件。

执行子任务：[T01 演示环境的 DRG 启用](https://github.com/CaiZongyuan/clinmesh/issues/319)、[T02 固定病例准备与直接住院页面](https://github.com/CaiZongyuan/clinmesh/issues/320)、[T03 从零岗位演示验收](https://github.com/CaiZongyuan/clinmesh/issues/321)。T01 与 T02 可并行，T03 由两者阻塞。

## 问题与目标

[PR #312](https://github.com/CaiZongyuan/clinmesh/pull/312)已经交付 PCI 业务联合链及分层测试。现有黄金浏览器旅程在开始页面操作前，通过公开 HTTP 准备入院、检验、药品执行与造影；固定病例准备、首次手工 Persona 与来源绑定直接住院也尚缺完整页面入口。规则物化和合成测试不能代替实际演示部署的受信审核与正常启动装载。

目标是在固定版本的合成演示环境中，从页面准备病例开始，由各岗位完成同一次 PCI 住院，包含术后用药、未知资金恢复和归档后财务更正，并能按手册重新执行。

## 范围

- 按[部署合同](../deployment.md#运行时-drg-规则启用)核对完整 v2 规则包、来源用途、编码兼容、适用性及算法证据，绑定实际临床 Reference Release，配置并验证正常启动。真实部署审核属于受信配置，不由测试通过或页面按钮自动签署。
- 管理员通过页面分别准备既有 PCI 目录资料和固定病例来源，创建、选择首个手工 Persona。登记员从就绪病例通过页面办理来源绑定直接住院，并交给护士接诊。复用已有 Query/Command、岗位授权、预期版本、幂等及回执，不创建第二套物化流程。
- 从上述页面起点开始，操作现有诊断、检验及报告、医嘱校对、发药给药、造影、支架与四类耗材预留替换；明确区分术前、术中及术后阶段。
- 在同一次住院继续完成患者待遇、预交金和组合收款、未知资金查询恢复、结算清床、审核归档、医保办核定和后续更正退款。业务不变量及其他病例回归继续引用原总体规格。
- 固定集成提交、规则及目录身份、虚拟时间、外部合成行为和预期账本，形成可重复执行的演示手册。普通 Web 为完整岗位旅程入口；受影响的共享交互遵守既有 React 18/19 Surface 合同。

## 用户故事

1. 作为演示环境维护者，我希望正常启动就能装载已实际核验的固定规则，并能说明分组与金额来源。
2. 作为管理员，我希望从页面准备固定病例和手工患者资料，随后交给登记员办理住院，无需先调用后台接口。
3. 作为演示操作者，我希望按岗位和时序走完整次住院，发生支付未知时也能根据界面继续原交易。
4. 作为验收人员，我希望复核同一病例的诊疗、账务和冻结历史，并按固定手册重新执行。

## 验收条件

### T01：演示环境的 DRG 启用

- [x] A1：按部署合同保留实际规则 Manifest、来源及版本、临床 Reference Release 和四项审核证据；任何未核实项保持明确缺口，不能填造 verified。证据不足时记录具体阻塞及责任，不以降级小规则完成完整规则启用验收。
- [x] A2：从正常 Server 启动入口装载被审核的同一完整 v2 包，医生页面能读取正式事实分组；固定 PCI 的无操作、造影主操作和支架主操作分别核对 FR59、FM59、FM39，FM39 使用既有合成支付参数 owner。FM59 缺参数、成本缺失继续如实显示。
- [x] A3：固定环境可按文档再次启动并复核相同规则身份；配置或审核身份不匹配时沿用明确失败，无配置时沿用规则未就绪状态。启用和重启保留既有业务及冻结历史。

T01 的固定来源、真实审核、正常启动、三阶段医生页面和历史保留证据见[完整规则部署核验](../research/2026-10-27-pci-drg-demo-enablement.md)；T02/T03 继续按各自条件验收，本规格整体保持 `approved`。

### T02：固定病例准备与来源绑定直接住院页面

- [ ] A4：管理员可从页面准备 PCI 目录资料和固定病例来源，分别观察结果；创建并选择首个有效手工 Persona，无需真实模型调用。现有 Persona 修订及旧病例事实保留。
- [ ] A5：登记员从就绪的同一 Synthetic Case Instance 选择接收病区并办理直接住院，护士可在原工作台接诊。来源、Profile、Persona 修订及本次住院关系可回查；预交金使用既有独立资金流程，不隐式产生门诊挂号或费用。
- [ ] A6：页面覆盖必要的空、加载、失败、未就绪、无权限及版本冲突反馈；请求丢失后按原幂等键和回执核对。重复准备、重复登记或恢复不重复产生病例、住院、目录库存或费用。
- [ ] A7：病例及目录准备、首次 Persona 和直接入院复用已有 Command；普通临床及登记视图不泄露 Case Truth。与 [Issue #314](https://github.com/CaiZongyuan/clinmesh/issues/314) 的岗位布局及通用直接入院界面复用，不重复重构已有工作台。

### T03：从零岗位演示验收

- [ ] A8：从固定、已就绪的合成环境开始，依次通过页面完成资料准备、手工 Persona、直接入院、护士接诊、诊断、九项检验及报告签收、必要医嘱校对与药品执行、造影和单枚支架 PCI、四类材料预留替换。环境安装可以由维护命令准备，验收中可见的病例与诊疗事实由相应岗位动作产生。
- [ ] A9：用药按病例脚本区分术前、术中和术后；PCI 完成后至少演示一项有明确术后用途的既有医嘱、发药及给药路径。按实际数量和价格独立核对账本，不机械沿用旧脚本总额。
- [ ] A10：在同一病例从页面演示患者待遇、预交金与组合补缴的一次未知结果；未知时首次财务完成及清床被阻断，查询原尝试取得确定结果后继续结算和清床。恢复与重复点击不重复入账。
- [ ] A11：同一病例完成病案审核归档、FM39 冻结与医保办模拟核定，再从页面完成一笔关联原费用的更正、医保补偿重算和原交易退款；核对当前账务变化、原归档及首次结算保留且临床状态不倒退。核定减原预估与核定减收费分别展示，允许合法零差异。
- [ ] A12：保留同一最终集成提交的真实岗位 Playwright 与公开 HTTP 账本证据，以及受影响的 React 18/19 合同；手册记录准备条件、角色、步骤、预期分组和金额、未知恢复及重新开始方法。通过独立重放或重新准备再执行证明可重复，不覆盖旧轮次历史；形成 #225 最终验收材料，由人类决定父任务关闭。

## 设计决定

T01 和 T02 无相互阻塞：前者验证正常部署的受信规则装载，后者使用既有病例与入院合同完成页面路径。T03 同时依赖两者。来源使用条件的实际核验如果需要外部补充，作为 T01 的真实阻塞记录，不因等待该项阻断 T02。

现有原型和 [#279](https://github.com/CaiZongyuan/clinmesh/issues/279) 的业务及分层测试作为复用基础；新增的是从零页面演示的证据与入口，不回退原任务完成状态。规则、财务、临床及患者资料的详细行为继续归各 owner。实现中若发现非平凡架构或流程取舍，按仓库规则补充 Agent Note。

## 测试策略

部署验收使用正常配置和启动入口，核对被审核包及实际 Reference Release；公开 HTTP 和真实临时 SQLite 验证分组、账务和不可变事实，浏览器负责岗位入口、人工审阅、异步反馈及完整时序。已有未受影响的有效测试证据继续沿用。

开发和自动化验收使用合成 Provider、受控模型流、确定性支付模拟器和临时数据库。普通操作者通过页面执行计划内业务；测试代码可做环境准备与只读结果核验，不在浏览器旅程前通过后台写入补齐本次要求展示的病例或诊疗步骤。实际部署核验与自动化隔离环境证据分别报告，不把测试构造的审核当成真实部署审核。

受影响的共享对话框与表单覆盖 React 18/19；DSH Surface 合同继续表明其证据边界。仅按变更范围运行必要检查，纯拆票及规格整理运行文档检查。

## 范围外

- 原生 DSH Session、Agent Tool proposal 及宿主中的完整 PCI Agent 操作验收；需单独确认后立项。
- 真实模型或负载测试、真实医保及支付渠道、财政票据、总账会计、完整医院成本和盈亏。
- 全院目录补全、全部病组支付参数、FM59 支付参数补录、地方正式分组一致性承诺。
- 重做已实现的支付、待遇、临床及分组内核，或重开已经完成的 #279、#303、#305。
- 在本次拆票阶段实施业务、修改运行环境、发布凭据、制作录屏或修改关闭 #225。用户要求媒体时另按既有证据规则交付。

## 依赖与风险

完整规则的来源用途、编码适用性及受信部署审核是 T01 的实际验收前置，完整性及有限样本测试不能替代。固定来源和手工 Persona 页面沿用现有合同；新增实质性产品选择需在实施前回到本规格确认。

#314 在重组住院岗位布局；实施 T02/T03 时核对其实际集成版本并复用交付。它不是当前逻辑阻塞，不因视觉结构调整复制登记或病例流程。术后执行可能改变药品数量及最终金额，应先固定时序和独立账本，再断言费用与待遇分配。
