# PR CI 分片并行与按检查输入复用成功结果

Status: approved

## 问题与目标

主 CI 的四个检查组并行运行，总耗时由最慢的组决定。最近 12 次成功运行中，执行阶段中位耗时为 `unit` 1713 秒、`browser` 1371 秒、`e2e` 900 秒、`checks` 154 秒；每组排队约 2 秒，环境准备 16–43 秒，耗时几乎全部来自测试执行。`unit` 与 `browser` 构成关键路径。

同一 PR 的一次提交已通过 CI 或部分检查组已经成功，随后追加普通说明文档、修复某一组专属测试或同步提交历史时，仍要再次等待全部测试组。现有 CI 按 PR 相对主线的完整净改动选择检查，不复用同一 PR 先前的成功检查，因此不能区分“本次需要覆盖的检查范围”和“这些检查的输入是否已经验证过”。

目标有两项：将 `unit` 与 `browser` 的完整测试集合各拆为两个并行分片，缩短单次运行的关键路径；在同一 PR 内复用输入完全一致的成功分片或检查组，减少重复执行。新一轮仍生成计划并产生自己的 `verify` 结果；主线 push 继续完整验证。收益以真实输入、真实 Actions 耗时和成功记录决定，不以改动行数、提交说明或“上次全绿”判断。

PR 运行的候选合并结果总是基于事件发生时的最新目标分支。上次成功后主线若带入非文档改动，或修改了源码，三个测试组的输入都会变化并重新执行；同步主线或解决冲突只在主线新增内容不影响该组输入时才可能命中。

## 范围

沿用现有主 CI 的 PR 与 `main`/`master` push 入口，以及 `checks`、`unit`、`browser`、`e2e` 四个检查组和最终 `verify`。现有检查选择、完整候选合并结果校验及默认回退全量的约束继续生效，见[测试策略](../testing.md#github-ci-的检查选择与并行)。

| 本轮情况 | 预期行为 |
| --- | --- |
| `unit` 或 `browser` 执行完整测试集合（`full` 或 `frontend` 计划） | 拆为 `1/2`、`2/2` 两个分片，在独立 runner 并行执行 |
| 定向测试计划（`tests`）或只有普通文档（`docs`） | 不分片，沿用现有命令 |
| `checks`、`e2e` | 不分片 |
| 同一 PR 的候选合并内容、检查范围、配置、依赖、生成输入和运行环境均一致，仅提交历史改变 | 可以复用相同检查组及分片的成功记录 |
| PR 已包含业务改动，随后只修改普通说明文档 | 文档检查重新执行；业务测试组仅在其全部有效输入仍一致时复用 |
| 普通文档变化导致 Tailwind 生成样式改变 | 受影响测试组重新执行，不能仅依据 Markdown 路径跳过 |
| 只修改某一测试组专属的已有独立测试文件 | 该组与 `checks` 重新执行；其他测试组在其余有效输入一致时复用 |
| 修改源码、共享 fixture/setup，或新增、删除、重命名测试文件 | 三个测试组全部重新执行 |
| 冲突处理或主线更新改变代码、测试、配置、依赖或其他有效输入 | 输入变化的检查组重新执行 |
| 首次运行、记录缺失、缓存不可用、记录损坏或无法证明输入相同 | 正常执行本轮必需检查 |
| `main`/`master` push | 同样分片执行；不使用本机制复用成功状态，按现有规则完整验证 |

## 用户故事

1. 作为开发者，我希望需要完整测试时等待时间由更短的关键路径决定，而不是由单台 runner 上的全部单元或浏览器合同决定。
2. 作为开发者，我希望仅同步提交历史、修改无关说明文档或修复某一组专属测试后，已经验证且输入没有变化的测试组不再重复运行。
3. 作为审查者，我希望知道哪些组和分片实际执行、哪些复用了哪次成功证据，并确认主线的新变化已经计入判断。
4. 作为维护者，我希望复用能力不可用时 CI 仍能完成正常验证，不因分片、缓存命中或缺失而漏测或误报成功。

## 验收条件

### 分片

- [ ] A1：`full` 与 `frontend` 计划中，`unit` 与 `browser` 各以两个分片在独立 runner 并行执行；`tests`、`docs` 计划及 `checks`、`e2e` 保持现有单组执行。
- [ ] A2：同一提交上，两个分片执行的测试并集等于分片前该组的完整集合且互不重复：Vitest 以测试文件为单位，Playwright 在 `fullyParallel` 下以用例为单位；`unit` 覆盖 turbo 各包测试与根 `scripts/` 测试。分片不改变测试命令的其他参数。
- [ ] A3：任一分片失败、取消、意外跳过或结果缺失时，最终 `verify` 失败；只有计划明确排除的组允许整组跳过。

### 成功复用

- [ ] A4：复用限定在同一仓库、同一 PR、同一检查组及同一分片；其他 PR、主线或其他分片的成功记录不能代替本轮检查。分片序号与分片总数纳入指纹，分片数改变时旧记录失效。
- [ ] A5：输入比较绑定本次事件校验通过的实际候选合并结果，包含目标分支的新内容。不能只比较两次 PR head、最后一个提交或 PR 改动文件列表。
- [ ] A6：指纹覆盖检查的完整执行范围、实际命令、相关文件内容与路径、文件模式、子模块锁定引用、依赖锁、CI/构建/测试配置、生成输入及运行环境。定向检查成功不能冒充全量检查成功。
- [ ] A7：同一 PR 的候选内容相同、执行范围和环境相同，即使提交 SHA 改变，也可命中已有成功记录；不同 PR 不命中。
- [ ] A8：已有业务改动的 PR 追加普通说明文档修改时，`checks` 重新执行；`unit`、`browser`、`e2e` 的其他有效输入及实际生成样式一致时可以复用。文档新增、删除和重命名适用同一判断。
- [ ] A9：只修改某一测试组专属的已有独立测试文件时，该组与 `checks` 重新执行，其他测试组在其余有效输入一致时复用。专属与独立沿用现有 CI 入口的判定：文件归属唯一测试组，状态为修改，不导出且未被其他文件引用。新增、删除、重命名、导出或被引用的测试文件，以及共享 fixture/setup 变化，使三个测试组全部失效。
- [ ] A10：普通文档引入或移除 Tailwind class，导致实际生成样式变化时，不复用旧测试结果；无法取得所需生成输入时正常执行检查。
- [ ] A11：源码、共享 fixture、权限、数据库、运行时 Skill/提示词、依赖、子模块、CI 或构建配置改变时，不沿用已不匹配的成功记录。主线带入这些变化时具有相同行为。
- [ ] A12：只有该分片或检查组要求的全部命令成功后，由其最后一步写入新的成功记录；失败、取消或未完成的执行不产生可复用成功证据。另一组或另一分片失败不否定本分片已经完成的有效成功证据。
- [ ] A13：成功记录只存放在 PR 作用域的缓存中，内容绑定完整指纹、检查组、分片及来源运行链接；读取时校验记录结构并要求指纹、检查组与分片精确一致，不使用前缀或近似匹配扩大范围。不调用 Actions API 核验来源，不新增 GitHub 权限，工作流保持 `contents: read`；成功标志不能来自环境变量、工作流输入或其他外部传入值。
- [ ] A14：缓存读写失败、未命中、记录缺失、损坏、身份不符或输入不能可靠计算时，正常执行本轮必需检查，不静默跳过。缓存服务故障本身不阻断检查执行。

### 门禁与证据

- [ ] A15：本轮计划及每个必需组和分片都产生可解释结果；实际执行失败、取消、意外跳过或结果缺失时，最终 `verify` 仍失败。复用成功必须经过明确校验，不能放宽现有汇总门禁。
- [ ] A16：`main`/`master` push 始终执行现有完整集合，不因 PR 或先前主线已有成功记录而省略检查。
- [ ] A17：Actions 日志或汇总列出各组和分片实际执行或复用、判断原因及复用来源运行链接。
- [ ] A18：交付时以真实 Actions 运行报告分片前后的各组、各分片及整体耗时；未取得真实运行前，不把预计节省的时间写成实测收益。
- [ ] A19：保留现有用例、断言、失败边界、React 18/19 覆盖、每个分片内的 worker 数与超时，不为提速降低验证强度；不新增真实模型或持续负载运行。

## 设计决定

分片只改变完整测试集合在 runner 之间的分配，不改变检查选择。`unit` 与 `browser` 固定两片：分片前 `e2e` 约 900 秒，两组拆分后预计分别降到其以下或接近，关键路径改由 `e2e` 决定；继续拆分 `e2e` 或增加片数对关键路径的边际收益很小。Vitest 与 Playwright 使用各自内建的分片参数；Vitest 按文件路径哈希排序后按文件数切分，不按耗时均衡。定向测试只运行少量文件，不分片。

检查选择和成功复用分开：先确定本轮需要覆盖的组和分片，再判断每个分片是否已有完全匹配的成功证据。复用不改变 PR 的影响范围分类，也不把完整 PR 比较替换为最后一次提交的增量比较。分片沿用所属组的输入边界，指纹额外包含分片序号与总数。

首版采用保守输入边界。`checks` 保留完整 Git 内容；每个测试组保留全部非普通说明文档的 Git 内容，只排除其他测试组专属的已有独立测试文件，不引入通用最小依赖推导。专属归属复用 CI 入口现有的测试组与独立入口判定，与 Vitest 排除规则及 Playwright 项目匹配保持一致。源码变化使三个测试组一起失效：同一源码可能经 Vite 动态加载或 HTTP 调用被多组覆盖，不按静态导入图删减。

普通说明文档候选范围沿用根 `README.md` 与 `docs/` 下 Markdown；各级 `AGENTS.md`、`CLAUDE.md`、`docs/agents/` 及已知机器读取的输入不因后缀为 Markdown 而排除。排除原文前必须覆盖实际消费者；运行时 Skills、提示词和素材清单继续参与指纹。

DSH 样式构建与部分浏览器合同在运行时以仓库根目录为 Tailwind 自动扫描范围，说明文档和其他组的测试文件即使不被导入也可能影响生成 CSS。因此测试组排除这些文件的原文时，改用同一 Tailwind 扫描器从中提取的候选 class 参与指纹；候选集合宽于实际 class，可能多跑但不漏跑。本需求不修改产品的 CSS 扫描范围。各组保留现有环境准备，依赖安装与样式准备仍会发生，主要节省后续重复测试时间。

运行环境至少区分 runner 系统与架构、镜像版本及实际 Node 版本；pnpm 与 Bun 由仓库树中的 `packageManager` 与 CI 准备步骤锁定精确版本，随树参与比较；工作流定义的配置也参与比较。存在未被指纹覆盖的外部资料、模型配置或其他可变输入时，不启用复用。

成功证据由记录的写入时机保证：只有本分片或检查组的命令全部成功后才写入，GitHub 将 PR 运行写入的缓存限定在该 PR 的合并引用，其他 PR 与主线无法读取。PR 运行执行 PR 自身的 CI 脚本，`verify` 门禁同样受 PR 代码控制，因此复用机制防范实现错误与输入漂移，不承担抵御恶意 PR 的职责；为此调用 Actions API 核验来源不增加安全性，不予采用。

具体存储与 workflow 接线在实施时保持精确匹配、来源可追溯和失败回退，决策理由另记 Agent Note。当前合同仍由[测试策略](../testing.md)拥有，规格不替代 owner 文档。

## 测试策略

唯一测试 seam 是现有 CI CLI 的进程边界（`plan`、`prepare`、`run`、`verify`），沿用 `scripts/ci-cli.spec.ts` 的真实 Git 临时仓库与 `PATH` 上的替身 `pnpm`：替身记录实际 argv 并可模拟失败，断言只看 CLI 输出、退出码、执行的命令和成功记录目录的内容。`scripts/ci.spec.ts` 继续覆盖计划选择与汇总的导出函数。成功记录在 CLI 中通过本地目录读写，真实 Actions 中由缓存步骤恢复和保存同一目录；缓存作用域与保存时序只由真实 Actions 证明。不依赖真实模型、已有业务库或长时间压测。

分片回归包括：`full` 与 `frontend` 计划下 `run unit`、`run browser` 带分片序号时向测试命令传递对应分片参数，`tests`、`docs` 计划与 `checks`、`e2e` 不分片；`verify` 拒绝任一分片失败、取消、跳过或缺失。两个分片的并集等于完整集合、且无重复，不作为常驻回归：实施验收时对同一提交分别列出分片前与两个分片的 Vitest 测试文件和 Playwright 用例，作为一次性证据。

复用回归包括：命中时不调用测试命令；未命中时执行且只在成功后写入记录；记录损坏或不匹配时回退执行；同内容不同 SHA 复用；代码不变且普通文档变化复用测试并重跑文档检查；只改某组专属测试时其他组复用；新增、删除、重命名或被引用的测试文件及共享 fixture 变化使全部测试组失效；生成样式变化导致失效；主线带入代码变化导致失效；执行范围、分片数、工具链、镜像、配置和子模块变化导致失效；跨 PR 与跨分片隔离；缓存异常回退；失败不发布成功记录；主线始终完整执行。

实施验收运行覆盖本次变更的最小检查；CI 配置变化按仓库要求运行 `pnpm check` 及适用的 Mobile 检查。真实 Actions 至少验证一次分片全量运行、一次未命中和一次同输入命中，回读各分片结果、用例总数、来源、最终门禁与耗时；未取得远端交付授权前先完成本地验证，保留真实平台验证为未完成项。同步测试策略 owner，并新增对应 Agent Note。

## 范围外

- 降低单个用例的固定开销，例如 server 测试复用已迁移的模板库。
- 调整 Playwright 或 Vitest 的 worker 数、超时或重试，按历史耗时均衡分片，或拆分 `checks`、`e2e`。
- 跨 PR 共享成功状态，或用 PR 成功结果减少主线完整验证。
- 根据改动行数、提交说明或手工标签跳过检查。
- 为所有模块建立最小测试依赖图，重写现有测试分层或改变产品样式扫描范围。
- 合并队列、分支保护调整、仓库管理设置、自动合并与发布。
- 自动提交、push、创建 PR 或触发远端工作流；这些操作沿用用户另行给出的交付授权。

## 依赖与风险

Vitest 分片按文件数而非耗时切分，server 少数完整 HTTP 闭环文件占据大部分耗时，两个分片可能不均衡；实际分布以真实 Actions 为准，调整片数或改用耗时均衡属于新的取舍，需重新确认。分片增加 runner 数量和每片约 20–40 秒的环境准备。

复用只能从新机制生成的有效记录开始，不能把没有输入指纹的旧绿灯追认为可复用证据。缓存过期、清理或 runner 镜像升级会增加未命中，正常回退执行，不承诺固定耗时或每次更新都提速。复用的节省只发生在三个测试组；`checks` 在任何内容变化时都重新执行，各分片的依赖安装与样式准备也照常进行。

普通文档可能成为隐式构建输入。后续新增文档消费者或改变扫描规则时，必须同步指纹边界和失效回归；无法覆盖的输入保留在指纹内或停用相应复用路径。

GitHub Actions 的缓存作用域、保存时序、矩阵 job 结果与分片耗时需要平台验证；本地 CLI 回归只能证明脚本行为，不能替代真实 Actions 命中、门禁与耗时证据。
