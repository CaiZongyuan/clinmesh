# Agent Note: 门诊申请应收与执行门禁

Status: proposed

## Problem

独立门诊检验、放射和病理会诊共用申请生命周期，却在开立后直接排入受理，没有门诊应收。现有支付以病例及类别读取目标并推进病例级旧检验流程；同次就诊出现多项独立申请时，单纯补建费用会使预览、确认和放行指向不同申请。业务目标与待确认的价格、取消、恢复规则由[正式规格](../../../spec/2026-10-26-outpatient-investigation-billing.md)拥有。

## Proposal

正式开立在同一共享 Command 事务冻结门诊价目、创建原申请及唯一应收，持久化申请的计费策略和原费用关联。新门诊申请受理时重验全额覆盖及确定资金，原子保存首次放行快照与 `accepted`；开始时校验该快照和临床状态。后续待遇撤销形成独立财务待办，避免在受理与开始之间因重算余额而卡死。资金查询恢复、医保确认和正常收款只调用同一个按原申请放行的边界，重复效果以原申请去重。

支付从预览到确认及恢复始终绑定原 ChargeItem，病例和类别只用于筛选。账单继续聚合原 Charge Record，支付、退款和医保分配保留原引用；不新增可编辑影子账或病例级第二套余额。原门诊兼容路径仍有独立的旧 LIS／药房策略，住院保持实际执行完成计费；历史未计费独立申请保留明确的原策略。

允许阶段的临床取消派生仅针对原费用的全额冲减；取消与放行在同一事务边界竞争。退款由收费员使用现有原交易退款能力另行处理，临床取消不会伪装成资金成功。本票待退款使 Run 保持 active，但不阻断医生完诊或药房发药；资金收敛后重新检查原完成条件，避免提前关闭 Run 导致不能预览或确认退款。首次放行前不允许普通冲减绕过付款条件，已执行事实及后续财务更正继续保留。

## Alternatives considered

- 仅在三类开立代码补建费用：不能阻止已有 outbox 立即执行，且病例加类别无法区分多个原申请。
- 只在收款成功时排受理：不能防御旧事件、重复派发或直接执行 Command；资金守卫应在共享生命周期内重验。
- 把独立申请转换为兼容检验病例状态：会占用单个原申请引用，关闭当前医生任务，无法表达同次多个并行申请，也破坏放射和病理身份。
- 完成执行后按住院方式记账：无法满足门诊收齐后才执行的目标，且将预交金住院模式引入门诊。
- 取消时自动退款或删除费用：混淆临床状态、应收调整与资金三条链，无法保留未知退款及原交易余额控制。
- 全量历史申请补费：旧在途、已完成申请没有审阅过门诊价格，补费会改变历史语义并可能阻断原执行。

## Acceptance criteria

按正式规格验证三类真实开单入口、同次多申请精确收费、确定资金后唯一放行、取消竞争、原交易退款、非空旧库迁移和原住院行为。主要矩阵通过公开 HTTP、临时 SQLite 与受控外部边界运行；standalone Web 与 DSH Surface 分别证明真实入口接线，不能用旧检验预建费用替代。

## Risks

国内目录零占位价不能直接收费，放射和病理缺少门诊价目；拟议合成价格必须明确批准并保留来源与用途。新增类别会穿过 SQLite CHECK、contracts、医保映射和所有支付 adapter，漏改任一边界可能造成读取失败或错单；迁移后旧支付预览必须仍关联原费用。共享内核服务门诊、住院和旧历史，必须按持久策略选择门禁，不能全局新增付款前置条件。
