# Agent Note: PCI 住院持续跟进与模型用量归属

Status: proposed

## Problem

页面 Agent 的短期上下文不能直接承担关闭页面后的持续病例跟进；后台 outbox 能可靠派发业务任务，但不会自动授予病例读取权限。现有手术又在一次执行中写入全部耗材、记费并完成手术，无法直接表达术中逐笔使用及剩余建议。

同时，关键记录变化、一次分析和一次实际模型请求不是同一个计量单位。把每条变化都交给模型会增加重复读取；只追求减少调用又可能继续展示已失效的临床建议。新增能力必须保留现有临床、费用及用量所有者，并让医生知道后台任务正在做什么、用了多少模型资源。产品范围与验收统一由[PCI 住院 DRG Agent 规格](../../../spec/2026-10-27-inpatient-drg-agent.md)拥有。

## Proposal

由医生在当前获授权病例主动开启住院跟进任务。任务保存病例与责任绑定、依赖版本、分析状态及问题引用，复用现有业务查询和 Command；临床和费用事实继续由原 owner 保存。任务持久化不依赖聊天记录或页面是否打开，模型调用在需要分析时派发，等待事件本身不形成模型请求。

后台分析采用明确的病例与岗位权限，在每次读取、派发及结果发布时核对有效性。页面切换不把已授权的后台任务改指向新病例，失权或责任变化后不得沿用旧绑定；停止与归档交接保留可追溯结果。人工审阅仍使用当时有效的人类会话和业务版本，后台任务不持有持续提交正式诊疗动作的批准。

由手术 owner 区分逐笔实际耗材使用与手术完成，复用共享计费及更正能力，建立预留部分消耗、额外使用与反向更正的关系。逐笔使用不能反复调用现有完成手术的 Command，也不能复制一套可编辑的费用账；具体接口和迁移在实施前核验。

记录变化先使受影响建议失效，再按任务依赖选择规则重算或模型分析。费用、分组及阈值比较调用现有确定性能力；候选生成、语义核查和差异解释保留必要依据与核验。连续变化可以合并，但失效提示与必要的确定性提醒不等待模型；复用须核对完整相关来源和规则版本，不能仅依据上次摘要或耗材名称判断仍然适用。

所有新增模型阶段通过现有受控派发入口记录实际尝试，Server 到 bridge 的转发沿用同一尝试身份。模型用量 owner 保存计量和费用估算，病例任务仅保存关联；摘要、阶段明细和当前住院权限由该关联共同约束。规则检查与复用只报告没有新增模型请求，不计算未经测量的节省量。沿用既有计价、缺失、未知、留存及有限额度准入合同，不在病例任务中复制预算账本。

### 复用现有模块

| 模块与现有职责 | 本需求的复用边界 |
| --- | --- |
| 住院、手术、计费与 DRG 模块 | 复用已确认诊断、实际操作、正式费用、预留、分组推演及归档。逐笔使用和分次预留消耗在手术 owner 内扩展，计费继续走共享账；一次性完成手术的现有动作不能直接逐笔调用 |
| `OutboxDispatcher`、`GenerationModelBinding`、`ModelTaskRecovery` | 接入现有 runtime 实例、handler 和受控 Provider，复用持久派发、任务模型绑定与成功步骤恢复。新病例任务负责自己的授权及依据有效性，不另建队列或通用恢复框架 |
| 指南检索、门诊建议与病历质控 | 复用可用的指南来源与引用能力，以及输入指纹、生成／核验和失效保护模式。当前建议与质控读取门诊病例及责任关系，住院参数、耗材证据和权限须独立适配，不能将现有门诊入口原样用于住院 |
| `ModelUsageService` 与既有用量页 | 复用逐次记账、计价、未知状态、控制及查询；扩展 DRG 功能身份、住院任务和阶段关联、病例明细权限与展示，不复制用量或预算账本 |

`ModelTaskRecovery` 的构造器承担进程恢复时对遗留派发状态的处理，病例任务应复用 runtime 已装配的实例，不能每次分析都重新构造。仅在住院与既有模块确有相同语义时抽取共用部分，保留各自事实读取、授权和结果发布职责。当前基础与限制分别见[模型步骤恢复](../../../../apps/server/src/application/model-task-recovery.ts)、[门诊建议](../../../../apps/server/src/application/doctor-recommendations-service.ts)、[文书质控](../../../../apps/server/src/application/clinical-document-quality.ts)及[用量 owner](../../../../apps/server/src/application/model-usage-service.ts)。

## Alternatives considered

- 只依赖当前页面的聊天 Agent：实现入口较少，但无法满足离开页面后继续跟进和明确交接的要求。
- 每次业务记录变化都运行完整模型分析：触发简单，但会重复发送未变化资料；业务事件数也不能代表实际生成、核验和重试请求数。
- 只按费用差额或耗材名称复用建议：可以减少调用，但遗漏病变、用途和其他适用条件变化，不能证明临床建议仍有效。
- 用业务事件计数估算 token，或把病例用量当整个 DSH 账单：便于给出一个数字，但不能反映服务商计量、模型内部阶段及当前覆盖边界。

## Acceptance criteria

以[正式规格的验收条件](../../../spec/2026-10-27-inpatient-drg-agent.md#验收条件)为唯一详细清单。验证应穿过公开病例授权、手术与计费入口、实际模型派发边界及 Web／DSH 界面，证明任务恢复、建议失效、人工处理、归档交接和用量归属一致；不能仅凭 outbox、已有费用页或用量内核的单项通过宣称整链完成。

## Risks

本提案尚未实现。具体器械的适用、数量与兼容依据仍须核验；当前有限 token／金额控制在生产适配器缺少可信上界时会拒绝派发，不能承诺配置额度后自动获得可运行的费用保证。相关事实由[选型依据研究](../../../research/2026-10-27-pci-material-recommendation-evidence.md)和[用量查询合同](../../../architecture/security-and-reliability.md#模型用量查询)拥有。

授权及实际模型请求结果不明时，后台恢复不得自动变成新的正式写入或不受控重发。AI 待办不新增临床出院门禁，原有临床、财务及归档条件由各业务 owner 继续执行；归档交接需要保留未解决问题的责任，不能用停止任务替代解决问题。
