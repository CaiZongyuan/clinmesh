# Agent Note: 共享支付、住院流程与 DRG 的职责边界

Status: proposed

## Problem

门诊收款与住院预交金分别维护交易状态和恢复逻辑，会增加规则分叉及重复维护的风险；两端费用入账和结算规则又有实际差别，统一交易机制须保留这些业务职责。独立合成住院评估上下文与正式住院并存，也会让同次诊疗出现两套金额与状态；归档后退款若直接覆盖首次结算，还会破坏临床和病案的冻结含义。

当前门诊与住院已复用渠道计划及完整的 `RefundLedger` 退款生命周期；收款尝试、确认、分配及结果恢复仍由两端各自拥有。各端收退款和 PCI 联合旅程通过，不能单独证明统一收款职责已经落地。

## Proposal

采用共享收款交易内核，由同一模块负责门诊与住院的收款尝试、结果确认及原尝试查询恢复；门诊和住院分别拥有业务入账规则。门诊 owner 负责费用关联、应收与结清判断及收费后的业务放行；住院 owner 负责预交金入账与抵扣、补缴、首次结算及后续调整，继续拥有临床执行、计费来源、出院与清床门禁及病案首页。原交易退款继续归既有 `RefundLedger`，业务 owner 消费正式资金结果，不重复维护收款交易状态机。

支付方式及其金额记录属于交易事实；收款抵扣哪些费用或哪次结算属于业务资金分配。共享交易内核不接管门诊费用分配或住院预交金使用政策。共同规则的实现与两端业务接入由 [#342](https://github.com/CaiZongyuan/clinmesh/issues/342)跟踪，需求及验收归[共享收款规格](../../../spec/2026-10-28-shared-payment-collection.md)。当前行为归[临床流程](../../../architecture/clinical-workflows.md)，#225 的已交付业务及结案边界归[一体化规格](../../../spec/2026-10-15-drg-prescription-budget.md)。

交易与资金分配始终绑定原就诊及业务用途。同一患者的门诊费用、不同次住院和各次住院预交金分别核算；本次住院预交金可以按本次住院规则抵扣其费用，不因共用交易存储而成为跨就诊余额。跨门诊或住院转款需要独立业务设计，不属于本次共享收款范围。付款方式组成与业务资金分配的领域术语见 [Payment Tender 与 Payment Allocation](../../../../CONTEXT.md#费用与医保)。

门诊与住院采用统一的收款交易存储，保存共同交易事实，各自业务账务引用原交易。当前开发阶段的旧合成历史交易不做数据迁移或旧格式读取兼容，切换时重建受旧支付结构影响的合成就诊运行链，再通过岗位流程重新产生运行事实；患者库和其他可复用资产保留。详细重建、保留及新交易恢复要求归[开发数据切换](../../../spec/2026-10-28-shared-payment-collection.md#开发数据切换)。

共享内核位于现有 Server 内，由门诊和住院 Command 分别调用。本地交易事实、业务入账、回执、审计及相关 outbox 沿用同一 Command 事务，保持状态职责分开而提交一致。门诊收费和住院财务分别保留原页面及业务动作，首期完成共享内核接入和原尝试恢复，不新增统一交易工作台。

[行业一手资料](../../../research/2026-10-29-his-outpatient-inpatient-payment-boundaries.md)支持共用支付渠道及对账平台，同时保留门诊与住院业务维度；资料未披露厂商内部状态机或账表。共享交易内核的理由是本项目实际重复的交易机制及一致性要求，公开平台能力不构成合并两端全部账务规则的依据。

患者医保待遇结算与医院 DRG 付费使用各自的规则和结果。DRG 读取已确认的临床与费用快照，不修改临床事实、不创建第二套可写收费账；费用、资金、收入与成本分别表达。

沿用住院端的财务结算后清床门禁。支付或退款未知时保持未结算，不封账、不清床；出院医嘱及出区按各自临床条件继续。这样保留同事现有流程语义，同时要求共享支付 owner 先查明资金结果，不能以重复收付或推定成功释放门禁。

结算与归档后的纠错使用业务账务 owner 中关联原费用、资金及结算的后续调整链。原病案及首次结算继续表达冻结时的事实，当前账务和差异由关联调整表达；不通过覆盖旧账、恢复床位或解除病案归档锁完成退款。首次结算门禁与后续调整状态分别管理，后续交易未知不倒退已发生的清床和归档。

医保办专岗承接医院侧 DRG、模拟核定反馈及差异复核。收费员继续拥有患者收付和待遇结算，病案人员继续拥有编码审核归档，临床事实由医生及相应执行 owner 确认。权限按所需投影划分，避免为了 DRG 复核而把完整病案读取或临床写入合并到收费岗位。读取与正式动作分别保留审计。

首次待遇冻结和后续补偿的独有取舍分别归[首次冻结决策](../../implemented/architecture/2026-10-22-inpatient-insurance-freeze.md)及[后续补偿决策](../../implemented/architecture/2026-10-22-inpatient-insurance-adjustments.md)；在院当前事实、审阅指纹及核定基线归[联合入口决策](../../implemented/feature/2026-10-25-drg-joint-acceptance-and-review.md)。这些已落地决策保留各自职责，不代表本提案的共享收款已经完成。

## Alternatives considered

- 保留门诊与住院两套收款交易实现，仅共享渠道及退款模块，并以同一组合同测试约束行为：短期改动较小，但未知结果与恢复等共同交易规则仍需分别维护，规则分叉的风险持续存在。
- 共享交易状态和恢复实现，继续由内部适配器读写门诊与住院两套交易存储：能够保留旧记录及引用，降低历史数据切换成本，但仍需维护两种存储映射。当前旧合成交易可以舍弃，选择统一交易存储以减少这部分兼容复杂度。
- 仅清除旧支付记录，保留原就诊的临床放行、结算和归档进度：操作范围看似较小，但保留的已完成状态及冻结账会失去资金依据。当前允许重跑受影响的合成病例，选择重建完整关联运行链。
- 将同一患者不同就诊的收款合并成通用钱包：可以直接跨门诊和住院抵扣，但引入独立的余额、转款及退款来源规则。当前重构保留原就诊和用途，不扩大为患者钱包。
- 同时新增统一交易及异常处理工作台：可以集中查看两端交易，但需要新的岗位可见范围、查询及恢复入口验收。当前以原门诊和住院页面完成交易内核接入，统一工作台留作独立产品需求。
- 将交易、门诊费用分配、住院预交金抵扣及结算门禁全部交给统一状态机：可以减少表面上的职责数量，但使交易机制依赖两端不同的账务及临床条件，扩大改动和回归范围，也难以分别解释资金结果与业务完成事实。
- 在 #225 重做住院临床及出院链路：可以自行安排流程，但重复同事已实现的住院范围，临床事实与费用容易产生多个 owner。
- DRG 继续只依赖独立模拟上下文：便于演示，但无法回答真实业务入口中同一次合成住院的费用、医保与分组如何对应。
- 资金未知时先清床、财务继续挂账：可更早释放床位，但会改变同事 #249 的门禁，首期采用结算后清床。
- 所有财务纠错必须先解档重开住院：可以继续沿用旧可写流程，但把资金问题扩大成病案和床位回退；首期保留归档边界，以关联调整表达财务变化。
- 收费员兼任医院 DRG 运营：减少一个岗位入口，但把患者资金操作与医院侧病例复核集中在同一权限集合；首期增加医保办专岗，分别验收职责和可见范围。

## Acceptance criteria

- 门诊与住院共享同一收款交易状态、恢复实现及交易存储，保留业务来源与支付原交易引用；门诊费用分配、住院预交金抵扣及业务结算仍由各自 owner 负责。
- 同一患者不同就诊的资金不自动合并或跨就诊抵扣；本次住院预交金只按其原住院及用途分配，恢复和退款仍能回查原款。
- 开发阶段切换重建受影响的合成就诊运行链，不要求迁移旧合成历史交易；患者库来源资产、可复用结果、账号配置、参考及指南保持有效。切换后的交易、未决尝试、退款引用和 Command 回执跨重启有效，恢复不重复产生资金或业务入账。
- 门诊收费和住院财务分别在原业务入口完成预览、确认及原尝试恢复，本地交易事实与业务入账保持同一 Command 事务提交。
- 住院流程只根据明确的账务结果推进门禁；未知结果不封账、不清床，查询确认后恢复，临床出区条件保持独立。
- 患者待遇结果与医院 DRG 支付参考分别可追溯；DRG 结果不反向修改临床或费用事实。
- 结算和归档后可受控追加财务更正、退款及医保重结算，原快照与更正差异可查，不恢复床位、不解档、不重复影响资金或待遇累计。
- 医保办、收费员、病案人员及住院医生按所需信息与业务动作分权，跨岗读写和越界操作有明确拒绝证据。

## Risks

统一收款时须保留业务来源和原交易引用，首次结算及病案归档绑定冻结账，后续更正通过独立关联链表达当前费用与收退差异。已完成 Scenario Run 只扩大受控财务更正与恢复能力，临床写入及 Workspace／Epoch 隔离继续生效；不能把后续退款直接追加到旧冻结数组后继续假定原校验成立。

支付、患者待遇、医院 DRG、临床及归档仍有独立状态和金额口径，岗位页面需保留原事实、当前调整与恢复入口。资金未知阻断首次财务完成，后续未知只保持对应调整待处理；两者不能共用一个会倒退临床完成事实的状态开关。

患者库来源资产与就诊运行事实位于同一 operational SQLite，重建关联合成就诊运行链须按保留清单处理，不能通过删除整库丢失患者库、账号及目录配置。现有 Epoch reset 关闭并保留旧 Epoch，不是清除旧交易存储或跳过 schema 变更的入口。切换路径须明确完成 schema 转换、隔离旧运行意图并通过保留资产的完整性检查，审计保留边界继续按[仿真合同](../../../architecture/simulation.md#106-重置与-epoch-隔离)执行。

开发阶段不迁移旧合成交易的取舍，仅适用于本次模型切换；新交易的持久化、引用完整性及未知结果恢复继续属于验收范围。

公开 HTTP 与 PCI 联合账本保留已实现部分的验收证据，范围由[测试策略](../../../testing.md)和业务规格的逐项验收拥有。共享收款交易内核及两端业务接入完成对应验收前，本提案保持 `proposed`。
