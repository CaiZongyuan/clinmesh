# Agent Note: 共享支付、住院流程与 DRG 的职责边界

Status: proposed

## Problem

门诊收款依赖门诊病例与药品或检验类别；住院闭环拥有独立预交金、多退少补和退款记录，出院结算在本地事务直接形成确定资金事实。独立合成住院评估上下文与正式住院并存会让同次诊疗出现两套金额与状态，支付结果未知时也缺少明确的住院门禁协作。

## Proposal

按[已批准规格](../../../spec/2026-10-15-drg-prescription-budget.md)收敛门诊与住院共享支付账务。住院团队继续拥有临床执行、计费来源、出院与清床门禁及病案首页；#225 承接已有账务实现并统一支付能力。业务门禁调用共享支付结果，不在住院适配层复制收退款状态机。

患者医保待遇结算与医院 DRG 付费使用各自的规则和结果。DRG 读取已确认的临床与费用快照，不修改临床事实、不创建第二套可写收费账；费用、资金、收入与成本分别表达。

沿用住院端的财务结算后清床门禁。支付或退款未知时保持未结算，不封账、不清床；出院医嘱及出区按各自临床条件继续。这样保留同事现有流程语义，同时要求共享支付 owner 先查明资金结果，不能以重复收付或推定成功释放门禁。

结算与归档后的纠错使用共享账务 owner 中关联原费用、资金及结算的后续调整链。原病案及首次结算继续表达冻结时的事实，当前账务和差异由关联调整表达；不通过覆盖旧账、恢复床位或解除病案归档锁完成退款。首次结算门禁与后续调整状态分别管理，后续交易未知不倒退已发生的清床和归档。

新增医保办专岗承接医院侧 DRG、模拟核定反馈及差异复核。收费员继续拥有患者收付和待遇结算，病案人员继续拥有编码审核归档，临床事实由医生及相应执行 owner 确认。权限按所需投影划分，避免为了 DRG 复核而把完整病案读取或临床写入合并到收费岗位。

## Alternatives considered

- 保留门诊与住院独立支付实现，再由报表拼接：短期改动较小，但退款、未知结果及资金分配会长期存在不同语义，难以验收跨场景一致性。
- 在 #225 重做住院临床及出院链路：可以自行安排流程，但重复同事已实现的住院范围，临床事实与费用容易产生多个 owner。
- DRG 继续只依赖独立模拟上下文：便于演示，但无法回答真实业务入口中同一次合成住院的费用、医保与分组如何对应。
- 资金未知时先清床、财务继续挂账：可更早释放床位，但会改变同事 #249 的门禁，首期采用结算后清床。
- 所有财务纠错必须先解档重开住院：可以继续沿用旧可写流程，但把资金问题扩大成病案和床位回退；首期保留归档边界，以关联调整表达财务变化。
- 收费员兼任医院 DRG 运营：减少一个岗位入口，但把患者资金操作与医院侧病例复核集中在同一权限集合；首期增加医保办专岗，分别验收职责和可见范围。

## Acceptance criteria

- 门诊与住院共享同一资金交易规则，保留业务来源与支付原交易引用。
- 住院流程只根据明确的账务结果推进门禁；未知结果不封账、不清床，查询确认后恢复，临床出区条件保持独立。
- 患者待遇结果与医院 DRG 支付参考分别可追溯；DRG 结果不反向修改临床或费用事实。
- 结算和归档后可受控追加财务更正、退款及医保重结算，原快照与更正差异可查，不恢复床位、不解档、不重复影响资金或待遇累计。
- 医保办、收费员、病案人员及住院医生按所需信息与业务动作分权，跨岗读写和越界操作有明确拒绝证据。

## Risks

住院闭环已经合入，统一账务仍须与其接口协调。现有归档校验将当前费用与首次结算资金快照绑定，增加后续调整必须明确冻结基线，不能简单追加退款到旧数组后继续假定原不变量。已完成 Scenario Run 的写入只扩大到受控财务更正与恢复。编码兼容、支付分配和交接接口仍有待完成的依赖；这些依赖未解决前不能把本提案标为 implemented。
