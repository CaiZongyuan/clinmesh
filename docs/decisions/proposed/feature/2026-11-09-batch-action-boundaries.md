# Agent Note: 按业务单元集中办理并区分跨患者连续队列

Status: proposed

## Problem

多项检查开立、医嘱校对和送检等工作需要重复选择和确认，而门诊处方、诊断与整台手术已有整组提交，只是添加过程繁琐。若只统一按钮样式或循环调用旧界面，不能解决手工检查单槽草稿和连续录入的问题；若把所有“确认”都视作同一种批量动作，又会混淆患者归属、处方完整性、实际执行事实和资金结果。

现有[开单工作区](../../implemented/architecture/2026-10-19-clinical-order-workspace.md)和[共享开单布局](../../implemented/architecture/2026-11-03-shared-order-composer.md)分别拥有工作区与布局边界；本提案只扩展多项录入和办理边界，不将布局组件升级成跨业务状态机。正式目标、场景与验收由[需求规格](../../../spec/2026-11-09-batch-clinical-actions.md)拥有。

## Proposal

集中办理限定为同一患者、同一次就诊或住院、同一种动作。跨患者任务使用逐病例的连续队列，减少定位和页面往返，同时让每次核对与写入仍有明确患者目标。检验、放射和病理分别在类别内部批量开立，各自保留临床信息。

目录选择统一采用弹窗内连续添加、清单编辑和集中确认，住院医嘱不再保留并行的页面内开立表单。未提交清单可以在当前登录期间恢复并严格绑定患者与就诊，避免减少点击后增加误丢输入或串患者的成本。

独立项目的集中办理在发送前暴露完整性与可用性问题，发送后逐项报告确定结果并保留成功项。处方、诊断组与整台手术等已有完整业务单元不能因界面多选被拆成半成品。响应不明先恢复原意图，不把它视作确定失败并重新提交。本提案计划部分替代[既有门诊建议确认](../../implemented/architecture/2026-10-18-prepared-clinical-confirmation.md)与[原规格 R17](../../../spec/2026-10-13-doctor-guideline-recommendations.md#自动准备与待开具清单)中的同批独立检查整体回滚要求；诊断组、整张处方和其他核验边界保留。新检查批次须显式规定逐项结果与恢复表达，更新对应合同和测试，不能用浏览器循环覆盖单项草稿冒充批量能力。

合并收费按所选费用的当前剩余应收收齐，并逐费用记录在同一收款中的对应金额；不在本轮引入任意不足额跨项目分摊。这样既减少患者支付次数，也让原费用余额、执行放行及原交易退款有确定依据。原有单费用分次收款继续保留，资金结果不明沿用查询原尝试的恢复语义。当前资金合同由[临床业务流程](../../../architecture/clinical-workflows.md#85-收费支付与退款)拥有。

## Alternatives considered

- 只改住院医嘱外观：局部成本低，但每项添加后仍关闭弹窗，医生仍须重复操作；选择连续添加与统一清单才直接对应重复劳动。
- 所有患者和所有动作共用一个批量按钮：减少更多提交次数，但患者授权、动作前置条件、理由、库存和资金恢复无法形成清晰的单一业务边界。
- 对所有项目强制整体成功或整体回滚：适合处方和整台手术，却会让互不依赖的检查或执行单因一项失败反复核对整组；因此按实际业务单元区分。
- 对所有项目都允许部分成功：独立检查可报告逐项结果，但处方、诊断组、整台手术和收款会失去原有完整性，不采用作为通用规则。
- 合并收费同时允许任意不足额分摊：支付次数相同，但还需定义费用优先顺序、放行、并发占款和退款分配；本轮选择收齐选中费用，原有单项分次付款继续满足既有办理方式。

## Acceptance criteria

验收以[已批准规格](../../../spec/2026-11-09-batch-clinical-actions.md#验收条件)为唯一详细归属，需求、测试 seam 和纵向拆票方案均已确认。Note 保持 `proposed` 表示尚未交付，规格批准及 Issue 创建均不代表已经实现或授权实施。

## Risks

旧门诊多项确认的原子性、原有整体提交单元和新独立项目结果不可混淆。草稿恢复与已提交操作恢复也须区分，避免响应丢失后重复开立、扣库存或收款。报告连续阅读后集中确认仍要求医生明确确认，实际给药、教育记录则要求逐项核对真实事实；不得仅因已勾选就推定已经阅读或执行。跨患者队列的下一项由用户显式打开，不因当前办理成功就自动跳转或提交。
