# Agent Note: 术后漏记耗材通过独立补登记追加事实

Status: implemented

## Problem

术中逐笔登记要求手术进行中，术后更正则必须引用原使用。两者都无法表达手术完成后才发现漏记另一种耗材的情况；通过替换无关使用或重新完成手术会混淆临床来源并可能重复收取术式费。

## Decision

使用独立 `inpatient.surgery.supplement-material` Command，仅允许本次住院责任医生在患者仍在院、账户开放且病案未归档时，为原已完成手术追加实际使用和材料费用。复用共享使用、预留、账务及 Command 事务，保留原 Procedure、完成时间、原使用和术式费。历史中的 `recordingKind=postoperative-addendum` 明确区分补登记，原记录默认为 `initial`，不按登记时间猜测历史性质。

补登记沿当前有效目录及所选版本；仍有效的关联预留保留原冻结单价，已释放的预留继续关闭。输入中的 `expectedCharge` 只断言医生已审阅的收费定义身份、单价和单位，任何差异均拒绝；实际金额由服务端依据目录或预留计算。使用、费用、预留版本、申请版本、审计与幂等回执一起提交或回滚。界面复用现有术后耗材弹窗，补登记与更正各自保留语义。

## Alternatives considered

- 放开原术中登记的完成状态限制：旧客户端无法明确表达补登记意图，历史也无法可靠区分术中登记和术后补记。
- 将漏记统一转换为更正某笔已有使用：无法覆盖没有原记录的耗材，也会让无关使用承担错误的更正关系。
- 重新开启或重新完成手术：改变原完成事实并增加重复术式计费风险。
- 允许离院未结算时追加：超出本次在院基础范围，保留现有术后更正合同，补登记继续受在院限制。

## Consequences

增加窄 Command、CLI 路径及历史性质字段，既有回执与历史记录按默认值兼容。补登记影响费用推演及术后核查的当前依据，相关旧分析依照原指纹规则失效；登记本身不派发真实模型。HTTP/SQLite 验证状态、归属、计价断言、并发、回执及回滚，Web 与 React 18/19 Surface 浏览器合同验证真实入口及未知结果恢复。当前业务合同见[住院手术](../../../architecture/clinical-workflows.md#住院手术最小闭环)。
