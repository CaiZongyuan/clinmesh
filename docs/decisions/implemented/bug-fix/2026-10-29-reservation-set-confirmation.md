# Agent Note: 耗材预留整批审阅使用集合指纹

Status: implemented

## Problem

同计划的耗材预留可通过单项入口持续累积，记录数与新预计清单的产品种类数不同。要求客户端逐项回传全部旧记录并设置数组上限，会使合法存在的旧预留无法整体替换；仅提高阈值会在下一个阈值重复失败。直接让服务端替换提交时的最新集合又可能释放医生尚未审阅的新预留。

本决策细化[单次预计决策](../architecture/2026-10-28-single-material-estimate.md)的整批确认协议，保留同计划完整审阅、共享 Command 事务及原幂等回执。当前字段和失败合同由[临床流程](../../../architecture/clinical-workflows.md#手术计划的单次耗材预计)拥有。

## Decision

预留读取同时返回完整记录与各计划的集合指纹，包括空集合。指纹由服务端对受信 Workspace、Epoch、住院、计划以及排序后的全部活动预留身份和版本规范化计算。预计确认与手工整批替换只接收医生审阅的集合指纹，事务内重新读取并比较；匹配后处理完整集合，不受旧记录数组长度限制。新清单的产品种类及数量继续沿原业务约束。

页面从同一次预留响应展示记录并取得指纹，审阅状态绑定该指纹。集合变化要求重新审阅；确认冲突不能自动取新指纹重试。其他计划和未绑定预留不属于本集合，部分使用继续由原实际用量工作流处理。指纹随原 Command 输入持久恢复，成功回执重放先复用原结果，不再次比较已替换的集合。

## Alternatives considered

| 方案 | 未采用的原因 |
| --- | --- |
| 将旧记录上限从20提高到30或500 | 单项入口仍可产生更多合法记录，无法消除容量不一致。 |
| 移除旧记录数组上限并继续逐项回传 | 客户端与请求大小随历史记录数增长，仍要求各入口复制完整集合及版本的装配。 |
| 服务端直接替换提交时的所有旧项 | 无法证明新增或变化的预留已经过医生审阅。 |
| 仅比较旧记录条数 | 记录替换、释放及版本变化可能不改变条数。 |

## Consequences

确认请求大小不随旧预留数增长，后台统一拥有完整集合的校验与替换。持久化格式不变，公开输入及预留读取合同升级，Operation Catalog、CLI 示例和运行时 Skill 同步维护。字段缺失的旧读取回执可回读，但缺少当前计划指纹时页面不能确认，须重新查询。

公开 HTTP 使用受控 Provider 和临时 SQLite 验证31笔旧预留整体替换、原键及重启恢复、审阅后新增／释放冲突、跨计划隔离和中途故障回滚；真实 Web 与 React 18/19 入口验证完整旧清单的审阅及整批确认。验证不调用真实模型，也不扩大合成材料依据范围。
