# Agent Note: 按指南库版本复用完整检索结果

Status: implemented

## Problem

诊疗建议读取为判定输入指纹与 `stale`，每次同步检索指南并重算全库正文完整性；病例与指南库未变时，五类建议仍重复这项工作。较大指南库中的秒级同步读取会阻塞其他请求，`pending` 轮询进一步放大切页签和切岗位的排队延迟。

## Decision

在 `GuidelineCorpus.search` 内复用完整检索结果，调用方继续取得相同的原文、不可用来源及内容 revision。每次检索先检查 SQLite 提供的外部提交版本和本连接写入计数，再决定能否命中；不要求各导入、维护或修复入口手工维护失效通知。版本检查与未命中读取处于同一事务，缓存身份与结果对应；版本变化清除全部旧条目。当前机制与容量由[存储合同](../../../architecture/storage.md)拥有。

缓存按最近使用淘汰，并复制返回值以隔离调用者修改。它是单连接实例的进程内优化，不保存到 SQLite，也不共享用途策略不同的实例结果。

## Alternatives considered

- 延长前端轮询间隔：只能减少频率，不能消除切换时的重复同步检索，也不能改善其他读取调用方。
- 在建议服务中按病例缓存：让业务层承担指南库内容失效与检索复用，且容易因五类建议使用不同缓存键而重复读取。
- 在每个写入方法手工清理缓存：不能覆盖其他进程或维护连接提交的来源状态、正文及完整性变更。
- 分别缓存正文哈希、段落统计与全文查询：可以进一步改善冷读取，但增加失效边界；本次先消除未变输入的整次重复检索。

## Consequences

每个新检索文本和每次指南库内容变化后的首次读取仍完整核对原文，可能耗时较长。缓存容量固定，条目淘汰后重新检索；无关数据库写入也会保守失效。指南库 schema、建议生成流程及前端轮询无需改变，回滚不涉及数据迁移。

`guideline-corpus.test.ts` 从公共检索入口验证重复读取不查询指南表、文本变化、同连接和跨连接导入失效、跨连接损坏停用、最近使用淘汰及返回值隔离。现有指南 HTTP 和诊疗建议回归验证原文与 `stale` 合同；较大合成数据副本上的 HTTP 计时与真实页面轮询验证排队延迟，具体验收阈值见[正式规格](../../../spec/2026-11-03-recommendation-read-latency.md)。
