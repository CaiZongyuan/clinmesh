# Agent Note: SQLite 迁移校验兼容 LF 与 CRLF

Status: implemented

## Problem

SQLite 迁移原先按 SQL 原始字节记录 SHA-256。Windows 的 Git 换行转换会使同一份已执行 SQL 从 LF 变为 CRLF，开发准备与启动验证因此拒绝现有数据库；同一个库也可能同时包含两种历史校验值。只验证空库或单一平台无法覆盖此升级路径。

## Decision

Operational 与 Reference SQLite 共用迁移校验模块。新记录对 CRLF 转 LF 后的 SQL 计算 SHA-256；验证同时接受当前原始文本、统一 LF 和统一 CRLF 三者的摘要，以兼容旧引擎已写入的原始校验值。该规则只处理换行，不忽略注释、空格、末尾换行或 SQL 内容变化。既有迁移记录的 checksum 与 applied_at 保持原值，不重跑已执行迁移。

迁移执行、启动验证与恢复校验使用同一规则。未知与待执行迁移继续失败；开发准备仍先创建并验证升级前备份，再执行缺失迁移。参考来源文件、导入清单和影像／病理素材的字节校验不使用此兼容规则。

## Alternatives considered

- 只固定 Git 检出为 LF：可以稳定未来文件，但不能兼容已经记录 CRLF 的数据库。
- 改写库内 checksum 或重建数据库：丢失历史校验依据，且不解决后续跨平台检出。
- 完全跳过历史校验或对全部文本做宽松格式化：会接受真实 SQL 改动，破坏迁移不可变性。

## Consequences

同一数据库可在 LF 与 CRLF 检出间切换，无需重写迁移记录或业务数据。真实文件数据库回归覆盖两种历史校验值、关闭后重开、迁移与验证入口、新增迁移、原记录保真和实际 SQL 修改拒绝；两套迁移引擎共用这些行为断言。该兼容仅解决文本换行差异，不提供已执行 SQL 内容变更的恢复通道。
