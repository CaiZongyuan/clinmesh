# Agent Note: 手工预留连续维护与逐项恢复

Status: implemented

## Problem

同一手术的多条手工预留需要逐条寻找并确认，关闭或刷新会丢失未提交输入。既有整批替换是完整 desired-set 事务，会关闭本计划原预留；把它用作选中项批量维护会误改未选记录。单项释放只检查住院依据时，审阅后发生部分消耗但仍有效的预留可能按变化后的余量被释放。

## Decision

新增与释放各自拥有同计划的待办清单，共同理由保留逐项覆盖，界面一次集中核对后顺序复用原单项 Command。每项继续独立拥有事务、审计和幂等回执，成功或确定失败按项结算；未知结果停止队列，沿共享住院写意图恢复原尝试，再由用户核对剩余项目。不改变术前确认所用的完整集合替换事务。

私稿绑定完整身份、患者、住院、计划和动作，保存人工内容及原提交行的关联。发送前冻结各行输入及幂等标识，释放项另保存原预留归属及审阅依据；重新读入和结算前逐条核验原命令与这些范围一致，不能只验证外层存储键。绑定不符时保留已验证的人工输入并阻写，不靠当前编辑猜测原请求；缺少原释放归属依据的旧记录同样安全阻断。成功或原回执只消费对应修订，后来编辑继续保留。持久化失败停止新提交；退出清理和明确丢弃沿既有私稿边界。

释放增加可选原预留预期依据，保留旧单项输入兼容，新界面显式传入。服务端在原事务内检查该依据，审阅后发生消耗或状态变化须重新核对；共享错误原因让界面和 CLI 不必猜测两类冲突。释放命令不携带手术计划。结算先定位同键同命令的有效记录；原草稿不可读时，使用成功回执中对应的写入效果及预留事实证明所属计划。不可读候选数量不能证明归属，同次住院其他计划的坏稿继续保留。确认丢弃时重查原键回执；缺少证明或回执不明则保留写意图和原文。

当前业务合同由[临床流程](../../../architecture/clinical-workflows.md#住院手术最小闭环)拥有，界面范围由[UI 设计](../../../ui/design.md)拥有。本决策扩展[手术连续录入](2026-11-10-surgery-material-batch-drafts.md)的私稿恢复方式，保留整台补录与最终核实各自的原子提交。

## Alternatives considered

- 使用 `replace-batch` 提交选中项：该接口表达完整目标集合，不能保留未选预留。
- 新增服务端多项维护事务：会把原本独立的维护动作改为整批回滚，并重复已有 Command 与审计边界。
- 结果未知时为整份清单生成新键再提交：可能重复创建已成功但丢失回执的预留。
- 只依赖住院预期依据释放：无法识别同次住院内原预留的部分消耗变化。

## Consequences

集中办理允许明确的逐项部分成功，界面与恢复都必须显示每项结果。公开 HTTP 回读同时核对预留数量、状态、费用及原回执，组件和双 React 版本真实入口验证私稿、理由、选择边界、上下文切换及窄容器操作；预留预计不被解释为实际库存扣减。
