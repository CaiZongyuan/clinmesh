# Agent Note: 收款交易事实与门诊资金分配分离

Status: implemented

## Problem

门诊收款的尝试创建及结果恢复嵌在临床工作流中，付款方式又由费用分配模块保存。交易恢复和业务放行混在同一 owner，住院接入时容易复制共同状态规则；退款预览直接引用门诊旧交易表，也使单独替换收款路径无法继续办理原款退款。

## Decision

`PaymentCollection` 拥有原始收款结果、冻结渠道查询计划、付款方式及追加确定结果。它只在调用方既有 Command 事务内写入，不创建另一条公开资金写入口。交易身份通过原就诊上下文固定患者和 Encounter，门诊费用分配使用包含就诊和金额的复合外键，避免同一患者不同次就诊共用原款。

门诊 owner 继续校验应收、预览、岗位和费用版本，关联原费用并执行既有放行。`RefundLedger` 继续拥有可退余额、未知预占和退款方式消耗，门诊只将新交易的原款及方式事实交给它。存储与事务的当前合同见[收款记录](../../../architecture/storage.md#门诊收款记录)。

本决策只交付[共享收款规格](../../../spec/2026-10-28-shared-payment-collection.md)的门诊路径及公共内核。住院接入和显式开发数据切换分别由 #355、#356 承接，[支付职责边界提案](../../proposed/architecture/2026-10-21-payment-inpatient-drg-boundaries.md)继续保留其尚未完成的整体范围。

## Alternatives considered

- 只抽出创建和恢复函数，仍分别保存两种交易格式：可以较少修改引用，但保留了两套读写映射和结果表达，后续维护仍需处理格式分叉。
- 在公共内核中同时判断门诊费用结清和住院预交金抵扣：减少调用方步骤，却让共同状态依赖两种业务状态机，难以独立恢复原尝试。
- 新收款继续向旧交易表双写以保留退款外键：短期可沿用旧退款预览，但制造两个可被当作权威的原款。采用直接关联新原款的门诊退款预览，不引入双写或旧交易读取适配。

## Consequences

交易结果、费用分配、预览消费、FHIR 版本、回执、审计和相关 outbox 共同提交或回滚。本地回滚不表示外部支付能够撤销；当前确定性合成渠道只冻结查询计划，未知结果必须查询原尝试。

公共内核测试验证三种结果、原始结果不可覆盖、固定查询计划、重启和事务回滚；HTTP 验证原账单、回执、原款退款及独立连接竞争；既有收费页面旅程和 React 18/19 合同验证实际接线。旧结构的迁移测试只证明其历史 schema 变换，不充当新内核能够读取旧交易的合同。

新交易使用统一事实，新门诊路径不读取旧支付格式。旧表的存在属于开发切换前的暂存，不能在正常启动时隐式清除旧业务数据；整体上线与旧结构移除须完成规格中的显式切换验收。
