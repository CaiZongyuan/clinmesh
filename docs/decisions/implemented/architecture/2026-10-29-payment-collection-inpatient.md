# Agent Note: 住院资金用途接入共同收款交易

Status: implemented

## Problem

门诊已使用共同收款内核，住院仍独立保存尝试、方式和查询结果。登记预交金直接入账，补缴退款的首次结算投影又引用旧尝试表，仅替换收费员收款函数会留下缺少共同原款或不能退款的资金链。

## Decision

住院登记现金预交金、追加预交金、首次及后续补收均通过同一 `PaymentCollection` 创建原款、冻结方式并查询恢复，使用与门诊相同的交易表。`InpatientPayments` 只拥有预览、原住院用途关联及成功预交金入账；后续更正继续拥有原费用和更正依据，`RefundLedger` 继续拥有原款可退余额、未知预占与退款方式分配。

登记款以没有独立预览的住院分配关联共同原款，保留登记安全整数现金政策，不计入公开独立收款尝试。这样不改变既有“从未有独立收退款尝试才可默认现金结清”的人工审阅合同。首次补缴退款使用直接引用新原款分配及退款的结算投影，避免向旧尝试双写。

分配不保存另一份金额或渠道状态。交易创建或追加结果、用途关联、成功入账、预览消费、回执及审计仍在原业务 Command 事务内共同提交或回滚。完整持久化合同见[存储与事务](../../../architecture/storage.md#门诊收款记录)，资金和冻结门禁见[住院出院与结算](../../../architecture/clinical-workflows.md#住院出院与结算)。

## Alternatives considered

- 保留住院尝试表，调用共同渠道函数：仍维护两套交易状态及存储，不能满足同一内核的恢复与重启合同。
- 把登记预交金解释为普通独立尝试：会改变默认现金结清的准入，并给原登记金额新增单笔方式上限。
- 新原款同时写旧尝试表以保留退款外键：产生两份交易权威。采用新的结算退款关联，旧合成运行链及结构由显式开发切换统一收口。
- 把费用抵扣与后续调整放入共同内核：会使资金恢复依赖住院结算状态。住院 owner 保留这些规则，公共内核只维护交易事实。

## Consequences

同一患者的门诊及多次住院仍分别绑定原就诊和用途，不形成通用钱包。未知资金继续阻断首次封账和清床；原尝试恢复后可继续，后续补收及退款不会倒退首次结算、出区、清床或归档。

公共内核和公开 HTTP 验证共同身份、三类结果、组合方式、幂等、重启、原款退款及故障回滚；独立数据库进程验证竞争。既有住院页面及 React 18/19 ShadowRoot 合同验证实际接线。旧合成交易及关联运行链由[开发切换决策](2026-10-30-payment-collection-development-cutover.md)收口，不在正常启动时隐式清除；整体验收入口归[正式规格](../../../spec/2026-10-28-shared-payment-collection.md#验收证据)。本地数据库回滚不表示外部支付可以随之撤销。
