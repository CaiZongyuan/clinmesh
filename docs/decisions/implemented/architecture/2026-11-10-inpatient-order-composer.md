# Agent Note: 住院多医嘱草稿与逐项原意图恢复

Status: implemented

## Problem

住院药品和护理治疗医嘱需要连续准备，每条仍拥有独立临床校验和执行生命周期。连续提交可能只有部分成功，响应丢失也可能掩盖已经签署的医嘱；单项费用预计的依据会因前一条医嘱成功而变化。

## Decision

页面只保留“开立医嘱”入口，目录、逐条字段和集中确认由一个弹窗拥有。最多保留 20 条待开医嘱，重复选择同一项目提示编辑原行；原单项 `inpatient.order.issue` 继续负责诊断、剂量、频次、过敏、组合、术后关联、版本和审计。批次仅由人类界面依次编排，不新增批处理 Command 或 Agent 写工具。当前业务合同由[医嘱生命周期](../../../architecture/clinical-workflows.md#83-医嘱生命周期)拥有。

草稿使用严格版本化 schema，按账号、完整 Actor、患者与住院绑定保存在 sessionStorage。每条发送前先保存冻结输入与原幂等键；存储不可用阻断发送并保留当前可见输入。成功立即消费原行并保存结果，确定业务拒绝保留输入，未知结果保留原 attempt 并停止队列。恢复由已有岗位级 write intent 查询原回执，只有明确不存在才使用原载荷、原 key 续发；回执查询后重放前重新读取 Session。全局与行级入口共享结算：按账号、完整 Actor、住院、原命令与幂等键持久消费成功行，再解除岗位级原意图。已挂载的清单同步读取结算结果；切回或刷新时直接读取新清单，无须再次查询同一回执。切页或切患者后不继续发送下一条。

费用预计按每条医嘱的单项 selection 计算，已审阅指纹和过期状态随行保存；编辑该行会撤销其预计。前一行成功后，在同一次草稿保存中将剩余行的预计标为过期，停止这些行的开立。用户必须重新预计并再次明确确认，刷新不会自动接受新依据。每次使预计过期同时更换审阅代次，旧重新预计的迟到响应不能撤销新过期状态，提交期间也不能重新预计。该预计仅供参考，开立依旧由服务端按原输入重算核对。

## Alternatives considered

- 一次提交整个数组：会扩大现有单项医嘱事务和恢复协议，且无法保留独立临床拒绝后的逐项结果。
- 仅在内存保存清单，复用一个岗位级待恢复操作：刷新会丢掉尚未发送的行及其字段，也无法确定公共恢复完成后哪条草稿已经生效。
- 整批预计后给每条传同一指纹，或在队列中自动更新指纹：前者不符合单项 Command 的预计输入，后者使后续开立使用未被用户审阅的新依据。

## Consequences

未决 attempt 阻止新批次及草稿丢弃，避免换键重复签署。退出登录清理未提交草稿，岗位级原意图仍维持其受信绑定。药品与护理可同窗准备，但开立仅产生待护士校对的 signed 医嘱；护士执行、药房发药、给药和费用事实继续分离。组件回归覆盖独立编辑、刷新、患者隔离、部分失败、原回执恢复及预计过期；真实岗位旅程回读两条正式医嘱且核实执行、发药和费用未发生，ShadowRoot 合同覆盖 React 18 与 19。
