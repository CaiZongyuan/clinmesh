# Agent Note: 门诊报告阅读上下文与持久选择分离

Status: implemented

## Problem

医生连续阅读同次就诊的多份报告后，需要集中确认已阅。选择清单需要在关闭、切患者和刷新后保留，但影像或病理是否已经实际显示只能由当前阅读器证明。把这两种状态一起持久化，会使刷新后的选择绕过阅读门禁；把所有状态一起丢弃，又会丢失已经准备的人工清单和结果不明的原尝试。

## Decision

同次门诊的检验、放射和病理报告共用连续阅读窗口，正式状态仍由 Query 和原报告 Command 拥有。具体行为由[门诊报告连续阅读与集中已阅](../../../architecture/clinical-workflows.md#门诊报告连续阅读与集中已阅)维护。

持久清单只保存完整身份及患者、就诊绑定的选择快照、修订和原写入意图。当前窗口另持有报告身份及版本绑定的打开、显示资格，切换报告可保留本轮资格，关闭或失去上下文后撤销。放射和病理的展示依据来自真实阅读器的成功回调，并继续要求素材当前可读；元数据可用、正文可见或先前选中都不能替代成功显示。

集中确认冻结人类核对的集合，逐项使用原 Operation、预期版本和独立幂等键。发送前持久保存原输入；确定成功先结算原清单修订，再清除写意图。结果不明时停止后项，仅查询匹配 operation 和键的原回执；明确404缺失才允许原输入、原键重发。恢复成功可以结算过去的操作，但不会给剩余报告补造本轮阅读资格，也不会自动接续旧计划。

门诊已阅回执的报告版本由不可变原 Command 绑定，输出中的申请版本、报告身份及已阅事实按原合同核对。已存在同份已阅事实时允许原接口返回无新增 Effect；不要求报告、ServiceRequest 或 Task 因已阅增版。更正后新报告仍须重新查看和确认，旧回执不能消费新修订清单。

## Alternatives considered

- 将已显示标记与选择一起持久保存：恢复后没有当前显示上下文，会绕过影像和病理门禁。
- 关闭窗口即丢弃全部输入：丢失人工选择，也无法安全恢复已经发送但结果不明的操作。
- 仍按三类申请各开一个确认窗口：开立类别边界不适用于同次就诊的报告阅读，不能完成连续阅读。
- 服务端新增批量已阅接口或客户端已读凭证：现有协议拥有权限、版本和素材可读性，客户端拥有本次真实展示事实；本需求无需扩大写接口或声称服务端能证明人已阅读。

## Consequences

恢复清单后可能仍需逐份重新打开，这保留了阅读事实的可靠性。原回执、清单修订与当前报告版本必须分别核对；存储失败时保留阻断，迟到结果只归原作用域。公开 HTTP 和临时 SQLite 验证原幂等键、版本、唯一已阅事实及重启恢复，真实岗位及 React 18/19 合同验证阅读生命周期和明确确认，短录屏绑定最终干净提交。
