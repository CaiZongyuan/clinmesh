# Agent Note: 固定 PCI 合成档案与首个 Persona 一次就绪

Status: implemented

## Problem

固定 PCI 演示来源及患者自述均可重复确定，仍要求管理员照手册手填九字段并另选首个修订，增加了与演示诊疗无关的准备工作。把此步骤交给模型会引入配置、等待和内容漂移；把私有作者底稿当作正式诊疗记录或患者已知病史则会绕过观察边界。[已批准规格的 B1–B3](https://github.com/CaiZongyuan/clinmesh/blob/1b4bc8aa1bb9722f3e305db3f1216a1e05eedd88/docs/spec/2026-10-28-inpatient-ai-assistance.md)要求固定患者准备后可继续原岗位流程，执行追踪为 [#345](https://github.com/CaiZongyuan/clinmesh/issues/345)。

## Decision

固定来源准备复用原共享 Command，将来源、病例和版本化合成 Persona 的创建与首次选用置于同一事务。模板保留可追溯的版本及作者来源身份，仅包含患者可知的自述；准备不依赖模型，也不产生本院诊疗或费用事实。病例仍停在待入院，由登记员办理直接住院、护士接诊分床。

重复准备优先复用当前有效选用和已有人工修订，已消费病例保留原绑定；历史病例已有未选修订时复用最新已有修订，仅无 Persona 时创建模板。准备与后续人工修订继续使用同一不可变修订体系，避免模板变更覆盖正在使用或历史绑定的患者表现。丢回执沿原准备意图与幂等键恢复，Epoch 重放沿原病例和选用修订执行；清空患者库后的新 Case 可再次完成固定准备。

本决策仅部分替代[固定 PCI 作者来源与直接住院实体化](2026-10-26-authored-pci-inpatient-source.md)中的人工首录取舍。该 Note 的来源身份、隐藏事实隔离、一次消费及直接住院实体化继续有效；一般动态病例保留原模型生成与人工修订入口。当前机制由[仿真场景合同](../../../architecture/simulation.md#103-场景定义)拥有。

## Alternatives considered

- 保留手工首录：无需模型，但重复抄写固定内容，无法满足一键就绪目标；原编辑入口保留用于人工调整。
- 每次由模型生成固定 Persona：可复用动态病例入口，但固定准备需要额外配置与等待，也难以保证重复内容；采用版本化合成模板。
- 页面依次请求建档和选用：可复用多个按钮，却会留下部分成功和多个恢复意图；由同一共享事务形成完整可消费状态。
- 每次准备重新生成或切回模板：可以强制恢复演示初始内容，但会覆盖人工判断或改变已消费来源；重复准备保留已有资料与绑定，完整重演使用新库或显式 Epoch 重放。

## Consequences

公开请求、CLI 路径与回执结构继续沿用，返回的病例状态及修订表达准备结果。版本与内容由服务端固定；模板更新不改写既有修订，后续临床事实继续经各岗位的原业务命令形成。

验收沿公开 HTTP、角色会话和临时 SQLite，覆盖首次就绪、重复准备、人工保护、原键恢复与 Epoch 重放；受控 Provider 拒绝模型请求。真实 Web 与 React 18／19 Surface 证明无需九字段手填即可继续登记分床，隐藏来源和准备阶段零诊疗边界由服务端合同验证。
