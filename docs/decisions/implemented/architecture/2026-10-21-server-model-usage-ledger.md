# Agent Note: Server 模型逐次计量与查询

Status: implemented

## Problem

完整任务内存在格式纠错和限流重发；只在任务外记录最终成功会漏掉真实消耗。DSH 与直接接口的缓存 Token 口径也不同，断流不能推断零费用。现有建议请求次数与成功步骤恢复已经持久化，新增账本不能先扣次数再因记账失败丢失机会。[正式规格](../../../spec/2026-10-19-model-usage-control.md)及第一张执行票定义本切片范围，后续控制决策由[总提案](../../proposed/architecture/2026-10-21-model-usage-accounting-control.md)拥有。

## Decision

单 SQLite writer 在两类 Provider 的每次实际派发前建立受信尝试身份，与已有次数闸门同事务。桥接发送同一身份及窄用量帧，兼容原 JSON 生成通道；每帧接收后以短事务保存已知部分及派发证据，不等待终态，因而进程退出后的未知请求仍保留已观察消耗。账本与网络不共持长事务。所有额度无限时仍须先持久记账；历史精确调用不补造。

账本只保存验证过的关联与计量元数据。实际 Provider/模型与语义映射属于当次记录，不由当前设置重新解释。DSH 分项快照合并后重算归一化合计，避免沿用较早快照的总量；原始计数仍保留证据。合批保留触发与支持来源；重新生成与显式继续由持久 outbox 意图确定手动触发，继续关联同一任务及事件，不从已有任务猜测意图，也不构造无法证实的完整因果树。跨 Epoch 汇总与逐次明细分别授权，医生明细依赖病例责任，行政调用仅管理员可读；SQL 在分页与计数前执行授权。

## Alternatives considered

- 装饰完整任务：接口更少，但遗漏内部尝试并破坏重试归因。
- 两套独立事务：实现直接，却会在账本失败时留下已消耗的旧次数。
- 只传最终 JSON 用量：兼容简单，但丢失 Host 已观察到、取消前尚未返回的用量。
- 仅在 Provider 内存中合并用量：减少写入，却会在收到帧与终态之间退出时丢失已知消耗。
- 以发起 Actor 开放明细：容易查询，但不能代表当前病例责任或历史 Epoch 权限。

## Consequences

记账故障会停止新模型请求。未知量和缺价明确显示，不能作为零费用或服务商实际账单。[Host 独立识别](2026-10-21-host-recognition-usage-admission.md)复用同一账本，[双层请求控制](2026-10-21-model-request-control-recovery.md)复用同一准入事务；Token／金额保护、计价及明细清理仍由后续票实施。当前合同见[模型账本](../../../architecture/storage.md#910-模型调用账本)和[查询权限](../../../architecture/security-and-reliability.md#模型用量查询)，验证见[测试策略](../../../testing.md)。
