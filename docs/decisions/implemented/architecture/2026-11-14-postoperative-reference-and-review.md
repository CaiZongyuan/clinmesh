# Agent Note: 术后待确认主操作的费用预计与核查清单

Status: implemented

## Problem

PCI 已完成而首页主操作尚未覆盖本次操作时，正式分组可能仍按先前造影比较。患者头部立即从 FM39 的计划参考回到 FM59，会使已完成手术看似突然接近或超出参考。正式主操作仍须由医生确认，显示需要表达这段待确认状态，不能用预计替代正式事实。相关主操作入口见 [#488](https://github.com/CaiZongyuan/clinmesh/issues/488)，手术范围见 [#489](https://github.com/CaiZongyuan/clinmesh/issues/489)。

术后把阶段费用、模型状态、来源历史与待办卡同时铺开，削弱了真正需要确认的数量差异。通用“每类一件”依据与把计划内登记原因拼入多用说明，也让医生难以直接核对本笔用途。

## Decision

费用推演只读返回 `postoperativeEstimate`，根据当前实际完成操作与最新首页确认覆盖范围重新计算。唯一新候选或全部候选得出一致病组及同身份支付参考时，提供共同的术后预计；其余情况保留待确认身份而让分组及参考未知。无可用待实施计划投影时，头部使用该结果和当前统一费用，标明“待确认主操作”；确认覆盖当前实际操作后自然切回正式口径。详细比较合同由[手术费用与医保说明](../../../architecture/clinical-workflows.md#手术费用与医保说明)拥有。

这一读取不确认主操作、不写首页或正式分组，也不沿用上一台或上一修订的预计金额。缺价、候选不一致或读取失败时如实显示未知，避免按尚未覆盖新操作的旧正式参考发出接近或已超提示。患者、角色、Epoch、归档与同份查询缓存边界继续生效。

术后主区采用一份紧凑核查清单，按项显示耗材、数量差异、已有规则处理说明及当前动作；编辑说明按需展开，费用与模型状态留在依据历史窗口，原记录与复查留在逐项来源窗口。逐条与一次全部确认继续调用原 Command，保留失败停止、未提交输入及迟到结果隔离。

核实及术后多用说明按同一材料和版本累计有效登记，仅引用超计划笔的理由。更正以最终有效替换承接原笔位置，撤销移出累计，替换链不重复计算。逐行计划依据优先复述本次已确认资料；旧通用依据仅在有同手术原确认与版本证据时作只读展开，自写依据及冻结快照保持原样。

本决策部分演进[手术流程减负](2026-11-13-surgery-flow-assistance.md)关于全部手术完成后立即回到正式费用参考及术后展示密度的取舍，其余临床写入、计费、模型和恢复边界继续有效。界面详细合同归[住院工作台](../../../ui/design.md)。

## Alternatives considered

- 完成即自动把 PCI 设为主操作：越过医生确认，也会在多台实际操作时隐含选择。
- 沿用最后一次术前 FM39 或参考额：诊断、实际术式、费用及规则已可能变化，旧缓存不能证明当前预计。
- 始终比较旧正式参考：会把待确认导致的口径缺口表现为费用异常。
- 多候选直接取最近完成的一台：完成时间不能决定主操作，候选结果不一致时必须保留未知。
- 继续堆叠阶段说明和旧待办卡：状态与规则文字抢占差异核查空间，医生仍需逐段寻找当前操作。

## Consequences

预计与正式结果保持独立，客户端和 Agent 都能识别待确认及未知。新的主操作确认入口可以消费同一正式事实后自然结束该过渡，无需迁移预计数据。公开 HTTP 与组件回归覆盖完成、费用变化、多候选及确认后的切换；Web 与 React 18/19 的真实术中和术后界面继续验证数量、说明、来源、批量确认及原型布局。
