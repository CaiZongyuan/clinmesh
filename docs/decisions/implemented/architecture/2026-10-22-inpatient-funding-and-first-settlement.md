# Agent Note: 住院共享资金与首次冻结账

Status: implemented

## Problem

原首次结算在一个Command中直接生成确定补退，无法表达真实的渠道未知与原尝试恢复。既有登记预交金、结算交易和病案快照已被使用；引入共享收退款必须保留这些事实及原receipt，且资金未知不能改变原医生出院医嘱和护士出区的临床责任。

## Decision

InpatientPayments在住院owner中组合共享渠道计划与RefundLedger，资金尝试、未知结果解析和成功原款分离。现代预交金成功时按原payment ID唯一投影入既有预交金表；现代补缴在首次封账前直接参与聚合，封账时按同ID投影到原结算交易。RefundLedger拥有按原款累计成功、未知占用和原方式分配，住院owner只负责本次应收退及封账策略。当前合同由[临床流程](../../../architecture/clinical-workflows.md#住院出院与结算)拥有。

首次封账须资金结果确定且净额已结清。独立预览绑定逐项明细、资金和受信岗位，确认与恢复均通过共享Command保留幂等receipt和审计；渠道未知使用原attempt查询，HTTP丢回执使用原Command receipt，两条恢复语义独立。尚未有独立尝试的历史settle调用保留人工审阅后默认现金结清的兼容路径；一旦出现独立尝试，拒绝或未知都不能回退默认路径。

财务动作的人工确认由 Operation Catalog 风险元数据驱动，统一覆盖收退款确认、原尝试恢复、后续费用更正及首次封账。`settle` 可走默认现金结清，因此必须与独立资金入口使用相同确认门槛；预览 token 及服务端授权不能代替 CLI 本地确认。当前 human/Agent 模式边界由 [CLI 合同](../../../architecture/agent-integration.md#710-human-与-agent-身份)拥有。

历史资金保留原ID、原金额和存储JSON。迁移只将已有成功退款适配进共享退款账，不再次发送渠道。现代补缴在首次封账前可能因费用冲正成为应退原款，因此增加补缴退款窄投影，保留原结算表的预交金外键。首次与后续更正资金用adjustmentId区分，首次读取和冻结不消费后续资金。

## Alternatives considered

- 继续由settle无条件生成成功补退：无法表示未知，渠道拒绝后也可能绕过资金门禁。
- 将全部旧资金复制成新余额：产生两个余额owner，历史冻结账和病案可能重复计费或改变。
- 重建原结算交易表并放宽来源外键：扩大非空迁移风险，且旧预交金退款的来源约束失去数据库保护。
- 删除旧默认结清路径：会改变已交付的首次结算调用合同，迫使历史集成同时迁移；受限兼容路径让独立尝试仍拥有严格门禁。
- 在 CLI 单独维护财务命令名单：与 Catalog 风险分级形成两个 owner，新增入口容易遗漏；沿用统一元数据检查。

## Consequences

收费员可在真实入口预览组合收款或原款退款、审阅确认并查询未知结果；护士继续在原出区入口工作，只有确定结清后才能清床。首次settlement-preview保留旧补退口径，当前尚应收退由payments.remainingFen提供，调用方须明确重新预览封账。公共HTTP与临时SQLite验证未知、拒绝、持续未知、重启、岗位、篡改、并发、零净额明细变化及补缴原款退款；非空升级验证旧事实和receipt不变，Playwright验证收费员及护士入口。
