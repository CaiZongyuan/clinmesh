# Agent Note: 门诊多费用预览独立冻结边界

Status: implemented

## Problem

原门诊预览、收款分配及退款从一笔原款推导一项费用。多选界面若循环单项按钮，会形成多笔资金尝试；若把多项预览塞入原单项记录，又可能被既有确认路径当作首项费用消费。选择与余额核对需要先有可独立验收的完整闭环，同时保持原单费用分次收款和恢复。

## Decision

使用专用 `payment.multi-charge.preview` Operation 和 `multi_charge_payment_preview` 持久记录，严格冻结同患者、同次就诊的完整项目与当前剩余应收。每项只能收齐自己的余额，付款方式组合覆盖全部所选余额；沿用共享 Command 的岗位、版本、幂等、事务、回执与审计边界。当前能力只到预览，旧单项确认不能消费新预览，不创建资金尝试、费用分配或临床放行。

原单项预览和确认保持原有 shape。未来的合并收款须由独立窄操作在确认时重验全部冻结依赖，以一笔共享收款关联多项费用；在具备原交易恢复和按原费用分配退款之前，不开放合并确认。当前存储、金额及工作流合同见[收费与支付](../../../architecture/clinical-workflows.md#85-收费支付与退款)和[门诊收款记录](../../../architecture/storage.md#门诊收款记录)。

## Alternatives considered

- 循环旧单项收款：各笔可得到不同结果，无法表达一个组合付款意图，也无法冻结整组选项，拒绝采用。
- 扩展旧预览并保留一个代表费用：旧确认和退款可能按该首项推导整笔归属，给未完成的多分配协议留下可消费入口，拒绝采用。
- 只在浏览器汇总金额：不能独立保证费用版本、未决资金或权限边界，也无法在响应丢失和服务重启后查询原预览回执，拒绝采用。

## Consequences

专用记录增加一个预览存储 owner，但隔离了旧单项资金协议。界面可以跨已有可收款类别准备和核对，选择、付款方式或账务依赖变化后重新预览；不会把草稿或核对结果宣称为已收款。公开 HTTP 回归覆盖新预览零资金副作用、旧确认拒绝、原幂等回执及真实 runtime 重启，真实岗位和双 React 浏览器回归覆盖选择、草稿隔离与布局。后续合并收款必须同时处理多分配存储、按交易分页、未知资金阻断与原分配退款，不能仅增加一个确认按钮。

未提交选择和付款方式作为会话私稿保存，完整账号、Actor、患者和就诊绑定避免串稿。服务端退出成功后，存储枚举或删除失败不会把退出改判为失败；当前页面运行时隐藏旧稿并阻止预览，待存储恢复后延期清理。这个内存补偿标记不保证跨页面重载，不能据此宣称受限存储下的跨重载清理保证。

读取失败后的空投影不能作为新草稿的保存来源，因此恢复动作区分重新读取与重试保存；自动补写会覆盖尚未读到的原输入。丢弃确认和窗口关闭复用操作在途及原意图门禁，避免已经展开的确认条绕过页脚保护；当前恢复合同由[收费与支付](../../../architecture/clinical-workflows.md#85-收费支付与退款)拥有。
