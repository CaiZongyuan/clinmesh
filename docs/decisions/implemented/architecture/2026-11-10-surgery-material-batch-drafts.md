# Agent Note: 手术耗材连续录入与原整台操作恢复

Status: implemented

## Problem

整台补录与最终耗材核实已经分别拥有完整事务和回执，但逐次下拉添加使多耗材录入反复往返。组件内输入在关闭、切换或刷新后丢失；仅恢复原 Command 却继续保留同一份待提交清单，又可能让成功操作被当成新补录。最终核实允许同一预留按不同冻结快照分行，逐行计算可释放余量会误判整笔预留是否仍有剩余。

## Decision

两个入口复用目录窗口内连续选择与完整草稿编辑，保留各自20种与100行上限。正式状态变化仍分别由原 `inpatient.surgery.execute` 或 `inpatient.surgery.complete` 拥有，不循环调用逐笔登记或释放接口。整台补录的原预留必须未部分消耗且整笔使用；部分使用仍走术中登记与最终核实。

浏览器草稿绑定完整身份、患者、住院、申请与动作，完成核实增加实施身份。持久化边界验证结构，允许未完成字段保留，正式发送再校验业务输入。发送时将原命令与对应草稿快照关联，共享住院写意图继续唯一拥有幂等键及原回执恢复；成功只消费与该提交一致的草稿，保护后来修改。持久化失败时停止新提交，清空需用户确认，退出清理未提交输入。

原操作成功但对应草稿不可读时，沿用共享恢复入口保留原意图及原文，允许重试读取或明确确认丢弃。确认绑定原幂等键，再次查询并证明原操作成功后，只删除原身份及原手术动作范围的不可读草稿，再解除意图；回执不存在、查询失败或存储读取被拒时保留原文，明确丢弃请求不重发业务操作。其他手术或患者的损坏草稿不阻塞当前结算，也不随当前确认删除。

可释放集合按本手术每笔预留全部行的净变化汇总余量，再与当前可释放状态相交；当前页全选不扩到其他计划、无余量或未展示项。取消选择不删除行或预留。输入、来源及选择变化后旧预览失效，最终在原事务重验指纹，未选项继续保留。

当前行为由[临床业务流程](../../../architecture/clinical-workflows.md#住院手术最小闭环)与[UI 设计](../../../ui/design.md)拥有。本决策扩展[最终耗材核实决策](2026-10-30-surgery-final-material-reconciliation.md)的录入及私稿恢复方式，保留原净差额、冻结依据和原子事务。

## Alternatives considered

- 只在组件内保留输入：不能恢复刷新或真实卸载后的编辑。
- 把草稿塞入服务端查询缓存：混淆未提交输入与正式业务状态，且不能可靠承担私稿持久化。
- 每种耗材单独提交：改变整台原子边界，失败时会留下部分用量和费用。
- 原回执成功后清空当前所有输入：会删除发送后或其他视图中的新编辑；选择按原快照消费。
- 按单行余量全选或默认释放所有预留：不能正确处理同预留的多个冻结快照，也无法表达保留意图。

## Consequences

两个编辑器共享小型私稿能力，不新增回执状态机或业务 Command。真实入口须同时核对连续添加、恢复和明确选择，HTTP 回读验证使用、预留及费用，组件与双 React 版本合同验证隔离、数量边界、预览失效和较新输入保护。
