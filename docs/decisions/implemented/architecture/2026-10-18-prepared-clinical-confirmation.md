# Agent Note: 门诊待开具项目的防过期确认、独立检查逐项保存点与回执恢复

Status: implemented

## Problem

门诊问诊回答与检查报告可在 Encounter 版本不变时异步到达；若浏览器读取诊疗建议后分步调用“保存草稿”与“正式开具”，既存在新资料已到达却仍开出过期自动建议的竞态窗口，又会因自身草稿写入改变全局指纹而自锁。同时，同类多项独立检查分别对应独立申请与应收账项，若沿用整批全退回滚会丢弃已合法通过的项目，而在网络超时后重新构造请求又会重复产生申请与费用。

## Decision

通过统一的页面确认入口 `POST recommendations/:kind/actions/confirm`（`doctor.recommendations.confirm`）连接人工／自动混合选择、资料防过期核验与按领域区分的事务边界，详细合同见[门诊业务流程](../../../architecture/outpatient-workflows.md)、[检验、检查与报告](../../../architecture/examinations-and-reports.md)与[连续办理私稿与逐项原回执恢复](../../../architecture/clinical-workflows.md)：

1. **混合选择防过期重验与纯人工零模型独立性**：确认请求显式绑定当前 Encounter 版本、目标草稿版本及每行来源（`agent` 或 `manual`）；只要包含任一 `agent` 项目，服务端即在单个 `BEGIN IMMEDIATE` Command 事务内重读负责医生、病例临床资料、权威目录与建议状态，精确核对建议代次、完整资料指纹与已核验项目身份（人工编辑过的 Agent 条目继续保留原建议证明，禁止借微调绕过时效校验）。纯 `manual` 选择不读取推荐状态、不检索指南也不依赖外部模型可用性，但仍完整执行岗位责任、真实目录解析、唯一主诊断、声明式药事安全及双层临床质控校验。
2. **诊断／处方整单原子提交 vs 独立检查逐项 SQLite Savepoint**：门诊主次诊断组与单源整张处方保持整单原子提交，任一条目非法即整单拒绝回滚；检验、放射、病理与功能检查等门诊独立检查则在外层统一通过身份与建议指纹校验后，对每项检查以独立 SQLite `savepoint` 核对已审阅门诊价目快照、保存并签发申请（原单草稿的显式替换放在首个成功项目的 savepoint 内，全部失败则保留原草稿），由最外层统一写入单份审计、Action Trace 与按原请求下标报告逐项成功／确定失败的幂等回执。
3. **会话限定回执恢复与失效建议清理**：该页面组合操作仅向医生认证会话开放，显式排除在 `hisOperationCatalog` 与 Agent Grant 之外（CLI 与页面提案继续调用各领域窄操作）。同窗最多连续准备 8 项私稿并按作用域持久化于 `sessionStorage`（见[临床连续办理私稿与逐项原回执恢复](2026-11-10-clinical-batch-draft-and-receipt-recovery.md)）；响应丢失后通过限定同账号、岗位、Workspace/Epoch、病例与类别的 `GET recommendations/:kind/confirmations/:idempotencyKey` 查询原回执，部分失败行从冻结请求还原回草稿供修正后以新意图提交。指南来源撤回返回 `hidePreviousResults: true` 时客户端立即清除保留的旧自动建议，人工已改字段与移除偏好按临床内容保留。

## Alternatives considered

- **仅在浏览器提交前 GET 建议或只比较 Encounter 版本**：无法拦截 GET 之后、写事务之前新落库的患者回答或报告。
- **独立检查继续整批全有或全无回滚，或由浏览器循环覆盖单草稿发送多条 Command**：前者无故作废同批合法检查，后者易覆盖并发手改且无法形成单份可对账的下标回执。
- **向通用 CLI 回执接口开放页面组合确认**：无谓扩大 Agent 跨项批处理能力面，采用医生会话专属只读回执路由即可满足刷新恢复。

## Consequences

医生可在同一待办面板无缝组合 AI 建议与手工目录条目并一次确认提交：诊断与处方维持整体医学一致性，多项独立检查支持部分成功落库与零重复费用恢复。已正式签发的记录在后续新病史或新报告到达时仅提示可证实的时间先后核对提醒，绝不自动撤回或篡改既有医嘱。
