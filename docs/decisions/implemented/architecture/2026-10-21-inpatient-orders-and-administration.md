# Agent Note: 住院医嘱计划、集中停嘱理由与批次发药库存增量边界

Status: implemented

## Problem

住院长期与临时医嘱需要跨越多日排程、病区护士校对、药房批次发药、床旁实际给药与中途停嘱核停。若复用门诊整单预付费处方或让时钟推进直接写入已完成给药，会制造虚假用药事实；若为住院另建独立库存表，门诊与住院将无法对同一药品批次做并发扣减保护。同时，在连续集中办理场景下，医生逐条填停嘱理由使护士看不到正式停嘱依据，而同一患者的长期多频次执行单共用同一库存批次时，若确认前死锁首版库存版本会让第 2 单必然冲突，若每单盲目取最新库存版本又会静默吞掉外部并发扣库。

## Decision

将医嘱计划、实际发药与实际给药解耦为三层独立事实，并在既有单条 Command 之上构建安全集中停嘱与同批次发药递进机制，详细合同见[处方、医嘱与药事](../../../architecture/orders-and-pharmacy.md)与[连续办理私稿与逐项原回执恢复](../../../architecture/clinical-workflows.md)：

1. **计划、交付与给药三层事实分离及共享批次库存**：`InpatientOrders` 在共享 `CommandExecutor` 事务中维护住院诊断、医嘱、护士校对与执行计划。`Task` 仅表达待执行时点计划；药房发药通过门诊处方 XOR 住院发药单外键在共享 `inventory_lot` 上执行数量与版本 CAS 扣减，原子写入 `InventoryItem`、库存移动、`MedicationDispense` 与 `InpatientBilling` 费用；护士床旁执行才创建引用原请求与实际发药单的 `MedicationAdministration`（声明式适应证、互斥与六种频次排程见[共享声明式药事规则](2026-11-13-shared-medication-safety.md)）。药师与收费员仅消费各自按药嘱或账项裁剪的窄 DTO，不读取无关临床备注或跨岗财务详情。
2. **正式停嘱理由标准挂载与分岗集中核停**：停嘱事务在原医嘱请求的标准 FHIR `Annotation` 中写入带稳定标记 `id=clinmesh-stop-reason` 的理由文本并投影为可选 `stopReason`（无需平行理由表，历史无标记记录保持空值而不从普通临床备注猜测）。医生集中申请停嘱（支持共同理由与逐项覆盖，显式空覆盖拒绝静默回退）与护士集中核停各自复用单条 `inpatient.order.request-stop`／`verify-stop` 与会话私稿恢复：申请停嘱立即冻结后续排程、发药与给药；护士核停取消 `pending` 与已发未给 `dispensed` 计划任务，但保留已发生的发药、库存扣减与费用（退药冲正由独立财务／药房逆向动作承担）。
3. **集中发药仅累加本批已证实成功的库存增量**：药房集中确认生成有界待发队列，不新增服务端批量发药状态机。每张执行单到达队首时重读当前患者药房窄投影核对医嘱、过敏与批次；对共用同一 `inventory_lot` 的后续执行单，将其预期批次版本设为“初始审阅版本 + 本批内已收到完整成功回执（含 `MedicationDispense` 与 `InventoryItem` 余额证明，同幂等键不重复累计）的触及单数”，预期库存设为“初始库存 − 本批已证实成功扣减总量”。一旦遇到外部并发消耗导致版本或余额偏离，立即保留该批次余项要求人工重审，绝不自动切换批次或盲目采用外部新版本。

## Alternatives considered

- **新增服务端跨医嘱批量停嘱／批量发药原子 Command**：破坏单条执行单的局部生效、库存 CAS 粒度与幂等回执合同，并无谓扩张 Agent 写工具面。
- **发药集中确认时一次性写死全部执行单的预期库存版本，或发送时无条件读取最新批次版本**：前者使合法同批次 BID 多时点发药自相冲突，后者绕过人工审阅时的并发安全边界。
- **将停嘱理由仅存在浏览器私稿或新建数据库列，或停嘱时自动回退库存与账项**：私稿无法跨岗位交付给护士与 CLI，自动退库冲账则会伪造尚未发生的实物退药事实。

## Consequences

门诊与住院共享同一套库存批次并发边界，计划、发药、给药与收费各自可审计追溯；医生、护士与药师在高频集中办理中既免去逐条弹窗重复输入，又严格守住单条 Command 的预期版本、外部并发拦截与丢响应原回执恢复（见[临床连续办理私稿与逐项原回执恢复](2026-11-10-clinical-batch-draft-and-receipt-recovery.md)）。
