# Agent Note: 停嘱理由归属与集中核停

Status: implemented

## Problem

医生逐条申请停嘱时重复填写相同理由，护士逐条核停还看不到正式理由。单纯汇总本地表单不能跨岗位提供可信依据；把任意历史 FHIR 备注当作停嘱理由又会混淆来源。集中办理还需要区分已成功、确定失败及结果未知，避免刷新后重复处理或把核停误解为退药退款。

## Decision

医生申请停嘱和护士核停分别集中选择、审阅及确认，使用两个独立动作和私稿绑定；新医嘱校对继续独立。每项复用原 `inpatient.order.request-stop` 或 `inpatient.order.verify-stop`，原事务拥有角色、责任、预期版本、医嘱状态、任务、FHIR 与审计。数量上限、持久选择及原尝试恢复遵循[临床连续办理私稿与回执恢复](2026-11-10-clinical-batch-draft-and-receipt-recovery.md)，不新增批量 API 或跨岗位状态机。

共同理由和逐项覆盖保存在医生动作的私稿中。不存在覆盖表示使用共同理由，显式空覆盖表示尚未填写，不静默替换为共同理由；最终逐项预览后才冻结发送参数。护士读取正式停嘱理由及执行任务影响，不消费医生未提交的本地输入。业务合同由[医嘱生命周期](../../../architecture/clinical-workflows.md#83-医嘱生命周期)拥有。

停嘱事务在原请求的标准 FHIR Annotation 写入 `id=clinmesh-stop-reason`，理由和状态在原事务中一并保存。DTO 只投影该标记的文本为可选 `stopReason`，复用已存在的请求读取，不增加平行理由账或数据库迁移。历史无标记记录保持缺失并说明，不从普通备注猜测；缺失不改变原核停能力。旧回执仍可恢复，不为补字段重写旧历史或新发停嘱。

## Alternatives considered

- 将理由仅保存在医生私稿：护士、CLI 和刷新后读取无法确认已正式提交的理由。
- 从最后一条普通备注推断：备注没有可验证的动作归属，可能是其他临床说明。
- 新建停嘱理由表或列：当前理由已随原请求事务保存，额外存储会形成两份须同步的来源，并扩大迁移及旧库升级范围。
- 新建一个跨医生、护士的批量状态机：两种动作的权限、状态及执行影响不同，现有原 Command 已提供完整事务及幂等恢复。

## Consequences

同患者的重复确认减少，医生逐项最终理由和护士取消影响仍可核对。申请停嘱立即冻结后续任务、发药和给药，核停取消 pending、dispensed 执行，保留已完成执行和既有发药、给药、库存扣减及费用；退药、退款仍由各自原动作拥有。确定失败不回滚前项成功，未知结果先查原回执，恢复不自动提交余项。公开 HTTP 验证理由来源、部分冲突和原键恢复，真实 Web 及 React18/19 Surface 验证跨岗位入口、私稿隔离和对话框可达性。
