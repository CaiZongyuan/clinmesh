# Agent Note: 手术流程指引、费用进度与受限助手

Status: implemented

## Problem

同一手术的首行、步骤与底部动作分别判断进度，使未完成的耗材确认与知情同意互相抢占。通用费用指纹还包含申请版本和收费事实，不能据其失效推断医生改了选型。逐笔登记后再次填写最终用量及术后说明，重复了已有记录；费用只在 DRG 页可见，也使偏离计划后的影响难以发现。正式范围见[手术流程规格](https://github.com/CaiZongyuan/clinmesh/issues/489)。

## Decision

术前当前动作由共享判定拥有，患者工作台与手术步骤使用同一客户端视图状态和正式查询。参数、耗材、同意、护士核对与开始按顺序衔接；选型重新核对依赖真实选型修订及原确认来源，费用推演失效仍保留其独立含义。数量与状态写入继续由原共享 Command 拥有，不放宽版本、说明或审计合同。

医生患者头部与 DRG 页共享查询和缓存，在任意页签保持一行费用进度。未完成手术存在可分组的计划结果时，以计划实施后的参考比较；缺少该结果时回到当前口径。接近阈值用于提醒和发现严格等效候选，不是开具门禁。费用口径和阈值的详细合同见[手术费用与医保说明](../../../architecture/clinical-workflows.md#手术费用与医保说明)。

按计划登记使用已有逐笔 Command 和对应预留；偏离登记仍先形成正式事实，再由独立任务说明本笔与冻结计划、已确认测量及后续余量的关系。任务按实际使用身份去重，派发和发布重验跟进授权及依据，生成与独立核验计入本次住院。模型失败不撤销已登记事实，也不增加完成门禁。申请理由使用独立草稿任务，服务端只提供已确认诊断与最近正式造影报告，正式申请仍由医生提交。

完成核实在打开时以已登记量请求既有预览，默认先展示结果，数量编辑按需展开。规则说明保留与模型文字不同的来源；医生修改或清空后不再被规则覆盖。术后一次确认顺序复用逐条待办 Command，已成功项保留，失败停止后续提交。这只调整输入负担，不改变最终差额事务、人工处置语义或 CLI 必须先预览的合同。

等效关系由版本化合成依据包显式声明，规则只在同类别、同规格、适用兼容且价格更低的候选内筛选。候选池与默认选中材料分开，避免同组产品被同时计入计划。多计划的明确工作稿分别贡献相对原预留的增量，候选、模型与界面共用全住院预计，避免叠加多份完整总额。医生采用或换回建议仍沿原清单保存、确认和预留路径；不允许因费用建议减量、改变规格、类别、诊断或术式。

本决策部分演进[住院 AI 减负](2026-11-02-inpatient-ai-usability.md)、[住院原型组合](2026-11-03-inpatient-prototype-composition.md)与[步骤融合](../feature/2026-11-05-inpatient-ai-step-fusion-and-ui-shell-alignment.md)中的展示和触发取舍，保留其原有业务、资料与模型边界；[最终耗材核实](2026-10-30-surgery-final-material-reconciliation.md)的预览指纹、差额事务和默认保留继续有效。

## Alternatives considered

- 继续分别判断首行和按钮：修改一处后仍可能出现互相矛盾的下一步，不能靠调整优先级长期维持。
- 所有逐笔登记都调用模型：计划内操作已有明确依据，增加延迟和用量却没有新增需要说明的偏离。
- 按费用或规格文字推断可替代品：无法证明兼容或临床等效，因此只接受显式等效组，并保留医生选择。
- 完成前再次手填全部数量和说明：已有登记足以形成默认核实输入，只有差异需要医生编辑；自动预览仍接受服务端完整重验。

## Consequences

TanStack Query 继续拥有正式数据，局部状态只表示当前计划、编辑与未提交输入。UI 的按行、批量和自动预览不新增另一套临床状态机。金额与候选都由程序确定，助手文字不能改写费用或业务事实。模型和后台任务的失败与恢复继续沿既有执行与计量机制；没有可核验计划或支付参考时明确表达缺失，不以预留余额、产品名称或目标病组补造依据。

界面合同见[住院工作台](../../../ui/design.md)，业务合同见[临床流程](../../../architecture/clinical-workflows.md)，验收继续使用公开 HTTP、组件和 Web／React 18／19 ShadowRoot 的受控合成旅程。十阶段业务闭环与完整宽度主题矩阵分别保留可追溯证据；常规旅程只重复受影响阶段的布局组合，完整矩阵可显式复跑，避免截图与几何循环挤占异步业务验收的时限。
