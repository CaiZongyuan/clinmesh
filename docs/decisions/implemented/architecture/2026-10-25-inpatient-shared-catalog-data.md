# Agent Note: 共享目录与 PCI 资料准备保持独立前置

Status: implemented

## Problem

住院目录以固定剂量示例筛选药品，未启用项目缺少可见原因。直接取消剂量限制会失去单位、数量和库存之间的约束；将首例资料准备直接连接病例物化，则会附带门诊挂号、费用或临床执行事实，并与已有 PCI 联合验收重复拥有同一流程。

## Decision

药品、检验和诊断复用已有主数据；药品按具体产品身份及版本映射，检验保留根项目和子项的区别。院内与 Reference 分别在各自数据库分页，候选携带明确缺项；可写身份仅来自唯一、完整的院内配置。旧可用目录保留，查询和正式写入共用准备条件，避免通过旧入口开立缺项项目。具体合同由[临床流程](../../../architecture/clinical-workflows.md#83-医嘱生命周期)拥有。

住院检查价目沿用已持久化合同：完整的 `inpatientInvestigationBilling` 通过院内服务 ID、目录版本及收费快照追溯，独立 `id` 作为可选元数据保留。为其新增必填标识会让旧检验和影像失效，因此读取与开立共同接受原合法形状，不改写旧行或制造补充编号；金额、币种、来源、适用范围和触发条件继续验证。

医生填写本次剂量，页面和服务端复用纯换算函数。明确制剂含量与每次上限取代固定允许剂量枚举；旧数据的建议值保留兼容。直接以声明单位输入无需猜测含量，质量换算则要求明确依据，制剂数保持现有整数库存合同。门诊既有处方规则继续独立验证。

PCI 前置数据通过独立版本和内容哈希提供，原始参考字段、原报价及其不完整性保留，合成院内单位、价格、规则和库存分别标明。管理员以当前 Epoch 和共享 Command 准备资料，目录补缺、基础批次、回执和审计原子提交；重复准备保留既有库存消耗和业务。固定底稿仅供后续病例编写，实际来源和就诊、可执行规则装载、DRG/医保页面及整链验收仍归原联合验收任务。

## Alternatives considered

- 复制门诊全库并全部启用：产生重复 owner，也把尚无住院单位、价格及规则的参考项目当作可开展项目。
- 合并两库所有条目后排序分页：查询成本随参考库增长，总数及分页语义不再对应真实来源。
- 仅把剂量下拉框换成输入框：服务端枚举仍拒绝合法输入，或去掉检查后允许单位和库存数量不一致。
- 启动时物化首例并自动发药、收费：资料准备产生业务副作用，重启与真实操作难以区分，且重复承担联合验收。

## Consequences

首批资料只覆盖固定择期单枚支架路径，其他候选继续显示缺项。药品发药与既有手术耗材实际使用计费复用原 owner，不扩建全院供应链。原始报价分母未知时保持未知，合成收费不能成为真实采购价或地区结算依据。公开 HTTP/Command 验证准备幂等、拒绝和局部业务接入，真实 Web 与 React 18/19 表单合同验证用户可见行为；完整 DRG 规则及整链验收各由对应任务提供证据。
