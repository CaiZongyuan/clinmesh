# Agent Note: 原款退款与费用更正分别追加

Status: implemented

## Problem

分次及组合收款后，费用录入更正与实际资金退回有独立生命周期。把退款直接扣减原费用或覆盖原支付结果会丢失原始含义；结果未知时若不保留资金占用，竞争退款可能超过原款或跨原款重复消费同一退费依据。需求来自 [Issue #269](https://github.com/CaiZongyuan/clinmesh/issues/269) 及其[固定批准规格](https://github.com/CaiZongyuan/clinmesh/blob/e322fef689b009cc0175931b4070b8713c8dedff/docs/spec/2026-10-15-drg-prescription-budget.md)。

## Decision

费用冲减、原款退款和渠道结果分别追加事实。共享 `RefundLedger` 只管理反向资金及其来源和结果；业务 owner 在同一 Command 事务读取原款成功结果、就诊归属和退费依据，重验原款余额与跨原款依据额度。未知退款同时预占二者，确定拒付释放；确定成功计入已退，原尝试的未知结果仍保留。

原款使用类型及 ID 引用已有资金事实，不为共享退款复制新的原款余额。组合原款按冻结的方式顺序反向分配，并扣除该方式已成功及未知的退款。门诊预览冻结费用版本、原款余额版本、金额、岗位上下文及渠道规则；人工审阅后确认，退款尝试保存后续查询计划。恢复只查询原尝试，回执处理响应丢失，事务和 expected version 处理并发；临床执行及放行由原 owner 保持。当前流程及存储合同分别由[收费与支付](../../../architecture/clinical-workflows.md#85-收费支付与退款)及[存储与事务](../../../architecture/storage.md#门诊收款记录)拥有。

门诊费用冲减、退款确认及原退款查询复用受信会话的写意图恢复模块，使刷新后的未知写结果沿用同一回执规则，避免各操作独立保存不完整输入或重新生成意图。原病例与对话框内均提供恢复入口，具体会话绑定及页面合同由上述收费 owner 维护。

## Alternatives considered

- 覆盖原支付或费用金额：实现较短，但失去原始收款、应收与冲减的独立含义，也无法解释未知渠道结果。
- 退款一发起便扣减实收：账单看似即时平衡，但拒付和继续未知会被误认为资金已退。
- 各工作流独立实现退款状态机：短期接线容易，长期会出现原款余额与恢复规则差异。共享退款资金内核，保留来源 owner 的权限及业务门禁，能够分别承担两类职责。

## Consequences

账单净应收从原费用及冲减投影，净实收从成功原款及成功退款投影。原款、冲减和退款记录仍可分别核对；退款不会撤销临床或库存事实。共享引擎允许后续住院来源接入，但不会自动开放结算或归档后的权限。调用者须在持有共享 Command 事务时提供已经核实的来源和依据，来源类型本身不构成授权。

## Validation

公开 HIS HTTP 与临时文件 SQLite 验证冲减、原款部分退款、拒付、未知预占及恢复、跨原款额度、回执重放、角色拒绝、刷新和重启后的原尝试。收费页和 CLI 通过同一合同办理，并保留预览审阅与原回执恢复；浏览器使用合成病例和文字断言。

真实 Web 入口及 React 18/19 Surface ShadowRoot 合同分别在冲减、退款确认、原退款查询服务端提交成功后丢弃响应，再刷新页面并恢复原回执，验证各命令仅发送一次、最终只有一笔冲减和一笔退款。写意图测试同时验证三种命令缺少回执时保留目标、完整输入及原键重放，以及会话变化、非法持久数据和并发挂载的拒绝规则。
