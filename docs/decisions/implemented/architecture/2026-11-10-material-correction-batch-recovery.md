# Agent Note: 既有耗材连续更正与顺序依据恢复

Status: implemented

## Problem

同一手术的多笔已用耗材需要反复展开、修改并单独确认，临时输入不能在刷新后恢复。各笔更正既有独立原子事务，却共享手术申请版本；直接复用批次开始时的版本会使后项必然冲突，直接使用最新版本又可能绕过原预留消耗变化的人工核对。同种耗材还可能有不同原使用、费用和预留来源，不能只按材料编号合并。

## Decision

以原使用身份建立同手术、同动作的有限更正清单，每笔保留原事实及独立修改、共同理由与逐项覆盖。集中检查后顺序复用既有单项更正 Command，不增加批次事务。原 Command 继续拥有原使用更正、精确费用冲正、可选替代使用及预留消耗变化；其成功不能解释为现金退款、器械取出或实际库存退还。漏记新耗材由独立业务入口拥有。

仅把前项成功响应中的本计划版本用于尚未发送的后项，已发送的输入和幂等标识不改写。每项保留审阅过的预留关联及版本；前项改变后项所依赖的预留时停止后续发送，展示更新后的消耗与余量，要求重新核对。外部变化沿原 Command 的版本冲突处理，不用当前读模型的最新值静默越过冲突。

人工输入与原尝试关联保存在绑定完整身份、患者、住院、计划及执行的私稿，读入、发送和结算均核验命令归属。关闭或刷新不丢失未提交输入，退出清除，丢弃须明确确认；存储失败停止新写。成功只消费对应原行修订，确定失败保留输入，未知停止队列并通过共享住院写意图恢复原回执。原回执结算后仍需用户重新核对余项，不自动继续，也不重复冲正已经成功的原使用。

当前业务合同由[临床流程](../../../architecture/clinical-workflows.md#住院手术最小闭环)拥有，界面合同由[UI 设计](../../../ui/design.md)拥有。本决策复用[手工预留连续办理](2026-11-10-manual-reservation-batch-recovery.md)的原回执恢复边界，增加共享手术版本和共用预留的顺序依赖规则。

## Alternatives considered

- 新增整批更正事务：会把原本独立的逐笔事实改为整批回滚，重复现有更正与审计边界。
- 按材料编号合并原使用：会丢失逐笔实际数量、冻结价格、原费用及预留来源。
- 为所有项目冻结相同手术版本：首笔成功即使后项版本失效，不能正常连续办理。
- 发送时替换为最新手术和预留版本：可能绕过外部变化或前项消耗变化所需的人工核对。
- 未知时重新生成整批幂等键：可能重复更正已成功但响应丢失的原使用。

## Consequences

集中办理保留确定的逐项部分成功，结果摘要与原历史必须一致。公共 HTTP 与真实 SQLite 回读验证两笔更正、共用预留旧依据拒绝、费用冲正及重启原回执；组件和双 React 真实浏览器验证私稿隔离、理由覆盖、选择范围、未知暂停及窄容器操作。逐笔更正的独立事务继续由服务端重验，不把客户端清单作为新事实来源。
