# Agent Note: 住院报告清单与原写意图分段结算

Status: implemented

## Problem

住院医生集中确认报告时，各报告仍由原 Command 独立提交。当前窗口的实际阅读资格会在关闭或切换上下文后失效，已经发送的原操作却可能仍待查明。住院共享写意图同时服务送检、取消和其他动作，若恢复时仅清除通用意图，报告清单可能保留已经成功的旧行；若把旧清单全部替换，又可能删除报告改版后准备的新修订。

## Decision

报告清单保存完整账号、行动身份、患者与住院范围，以及人类选择的原申请、报告和版本快照。当前窗口单独保存阅读及影像实际显示资格，关闭或失去上下文后撤销。具体交互和数量边界由[住院报告连续阅读与集中已阅](../../../architecture/clinical-workflows.md#住院报告连续阅读与集中已阅)维护。

原 `inpatient.investigation.acknowledge` 继续拥有权限、版本与唯一已阅事实。共享住院写意图保留原 Operation、输入和幂等键，报告专用结算在解除原意图前，先验证原响应并持久结算原范围的对应行修订。成功只移除该修订，迟到回执不消费新的报告版本。其他动作保留各自结算与恢复合同。

报告已阅的响应是原住院检查投影。成功依据包括同住院、同申请和报告版本、申请增版及已阅身份；ServiceRequest、Task 与报告资源不因确认已阅而增版。不能复用取消或重试申请所需的执行资源增版判断。结果不明时停止余项，查明原操作后仍须逐份恢复本轮阅读资格并重新明确核对；原成功不授权接续旧计划。

## Alternatives considered

- 为集中已阅新增服务端批量接口：原单项 Command 已有权限、幂等和审计，客户端集中核对不需要另一套状态机。
- 通用写意图恢复成功后只清除意图：不能保证原报告清单已经结算，会留下重复办理入口。
- 沿用取消或重试的成功证明：两类动作更新的资源不同，会把合法已阅回执误判为未知。
- 关闭窗口丢弃清单，或持久保存已显示标记：前者丢失人工准备，后者无法证明当前窗口真实显示成功。

## Consequences

选择清单、原写意图和窗口阅读资格分别承担不同生命周期。恢复和迟到回执必须先完成原范围的持久结算，存储异常时保留阻断；成功、确定拒绝与未知分别反馈。公开 HTTP 验证唯一已阅事实、版本与重启原键重放，真实岗位及 React 18/19 验证阅读门禁、窗口生命周期和原回执恢复，短录屏绑定最终干净提交。
