# Agent Note: 五类开具窗口共用两栏目录与填写布局

Status: implemented

## Problem

诊断、药品、检验、放射与病理的开具入口已有检索、包装选择、草稿和人工确认合同，但各自组合目录与填写区域。窄工作区里，目录和字段上下堆叠会让换项目需要反复滚动；单独修正文留白又容易让已有表单出现双重内边距。已批准的[门诊细节规格](../../../spec/2026-11-03-outpatient-detail-polish.md)要求保持业务流程并统一开具体验。

## Decision

五类开具窗口通过 `OrderComposerLayout` 组合目录与项目详情，左侧搜索和候选始终可用，右侧填写所选项目，底栏统一呈现下一步与加入操作。左右区分别滚动，宽度以弹窗内容容器决定：空间足够时采用 5:6 两栏，容器过窄时上下排列，适配 standalone Web 与 React 18/19 ShadowRoot。

候选采用同一整行按钮和选中标记；原有不可用原因继续可见。药品包装是独立表单控件，不嵌套在选择按钮内；修改包装与正式加入处方仍按原选择和确认合同执行。布局组件只组织 React 内容，不拥有查询、临床草稿、Agent 目录身份或提交状态。住院证仅含病区与原因，保留简短表单。

共享 Dialog 样式为未声明留白的直属正文提供默认内边距，显式布局和已有分区表单继续拥有自身留白。具体样式与交互合同由[临床 UI](../../../ui/design.md)拥有。

本决策部分取代[诊疗开具工作区](2026-10-19-clinical-order-workspace.md)关于首次开具时目录与字段直接融合在业务页的决定。其外层两阶段视图、正式记录、待开具清单及事务边界继续保留。

## Alternatives considered

- 各窗口分别调整：局部修改较少，但候选状态、底栏、窄容器和正文留白会继续漂移。
- 继续在一列中展示目录和填写项：容易实现，但长目录与长字段无法同时观察，换项目会改变滚动位置。
- 使用固定视口断点：standalone Web 可用，嵌入 Surface 时宿主宽度与真实内容宽度不一致。
- 将检索、草稿和提交一起抽入通用表单：统一更多代码，却会混合各类项目不同的真实业务合同。

## Consequences

窗口共享结构和候选交互，各页面保留原有检索、包装身份、可用性、草稿、人工确认与错误恢复。组件回归验证整行选择与禁用项目，浏览器合同验证真实两栏、字段可达、长候选、键盘以及 React 18/19 兼容性；测试通过不替代与已批准原型的结构对照。
