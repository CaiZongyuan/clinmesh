# Agent Note: 集中送检沿用单申请事实与原尝试恢复

Status: implemented

## Problem

护士为同一患者逐条送检需要重复核对和确认。集中办理能减少重复操作，但送检不会立即改变申请版本或状态，响应丢失后仅凭 `issued` 可能再次送检；清写意图与消费草稿之间的中断也可能留下可重复提交的项目。

## Decision

集中核对有界的同住院申请，逐项执行既有送检 Command。资格与成功结算都核对原申请的 `sent` 事实，沿用服务端版本、权限、幂等及审计，不增加批量状态机或公开批处理工具。当前流程合同由[临床业务流程](../../../architecture/clinical-workflows.md#82-住院闭环)拥有，界面由[住院工作台](../../../ui/design.md#住院工作台)拥有。

人工选择和原尝试使用独立、严格验证的私有草稿，完整绑定账号、Actor、患者、住院与送检动作。发送前冻结单项 Command 与幂等键；写入器在清原写意图前持久结算该尝试，成功只消费原修订。未知结果停止后续发送，通过原回执或原 Command 恢复；恢复不会自动继续余项，须重新核对。切换患者或岗位后，迟到结果只能结算原绑定，不能消费新上下文的草稿。

## Alternatives considered

- 新增整批事务：会改变每份独立申请已有的执行与恢复边界，不能保留明确的逐项成功结果。
- 按页面剩余项换键重试：送检后的申请可能仍为 `issued`，无法证明原写入是否成功，会引入重复尝试。
- 清写意图后再由组件删除草稿：页面卸载或存储失败会留下已成功项目的待发送状态。结算放在写入器持久化边界，失败时保留原意图。
- 将人工选择写入服务器状态缓存：会使 Query 同时承担未提交输入和正式事实，且无法可靠隔离账号、岗位与患者。

## Consequences

送检仍只产生送检关联和受理调度，受理、执行、报告与费用继续由原 owner 决定。存储不可用时阻止发送，不能通过丢弃草稿绕过未知写意图。需要维护草稿绑定、原回执恢复、部分成功和迟到响应的公共组件及 HTTP 合同；对话框同时验证 React 18/19 和窄容器。无新增服务器批量 API、CLI 或持久化表。
