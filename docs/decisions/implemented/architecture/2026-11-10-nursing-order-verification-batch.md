# Agent Note: 新医嘱集中核对与逐项原回执恢复

Status: implemented

## Problem

病区护士逐条校对新医嘱需要反复确认。将新医嘱与待核停医嘱作为同一待办，或在一次点击后临时循环生成新幂等键，会混淆动作与恢复归属；刷新和响应丢失还可能使已成功项重复校对，或把其他患者的选择带入当前住院。

## Decision

新医嘱集中校对只编排原单项 `inpatient.order.verify`，不新增批量状态机。原事务继续拥有每项医嘱版本、校对记录、执行计划、FHIR 和审计；业务边界由[医嘱生命周期](../../../architecture/clinical-workflows.md#83-医嘱生命周期)拥有。本决策扩展[计划与实际执行分离](2026-10-21-inpatient-orders-and-administration.md)，不改变发药、给药或实际服务执行的条件。

未提交选择与审阅快照按账号、完整 Actor、患者、住院和动作隔离，关闭窗口、切页、切患者和刷新后恢复；退出登录清除。清空选择只取消勾选，丢弃全部未提交输入需要明确确认。冻结清单有公开的20项上限，每项预先持久化原参数、预期版本和独立幂等键；存储失败阻止发送并保留输入，损坏或归属不符的记录不能发送。

发送前核对完整已选清单，变化项提示重新核对；成功只消费原行修订，保留后来编辑。确定拒绝逐项保留原因和输入，其他成功不回滚。结果未知停止后续项，沿共享写意图读取原回执；只有可信的原回执不存在才用原参数和原键重发。恢复不自动继续其余项目，用户重新核对后才能办理。新医嘱选择不包含待核停项目，PRN校对不等同发起按需执行。

## Alternatives considered

- 新建批量校对 API：现有单项 Command 已提供完整事务及幂等回执；当前需求只需要有界编排与逐项结果，新协议增加了重复的状态和授权入口。
- 临时循环单项按钮：发送前没有完整冻结清单和幂等键，刷新后难以分清未发送与结果未知项。
- 合并新医嘱与停嘱核对：两种动作的前置状态和任务影响不同，无法用同一确认表达。
- 对未知结果生成新键重试：可能重复办理已成功事务，失去原尝试的恢复依据。

## Consequences

界面减少重复确认，同时保留每条原事务及真实执行事实。持久私稿是人工选择和尝试的 owner，服务端临床结果继续由 TanStack Query 拥有。公开 HTTP 与临时 SQLite 验证部分失败、服务重启后的原回执及没有重复计划；组件和真实 Web、React18/19 Surface 分别验证身份隔离、存储失败、重审和可达性。短录屏绑定精确代码提交，只演示本票的真实岗位入口。
