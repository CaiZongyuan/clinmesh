# Agent Note: 临床连续办理会话私稿、逐项原回执恢复与跨患者具名续办

Status: implemented

## Problem

门诊与住院各岗位普遍需要在同一患者内连续准备多项操作（诊断、处方、独立检查开立／取消／重试、报告已阅、住院医嘱开立／校对／停嘱／给药、送检、耗材预留与更正），以及在病案审核、病案归档、医保核定和患者库开始就诊时逐份连续处理不同患者。若维持“一窗一条、关窗丢稿”会造成大量重复检索点击；若新建服务端跨项／跨患者批量写接口会破坏单条业务的局部生效、库存版本 CAS 与窄 Agent 工具边界；若在组件内存循环点按钮、网络超时后换新幂等键重发，或点击“下一位”时按实时队列自动跳转自动提交，则会导致刷新丢稿、重复开单扣库或因并发队列变动误操作另一名患者。

## Decision

在既有共享 Command 与单条幂等回执之上，建立客户端作用域私稿、三类提交恢复模型与跨患者具名冻结续办机制，详细合同见[连续办理私稿与逐项原回执恢复](../../../architecture/clinical-workflows.md)、[存储与事务](../../../architecture/storage.md)、[FHIR 与共享 Command](../../../architecture/fhir-and-commands.md)及[前端架构](../../../frontend-architecture.md)：

1. **`sessionStorage` 严格作用域私稿与有界分页**：未提交选择、行编辑稿与勾选偏好按 `账号 + Workspace/Epoch + 完整 Actor/岗位 + 患者 + 就诊/住院 + 动作` 隔离保存在 `sessionStorage` 并经运行时 schema 校验（存储写失败阻断新发送，读取损坏保留原文并仅在核实无原完成回执后允许用户显式确认丢弃；放射影像与病理切片的真实阅片显示资格仅留存当前窗口内存，不落入 `sessionStorage`）。多页列表每页 10 项、“全选本页”仅限当前可见页，单次连续上限 20 项（门诊目录开具 8 项，手术完成核实 100 行）；退出登录延迟补清理与未决意图裁剪保留遵循[住院写入与私稿清理恢复](../bug-fix/2026-10-20-inpatient-command-intent-recovery.md)。
2. **按业务原子性划分的三类提交与 `404` 原回执恢复**：
   - **整单原子确认**（门诊诊断组、单源整张处方）：同窗连续编辑，存在未保存行改动时锁定确认，经单次 `doctor.recommendations.confirm` 全有或全无提交。
   - **单回执逐项 savepoint**（门诊独立检查开立）：外层统一核验身份与建议指纹，内部逐项 SQLite savepoint 独立计价签发并按原下标返回逐项结果（见[待开具项目的防过期确认](2026-10-18-prepared-clinical-confirmation.md)）。
   - **冻结队列逐项单 Command**（住院医嘱／校对／核停／发药／给药、送检、报告已阅、检查取消／重试、耗材预留与更正）：确认前将每项不可变载荷与原 `idempotencyKey` 与未发私稿分键落盘，队首顺序发送并在持久层先推进前序成功项触发的临床 revision、消费对应私稿行再清除意图（同批次发药版本递进与停嘱理由归属见[住院医嘱计划与批次发药](2026-10-21-inpatient-orders-and-administration.md)，门诊合并收款见[门诊合并原款](2026-11-10-outpatient-multi-charge-collection.md)）。
   - **未知结果原回执恢复**：遇到超时、`503` 或响应不可解析时立即停发后续待办并锁定新提交，在同身份作用域查询原回执（即使病例已转为只读仍允许查清既有未知意图），仅在明确返回 `404 COMMAND_RECEIPT_NOT_FOUND` 时原样重放原载荷与原幂等键，恢复后余项必须经人工重新审阅确认。
3. **跨患者具名冻结续办**：病案审核／归档、医保核定与患者库开始就诊（接入 `registration.synthetic-case.start` 并仅按本页有界详情核实可开始状态）在当前患者确认成功后展示具名“下一位”入口，冻结目标患者／病例／住院身份、原队列与页码；点击时重读核验该特定目标资格（若已被他人处理或状态变化则提示并刷新列表，绝不在一次点击内静默偷换目标），导航后仍须独立审阅确认，绝不自动跳转或自动提交。

## Alternatives considered

- **为各类临床与跨患者操作新增服务端批量写 API**：扭曲独立医嘱、库存 CAS 与单病例审计边界，成倍扩张公开写接口。
- **仅在 React 组件内存维护待发数组，或超时后生成新幂等键重提**：组件卸载或刷新即丢失已发队列身份，换新键重提必然造成重复医嘱与重复扣费。
- **“下一位”动态取当前列表首行或预扫全库求下一合格患者**：并发变动会导致按钮显示姓名与实际跳转患者不符，全库预扫则把单页办理退化为全表详情读取。

## Consequences

高频多条开立、校对、发药与跨患者审阅操作可在单窗口或具名衔接中顺畅完成且跨刷新不丢稿；网络中断或服务重启时多一次显式原回执查询与余项重审点击，换取零重复执行、零跨患者串稿与严格状态所有权隔离。
