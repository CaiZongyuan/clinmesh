# Agent Note: 临床连续办理私稿与逐项原回执恢复

Status: implemented

## Problem

门诊与住院多岗位工作台普遍存在同患者连续准备多项临床操作（诊断、处方、独立检查申请／取消／重试、报告已阅、住院医嘱开立／校对／核停／执行、检验送检、手术耗材预留与更正）的日常场景。若延续“一次弹窗只落一条、关闭即弃置输入”的交互，操作者需反复重开目录且刷新即丢稿；若改为新增整批原子写接口，则会改变既有单条业务的部分成功语义、库存与版本 CAS 边界及 Agent 窄能力面；若在浏览器内存循环调用单条按钮或在网络超时后换新幂等键重试，又会在刷新、退出或响应丢失时造成重复开立、重复扣库或跨患者串稿。

## Decision

连续办理建立在既有共享 Command、服务端回执与前端会话私稿之上，按业务原子性分为三类执行模型，不新增通用批量写 API，也不把未提交草稿写入 TanStack Query：

1. **客户端会话私稿与分页隔离：** 未提交选择、行编辑稿与勾选偏好保存在 `sessionStorage`，严格绑定 `账号 + Workspace/Epoch + 完整 Actor/岗位 + 患者 + 就诊/住院 + 动作`，读取时做运行时 schema 校验；写入失败阻断新发送，读取损坏时保留原文并禁止自动覆盖，仅在核实原完成回执后允许用户显式确认丢弃坏稿。多页列表保持每页 10 项、单次批量上限 20 项（门诊目录开具上限 8 项，手术完成核实上限 100 行），“全选本页”只作用于当前可见页。阅片窗口中的放射影像与病理切片已阅显示资格证明保持当前窗口内存态，不写入或从 `sessionStorage` 选择私稿恢复。服务端退出登录清理未提交私稿，存储受限时的延迟补清理与未知原尝试保留边界由[退出清理恢复决策](../bug-fix/2026-11-10-inpatient-draft-discard-recovery.md)拥有。
2. **三类提交与部分成功边界：**
   - **整单原子确认（门诊诊断组、整张处方）：** 同窗连续添加并按稳定行身份保留未保存编辑，有未保存行编辑时阻止正式确认与自动回填覆盖；一次 `doctor.recommendations.confirm` 整单校验并提交，任一项非法则整单拒绝。
   - **单回执逐项 savepoint（门诊三类独立检查开立）：** 外层统一校验身份与建议指纹，每项以 SQLite savepoint 独立计价与开立，单份回执按原下标返回成功或失败，详见[独立检查逐项确认决策](2026-11-09-independent-investigation-confirmation.md)。
   - **冻结队列逐项单 Command（住院医嘱开立／校对／执行、送检、报告已阅、检查取消／重试、耗材预留与更正）：** 确认前为每项冻结不可变 Command 载荷与原 `idempotencyKey` 并与未提交私稿分键持久保存；队首逐项顺序发送，某项确定业务拒绝时保留前序已完成事实并将失败项留回草稿重审。住院医嘱开立的费用预计绑定生成时的待开集合修订，草稿增删改后旧预计立即失效；术后耗材逐笔更正按前序成功回执顺序递进 `surgeryRequest` 预期版本，共享预留变化时立即停止后续项目（同库存批次发药的版本递进见[集中发药库存增量决策](2026-11-10-inpatient-dispense-stock-progress.md)，停嘱理由归属见[停嘱理由与集中核停决策](2026-11-10-order-stop-batch.md)，跨患者具名续办见[具名连续办理决策](2026-11-10-cross-patient-continuation.md)，多费用合并收款见[门诊合并原款决策](2026-11-10-outpatient-multi-charge-collection.md)）。
3. **前序修订结算与未知结果原回执恢复：** 持久写入层先推进前序成功项触发的临床／病例 revision 并消费对应私稿行，再清除已发送意图，不依赖弹窗或页面组件仍挂载。遇到超时、`503` 或响应不可解析等未知结果时立即停止后续待发项，冻结新提交入口，在同身份作用域下查询原回执（通用 `GET /api/his/v1/command-receipts?operationId=...&idempotencyKey=...` 或限定医生 Session 的 `GET .../confirmations/:idempotencyKey`）；仅在明确返回 `404 COMMAND_RECEIPT_NOT_FOUND` 时才重放完全相同的原载荷与原幂等键，查询恢复后余项须经人工重新审阅确认，不自动接续旧队列。只读上下文门禁与原回执恢复分离，病例变为只读后仍允许查询结清先前已发出的未知意图。

本决定推翻早期门诊弹窗“一次一条、未确认关闭即弃置”的临时约束，并在[住院医嘱计划与给药分离决策](2026-10-21-inpatient-orders-and-administration.md)的单条事务边界及[共享开具工作区决策](2026-11-03-shared-order-composer.md)的双栏结构上补齐跨刷新私稿与原回执恢复。当前存储与业务合同归[浏览器未提交私稿](../../../architecture/storage.md#浏览器未提交私稿)、[幂等与回执](../../../architecture/fhir-and-commands.md#65-idempotency)和[连续办理私稿与逐项原回执恢复](../../../architecture/clinical-workflows.md#连续办理私稿与逐项原回执恢复)。

## Alternatives considered

- 为每类岗位动作新建服务端批量原子 Command：会破坏独立医嘱、执行单、送检与报告的逐项生效和库存／版本 CAS 语义，并成倍扩大公开写接口与 Agent 能力面。
- 仅在组件内存保存多选并循环触发单条按钮：弹窗关闭、刷新或卸载后即丢失待发队列与原幂等键，且迟到回调易串入已切换的患者。
- 网络结果未知时生成新幂等键重提或自动清空坏稿：无法判断首次请求是否已落库，会导致重复开立、重复扣库或误删尚未提交的人工输入。
- 将未提交选择写入 TanStack Query 缓存：混淆正式服务端状态与客户端临时工作稿，违反状态所有权规则。

## Consequences

操作者可在同一窗口连续准备多项临床操作并在跨刷新后恢复草稿，同时完整保留既有单条 Command 的权限、预期版本、幂等回执与审计不变量。未知结果恢复增加一次显式查询与余项重审点击，换取丢响应、重启和退出重登场景下的零重复执行保证；公开 HTTP 合同与真实 Web / React 18·19 Surface 浏览器回归共同覆盖正常连续提交、部分冲突、未知回执恢复及跨患者／跨岗位隔离。
