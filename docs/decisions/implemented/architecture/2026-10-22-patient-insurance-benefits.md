# Agent Note: 患者医保待遇使用共享计算与追加补偿账

Status: implemented

## Problem

普通门诊和住院都需要解释基金、个人账户与患者负担。若把医保当作现金方式，账单无法区分待遇和实收；若只允许每次就诊一份结算，检验缴费后新处方不能继续享受待遇。撤销覆盖账户余额还会抹去同年后续就诊的真实影响。

## Decision

由共享 InsuranceService 根据各场景提供的真实费用及明确目录计算待遇，门诊和住院共用患者年度个人账户，分别累计各自起付和基金限额。费用和现金保留原 owner；待遇只提供覆盖额，临床放行仍由原 Workflow Command 执行。

预览冻结费用及目录指纹、受信岗位、虚拟日历年和账户版本，确认重新读取依赖。门诊逐批处理尚未有效分配的费用，保留检验与后续药品的独立结算。年度首次结算固定合成方案，取消不释放切换方案的入口。

撤销追加原结算的逆向影响，并以唯一原引用防止重复补偿。撤销版本绑定原结算年度，读取同时提供当前年与原结算年度余额；虚拟时间跨年不能改变原补偿的账户归属。原待遇、资金和后续余额影响均保留；已经放行的费用产生补收，不回退检验或发药状态。页面写入复用既有受信会话意图及 receipt 恢复机制，使丢失响应的重试保持原键和原目标。

## Alternatives considered

- 将医保放入 payment tender：会把患者待遇当作已收资金，退款和临床放行难以追溯。
- 门诊与住院各维护一个待遇服务：同一患者个人账户和并发版本可能分叉。
- 每个就诊只保留一份当前医保状态：后续处方会使已付检验待遇失效，或需要覆盖历史结算。
- 撤销时把账户重置到原快照：会删除该结算之后的其他就诊影响。
- 因为待遇撤销而回退临床进度：财务更正会重复触发实际检查或发药，无法反映已经履约的事实。

## Consequences

待遇与现金可以独立核对，原费用、分配和补偿可追溯。公开待遇查询保留成功与拒绝的读取审计；Command 内部返回投影沿用原事务及动作审计。共享账户版本使竞争的预览明确失效；费用与目录映射缺失时拒绝计算，不自动推测地区政策。当前是两套固定合成参数，不宣称地区医保平台申报或院方 DRG/DIP 支付。

详细合同由[医保模拟](../../../architecture/clinical-workflows.md#86-医保模拟)、[待遇存储](../../../architecture/storage.md#患者医保待遇记录)和[预览与提交](../../../architecture/fhir-and-commands.md#66-预览与提交)拥有。验证使用合成 Provider、公开 HTTP 和文件 SQLite，覆盖整数分、年度限额、幂等竞争、两阶段费用及放行后补收，并由真实收费页面及 React 18/19 ShadowRoot 审阅弹窗验证入口。
