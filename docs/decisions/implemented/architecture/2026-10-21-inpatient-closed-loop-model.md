# Agent Note: 住院闭环的分层状态、床位互斥与岗位门禁模型

Status: implemented

## Problem

门诊闭环把 `Encounter.status` 当作唯一生命周期事实，这对一次完诊即结束的就诊成立。住院就诊跨越数天，中间行政状态密集：入科、转科、待出院、已出区、待清床、召回；床位占用有强互斥语义。若把这些状态压缩进单一 `Encounter.status`，会破坏 FHIR R5 `Encounter.status` 的标准取值合同，原子转床、占用冲突、出院门禁与召回审计都无法表达。

真实医院的出院处理、财务结算、清床与病案归档由不同岗位分担。合并为单一"出院"动作会把临床、财务、床位与病案责任压进一个命令，无法审计，也无法表达"未出院处理不能结算、未结算不能清床"的业务门禁。

住院诊疗按日推进：床位费按日计、长期医嘱每日产生执行时点。真实等待既不可测试也不可演示；若把时间推进建模为医院岗位能力，会污染岗位边界。

## Decision

需求与验收由[住院闭环规格](../../../spec/2026-10-20-inpatient-closed-loop.md)拥有；本 Note 记录其架构取舍的动机与后果。

- 分层状态模型：`Encounter.status` 只表达 FHIR R5 标准生命周期；住院行政状态使用有明确取值约束的扩展字段与独立任务表达（入科、转科、待出院、已出区、待清床、召回），关键操作全程生成审计记录，行政状态不反向写入标准生命周期取值。
- 床位所有权是领域互斥事实：床位同一时刻只被一次有效住院占用，再次分配返回业务冲突；转床与换床以原子命令完成，不产生中间占用状态。`Encounter.location` 仅作为互操作投影，不参与所有权判断。
- 岗位边界：新增住院医生、病区护士、病案人员；登记员、药师、收费员复用既有岗位并增加住院语义入口；administrator 保持平台管理者边界，不进入医院业务岗位。
- 虚拟时间推进是场景控制能力，不属于医院岗位：推进过夜触发床位费与当日到期长期医嘱执行任务，测试可显式推进到任意住院日；衔接保持既有 Workspace/Epoch 隔离。
- 出院处理 → 财务结算 → 清床 → 病案归档是四个独立门禁动作，前一动作完成是后一动作的前置；结算按预交金与逐项费用账多退少补，冲正保留原始记录并形成关联；召回仅在规定状态窗口内可用并生成完整逆向事件。
- 手术取最小闭环：申请 → 术前准备 → 执行记录 → 术后医嘱；术前检查核对与知情同意签署完成前不得执行。病案首页的手术操作取自执行记录而非申请，编码审核通过后才能归档；诊断与操作编码为 DRG 只读投影预留事实位置，本次不实现分组。

## Alternatives considered

- 把住院行政状态压缩进 `Encounter.status` 单值：破坏标准生命周期合同，转科与召回沦为隐藏状态机，门禁与审计失去挂载点，被拒绝。
- 用 `Encounter.location` 历史表达床位占用：location 是互操作投影，写入时序无法保证原子互斥，冲突检测需要额外锁且审计分散，被拒绝。
- 真实时钟加可注入时钟测试：演示与测试要等待真实天数，快进语义分散在各业务命令里；集中到场景控制一处推进更可审计，被拒绝。
- 单一"出院"聚合命令：任一环节失败都要补偿回滚，与共享 Command 模块的原子语义冲突，四种责任也无法分别授权与审计，被拒绝。
- 进入本需求即建设手术室排班、麻醉监护采集与耗材供应链：[DRG 前置研究](../../../research/2026-10-20-drg-operations-prerequisites.md)指出"本次实际实施操作"事实才是分组分析的前置条件，完整套件后置，被拒绝。

## Consequences

行政、财务、床位和病案分别保存正式事实，FHIR 资源保存标准生命周期与互操作投影；门禁、虚拟时间及当前范围由[临床业务流程](../../../architecture/clinical-workflows.md#82-住院闭环)拥有。各子流程的事务、版本和只读限制由对应[住院实现决策](2026-10-20-inpatient-admission-owner.md)及其关联 Note 说明，需求验收仍只由上述规格拥有。
