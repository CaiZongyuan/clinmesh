# Agent Note: 门诊分次收款保留原支付尝试与追加恢复结果

Status: implemented

## Problem

原门诊支付把一次成功收款等同于费用全额完成，无法表达分次及组合方式。结果未知后若重新收款，可能重复入账；若覆盖原 outcome，又会丢失最初的不确定结果和查询依据。既有检验与药房流程仍须由原临床 owner 推进。

## Decision

在现有 Charge Record 上增加分配、方式及原尝试的唯一追加结果。账单从原费用和有效成功结果计算实收及余额，保持只读；Payment Ledger 负责资金事实查询，Workflow Command 负责原临床放行。确认及查询恢复均在同一 Command 事务内提交账务、FHIR、审计和 outbox，累计成功金额达到原应收后才放行。

未知支付只能查询原尝试，未查明前阻止重复收取。模拟查询计划在创建尝试时冻结；历史未知保留未知，不由迁移猜测外部结果。原 outcome 不被修改，确定查询结果以唯一原 payment ID 追加，回执与版本防止重复执行。历史分配只在原费用来源可唯一确认时回填，歧义使迁移回滚。

资金余额与历史列表采用独立读取范围：余额始终聚合全部成功分配，历史按页读取并批量加载方式。恢复直接定位原 payment ID，使写事务的读取成本不随历史条数增长；部分收款仍在原队列时保留页码与选中费用，避免后续收款落到另一患者。

## Alternatives considered

- 新建可编辑 Invoice 与余额：会与现有 Charge Record 和交易形成两个权威，增加同步与修复状态。
- 每次查询创建新支付：无法区分查询原结果与再收一次，可能重复累计资金或重复临床放行。
- 将未知直接重置为失败或成功：没有渠道证据，重试和迁移都会制造错误资金事实。
- 支付模块直接复制检验和处方状态机：后续临床门禁容易在不同入口漂移。
- 返回全部历史再由页面切片，或恢复时扫描整单：响应和事务成本持续增长；静默截断则使旧未知支付失去可达入口。

## Consequences

原尝试可追溯，拒付可重新预览，未知可跨刷新和重启恢复；部分收款和未知处方须在原收款链路解决后才能撤回。挂号应收显示为未收，既有兼容检验与药品收款继续使用此账本；患者待遇由[独立医保内核](2026-10-22-patient-insurance-benefits.md)分配，保持现金事实归属。零价历史保持可读，新显式支付方式金额仍须为正。

当前合同由[临床流程](../../../architecture/clinical-workflows.md#85-收费支付与退款)、[存储](../../../architecture/storage.md#门诊收款记录)及[Command 协议](../../../architecture/fhir-and-commands.md#66-预览与提交)拥有。验证使用公开 HTTP、文件 SQLite 的余额与放行、未知恢复、并发、幂等、权限和重启场景，并由真实收费页面及 React 18/19 审阅弹窗合同覆盖入口。
