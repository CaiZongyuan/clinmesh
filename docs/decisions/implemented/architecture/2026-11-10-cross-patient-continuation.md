# Agent Note: 具名连续办理与原患者写意图

Status: implemented

## Problem

病案审核、病案归档、医保核定和患者库开始就诊分别以一份病例为业务单元。办理成功后重新定位下一份增加操作，但自动跳转或自动提交会省略患者核对。列表刷新、筛选跟随和其他操作者消费候选，还可能使一个已经显示的“下一位”按钮转向另一人。未保存输入与网络结果不明的请求也有不同的保存和恢复责任。

## Decision

连续办理保留各自原 Command，只在原操作确认成功后展示具名下一目标。入口冻结患者、病例或住院身份及原队列、动作和页码；点击重读这一目标，资格变化则解释并刷新队列，由用户再次选择，不在一次点击内替换目标。切换只定位病例，下一份仍通过自己的审阅与确认提交。当前失败停留原病例，成功也不会自动跳转。

病案队列区分审核与归档，不从状态跟随后的筛选推断原候选；医保保持每页十份及本页核定历史读取，当前页完成不等于全队列完成。患者库仅对本页有界详情核验当前 Case、活动 Persona 和可开始状态，列表的无活动就诊摘要不作为可开始依据。当前队列的错误、加载和空态分别呈现，后页通过显式入口读取。

未发输入按账号、完整 Actor、患者和就诊或 Case 隔离保存，切页和刷新可恢复，退出清理。已发送操作另由持久写意图保存固定输入、原幂等键与身份，离开页面不取消服务端事实。患者库门诊开始接入既有窄 Operation 和原回执恢复：原身份下先查 `registration.synthetic-case.start`，只有 HTTP 404 且错误码为 `COMMAND_RECEIPT_NOT_FOUND` 才重发同键同体；其他身份或 Epoch 的缺失不能证明原请求未发生。成功回执须匹配原 Operation、原幂等键，通过该 Operation schema，并绑定原 Case。

持久成功处理在写入层完成，先消费原提交的私稿版本并记录队列交接，再移除原意图；挂载组件只同步当前视图。正常迟到响应、原完成回执和明确缺失后的重发共用此顺序。持久处理失败保留恢复意图，查询原回执再次完成本地处理，不另发新的业务请求；原提交后的新编辑继续保留。私稿读取失败保留原文，写入失败保留本次编辑。原意图仍待恢复时，只有重新核实同键、同操作、同病例的完成回执，才能按用户确认丢弃该操作的不可读记录；此时回执缺失不会触发重发。

退出清除已完成或未绑定待恢复命令的交接。与原意图匹配且尚未完成的住院交接随该意图保留，重新登录后可恢复；退出后的迟到响应可以结清原意图，不重新发布上一会话的交接提示。

## Alternatives considered

- 自动转到下一位并复用上次确认：减少点击，但取消逐患者核对且让迟到结果有机会影响另一患者，因此不用。
- 点击时重新寻找第一份合格病例：实现较短，但按钮上显示的人与实际导航的人可能不同，因此冻结目标并重验。
- 为求出全队列的下一人提前读取所有核定历史或患者详情：增加跨页请求并把本页办理变成全库扫描，因此保留有界读取和显式翻页。
- 只在组件成功回调清输入：组件卸载或切换身份后回调可能不执行，原成功稿会在返回时复活，因此把持久消费留在原写意图完成层。
- 网络异常后用新键再次开始：无法判断第一次是否已落库，因此复用原回执与原输入恢复。

## Consequences

连续办理不新增跨患者批量写接口，不改变病案、资金和开始就诊的服务端门禁。用户多做一次明确导航和每份确认，换取显示目标、实际目标及恢复归属一致。查询结果仍归 TanStack Query，客户端只保存未发输入和导航快照。

当前行为由[临床流程](../../../architecture/clinical-workflows.md#病案首页与归档)、[患者库开始](../../../architecture/simulation.md#103-场景定义)与[前端状态所有权](../../../frontend-architecture.md#状态所有权)维护。验收通过真实岗位入口、原 Command 回执及业务回读证明成功停留、失效目标、分别确认、分页、刷新恢复与不重复生效；React 18/19 共用同一应用实现。
