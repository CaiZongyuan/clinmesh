# Agent Note: 连续选药与整张处方原意图恢复

Status: implemented

## Problem

门诊处方在同一业务单元中包含多种药品。逐药重开目录增加操作，刷新后丢失未提交用法会破坏人工核对；提交丢回执后另开新请求可能形成重复处方。[集中办理规格](https://github.com/CaiZongyuan/clinmesh/blob/spec/batch-clinical-actions/docs/spec/2026-11-09-batch-clinical-actions.md)要求连续准备与整张原子性同时成立。

## Decision

目录保持打开，加入后重置当前药品输入，在同窗展示与编辑同一份待开清单。关闭保留尚未加入的输入；显式清空需要确认。页面私有草稿与统一清单的选择偏好复用账号、岗位、Workspace/Epoch、病例及 Encounter 隔离的浏览器存储，持久输入验证结构，退出清理；服务端临床草稿继续由原 Command 拥有。

复用准备确认的完整原意图存储及限定医生 Session 的回执读取，将支持范围扩展到 prescription。发送前保存全部药品、版本、来源证明和幂等键；结果未知时冻结新开具，先读原回执，只有明确查无回执才以原载荷与原键重放。临床拒绝保留全部行；成功仅消费仍属于本次请求的输入，不抹去较新编辑。具体恢复合同与业务原子性由[临床流程](../../../architecture/clinical-workflows.md#81-门诊闭环)拥有。

## Alternatives considered

- 每加一药关闭窗口：字段责任清晰，但重复打开不满足连续操作；改用同窗编辑与显式完成。
- 沿用独立检查逐项成功：会形成不完整处方；处方始终由一次 Command 整单保存并开具，任一药非法全部拒绝。
- 只保存服务端有效草稿：无法保留未完成输入、选择偏好及原幂等键；浏览器私有输入承担这些职责，不在退出时删除共享临床草稿。
- 新增通用 Agent 回执能力：扩大能力面；沿用病例、类别和身份限定的 Session 查询，不扩展 CLI 或 Agent Grant。

## Consequences

最多八药、目录单一来源、真实包装、联用、剂量及适应证规则保持有效。React 18/19 共用目录与确认界面；浏览器真实入口验证连续两药、刷新保留、整单拒绝及原回执恢复，HTTP 合同验证无部分处方、无重复用药与费用。
