# Agent Note: 集中发药只推进本批已证明成功的库存增量

Status: implemented

## Problem

同一患者的长期 BID 药嘱可以有多张待发药执行单，它们会共同消耗同一库存批次。若集中核对时就固定所有 Command 的库存版本，首单成功后余项必然冲突；若每单直接使用最新版本，则会静默接受其他发药造成的库存变化。集中办理还必须保留每张执行单的独立库存、发药、费用和原回执恢复，不能把发药写成给药。

## Decision

药房在既有岗位窄投影和单执行单 Command 之上集中核对，不增加 batch API 或服务端状态机；`sessionStorage` 私稿隔离、确认窗口锁定与未知结果原回执恢复遵循[临床连续办理私稿与回执恢复](2026-11-10-clinical-batch-draft-and-receipt-recovery.md)，当前合同由[医嘱生命周期](../../../architecture/clinical-workflows.md#83-医嘱生命周期)拥有，患者分页沿用[住院岗位组合决策](2026-11-03-inpatient-prototype-composition.md)。已选批次在当前药房投影中消失后不可重新选择或全选，原清单保留供人工处理。

集中确认只准备有界的未发送计划。每单到达队首时重新读取当前患者药房投影；只有医嘱、执行单、过敏及批次内容与核对依据相符，才持久化不可变 Command 与幂等键并发送。共享批次的预期版本等于原版本加本批已明确成功触及该批次的执行单数，预期数量等于原库存减这些成功单的数量总和。版本按单推进，不按发药数量推进；响应须证明原执行单、真实发药记录、`MedicationDispense` effect 和 `InventoryItem` effect 及余额，相同 key 的重复结算不再次累计贡献。外部变化使依赖该批次的项目保留输入并要求重新核对，不自动换批次或接受新版本；其他独立批次仍可逐项办理。

## Alternatives considered

- 将多张执行单放入一个原子 Command：改变既有逐单提交、库存 CAS、费用与部分成功合同，也扩大 Agent 写入能力。
- 确认时一次固定所有实际 Command：合法的同 lot 多时点会被本批首项成功制造的版本变化阻断。
- 每次发送前无条件使用最新 lot 版本：无法区分本批成功与外部竞争，会绕过人工核对的并发边界。
- 复制库存到全局客户端 store：产生与 Query 竞争的正式状态来源；清单只需要保存核对依据与尝试记录。

## Consequences

集中发药保留单执行单的原子性，已成功项目不随失败或恢复重复扣库。零库存 lot 可以从药房投影消失，完成后的余额用公开 FHIR `InventoryItem` 验收；页面不伪造厂家批号、部分发药或给药记录。测试同时覆盖公开 HTTP 的库存/费用/回执、组件的本批推进和外部冲突，以及真实 Web 与 React 18/19 Surface 的集中核对、原尝试恢复、窄屏和患者隔离。
