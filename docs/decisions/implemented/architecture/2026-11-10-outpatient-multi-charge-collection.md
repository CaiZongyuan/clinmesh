# Agent Note: 门诊收款分配解耦、多费用合并原款与逐分配退款

Status: implemented

## Problem

门诊收款若将交易状态恢复嵌在单个费用或临床工作流内，既无法与住院共用统一的支付状态机，又会使一次多项目缴费被迫拆成循环调用多笔单项收款（导致部分成功或部分未知）；若在账单和退款模型中沿用“一笔原款只对应一项费用”或把首项费用冒充整笔归属，则会截断费用分配、重复累计整笔金额或让单项退费挤占同笔付款内其他项目的可退额度。同时，存量旧格式合成交易若直接删库会连带毁掉患者库、账号目录与门诊号高水位，若长期双写旧表又会固化两套支付状态机。

## Decision

在[共享支付与住院边界](2026-10-21-payment-inpatient-drg-boundaries.md)基础上，解耦 `PaymentCollection` 交易事实与门诊费用分配，提供多费用合并原款与逐分配退款窄操作，当前合同见[收费、结算与医保](../../../architecture/billing-and-insurance.md)、[存储与事务](../../../architecture/storage.md)及[部署指南](../../../deployment.md)：

1. **`PaymentCollection` 交易事实与门诊费用分配分离**：`PaymentCollection` 仅在调用方既有 Command 事务内维护原始收款尝试、冻结渠道查询计划、付款方式与追加确定结果，交易身份通过就诊上下文锁定患者与 Encounter；门诊业务 owner 负责应收校验、复合外键费用分配及收费成功后的检查受理／处方待发药放行，共享 `RefundLedger` 负责原款可退余额、未知预占与原方式逆序消耗。
2. **多费用合并原款与三重约束逐分配退款**：专用 `payment.multi-charge.{preview,confirm,recover}` 通过独立 `multi_charge_payment_preview`（默认 5 分钟有效，零资金副作用且禁止旧单项确认混用）冻结同次就诊多笔账项的剩余应收与组合支付方式；确认在同一事务重验全部依赖、创建唯一原款（`kind: 'multi-charge'`）与完整不可变 `allocations` 并逐项触发临床放行，整笔交易共享单一 outcome，恢复只查原 `paymentId`。`refund.allocation.preview` 显式指定原 `paymentId` 内的目标 `chargeId`，同时核验“整笔原款剩余可退、该原分配剩余可退、该账项跨原款冲减依据剩余可退”三重上限（同原款存在未知退款时新退款须先查明原尝试，旧单项退款接口拒绝从合并原款猜测唯一费用）。客户端未发勾选私稿、已发资金意图隔离与原回执恢复遵循[临床连续办理私稿与逐项原回执恢复](2026-11-10-clinical-batch-draft-and-receipt-recovery.md)。
3. **显式 `db payment-cutover` 存量隔离边界**：不在正常服务启动时隐式删数，也不双写旧交易表；仅对遗留旧格式交易的开发库提供显式 `db payment-cutover` 维护入口（单事务关闭旧运行 Epoch、开启新活动 Epoch 并完整保全合成患者库、账号权限、门诊号高水位与模型账本），所有统一交易模型下的正式交易、未决尝试与回执一律受前向迁移保护。

## Alternatives considered

- **循环调用旧单项收款，或给多费用原款填首项费用 ID／按费用复制整笔退款来源**：拆碎整笔支付原子性与组合方式，截断分配归属或突破总原款可退上限。
- **长期保留新旧两套交易表读写适配器，或仅删旧支付行却保留已放行临床／归档状态**：前者背负永久双格式维护负担，后者使已完成检查、结算与归档丧失资金依据。
- **直接删除整个 operational SQLite 文件**：连带丢失共库保存的合成患者库、门诊号历史高水位与跨 Epoch 模型账本。

## Consequences

门诊单项与合并收款共用同一账单读取联合类型与原款、分配、反向退款投影，关联账项存在未决收退款时严格阻断新资金操作而不回退已发生的检查与发药事实；所有统一模型交易、未决尝试、分配引用与回执均受正式前向迁移保护，不允许后续升级舍弃交易历史。
