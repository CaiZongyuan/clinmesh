# Agent Note: 门诊合并原款与逐分配退款

Status: implemented

## Problem

一份多费用冻结预览表示一次完整付款意图。循环单项收款会产生多笔可分别成功或未知的尝试；沿用“一款一费”的历史与退款投影则会截断费用分配、重复整笔金额，或让某项退款占用其他项目的额度。响应丢失与渠道结果不明还属于不同恢复层，不能都通过新预览再付款处理。

## Decision

专用 `payment.multi-charge.confirm` 与 `payment.multi-charge.recover` 复用共享 Command 和 `PaymentCollection`。确认在同一事务重验全部冻结依赖、创建唯一原款及完整不可变费用分配，再按每项原有资金和临床条件应用结果。整笔资金只有一个 outcome；恢复查询原 payment ID 并追加确定结果，不新增收款，也不重复临床放行。[独立冻结预览](2026-11-10-outpatient-multi-charge-preview.md)继续拥有准备边界，旧单项确认仍不能消费多费用预览。

账单按原款分页后批量读取完整分配与方式。旧单项 DTO 保留原字段，新记录用 `kind: 'multi-charge'` 和完整 `allocations` 表达，整笔金额与方式只出现一次；不用首项费用冒充整笔归属。

`refund.allocation.preview` 明确选择原 payment ID 内的 charge ID。退款同时受整笔原款剩余、该原分配剩余和该费用跨原款冲减依据剩余约束；成功退款扣减，未知退款预占。同一原款有未知退款时，基于该原款的新退款先等待原尝试查明；其他费用的新动作仍分别检查其未决资金。原款方式只读取一次，由共享退款账沿其顺序分配反向金额。确认从冻结目标读取原分配，恢复从不可变退款依据定位同一费用；旧单项退款协议保留，但拒绝从合并原款猜测唯一费用。当前金额和工作流由[收费与支付](../../../architecture/clinical-workflows.md#85-收费支付与退款)拥有，持久化约束由[门诊收款记录](../../../architecture/storage.md#门诊收款记录)拥有。

发送前持久化原命令、幂等键和完整身份与就诊绑定。传输结果未知时先查询原回执，仅确切未发生时按原键和原载荷重放；已有渠道未知原款或退款通过其稳定 ID 恢复。未提交私稿与已发送意图分别保存，独立私稿损坏不能阻断原资金恢复。患者切换和迟到结果不能改变原意图归属。

追加迁移保留历史原款、单项及零元分配和已有退款预览；新分配主键允许同一原款关联多个不同费用，保留原款就诊和费用就诊外键。分配合计由同一 Command 事务验证，不修改任何已应用迁移或原开发 cutover。

## Alternatives considered

- 循环旧收款：拆开整笔结果和幂等边界，无法可靠处理组合方式与未知资金，拒绝采用。
- 给多项记录填入第一项费用：会让历史分页、恢复与退款在不完整归属上执行，拒绝采用。
- 按费用复制整笔退款来源：重复原款金额与渠道余额，无法保护总退款上限，拒绝采用。
- 只依靠浏览器禁用按钮或重建预览恢复：无法覆盖并发、重启、丢响应和其他客户端，拒绝采用。

## Consequences

多项资金增加专用窄操作与明确的读取 union，旧单项调用无需迁移。账单仍从原款、分配及反向记录计算，不新增可编辑余额。关联费用在未决资金查明前阻断新资金操作；退款保留已发生的检查、发药与临床事实。公开 HTTP 验收核对原回执、真实 runtime 重启、唯一交易与分配、完整交易分页、退款预占及原渠道；真实岗位和双 React 验收核对明确确认、原尝试恢复与逐项可追溯。
