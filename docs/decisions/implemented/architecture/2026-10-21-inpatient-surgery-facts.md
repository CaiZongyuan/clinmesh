# Agent Note: 住院手术申请与实际实施独立拥有

Status: implemented

## Problem

手术计划可能取消、改期或变更术式。用申请或计划时点填充实际 Procedure、费用和病案首页会制造未发生的操作；把分类码作为收费ID则混淆临床分类来源与本院价目。

## Decision

InpatientSurgery 在 InpatientService 与既有 CommandExecutor 内拥有申请、两个独立准备确认、实际实施和取消。ServiceRequest 表达计划，唯一实际执行创建只读 R5 Procedure，术后医嘱在普通签发事务引用实际执行。现有账本记录实际手术与耗材，投影、用料、两类费用、完成状态与审计原子提交；不引入第二套医嘱或费用生命周期。当前行为由[临床流程](../../../architecture/clinical-workflows.md#住院手术最小闭环)拥有。

Scenario 提供有来源定位的八条临床分类摘录与独立合成院内价目；操作代码保持完整字符串，来源限制沿[编码研究](../../../research/2026-10-20-inpatient-record-coding-and-recall.md)。不虚构 cn-health 手术Release，不把有界摘录宣称为全量目录；耗材仅记录实际使用及费用，避免将最小闭环扩成供应链。

## Alternatives considered

- 申请直接作为已实施操作：无法表达取消、双准备门禁或实际术式不同，首页与账目失真。
- 用临床分类码作收费项目ID：分类来源不定义本院价目，不能冻结实施时实际收费身份与价格。
- 为术后另建医嘱状态机：绕开原护士校对、药师发药与护士给药门禁。
- 计划时间由场景推进自动实施：时间到不证明患者实际接受手术，也不能代替责任人记录。

## Consequences

出院与转科交接、接收在自身事务检查未收口手术，首页只读本次实际执行。内部阻塞查询由已完成业务授权的调用方使用，避免把原科普通详情权限错误套给尚未接管的目标护士。转科后继续校验当前住院责任，保留申请原作者与既往费用科室。护士核对与医生记录已签同意形成可审计的确认事实，不宣称提供真实电子签名。HTTP与真实SQLite验证门禁、原子回滚、版本、幂等及窄引用；真实Web旅程验证岗位交接、实际术式和丢回执恢复。
