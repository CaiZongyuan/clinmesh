# Agent Note: 检查申请集中动作沿原 Command 逐项恢复

Status: implemented

## Problem

医生取消多份未执行申请或重试多份明确失败申请时，需要重复定位与确认。临床申请、执行任务、资金前置和住院送检有不同限制；把多个按钮简单循环，无法区分确定拒绝、已经成功但响应丢失，以及尚未发送的后续项目，也可能把取消误当成退款。

## Decision

集中办理只组织同患者、同次就诊或住院、同种动作的人工核对，不改变共享申请内核。门诊三类申请分别组织清单，住院适配原检查 Command；取消与重试各有独立范围。当前行为由[检查申请集中取消与失败重试](../../../architecture/clinical-workflows.md#检查申请集中取消与失败重试)拥有。

每项保留审阅快照和清单修订；最终确认锁定实际展示的集合，不接受另一界面扩大选择范围。正式状态继续归 Query，持久清单只保存账号、完整 Actor、患者、就诊或住院、类别及动作绑定的人工输入和原尝试，不建立第二套正式申请缓存。

独立申请使用既有窄 Command，分别校验预期版本、权限、状态和资金前置。发送前保存不可变原输入和幂等键；确定成功或拒绝后先结算原清单，再解除原写意图。响应、回执读取或存储不确定时保留原尝试并停止后续，恢复查询同一原回执，只有明确缺失才同键重发。恢复后的余项重新核对，不自动接续旧计划；迟到结果只结算原范围与原修订。

保留取消和资金事实之间的边界。门诊取消固定使用既有“不再需要”理由，重试与住院动作不新增自由文本必填；取消成功仍可能留下原交易退款责任，未知资金或有效医保仍须由对应 owner 先处理。重试成功只代表原生成任务重新受理，报告和费用由原工作流继续产生。

## Alternatives considered

- 新增跨申请原子批量 Command：改变独立申请的部分成功合同，也扩大服务端和 Agent 写能力。
- 循环旧按钮并遇错继续：无法在响应丢失时停止、定位原尝试或阻止重复生效。
- 刷新后按当前状态推断本批成功：其他操作者也可能改变状态，不能证明原幂等键的结果。
- 为所有动作强制新增共同自由文本理由：现有取消已有固定理由，其他动作未要求该字段，会扩大本票业务合同。

## Consequences

一次集中确认可以保留确定的部分成功，未知结果则缩小为单项恢复，不把未提交项目自动补发。客户端需要持久清单和明确的存储故障处理；这类输入不能代替服务端状态、费用或报告事实。公开 HTTP 验证重启后的原回执、唯一冲减、原费用和报告；真实岗位及 React 18/19 合同验证选择、患者隔离、失败恢复和窄容器操作，演示绑定最终干净提交。
