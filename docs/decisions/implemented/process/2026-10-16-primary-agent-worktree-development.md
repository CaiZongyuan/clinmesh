# Agent Note: 主 Agent 统筹的 worktree 开发

Status: implemented

## Problem

独立 skills 提供了澄清、实施和审查方法，但让用户选择入口、分派任务和跟进集成仍会增加协调负担。新版 Matt `implement-spec` 提供依赖图与 worktree 编排，却是显式入口，默认还包含 PR 转 ready、reset 和清理；直接自动调用或照搬这些动作，会与宿主调用策略及项目授权冲突。提交前执行 `code-review` 时，仅用三点 diff 也会漏掉未提交和新增文件。

## Decision

主 Agent 根据用户的自然语言需求负责选择执行方式、安排可独立实施的 worktree、集成和最终交付。自动编排由项目规则明确规定，Matt 原文和显式调用设置保持上游；实际调用入口必须满足宿主能力和调用条件，原生工具执行不冒称 skill 调用。单个紧密依赖的任务由主 Agent 直接完成，多切片任务围绕同一正式需求和集成分支推进，具体合同由 [Agent 工程开发](../../../../docs/agent-development.md#开发入口)拥有。

本决定部分取代 [Task-scoped Agent skills](2026-10-02-task-scoped-agent-skills.md) 的按需选择与直接实施入口。需求澄清继承已有批准，行为变化保留 TDD，最终变更进行双轴审查；不强制为小任务建立 tickets、制作演示媒体或执行复盘。正式需求继续由[仓库规格](2026-10-06-repository-owned-specs.md)拥有，Issue 只追踪执行。

通用 skill 的交付、清理、PR 正文和复盘由项目 owner 适配。主 Agent 对完整待交付快照负责，覆盖提交及 WIP；默认交付与清理沿用实际授权。复盘先形成有证据的改进候选，不自动实施候选。

## Alternatives considered

**修改 Matt 元数据，使所有入口自动触发。** 可以改变发现和选择方式，但会制造上游分叉，且无法取代宿主的真实调用能力与项目授权规则。

**要求用户每次点名 `implement-spec` 并亲自分派。** 保留显式策略，却把任务选择和跟进成本留给用户，不能满足减少协调负担的目标。

**为每个任务强制创建 tickets、worktree、独立集成 Agent 和复盘。** 形式统一，但紧密依赖或很小的任务不能从并行获益，反而增加准备与重复审查成本。

## Consequences

全局偏好与仓库具体合同分别由各自规则拥有；没有对应显式入口时，主 Agent 仍可在实际可用、允许的原生能力范围内完成编排。工作区隔离不提供权限或运行环境隔离，主 Agent 仍需核验基线、文件归属、可写数据和最终证据。

当前流程文件可通过文档、链接和双轴审查验证；并行效率、冲突率和真实交付耗时需要实际任务数据，不能仅凭规则更新宣称改善。
