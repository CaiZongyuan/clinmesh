# Agent Note: PR CI 按分片并行并按检查输入复用成功记录

Status: implemented

## Problem

主 CI 的关键路径由单台 runner 上的完整 `unit` 与 `browser` 决定，环境准备只占少数时间。同一 PR 在追加普通文档、修复某一组专属测试或只改变提交历史后，仍按完整净差异重跑全部测试组；“上次全绿”不能证明这次的输入已被验证。浏览器合同与 DSH 样式构建以仓库根为 Tailwind 扫描根，普通文档和其他组的测试文件即使不被导入，也可能改变运行时生成的 CSS。

## Decision

检查选择保持不变，执行层只在完整集合上分片：`full` 与 `frontend` 计划中的 `unit`、`browser` 固定两片，由各自运行器的内建 `--shard` 切分；`checks`、`e2e` 和定向测试不分片。片数是关键路径与 runner 开销的折中，拆分后关键路径由 `e2e` 决定，继续拆分的边际收益很小。

成功复用以“检查组 + 分片”为单位，用完整输入指纹作为精确缓存键。指纹绑定 PR 编号、计划与实际命令、runner 身份和候选提交的 Git 树；测试组排除普通文档内容，并对其他组专属且独立的测试只保留路径和模式，被排除内容改以 Tailwind 扫描器提取的候选 class 参与比较。候选集合比实际生成的 class 宽，可能多跑，但不会因文档或测试中的新 class 漏跑。只有本组全部命令成功后才写入记录，记录在使用前再次比较指纹、检查组与分片。

成功证据由写入时机和 GitHub 的 PR 缓存作用域保证，不调用 Actions API 核验来源，也不扩大工作流权限。PR 运行执行 PR 自身的 CI 脚本，最终门禁同样受 PR 代码控制，因此该机制防范实现错误与输入漂移，不防恶意 PR。主线 push 不读写成功记录，仍执行完整集合。

## Alternatives considered

- 只比较提交 SHA、PR head 或改动文件列表：同步历史后无法命中，也会漏掉主线带入的新内容。
- 用预生成的 DSH 样式代替文档内容：浏览器合同在测试运行时以仓库根重新构建其他 CSS 入口，单一产物不能覆盖这些消费者。
- 为每个测试组推导最小依赖图：Vite 动态加载和 HTTP 消费者不等同于静态导入，无法可靠证明；源码变化继续使三个测试组一起失效。
- 用缓存前缀恢复最近一次记录：只能保留一份记录，回退到旧内容时无法命中，并扩大匹配范围。
- 调用 Actions API 核验来源 job：需要额外读权限和网络依赖，在 PR 代码可控制门禁时不增加安全性。
- 按历史耗时均衡分片或增加 worker：需要额外耗时数据或改变资源争用边界，首版沿用运行器内建切分和原 worker 数。

## Consequences

关键路径缩短取决于两片的实际均衡程度；Vitest 按文件数切分，少数长耗时文件可能让某一片明显更长，调整片数或均衡方式需要重新取舍。每片增加一次环境准备，复用命中时仍执行依赖安装与样式准备。缓存过期、runner 镜像升级、文档或测试新增候选 class 都会导致未命中并正常执行。

分流、执行组与最终汇总的既有理由见 [CI 分流与并行决策](2026-10-25-selective-parallel-ci.md)。当前机制由[测试策略](../../../testing.md#github-ci-的检查选择与并行)拥有，验收由[正式规格](../../../spec/2026-11-04-ci-success-reuse.md)拥有。
