# Agent Note: PCI 从零岗位旅程与独立账本证据

Status: implemented

## Problem

PCI 的 HTTP 联合验收覆盖诊疗、支付与冻结历史，浏览器合同则在后台准备入院、九检、五药和造影后进入页面。分段通过无法证明管理员、登记员、护士、医生和药师能从空环境交接完成同一次住院，也不能证明术后用药发生在 PCI 完成后。沿用旧费用总额还会漏掉新增执行对患者待遇和补缴金额的影响。

## Decision

普通 Web 的 PCI 旅程从页面准备目录与固定来源、手工 Persona 和来源绑定直接住院开始，临床及资金写入由真实岗位页面发起。环境准备只安装参考资料和规则、创建合成运行环境；后台 worker 按已送检的真实申请生成报告。公开查询解析合同 schema，独立核对来源绑定、九项报告、六次药品执行、两项操作、四项材料替换、患者资金和不可变快照。术后医嘱显式关联本次 PCI 执行；未知组合收款先展示结算及清床阻断，再查询原尝试恢复。

HTTP 层保留完整业务矩阵和正常持久化重启证明，React 18/19 ShadowRoot 继续验证共享视图、Portal、审阅和资金恢复。后两者可沿用有明确边界的 HTTP 前置，不以此声称它们完成从零页面准备或原生 DSH Session 验收。分层归属见[测试策略](../../../testing.md)，具体岗位步骤和独立账本由[演示手册](../../../pci-demo.md)拥有。

账本预期由固定单价、数量和合成待遇逐项取整推导，再与公开账务读取比较，不用被测收费总额反推预期。金额一致不能证明用药阶段：浏览器另按真实写请求断言术前三药先于造影申请，术中肝素和碘海醇的医嘱、发药及给药位于造影知情同意与实际操作记录之间，术后阿司匹林晚于实际 PCI。FM39 医院侧核定分别比较冻结支付预估和冻结医疗费用；后续更正保留原归档、首次结算、冻结分组、医保办核定和临床状态。

重复性通过同一固定代码和规则在独立临时库重新准备并执行证明，每轮都包含后续更正后的历史保留断言。管理员在同库重置属于另一条既有协议：保留患者库时，新 Epoch 按原修订重放住院，旧 Epoch 仍在库内；它不能替代从空库重新走准备与登记的证据。规则完整性、实际部署审核及临床 Release 身份与浏览器接线证据分别报告。

## Alternatives considered

- 继续把准备页合同和原黄金旅程并列作为完整演示：不能观察同一病例在准备、登记、检验及药房之间的真实交接，也会继续遗漏术后执行。
- 每个浏览器版本都执行全部页面及后端失败矩阵：重复已有 Server 合同并增加构建和浏览器成本；完整普通 Web 主线与共享交互兼容性分别拥有证据。
- 从读回总额生成支付和退款断言：只能证明相同错误在多处一致，无法发现数量、计价单位或术后新增药费遗漏。
- 在同 Epoch 再次准备固定病例作为重演：准备是幂等动作，病例普通开始只能消费一次，不能据此证明第二次完整住院。
- 以默认自编小规则通过声明完整部署验收：小程序只能验证接线；完整包身份和受信装载仍需实际完整来源及审核证据。

## Consequences

完整岗位旅程比局部合同更长，但可直接复用为人工手册的顺序依据。测试和文档按同一价格与执行数量维护，术后药费或临床时序变化会明确影响费用、医保分配和补缴预期。产出记录固定提交及实际命令结果，保留合成 Provider、临时数据库和无真实模型调用的验证边界；不把一次成功外推为全部病例、地方正式结算或原生 DSH 能力。
