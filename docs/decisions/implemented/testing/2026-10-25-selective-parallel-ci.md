# Agent Note: PR 影响范围分流并行、分片输入指纹复用与重型手术旅程分阶段隔离

Status: implemented

## Problem

若每次 PR 提交都在单台 runner 上串行跑完整个仓库的检查、全量 Server Vitest、双版本浏览器合同与 Web E2E，纯文档微调、独立脚本测试或追加文档后的同 PR 二次推送都要支付完整关键路径等待；反之，若仅按改动后缀名或静态 import 图跳过测试，又会漏掉动态 Vite 构建、跨文件 HTTP 消费者以及仓库根 Tailwind 扫描（文档或其他组测试中新增候选 class 可能改变运行时生成的 CSS）。此外，覆盖十阶段临床写入、助手核对与多宽主题矩阵的手术全程浏览器旅程（`@surgery-flow`）在与其他浏览器用例同 runner 并发争抢资源时易在末尾耗尽单测时限，而全局降为单 worker 或拉长超时则会拖慢整套套件并削弱卡死检测。

## Decision

在 CI 中分层实现保守影响分流、4 组并行执行、双分片精确输入缓存复用与 `@surgery-flow` 同组两阶段隔离，详细规则与入口见[测试策略](../../../testing.md)：

1. **基于候选合并净差异的保守分流与四组并行失败关闭**：计划器仅依赖 Node 内建模块核验 PR base/head 与第一父提交完整净差异（身份不明、存在外部引用／别名或主线 `main` push 一律回退 `full` 全量）：划分为窄文档范围、已核实无外部消费者的独立测试、前端范围（保留消费者组件单测、全局类型／构建及完整浏览器与 E2E，省去整套 Server Vitest 但仍保留真实 HTTP+SQLite E2E 接线）与全量范围。四个执行组在独立 runner 并行准备各自 DSH 样式并执行，最终 `verify` 门禁对任何组失败、取消、结果缺失或意外跳过一律失败关闭，且严禁将文件名或事件载荷拼接进任意 shell 命令。
2. **`unit`／`browser` 双分片与含 Tailwind 候选集的精确输入成功复用**：`full` 与 `frontend` 计划中的 `unit` 和 `browser` 固定使用运行器内建 `--shard` 切为 2 片（`checks`、`e2e` 与定向测试不分片）。同一 PR 内的成功记录按“检查组 + 分片”绑定完整输入指纹（PR 编号、计划与实际命令、runner 身份及候选 Git 树：排除普通文档正文与无关独立测试实现，但显式纳入 Tailwind 扫描器从这些被排除文件中提取的候选 class 集合），仅在本组全部命令通过后写入并在命中前二次核验，主线 push 永不读写缓存。
3. **`@surgery-flow` 重型旅程同 runner 两阶段无分片隔离**：为三条手术全程用例标记 `@surgery-flow`。在 `browser` 与 `e2e` 执行组内，第一阶段先排除 `@surgery-flow` 并行跑完常规集合（`browser` 维持两分片）；常规集合通过后，第二阶段在首个 runner 上单独无分片运行 `@surgery-flow`（保留运行器“匹配零条测试即报错”守卫防止漏标标签被空分片掩盖，保持全局 2 workers、零自动重试与原有时限／几何断言不变，任一阶段失败均阻止写入分片成功缓存）。

## Alternatives considered

- **PR 仅运行本次改动的 `.spec`/`.test` 文件，或仅靠 `vitest related`／包依赖图筛选**：产品源码改动未改测试文件时会直接漏检，静态包图也无法完整表达动态构建与 Tailwind 全仓扫描耦合。
- **仅按提交 SHA 缓存或用缓存前缀模糊匹配最近一次记录**：rebase 后无法命中，模糊前缀则会在回退代码时误命中过期记录；PR 代码本身控制工作流脚本，额外调 GitHub Actions API 核验来源并无附加安全收益。
- **将全部浏览器测试降为单 worker、盲目放宽超时，或为 `@surgery-flow` 新开第五个独立 runner job**：前两者拖慢全量常规用例并掩盖死锁，新开 job 则重复支付完整依赖安装与构建准备成本。

## Consequences

纯文档改动与同 PR 增量迭代显著缩短等待时间，同时通过保守回退、Tailwind class 指纹与主线全量复跑严守零漏检底线；重型手术旅程获得独占进程资源窗口而无需牺牲常规用例并发度。
