# Agent Note: PR 按可靠影响范围分流并并行验证

Status: implemented

## Problem

PR 与主线均串行运行完整检查，局部文档、独立测试或前端显示改动也等待整套 Server Vitest。各测试入口还存在相对源码导入、Vite 动态构建和真实 HTTP 接线，单靠文件后缀或包依赖筛选会漏掉实际消费者。

## Decision

CI 将检查选择、执行和最终汇总分开。PR 候选提交必须与本次事件的 base/head 和 checkout 身份一致，从候选第一父提交读取完整净差异；不读 PR 的后来版本，也不依赖额外 GitHub API 权限。任何身份、差异或影响范围不确定时选择全量，主线固定全量。

分流使用窄文档范围、已有独立测试入口和明确的前端源码边界。测试入口有导出、静态引用者、相关 JSON 别名或无法核验独立性时回退全量；该保守检查可以多跑，不能代替通用动态依赖推导。前端选择保留实际消费者组件测试、全局类型/构建和完整浏览器/E2E，因此省略 Server 整套 Vitest 时仍有真实 HTTP 与 SQLite 接线验证。Server、宿主协议和关键共享边界在不能证明更窄集合时继续全量。

四类执行组使用独立 runner 和同一提交并行，各非文档组在依赖安装后准备自己的 DSH 生成样式，避免依赖其他 runner 上 typecheck 的副作用。最终 `verify` 对失败、取消、必需组意外跳过及结果缺失失败关闭。计划和汇总只依赖 Node 内建能力；业务依赖安装失败不会让最终门禁因无法启动而静默跳过。执行命令和路径参数由脚本固定选择，不执行来自文件名或事件数据的任意 shell 字符串。

## Alternatives considered

- 每次全量串行：覆盖简单，但局部修改和独立测试仍支付全部等待时间，后层失败也较晚暴露。
- PR 一律仅运行改过的测试文件：产品代码没有同步修改测试时会漏检，无法覆盖 HTTP、动态 UI 或跨包消费者。
- 仅使用 Vitest related、Turbo 包图或 Playwright 静态依赖选择：不能完整表达本项目的动态 Vite 构建与 HTTP 语义，因此保留上层集合并对不明情况全量。
- 在同一 runner 增加 worker：会放大 SQLite、CPU 和内存争用，独立 runner 更容易保持现有测试时限及资源隔离。
- 合并后复用 PR 的缓存成功状态：降低真实主线复检价值，当前继续运行完整集合。

## Consequences

并行主要缩短等待时间，可能增加 runner 总用量；实际收益受最慢检查组和队列影响，不以固定墙钟阈值验收。更多模块可以在拥有明确消费者及回归证据后增加映射，未知路径保持全量，避免静默扩大快路径。

现有短 count/storage 门禁仍属于完整集合；新方案不授权持续负载或真实模型运行。CI 的最终结果与分支保护独立，启用强制合并规则仍需仓库管理权限。当前分类及测试入口由[测试策略](../../../testing.md#github-ci-的检查选择与并行)拥有，验收由[正式规格](../../../spec/2026-10-25-selective-parallel-ci.md)拥有。
