# ClinMesh UI 设计合同

ClinMesh Web 与 Desktop 共享一套面向临床工作的界面语言：安静、高密度、可快速扫读。患者事实、业务状态和当前任务优先于装饰，界面通过表面、边线、排版和间距建立层级。

## 核心原则

1. **安静的密度**：在单个视口中呈现足够的临床上下文，但不用装饰色、大标题或重阴影竞争注意力。
2. **表面优先于阴影**：常驻区域使用中性背景、1px 边线和稳定间距；阴影只属于菜单、Dialog、Sheet 和 Toast 等临时覆盖层。
3. **动作紧邻对象**：确认诊断、签署病历、签发处方、签发申请、取消和更正位于所操作事实附近，长表单的提交区保持稳定。
4. **渐进展开**：默认只显示当前任务所需信息；使用 Tabs、Sheet 和菜单切换上下文，不把完整病例堆成一条长页面。
5. **工作区连续性**：侧栏、顶栏、当前岗位和设置入口在页面间保持稳定，避免重复 Dashboard 和跳转迷失。
6. **语义色克制**：色彩用于选中、焦点、成功、警告和风险，不作为大面积装饰。

| 内容 | Owner |

| Button、Field、Table、Tabs、Dialog 等 primitive | [`packages/ui/src/components/`](../../packages/ui/src/components/) |
| Web 工作区布局和平台交互 | [`apps/web/src/app/`](../../apps/web/src/app/) |
| 真实组件目录 | [`apps/web/src/app/component-catalog.tsx`](../../apps/web/src/app/component-catalog.tsx) |

`packages/ui` 不包含 Patient、Encounter 或 Medication 等业务概念。业务页通过公开组件入口和语义 token 组合界面，不复制 primitive 样式。Mobile 使用独立 React Native UI，不导入 DOM 组件。

## 应用框架

### 桌面端

| 区域 | 合同 |
| --- | --- |
| 侧栏 | 220px；冷灰表面；导航行高 32px；当前项使用中性表面，不使用强彩色底 |
| 折叠侧栏 | 48px 内容宽；只显示图标，通过 Tooltip 补足名称 |
| 顶栏 | 54px；包含唯一页面 H1、通知和用户菜单；设置由左侧栏承接，独立 Web 使用侧栏底部入口，DSH 使用医院工作台菜单 |
| 主内容 | 16–20px 页边距；不重复顶栏标题；业务网格充分使用宽度 |
| 应用表面 | 主区域与侧栏通过背景、边线和最大 8px 圆角区分，无常驻阴影 |

侧栏只显示当前岗位工作台。管理员以“模拟数据”为唯一岗位首页，患者库页头提供生成患者和带影响说明、可选清空患者库及二次确认的重置操作。设置使用同一框架，但侧栏切换为“设置”与“开发者”导航。

### 移动端

`< 768px` 时桌面侧栏替换为 Sheet。主内容使用 16px 页边距，多列表单回落为单列，Tabs 可水平滚动。表格保持列语义并在自身容器内水平滚动，不通过缩小字号隐藏数据。

## 密度与排版

| 用途 | 标准档尺寸 | 规则 |
| --- | ---: | --- |
| 顶栏标题 | 13px | 600 字重，单行截断 |
| 业务分区标题 | 13–16px | 与内容紧密对齐 |
| 正文与控件 | 13px | 1.5 行高，不随视口缩放 |
| 辅助信息 | 11–12px | 使用 `muted-foreground` |
| 按钮 | 24 / 28 / 32 / 36px | XS / SM / 默认 / LG |
| 常规控件圆角 | 6px | Button、Input、Select、Tabs |
| 业务表面圆角 | 最大 8px | 独立重复项、弹层和真正的工具容器 |

Web“设置 → 外观”的字号偏好提供“标准 / 较大 / 大”三档，分别按 `100% / 112.5% / 125%` 调整 ClinMesh 应用内容的语义字号。“标准”同时承担重置功能；选择即时生效并作为设备本地 Web 偏好持久化。Desktop 消费标准档 token，不拥有该 Web 本地偏好。

字号比例只进入语义字体 token。图标、控件高度、间距和页面几何尺寸保持不变；standalone Web 的文档根字号保持 `16px`，DSH Surface 不修改宿主根元素。持久化和作用域取舍见 [Web 应用级字号偏好](../decisions/implemented/feature/2026-09-02-web-font-size-preference.md)。

全局字距为 0。日期、时间、金额和检验值使用等宽数字特性。页面不使用负字距、视口缩放字号或超大仪表盘标题。

## 颜色与主题

业务组件只消费语义 token，不直接写入 Tailwind 色阶。

| Token | 用途 |
| --- | --- |
| `background` / `foreground` | 主画布与默认文字 |
| `card` / `popover` | 独立业务项与临时覆盖层 |
| `primary` | 主操作与品牌强调；独立 Web 为靛紫，桌面与 DSH 基线另有主色 |
| `info` / `ring` | ClinMesh 品牌标识、信息和键盘焦点 |
| `success` | 正常、通过和已完成 |
| `warning` | 待复核、偏高和需要注意 |
| `destructive` | 过敏、危急、删除和不可逆风险 |
| `secondary` / `muted` | 中性状态、辅助表面和弱化文字 |
| `border` / `input` | 分隔线和控件边界 |

独立 Web 采用“AI 原生工作台”视觉语言（[规格](../spec/2026-10-19-ai-native-doctor-workspace.md) 方向四）：浅色画布配靛紫点缀，深色主题为紫调中性画布与亮靛紫点缀，两主题同等成立；AI 参与面的进行中状态使用 `--clinmesh-glow` 环绕柔光作为辅助反馈。暗色主题独立映射画布、文字、边线和语义色，不直接反相亮色值。桌面与 DSH 消费 `:root` / `.dark` 基线，视觉基线在 DSH 集成步骤对齐。独立 Web 的主题选择写入 `clinmesh.preferences:v1`，公共组件目录和登录后工作区使用同一机制。DSH 模式的主题选择与作用域见[Surface 与 Host 边界](../architecture/agent-integration.md#71-surface-与-host-边界)。

## 门诊医生工作台

门诊医生工作台位于稳定的应用侧栏和顶栏内。内部布局断点全部由容器查询声明，按实际容器宽度改变组合，不缩放字号：

| 容器宽度 | 布局合同 |
| --- | --- |
| `>= 1080px` | 200px 候诊栏、病例主区与 280px 建议栈三栏并排 |
| `720px – 1080px` | 200px 候诊栏与病例主区并排 |
| `< 720px` | 候诊栏与病例详情切换显示，保持挂载和草稿；建议栈折叠为右下角浮动按钮与右侧抽屉 |

建议栈展示完诊未完项、质控开放疑点与医生推荐状态，内容全部来自确定性服务查询，窄容器下经抽屉访问，双挂载组件不声明 DOM id。患者横幅固定在业务页签上方，压缩为两行：身份行展示姓名、性别、年龄、门诊号、主诉、分诊、过敏、病例状态与完诊动作；生命体征与完诊进度合并为同一行，进度以"N / 7 + 未完 k 项"计数摘要呈现，七项逐项状态与状态文字移入建议栈完诊分区。未取得完诊预览时不显示进度。取舍见[Agent Note](../decisions/implemented/architecture/2026-10-20-doctor-suggestion-stack-banner-progress.md)；横幅高度上限、独立滚动与无病例上下文栏等既有结论继续适用，历史取舍见[完诊清单 Note](../decisions/implemented/architecture/2026-10-06-doctor-inline-completion-checklist.md)。

患者横幅最多占病例内容区一半高度，长主诉、多条过敏或大字号导致内容超出时，横幅独立纵向滚动，保留业务页签的可用空间。业务区滚动时横幅位置保持稳定。

病例主区按以下顺序提供五个业务页签；没有 Consultation Record owner 的旧病例不显示“问诊记录”：

| 分区 | 内容 |
| --- | --- |
| 问诊记录 | 受控问题与按序追加的患者回答，不覆盖正式病历 |
| 病历记录 | 主诉、现病史、既往史、查体、辅助检查、临床评估、处置、随访、签署和受控修订 |
| 检验检查 | 检验、放射检查和病理会诊分类，目录与申请信息、申请列表与选中详情、追加、取消、重试、报告历史和已阅 |
| 诊断 | 受控诊断目录、主次诊断、自动保存草稿和可继续修订的正式确认版本 |
| 处方 | 用药结论、按临床产品分组的真实包装选择、剂量、频次、疗程、数量、自动保存草稿、正式开具和撤回 |

“检验检查”按当前病例、当前分类的完整已签发申请集合派生阶段：无申请且可编辑时直接显示融合目录与申请信息，右侧放待开具清单；已有申请时左侧保留开具表单、待办及可搜索筛选的申请列表，右侧显示选中申请详情。开具后目录结果默认收起，搜索行保持可见。取消记录与筛选为空仍保留管理阶段，草稿保存不切换阶段。三类目录、草稿与报告保持独立；分类切换保留未保存输入，刷新恢复已保存草稿。检验默认展示完整指标，可切换仅异常，历史默认收起；放射和病理保留各自阅读器与实际显示后的已阅门禁。药品 picker 不自动选择目录第一项；医生必须明确选择真实产品 ID，同一临床产品的包装变体共享通用名、规格、剂型、厂家和批准文号信息。

没有病例责任人的 `awaiting-doctor` 病例在接诊动作成功前不开放病历、检验、诊断、处方或问诊写入；开始首诊动作固定在病例页签上方，切换业务页签仍可到达。病例进入 `first-visit` 后才启动普通草稿 autosave 和完诊预览；`awaiting-revisit` 继续显示开始复诊动作和服务端允许的既有修订入口。

患者横幅常驻“完诊”动作。存在阻断项时，Dialog 显示服务端完诊清单并可跳转到对应页签；满足条件后才允许确认完诊。已完诊病例默认只读，服务端允许的纠错入口先激活目标页签，再将焦点和滚动位置移到目标区域。管理员工作台有界搜索 orderable LOINC 候选，选择根项目并观察 enrichment publication job；医生检验选择器只显示发布成功的根服务，panel dependency-only 分项不平铺，不显示 Agent、Case Truth 或生成 capability。

未提交的 Clinical Document 输入以 `caseId` 隔离保存在当前前端会话状态中；切换页签或患者不会丢失输入，也不会将内容带入另一病例，刷新或关闭页面会丢弃未提交内容。诊断、检验和处方的有效修改在短暂静止后自动保存，界面只显示等待、保存中、已保存或保存失败，不提供普通“保存草稿”按钮。删除整个草稿、确认诊断、开立申请、正式开具和无需用药仍是明确命令；当前输入尚未自动保存或保存请求仍在进行时，这些终结动作保持禁用。界面不显示草稿版本、FHIR 版本或乐观锁版本，服务端继续执行 expected version、幂等、审计和冲突检查。

诊断确认不结束本次 Encounter 的诊断编辑。确认后仍显示当前主次诊断和添加、更换、删除、备注入口；修改自动形成新草稿，再次确认创建新的正式 revision 并保留上一版本。Encounter 完成后诊断页回到只读。

诊断与处方首次填写将目录选择与字段编辑融合在同一栏，旁侧放紧凑待办，不自动选择目录第一项。已确认诊断左侧保留目录、编辑、待办及可按主次筛选的列表，右侧显示选中正式诊断；已开具或撤回处方显示药品列表与选中只读详情，保留未开具项目的可见性及现有处方限制。窄分栏可在列表与详情之间返回，搜索、筛选与返回不删除记录或清空输入。确认诊断作用于整组，开具、删除草稿、撤回及无需用药保持明确的对象预览和确认；布局与阶段归属见[开具工作区决策](../decisions/implemented/architecture/2026-10-19-clinical-order-workspace.md)，正式记录与处方生命周期继续见[两阶段视图决定](../decisions/implemented/architecture/2026-10-10-diagnosis-prescription-workspace.md)。

所有演示患者和岗位在底层仍带 synthetic provenance、FHIR extension、受控标识和审计边界。临床显示名称、岗位名称和患者抬头不添加“合成”前缀，也不显示“教学环境”等与当前诊疗无关的提示。

## 住院工作台

住院工作台以患者列表与患者详情承接实际岗位任务。列表可返回，详情页提供患者切换器；患者横幅在业务区滚动时保持可见，展示真实姓名、住院号、病区、当前床位、行政状态、预交金、累计费用与结算状态。药师使用窄 DTO，只展示允许读取的患者姓名、住院号、住院状态与药品过敏风险，不补造年龄、床位、费用或住院天数。

患者详情按“入科分床、诊断医嘱、检查检验、手术、费用、出院结算、病案”组织为可访问阶段导航，初次进入根据当前岗位与真实住院状态定位工作区。每次只显示一个阶段，横幅和导航位于独立滚动区之外；导航复用共享目录元数据，未访问阶段不挂载业务内容或查询业务详情，已访问阶段保留挂载以维持原输入、主操作选择基线与冻结的结算预览。切换阶段不会自动提交，也不会更换账户或岗位。跨病区环境另提供转科交接；默认一科一病区不展示转科入口。

每个阶段说明负责岗位、前置条件与实际办理路径，具体阻断仍以共享 Command 返回的业务事实为准。开具住院证后明确提示“登记员 → 住院登记 → 门诊住院证转收”，登记完成后提示病区护士接诊分床；出院沿用医生开医嘱、护士出区、收费员结算、护士清床的独立步骤。首页由医生提交、病案人员审核并归档，归档后通过病案区读取固定快照，诊疗写入入口关闭。界面只根据服务端已知状态给出下一办理环节，不复制原型状态机或显示虚构进度。

## 组件与组合

- 命令使用 Button。新增、确认、签署、签发和删除使用来自统一 Lucide 集合的图标加文字；熟悉的工具动作可使用带可访问名称的图标按钮。
- 表单使用 `FieldGroup + Field + FieldLabel`。错误同时设置 Field 状态、`aria-invalid` 和具体 `FieldError`。
- 状态使用 Badge，集合加载使用 Skeleton，操作中使用 Spinner，完整错误和风险提示使用 Alert。
- Card 只包裹独立重复项、弹层和真正需要边界的工具；页面分区不做浮动 Card，不嵌套 Card。
- 长表单的提交区使用顶边线和稳定高度，不用常驻阴影。

## 开发者组件目录

设置中的“开发者 → UI 组件”与公共 `/components` 路由共享同一个真实目录实现。目录静态导入 `@clinmesh/ui/components/*`，在单栏内容流中依次展示控件与表单、临床数据与状态、弹层与反馈、基础与导航、会话组件。

组件目录使用产品实际 token、主题和本地化文案，不维护第二套示例样式，也不使用同质化的名称清单代替真实组件。新增共享组件时，目录必须同步增加至少一个可视状态。

## 可访问性与验证

所有交互控件必须有可访问名称，装饰图标使用 `aria-hidden`，键盘焦点使用 `ring` token 且不被布局裁切。Tabs 保留方向键移动焦点和 Enter / Space 激活行为。Dialog 和 AlertDialog 在关闭后将焦点还给触发器。

产品可见改动从真实 Web 入口在桌面和窄屏视口验证，检查导航、长中英文、Tabs、表格滚动、弹层、主题和焦点。只运行覆盖当前 diff 的最小检查。
