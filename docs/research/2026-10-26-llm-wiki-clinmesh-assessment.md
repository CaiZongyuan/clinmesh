# LLM-Wiki 课程技术核验与 ClinMesh 借鉴评估

核对日期：2026-10-26。研究对象为飞书《LLM-Wiki》正文 revision 82，使用飞书 CLI 以用户身份读取；文档地址见来源 [F]。本轮取得正文及带块 ID 的内容，没有取得 8 个内嵌电子表格，原因是现有 CLI 身份缺少 `sheets:spreadsheet:read`；正文返回的外部参考标签也没有可追随的非图片 URL。下文独立找到并核验相应一手来源，不把它们误称为课程已经提供的可下载附件。课程所述 `page-specs`、脚本、冻结文件和查询轨迹未独立取得或复现，因此有关课程实例的事实均限定为正文自述。

本文记录外部证据和候选方案，不表示已经批准或实施。ClinMesh 当前行为由[临床流程](../architecture/clinical-workflows.md)、[Agent 集成](../architecture/agent-integration.md)、[指南全文交付（PR #221）](https://github.com/CaiZongyuan/clinmesh/pull/221)和[诊疗建议需求（Issue #179）](https://github.com/CaiZongyuan/clinmesh/issues/179)拥有；已有检索质量与工具缺口见[指南检索与 Agent 使用能力优化研究](2026-10-26-guideline-retrieval-agent-usability.md)。

## 采用判断

值得借鉴的是“保存原件，再建立可追溯、可增量更新的主题知识层”，以及让 Agent 通过搜索、读取和链接逐步补齐证据的方法。对 ClinMesh，合适的方向是在已有 SQLite 全文证据层之上试验少量经过复核的临床主题页，让 Agent 更容易找到一项决策所需的不同条款、条件和例外；原文继续承担引用依据。没有证据要求先替换 FTS5、增加向量数据库或引入完整 GraphRAG。

该课程适合用作知识组织和证据路径的教学参考，尚不足以作为自动临床知识编译器的选型依据。课程没有证明 Agent 能从任意指南自动形成正确知识页，论文也没有验证中国临床指南、PCI 场景或 HIS 业务动作。采纳范围应从受控主题索引与对照评估开始，不能把模型维护个人 Wiki 的自由写入方式直接授予临床运行中的共享指南库。依据：[F] §1.2、§2.6、§3.3、§4.4；[K] Architecture / Operations；[W] §4、Limitations。

## 原始来源实际支持什么

| 一手来源 | 已核验事实 | 可以支持的结论 | 不能据此推出 |
| --- | --- | --- | --- |
| Karpathy 的 `llm-wiki.md` [K] | Gist 创建于 2026-04-04；原文明示是 idea file 和 pattern，区分只读 raw sources、派生 Wiki、schema，提出 ingest、query、lint，以及 index 和 log | 持久主题知识层是一种可实施的组织模式；具体目录和工具可按领域选择 | 已有统一标准、经验证的临床正确率，或维护成本真的接近零 |
| `Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki` [W] | arXiv `2605.25480v2`，2026-05-25 首投、05-26 更新；作者为 Haoliang Ming、Feifei Li、Xiaoqing Wu、Wenhui Que。系统提供结构化页面、双向链接、`wiki_search`、`wiki_read` 和 Error Book | “编译知识结构 + 多步取证 + 持续纠错”已有明确研究实例 | 与 Karpathy 模式属于同一实现，或对 ClinMesh 必然更快、更准、更省 |
| 原始 RAG 论文 [R] | 结合参数化生成模型和非参数记忆；具体实现使用 Wikipedia 稠密向量索引和神经检索器 | RAG 是利用检索证据辅助生成的方法；原始实现有明确模型与索引选择 | 所有 RAG 只能使用向量库，或加入 Wiki 后就不再属于检索增强生成 |
| Microsoft GraphRAG 官方文档 [G] | 从 TextUnits 提取实体、关系及相关信息，建立社区层级与社区摘要；区分 Global、Local、DRIFT 和 Basic Search | GraphRAG 有图结构、社区处理与相应查询职责 | 普通 Markdown 互链已经等同 GraphRAG，或所有知识图谱都采用同一实现 |

Karpathy 原文关于中等规模适用性及维护成本的表述属于作者经验与构想，未提供该领域的受控性能证据。[W] 是具体研究系统的 arXiv 论文；其结果可以支持开展试验，不能代替本项目数据与任务上的验证。课程本身也明确区分这些来源，未声称 Wiki、RAG 与知识图谱互相淘汰。[F] §1.1、§1.4。

## 课程实例的证据边界

正文明确写道：“页面内容先在公开规格中确定，脚本只按规格落盘并检查统一结构。”八页终态来自预先确定的 `page-specs` 与确定性的 `compile_wiki.py`。因此，它展示的是透明的结构构建方法，而非同一课堂 Session 中的 DSH Agent 自行理解四篇任意资料并实时编写八页。课程已经主动说明此界限，评估时应保留，不能把它解读成已完成自动知识编译。[F] §2.6。

| 课程正文所述演示 | 能说明什么 | 尚未验证什么 |
| --- | --- | --- |
| R1–R4、P1–P8、四类页面及 30 条链接 | 可以建立一篇来源支持多页、一页综合多篇来源的主题结构 | 临床信息是否完整，任意新文档能否正确归类，以及链接是否具有医学语义 |
| 单页事实、跨页综合、语料外问题三类查询回放 | 指定问题可按索引、页面、原件形成可见读取路径；指定无证问题可停止强答 | 通用准确率、所有语料外问题的拒答率，以及优于现有检索的幅度 |
| 增加 R5，仅更新 P1、P5、P7 和导航、日志、清单，再回放固定问题 | 受影响页面可被局部更新，并可检查回答是否采用新证据 | 自动发现外部新版、可靠解决所有冲突、大规模无人维护 |
| 薄只读浏览页与文件清单 | 人和程序可以读取同一组派生文件 | 完整权限审计、多租户、容灾、问答后端或医学质量评估 |

这些是正文描述的课程结果，本轮没有取得其底层文件逐项复算。正文还将 rc.6 本地验证、rc.7 CLI 查询和 rc.11 固定官方源码声明分开；工具轨迹只能证明访问过哪些对象，不能作为隐藏推理或最新 DSH Desktop 完整验收。缩微 Markdown 示例也不能继承完整 FF–LLM Wiki 应用宣称的 SQLite、图谱和评估能力。[F] §3.3–§4.4。

## 论文效果如何解读

[W] 的系统比课程缩微示例更完整：编译时先选择要维护的页面，再生成或更新页面；查询时让 Agent 组合搜索和读取；Error Book 将断链、缺失字段、引用格式问题、无依据事实和跨页矛盾等检查结果转为后续约束和修复任务。[W] §3、附录 F。这个机制值得借鉴为“发现问题、登记问题、修复后重新核对”，但模型判断“有依据”仍需适合任务的外部验证。

论文报告了多跳问答优势，同时明确保留以下实验条件和限制：[W] §4、§6、Limitations、附录 G。

- HotpotQA、MuSiQue 和 2WikiMultiHopQA 各使用原始顺序前 500 题，语料是这些题所附上下文段落的并集，属于给定上下文场景，并非从整个 Wikipedia 开放检索。
- 同一比较使用 GLM-5.1 作为回答模型及需要模型的索引处理，向量相关方法采用 Qwen3-Embedding-8B。BM25 和 Dense RAG 基线是固定 top-5 段落；Wiki Agent 最多可调用 15 次工具。作者明确比较的是端到端系统，并没有等化每一项检索能力，不能把差异全部归因于 Markdown 页面本身。
- 摘要所述较若干基线提高 2.0–8.1 个 F1 点，是对应基准条件的结果。AuthTrace 还采用模型评分协议；这些分数不能直接转换为临床适用性、医学严重错误率或处方字段正确率。
- 查询延迟并非全面更低。例如 MuSiQue 上 Wiki 为 27.1 秒/题、Dense RAG 为 26.9 秒/题；GraphRAG 在其比较配置中更快，但准确性表现不同。数字依赖这些模型、数据和检索配置，不能作为 ClinMesh 延迟承诺。
- 初始编译需要额外成本；达到上万页面时，目录大小、页面选择、陈旧事实及全局维护会成为问题。作者将大规模动态维护等列为后续工作，未证明任意更新频率下都可以低成本保持正确。

Microsoft 的 GraphRAG 入门文档也提示索引会消耗较多模型资源，并建议先从小语料理解流程；官方主页建议针对数据调整提示。[G] 因此，目前没有依据为本项目跳过原文质量与固定检索评估，直接建设更重的图索引。

## 映射到 ClinMesh 的候选方案

本轮项目对照基线为 `0ec0f38ff4aa4521f79fc07ebf02d4dcd77357d2`。现有实现已具备独立 SQLite 原文库、FTS5 trigram、短词兜底、主题别名、来源及哈希、用途过滤、物理页定位，以及最多 8 段和 48 KiB 的证据准入预算。内置诊疗建议从非人口学病例证据拼接一次检索，再合并固定证据；这不同于模型自主多轮补查。右侧 DSH／CLI 尚未由诊疗建议路由获得独立指南检索授权。实现入口分别见[指南检索](../../apps/server/src/infrastructure/sqlite/guideline-corpus.ts)、[建议服务](../../apps/server/src/application/doctor-recommendations-service.ts)及[Agent 接入合同](../architecture/agent-integration.md)；详细分析见[已有研究](2026-10-26-guideline-retrieval-agent-usability.md)。

候选结构为“原件 → 可靠提取的全文证据 → 复核主题页／决策索引 → 受控搜索与原文读取 → 病例适用性核对”。主题层解决按问题组织和发现关联条款，全文层继续提供可核查原文，业务 Command 与原有确认流程继续拥有诊疗动作权限。下列各项均为后续候选，并未因本研究自动接入。

| 候选借鉴 | ClinMesh 中的具体落点 | 必须保留的边界 |
| --- | --- | --- |
| raw 与派生层分离 | 原 PDF、原始哈希及提取产物保留；主题页可重建 | Wiki 或 OCR 不覆盖原件；提取失败、乱码及未复核部分保持不可引用状态 |
| 按临床问题组织主题 | 首批围绕 CCS／ACS 区分、PCI 适应证核对、抗栓、肾功能风险、术后判读等少量决策建立索引 | 这里只确定组织主题，不预设任何患者应该接受 PCI 或使用哪种药物 |
| 结论与原文分开 | 每项结论绑定 source ID、版本/hash、物理页或条款，以及适用人群、阶段、例外和原始推荐等级 | 没有取得或复核的字段为未知；不把多机构分级合并成自造统一医学分数 |
| 导航链接与依据分开 | “还应读什么”可指向关联主题；“为什么成立”必须指向具体原文 | 指向某篇文件或某个页面不证明其中每条结论有依据 |
| search/read 组合 | 内置模型与外部 Agent 复用受控只读检索内核，允许有界地展开完整条款和例外 | 工具仅接收受控问题与证据 ID，不开放任意路径、SQL 或 URL；病例可见性、用途限制、撤回状态每次复查 |
| Error Book 与 lint | 登记缺链、失效版本、遗漏例外、相互冲突和无证结论；修复后复跑受影响问题 | Agent 提交问题或修改候选；经复核、验证和发布后才成为共享临床知识，运行时读取不同时授予发布权限 |
| 增量维护 | 保留来源→条款→主题→引用结果的依赖；源版本、用途、提取规则或复核状态变化后使依赖项失效 | 更新日志和哈希只能证明文件变化，不能替代内容复核；同一来源变化不能遗漏相关旧结果 |

一个实际使用路径可以是：Agent 针对当前合成病例提出明确决策问题，先定位相关主题，再读取主题所列的原文条款及例外；核对当前病例是否满足适用条件，列出尚未取得的资料；最后沿用现有生成后核验与医生确认。主题摘要帮助找证据，不能把一般推荐填成患者事实，也不能仅凭药名依据推定剂量、频次和疗程。[已有研究](2026-10-26-guideline-retrieval-agent-usability.md)已说明对应缺口，本报告不另建一套产品合同。

## 建议的采用顺序与验收问题

先完成旧指南和新冠心病资料的可靠获取、提取质量、版本清单及测试安装分发，再从已复核原文中选择少量主题做试验。材料与分发工作有独立范围；主题层、search/read 接口及相应授权需要另行形成需求与验收，不能混为“入库完成后自然具备”。

试验应比较现有 FTS、改进查询与上下文读取、以及再增加主题索引三种配置；尽量保持同一语料版本、同一问题、相同可见病例、模型及合理一致的取证预算。这样才能区分改进来自更好的查询、多轮读取还是主题组织。无须先搭建完整图数据库，也不以页面数或链接数作为医学质量指标。

| 验收问题 | 应取得的证据 |
| --- | --- |
| 主题页有没有丢失决定性信息？ | 独立复核的完整条款，包括阈值、单位、否定、例外、表注及适用阶段；逐项对照原件 |
| 比当前方案更容易找到必要依据吗？ | 同一固定问题集上必要条款及例外的召回、错误适用证据、读取次数和证据覆盖说明 |
| 引用能解释一个具体判断吗？ | 判断→原文的可解析映射；原文确实支持该判断，不能只检查 ID 存在 |
| 无证和冲突能被正确处理吗？ | 刻意缺证、版本冲突、人群不适用等合成输入下，未知保持未知、缺口可见、错误行动被阻止 |
| 来源更新后旧知识还会继续误用吗？ | 替代、撤回、用途收紧、提取或复核状态变化后，受影响主题和旧建议失效的可观察结果 |
| 维护与查询成本值得吗？ | 分开记录初次编译、人工复核、增量更新与每次查询的资源和耗时，不能只统计回答阶段 |

临床负责人确定的参考答案与证据集应独立于被验收模型，不能只用 Wiki 自己生成的问题和答案证明自己正确。初期工程验证使用合成病例、受控 Provider 和临时数据库；本轮未运行真实模型、压测、课程脚本或医学效果试验。
