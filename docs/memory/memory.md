## 协作与交付偏好

- 修复和 CI 优先；复用仍有效的界面证据，只按实际视觉改动补充必要截图，不默认重拍完整矩阵，也不以补图阻塞提交、CI、Ready 或审查。

- 用户要求先通过 `to-spec`、`to-tickets` 整理和拆分的任务，设计确认后先完成规格、测试 seam 和拆票审阅，明确获准实施后再写业务代码；已批准的 spec、测试 seam 和拆票结构没有未决分支且已获实施授权时，直接连续实施，不重复展示待发布全文或逐项请求内容批准。

- 已确认局部 UI 调整方向且用户明确要求“直接开干”时，沿用已有 Issue、当前对话和实施授权，直接完成本地修改和必要验证，不重复拆票或阶段确认；尚无 Issue 时先按根规则创建或关联，再修改代码。外部发布仍按已有授权执行。

- 仅按需使用 `superpowers:brainstorming` 的可视化辅助，不启用其完整流程或其他 superpowers skills；开发与交付遵循仓库自身工作流。

- 全局 DSH 不再托管 ClinMesh、旧 HIS Demo 或本项目专用的 React Surface、AG-UI 链接与配置。ClinMesh 开发和验收只使用项目隔离的 DSH 运行环境；排障或升级时不得重新接入全局 Profile。

- ClinMesh 与实际必需的 DSH 桥接组件（React Surface、AG-UI）持续适配最新公开正式版和 RC，不跟踪 alpha。升级范围按实际需要确定，不因插件已安装就升级或逐项验收全部插件；其他插件保留原配置和数据。接口或行为变化时主动更新 ClinMesh 和必要组件，不以长期停留旧版本或修改 DSH 来迁就旧实现作为维护方案；DSH 官方仓库 `deepseek-ai/deepseek-harness` 由官方维护，不修改其源码，也不维护宿主补丁或 fork；集成需求由 ClinMesh 与必要桥接组件通过现有宿主扩展能力实现，能力不足时调整方案。桥接组件未及时适配时优先贡献修复，必要时维护桥接组件 fork。依赖锁用于复现已验证组合，不代表停止跟进上游。持续升级自动创建 PR，由用户决定合并。

- 用户要求“完整整个 issue”时，一口气完成全部 tickets，最终只提一个集成 PR。Tickets 用于执行和追踪，不自动等于一个 ticket 一个 PR。

- Merge、发布或合并现有工作区变更仍以用户明确授权为边界；授权已经给出后直接执行，不再增加一次确认。

- 用户要求提交并推送当前工作区修改时，沿用当前非 `main` 工作分支；“独立工作分支”不表示每次提交都新建分支。针对已有 PR 的修复，交付目标是该 PR 的 head 分支；审查或验证使用的临时分支不改变推送目标，不另推分支或另提 PR，除非用户明确要求。只有当前位于 `main`、用户明确要求或任务确需隔离时才另建分支。

- 合并前先核对用户约定的交付分支和 PR 的实际 base。已指定总 Issue 集成分支时，子 PR 只合入该分支；PR 原有的 `main` 目标不构成改投主线的授权，发现不符须先纠正 base 再合并。只有整个集成成果另获主线合并授权后才进入 `main`。

- 用户授权合并 PR 时，收尾同步实际目标分支；目标为 `main` 时切回并同步本地 `main`，目标为集成分支时同步该分支。删除已合并的本地开发分支前，先确认没有未保存修改、合并后新增提交或其他 worktree 占用，保留这些内容后再清理。涉及子模块开发提交时，同时核对子模块的 PR、目标分支和父仓库引用，取得该仓库的合并授权后完成对应收尾。

- 用户明确要求把当前工作区 changes 一并提交时，先辨认并保真保存这些修改，再纳入目标 PR；不丢弃、不改写为自己的内容，也不额外推送原工作分支。

- 用户询问进度时，先报告已经完成、正在处理和剩余阻塞，然后继续执行，除非用户要求暂停。

- 用户询问合成演示账号或密码时，从当前 Scenario 或 seed owner 直接给出可试用信息；真实凭证、平台密钥和患者信息永不写入本文或公开 artifact。

- 用户要求运行开发分支进行手工测试时，启动该分支的真实应用，沿用已有 Provider 配置和完整参考目录，并使用持久化业务数据；需要隔离时使用现有数据的一致备份，明确告知数据副本的边界，不用少量 fixture 代替实际运行环境。

- UI 预览参考 `agentic-axum-saas-demo` 的体验设计方式，按任务交付可运行且保留版本的交互体验，不在正式 Web 内维护长期 mock 展示站或方案切换器；具体规则见[交互预览](../agent-development.md#交互预览)。
