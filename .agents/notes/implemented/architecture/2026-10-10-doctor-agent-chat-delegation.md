# Agent Note: 医生助手聊天委托代问

Status: implemented

## Problem

同一个问诊输入框同时承接向患者提问和向助手交代任务，医生必须靠提交按钮判断接收者。右侧原生助手聊天已经能表达任务，但消息的 `kind:user/rpcId` 可由注入入口构造，不能单独作为医生授权；主会话模型声明已得到许可也无法证明来源。

## Decision

医生通过现有右侧「ClinMesh 医院助手」聊天明确交代追问范围；左侧输入只向患者发送问题。该入口部分取代 [纯查询绑定 Note](2026-10-08-doctor-agent-query-binding.md)中问诊区独立提交的选择，读取、任务锚点、proof 和恢复决定继续适用。详细合同由 [#176 规格](../../../../docs/spec/2026-10-08-doctor-agent-context-execution.md)拥有。

Client 观察公开 `SessionSnapshot.pendingSubmissions` 的新提交，经当前已提交 frame 请求原文签名凭证，再向 Host 登记；原生 `prompt` 不被替换或重发。Host 首次医院工具执行前等待凭证并匹配原 RPC、Session、正文 hash 与输入绑定，解决登记与原生发送的竞态。快照正常退役表示已入队，不当作取消；旧快照不补授权。

Host 对已选病例的本条真实输入作一次独立、无工具的结构化意图识别，使用原请求模型，不提供历史、患者资料或业务 persona。只有明确的当前委托及具体范围建立代问许可；结果还须引用原文，失败、无效或含糊时拒绝。先核实来源再识别意图，主会话模型的工具调用和自述不能建立许可。原病例、身份、任务标记、精确问诊绑定与未知结果暂停仍由现有链路逐次核对。

## Alternatives considered

- 保留问诊区按钮但调整文案：输入仍有两个接收者，不能消除语义混用。
- 让聊天模型填写授权字段：模型、历史或工具结果会自行取得代问能力。
- 只根据关键词授权：无法可靠区分否定、引用、假设和功能讨论。
- 直接相信 `kind:user/rpcId`：公开注入入口可构造相同来源形状，缺少真实侧栏提交证据。
- 假定 Client 总能先登记：原生发送不等待快照观察者的 HTTP，必须由 Host 门禁明确等待。
- 接管 composer 或修改 DSH：当前公开快照、签名凭证与执行 hooks 已能承接，保留宿主维护归属。

## Consequences

每个已选病例医院工具任务增加一次模型意图识别，会增加延迟与模型调用成本。自然语言识别仍可能误判，不能代替来源、病例、操作白名单或正式人工审阅；真实模型样本和确定性权限负例共同验证。当前任务只接收有界纯文字输入，附件不建立医院执行任务。

输入凭证 version 2 与新的 proof 委托 hash 必须随 Host、Surface 和 Server 一起部署；旧代问客户端不能降级授权。任务结束后的晚到登记、取消及对象变化仍需拒绝，正常同病例读取和原生提交退休不应被误判为失去授权。验证从真实侧栏提交，观察实际问诊次数，并保留未知结果不重放的故障注入。
