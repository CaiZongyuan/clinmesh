# Agent Note: 诊疗开具工作区与两阶段布局

Status: implemented

## Problem

将医生目录与填写表单放入添加对话框，会使手动开具入口与 AI 待办脱离。首次开具时拆成目录、填写和待办三栏又挤压字段空间；正式开具后若只显示第一条记录或隐藏待办，未开具的第二项难以继续处理。需求由[诊疗建议规格的 R 条件](../../../../docs/spec/2026-10-13-doctor-guideline-recommendations.md#自动准备与待开具清单)拥有。

## Decision

诊断、处方和检查保留独立业务栏目。`DoctorOrderWorkspace` 只组织已有页面提供的开具表单、待办、记录列表与详情，不拥有领域状态、查询、草稿或提交动作。开具前目录与字段上下融合为一个主要栏，旁侧放较窄待办；开具后主要空间交给正式记录详情，左侧保留开具入口及待办、正式记录列表。宽屏比例分别约为 70/30 与 35/65，窄容器按可用宽度堆叠。

阶段继续由正式诊断确认、处方或检查申请集合派生。草稿保存、自动准备、筛选为空和申请取消都不把页面当成新的首次开具。目录 picker 复用原检索、分页、错误恢复和产品包装身份；`collapsible` 默认关闭，开具后可收起结果而保留搜索行，聚焦或明确操作再展开。目录与字段只有一份活动输入，不增加另一套临床表单状态。

待办仍使用原准备器与确认入口，完整人工项目不依赖模型成功。正式成功仅消费本次选择，未选择项目与后来手改保留；所有已开具项目均可从列表选择对应详情。多个药品遵循整张处方模型，多个检查形成独立申请并保留各自报告。已有有效处方阻止另行开出新有效处方，剩余未开具项目的展示不扩大处方能力。原子确认、来源防过期、版本及审计仍由[准备确认决策](2026-10-18-prepared-clinical-confirmation.md)拥有。

只有只读思路的完成结果可以保留 `ready` 作为处理状态，但界面按实际可执行项目说明结果，不能把“有思路”表达为“有待确认项目”。详情仍收在“依据与说明”，病例、指南、目录或核验问题不变成患者的统一前置缺项。

本决策部分取代[诊断与处方两阶段视图](2026-10-10-diagnosis-prescription-workspace.md)中的目录与字段布局，以及[准备确认决策](2026-10-18-prepared-clinical-confirmation.md)中的默认添加对话框；两者的正式事实、草稿与事务边界保持各自归属。

## Alternatives considered

- 继续通过添加对话框进行首次开具：复用旧入口，但医生不能直接在业务页完成目录选择与填写。
- 使用开具、待开具和已开具三个页签：节约横向空间，但割裂同一临床流程，也使未开具项目在阶段切换后难以发现。
- 三个并排栏分别放目录、字段和待办：各块可见，但窄工作区无法给字段与主要任务分配足够宽度。
- 所有阶段永久展开完整目录并使用相同宽度：首次易用，但开具后目录占据正式记录详情的主要空间。
- 新增服务端页面阶段或多处方能力：与本次布局目标无关，且会扩张现有领域合同。

## Consequences

页面组件继续拥有表单、正式记录选择与领域动作；共享布局与目录折叠只保存视图状态。组件回归验证输入保留、待办消费与第二项记录选择，真实 Web 和 React 18/19 ShadowRoot 合同验证目录行为、两阶段宽度、键盘及窄容器。既有 HTTP/SQLite 回归继续证明批量原子性、版本、幂等和正式资源，不以原型代替业务证据。
