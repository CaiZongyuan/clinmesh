# Agent Note: 胸片与胸部 CT 阅片闭环

Status: implemented

## Problem

门诊仿真只有结构化检验报告。医生开立胸片或胸部 CT 后没有可看的影像，Agent 评测也无法覆盖“开单、等报告、阅片、确认”这段流程。合成像素不能支撑阅片：没有可信的病灶，也没有可核对的报告依据。接入真实影像又与“只使用合成数据”的规则冲突，并带来素材分发、报告正确性、病例一致性和隐藏信息泄漏四个问题。

本决策由 [issue #123](https://github.com/CaiZongyuan/clinmesh/issues/123) 交付。当前行为的详细归属是 [系统架构 8.7 与 10.7 节](../../../../docs/architecture.md)、[前端架构的阅片器](../../../../docs/frontend-architecture.md#阅片器) 和 [影像素材清单](../../../../imaging-assets/README.md)；本记录只保留取舍。

## Decision

**真实影像是规则的窄例外。** 例外只覆盖公开授权、已去标识并登记在清单中的影像像素及其来源标识。患者身份、病史和本院事实仍全部合成，来源受试者的其他信息不导入病例。像素不进入 Git、日志、模型输入或 SQLite；Agent 在开发和验证中同样不读取像素。

**清单归 ClinMesh，像素归本地素材目录。** 清单随仓库公开提交，写明合集 DOI、许可、来源 UID、每个来源文件的哈希、转码版本和输出哈希，同步由清单驱动且可重复。cn-health-data 只处理表格型参考数据并明确不处理患者数据，因此不承载影像。

**报告由模型整理、规则核对、人工复核。** 模型只读结构化的来源读片标注，不读像素；自动核对拒绝与标注不一致的草稿；人工对照影像签署，签署绑定的哈希覆盖输出像素、来源实例、合集许可、整理规则文件、引用该素材的适配条目、标注和报告内容，任何一项变化都要重新签署。报告范围限于来源标注覆盖的肺结节所见，不描述标注没有依据的结构。未发布的素材不进入匹配。

**病例事实与补充细节分离。** 匹配只依据来源编码，把素材当作对既有病例的补充影像表现；它不改写疾病、侧别、手术史或已固定的事实，冲突、未知和无素材都不配片，不当作正常。首批素材都是未手术的胸部，因此冲突手术（肺移植、胸骨切开、瓣膜置换、起搏器等）对每个条目生效，曾患肺癌的病例也不能使用阴性素材。未覆盖疾病清单按固定版本 Synthea 全部模块实际产生的疾病编码逐项整理，而不是凭印象列举；Synthea 升级时需要重新核对。病例与素材的对应关系只留在管理员边界。

**放射与检验共用申请生命周期内核。** 两类申请共用状态机、幂等、版本和审计，类型策略只提供差异；申请表的类型列不枚举取值，病理等后续类型只增加适配器和自己的明细表，不重建申请表及引用它的放射表；已发布的检验合同不改名、不扩大语义，放射使用新增的窄操作。

**阅片器是轻量外壳加可替换引擎。** 外壳负责导航、全屏和可用性，按序列 `kind` 查登记表取得引擎、像素块路径函数和序列摘要；位置类型由引擎自己声明，外壳和调用方不构造位置，因此新增分层瓦片等 `kind` 不改动外壳和放射页面。HU 换算、方向、层面顺序和 MONOCHROME1 在服务端摄取时规范化；窗宽窗位、显示反相和纵横比例是 `core` 中的纯函数，浏览器与后续服务端渲染共用。当前只有 canvas 灰度堆叠引擎。

**素材流水线是通用素材包存储加摄取适配器。** 通用部分负责来源下载与校验、原子安装、回执、修复和读取缓存，不认识检查类型、模态、来源数据集或读取寻址；放射适配器拥有 DICOM 规范化、`series.json`/`frames.bin` 布局和按帧按块读取。病理等后续素材包增加自己的适配器、清单目录和素材目录。

**Agent 通过报告参与，阅片留给人。** DSH Tools 与 CLI 只读取申请、报告和阅片入口。DSH browser Tool broker 每次注册最多 32 个 Tool，医生“接诊”页原有 27 个，因此放射只新增草稿、开立、取消、重试和更正五个 Tool；已阅并入通用的报告已阅提案，导航阅片并入栏目切换。影像未在人类面前成功显示时，已阅提案被拒绝。

## Alternatives considered

**使用程序生成的合成影像。** 完全符合原有规则，但没有可信病灶，也无法让报告有据可查，阅片会变成对着噪声确认。真实去标识影像配合窄例外才能让“看片”有内容。

**把像素存入 SQLite 或作为 FHIR Binary。** 部署更简单，但一例 CT 数百 MB，会拖垮数据库备份和 perf gate，也让像素进入一切读数据库的路径。数据库只保存对应关系；清单和哈希只能校验，不能恢复，因此备份需要包含素材目录中的来源文件或可独立校验的副本。

**把素材交给 cn-health-data 分发。** 可以复用现有发行流程，但该仓库的产物是经 Git 分发的 SQLite/Parquet，并明确排除患者数据。

**直接使用来源数据集的报告或让模型看图写报告。** LIDC-IDRI 没有文字报告；让模型读像素既违反像素不进入模型输入的边界，也无法核对。结构化标注到模板化报告的路径可以被规则自动检查。

**引入 Cornerstone 等完整医学影像库。** 功能完整，但体积、Web Worker 与 WASM 加载方式和 DSH lazy-CJS 宿主不相容的风险都高，首期只需要灰度堆叠。引擎接口保留了以后接入的位置。

**为放射新增全部七个 Agent Tool。** 语义最直接，但医生页会超过 broker 上限并在运行时注册失败。按当前诊疗页发布 Tool 可以根本解决容量，但会改变既有检验 Tool 的发布时机，需要单独设计；病理接入前必须先做这件事。

**在通用存储中按模态分支。** 改动最少，但每增加一种模态都要修改共享的安装与读取代码，放射行为也随之暴露在回归风险中。

**为放射复制一套申请状态机。** 实现独立，但取消竞争、重试、重复投递和修订的规则会在两处漂移。

## Consequences

仓库中出现了真实来源的标识（受试者编号、Study/Series/Instance UID 和文件哈希），它们是公开数据集的公开标识，用于同步和追溯。任何录屏、截图或再发布都要保留清单要求的署名。

素材覆盖面决定了能演示的病例：首批只有一个阳性条目和两个阴性条目，其余病例开立放射申请会以“未取得结果”结束。阴性条目适用同一类病例，按来源哈希二选一，因此部分阴性病例只有 CT。0028 与 0668 的来源性别和年龄未公开，规则按成年、不限性别使用。

报告只覆盖肺结节相关所见，不是完整的胸部影像报告；首批复核人不是放射科医师，签署中如实记录。胸片读片标注中的 `confidence` 与 `subtlety` 没有公开定义，只把全员一致的极端值当作可见或不可见。规格中“匹配同时检查 Persona 中明确的症状信息”没有实现，Persona 是自由文本，没有可靠的结构化依据。

Synthea 导出的病例已经写下就诊之后的病程，匹配以 Index Encounter 的开始时间判断疾病是否缓解；这条规则是在真实 Provider 生成的病例上发现并修正的，合成 fixture 现在按真实形态生成缓解时间。

医生“接诊”页的 Tool 目录曾到 32 个，现已改为按当前诊疗栏目发布，见 [医生 Tool 按诊疗栏目发布](2026-10-02-doctor-tools-by-section.md)；放射 Tool 归属“检验”栏目，病理等检查类型的 Tool 按所属栏目计入名额。

Docker 一键镜像不包含清单与素材，其中的放射服务显示为未开展。
