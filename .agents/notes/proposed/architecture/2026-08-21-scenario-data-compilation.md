# Agent Note: Scenario 数据编译与参考数据接入

Status: proposed

## Problem

ClinMesh 需要生成彼此一致的患者、医院目录、临床事件、费用、库存、外部系统响应、Hidden Fact 和 Reveal Policy。Synthea 能提供患者临床历史素材，但其地域、机构、支付方和 FHIR R4 输出不能直接表示中国公立医院流程。医保、药监和卫生标准网站提供真实代码或政策参考，却通常没有明确允许整库再分发，也不提供某家医院的运行事实。

如果各页面分别生成演示数据，处方、收费、检验、库存和审计会产生相互矛盾的事实。直接提交官方目录快照还会让来源版本、地域、生效日期和许可条件失去控制。详细来源能力与限制由[合成医院数据来源研究](../../../../docs/research/synthetic-hospital-data-sources.md)维护。

## Proposal

建立离线 `Scenario compiler`，将外部素材和项目维护的合成规则编译为版本固定的 Scenario package。运行时只安装已编译且校验通过的包，不访问外部参考网站，也不把 Synthea 作为在线依赖。

编译输入分为四类：

- `Hospital Baseline`：虚构榆江市三级综合公立医院、固定为 2026-08-01 的政策基准日、服务能力和规模边界；首期不声明任何省级医保规则。
- `Reference Data Package`：术语、目录、政策和映射的版本固定集合，每个输入记录来源 URL、发布者、获取时间、生效期、地域、内容哈希和再分发等级。
- 生成器输入：随机种子、虚拟时间、人口与利用率分布、临床模块、流程模板和故障规则。
- 作者真值：患者病情、可揭示证据、业务前置条件和外部系统结果的结构化定义。

Reference Data Package 按使用条件分级：明确允许再分发的数据可以固定原始版本；许可未确认的数据只允许由受控构建步骤从官方入口获取并保存哈希，仓库仅提交映射规则和最小合成子集；只能人工查询或受版权约束的资料仅用于校验项目维护的映射；真实患者、真实交易、真实追溯码、真实医院配置和凭证永不进入管线。

编译顺序为 `acquire -> normalize -> map -> synthesize -> compile -> validate -> publish`。获取层不能成为应用运行依赖；规范化层必须验证外部结构并保留原始来源键；映射层显式记录源代码、目标代码、适用版本、映射关系和审核状态，不能依赖模糊字符串自动合并；合成层只产生虚构身份和业务事实；编译层从同一结构化真值派生 FHIR R5 资源、领域 fixture、费用、库存、事件和外部规则。

Synthea 可以在后续成为可替换的患者历史适配器。该适配器必须读取版本固定的 R4 Bundle，转换到 ClinMesh 中间模型，丢弃美国机构、支付方和标识符语义，再由 Scenario compiler 生成满足项目 profile 的 R5 资源；首期只接受项目维护、可人工审阅的结构化合成输入，不建设 Synthea 导入路径。

首期维护两个发布档：`golden` 是规模小、字段完整、可人工审阅并覆盖普通门诊发热闭环的数据集；`density` 使用相同 schema 和业务规则扩大患者、队列、目录和历史事件数量，用于列表密度、分页和性能验证。二者共享同一套不变量，不能用另一个简化数据模型。

临床和业务结构先生成，文书叙述后生成。未来 LLM 只能根据结构化事实生成主诉、现病史、报告描述等文本，输出必须通过事实引用、否定项、时间和敏感信息检查；首期不引入 LLM，诊断代码、剂量、价格、库存移动和支付结果始终来自受验证的结构化输入。

OpenHIS 只提供中国医院领域词汇、状态机、表关系和导入形状的参考。ClinMesh 不复制其生产配置、外部系统凭证、真实机构数据、完整 seed 或 PostgreSQL 物理模型。

每个已发布 Scenario package 包含 compiler 版本、schema 版本、FHIR IG 版本、Reference Data Package 标识、全部输入哈希、生成器版本、种子、虚拟时间和 canonical state hash。相同固定输入必须产生相同规范化业务事实；真实构建时间和文件压缩元数据不进入 canonical hash。

## Alternatives considered

**直接运行 Synthea 并导入 FHIR Bundle。** 这能快速获得患者记录，但保留了美国地域、支付方和机构假设，输出版本也是 R4，无法生成中国医院目录、岗位流程、费用、库存和共享评测真值。

**把医保、药监和 OpenHIS 目录完整复制进仓库。** 这降低首次启动成本，却无法证明多数官方目录的再分发权利，也容易混入真实机构配置、过期政策和敏感凭证。

**由各业务模块独立 seed。** 模块局部实现简单，但同一处方的临床、收费、库存、Action Trace 和审计事实无法稳定对齐，reset 也不能复现完整状态。

**让 LLM 直接生成完整病历和业务数据。** 文本更丰富，但金额、剂量、引用、状态机和时间不可可靠验证；LLM 因此只承担可从结构化真值校验的叙述生成。

## Acceptance criteria

- Scenario compiler 对输入和输出使用版本化 schema，并拒绝未知字段、悬空引用、跨患者引用、金额或数量精度错误、非法状态和不满足 FHIR R5 profile 的资源。
- 每个外部输入都有来源、生效期、地域、哈希和再分发等级；构建日志不会记录凭证或患者信息。
- 相同 compiler、Reference Data Package、生成器、种子和虚拟时间产生相同 canonical state hash。
- 普通门诊发热数据从挂号、分诊、接诊、首次收费、模拟 LIS、复诊、病历签署与 Encounter 完诊、二次收费到发药和 Scenario Run 完成均可执行，临床、费用、库存、任务、Action Trace 和审计引用同一业务对象。
- 病例未经临床专业人员审阅时只能标记为 `draft` 或 `demo`；完成审阅后才可发布为 `golden`。
- `density` 数据使用与 `golden` 相同契约，并覆盖列表分页、筛选、空态、并发版本冲突和队列积压。
- 仓库扫描拒绝真实患者信息、真实医保或支付凭证、真实药品追溯码、平台密钥及已知 OpenHIS 敏感配置。
- 编译器有许可证策略测试、映射测试、跨投影一致性测试和固定种子快照测试；Synthea adapter 进入范围时另行增加 R4 到 R5 合约测试。

## Risks

官方查询入口和字段可能无版本通知地变化，构建获取器需要显式失败并由人工审核更新，不能静默接受新结构。

目录代码之间并非总是一一对应。未经审核的自动映射会造成临床和计费语义错误，因此首期应保持小型、场景驱动的已审核映射集。

固定种子只能保证固定工具链内复现。生成器、排序、序列化或 FHIR profile 变化必须产生新 Scenario 版本，不能承诺跨版本 hash 不变。

合成文本仍可能产生与真值冲突或看似真实的身份信息。发布前需要受限模板、事实校验和敏感信息扫描；无法验证的文本不得进入 `golden` 数据集。
