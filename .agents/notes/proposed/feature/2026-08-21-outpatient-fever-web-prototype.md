# Agent Note: 普通门诊发热 Web 交互原型

Status: proposed

## Problem

ClinMesh 的首位设计评审者不熟悉 HIS，单独展示挂号、医生或收费页面无法解释岗位之间如何交接，也无法验证多用户是否真的共享同一患者状态。传统按系统模块展开的全量菜单会掩盖首期业务闭环，并诱导实现尚未支持的住院、医保和病案能力。

原型还需要回答医生工作台应以工作队列、患者病历还是就诊流程为主要信息骨架。这个问题会影响后续页面路由、查询边界、组件共享和桌面信息密度，不能只用静态线框图决定。

## Proposal

本 Note 只限定 throwaway 原型的设计边界，不定义正式业务顺序、API 或验收范围。正式首期以[多岗位发热门诊首期闭环](../../implemented/feature/2026-08-23-outpatient-fever-first-release.md)为准；原型中的“发药后完诊”和 evaluator 页面不得迁入正式状态机。

建立仅用于设计评审的 Web 原型路由 `/prototype/his-flow`。原型使用内存中的单个合成 Workspace/Epoch 和一名发热患者，让评审者通过预置合成账户切换岗位，并观察同一状态如何进入不同岗位的工作队列。原型不调用真实认证、FHIR 或 Command API，也不作为生产实现复用。

全局壳层持续显示虚构医院、Workspace、Epoch、虚拟时间、当前岗位和地点。角色切换保留内存中的患者状态，模拟多用户看到同一 Epoch；每次动作写入可见的业务时间线。左侧导航按任务表面组织，不展示未实现模块。

原型页面如下：

| 页面 | 主要 Actor | 决策或动作 |
| --- | --- | --- |
| 登录 | User Account | 选择预置合成账户并建立演示会话 |
| 岗位选择 | Workspace Membership | 选择允许的 Practitioner Role 和地点 |
| 全院流程 | 所有岗位 | 查看患者当前阶段、责任岗位、等待时长和交接历史 |
| 挂号工作台 | 挂号员 | 检索患者、确认科室与号源、创建门诊就诊 |
| 分诊工作台 | 分诊护士 | 录入生命体征与主诉、设置分诊级别、送入候诊队列 |
| 医生工作台 | 门诊医生 | 首诊开检验，复诊查看结果、记录诊断和开药，发药后完诊 |
| 收费工作台 | 收费员 | 分别处理检验费用和药品费用，显示账单来源而非混成一次支付 |
| 模拟 LIS | 模拟外部系统 | 接收检验申请、推进采集与检验、签发结构化结果 |
| 药房工作台 | 药师 | 审方、选择合成库存批次、发药并记录追溯事件 |
| 仿真控制 | evaluator | 查看虚拟时钟、事件和审计，重置当前内存演示 |
| 数据包 | evaluator | 查看 Hospital Baseline、Reference Data Package、生成器版本和来源处置等级 |

普通门诊发热状态按以下责任交接推进：

```text
待挂号
  -> 待分诊
  -> 候诊
  -> 首诊中
  -> 待检验缴费
  -> 待检验
  -> 待复诊
  -> 复诊中
  -> 待药品缴费
  -> 待发药
  -> 待完诊
  -> 已完诊
```

收费工作台根据 Charge Item 的业务来源区分检验和药品队列；模拟 LIS 只在检验支付成功后接收任务；药房只在处方签发且药品支付成功后调剂。所有动作显示当前 expected version，原型可模拟一次版本冲突并刷新最新状态。

医生工作台在同一路由通过 `?variant=A|B|C` 提供三种结构：

- A“工作队列优先”：左侧候诊与复诊队列，中间病历和医嘱，右侧患者上下文与费用状态，适合连续接诊。
- B“患者病历优先”：顶部患者 banner，中央病历 tabs，右侧固定任务栏，适合围绕单患者深入处理。
- C“流程阶段优先”：横向就诊时间线与阶段画布，当前阶段展开编辑器，适合教学和异常定位。

三种方案共享完全相同的合成数据和内存动作，只替换渲染结构。浮动原型切换器只在开发环境显示，左右按钮和键盘方向键更新 URL；输入控件聚焦时不拦截方向键。

Web/Desktop 的目标设计以安静、紧凑、可扫描为主。页面使用 shadcn Base UI primitives 和语义 token；命令使用图标加文本，工具使用带 tooltip 的图标按钮，状态使用 Badge，表单使用 Field，列表使用 Table。卡片只用于独立重复项，不把页面区块层层装进卡片。

## Alternatives considered

**每个 HIS 模块各做一张独立静态图。** 产出快，但不能观察状态交接、队列变化、多岗位共享和并发冲突，也无法判断页面信息是否足以完成动作。

**先复刻 OpenHIS 全部菜单。** 它覆盖面广，却会让尚未实现的住院、医保、病案和库存能力看似可用，并把首期闭环淹没在模块层级中。

**所有页面都做三种方案。** 比较范围最大，但大部分列表和表单页面的结构风险较低，工作量会从验证关键决策变成重复视觉探索。首期只为医生工作台保留三种根本不同的信息架构。

**直接把原型写成生产页面。** 可以减少一次重写，但原型没有真实 API、错误处理、授权和测试，过早共享组件会把未经验证的状态模型固化。选定方案后应按正式 issue 和 TDD 重新实现。

## Acceptance criteria

- `pnpm dev:web` 可以打开 `/prototype/his-flow`，无需后端或凭证即可使用预置合成账户。
- 评审者可以从待挂号推进到已完诊，并在每次角色切换后看到同一患者的最新状态、版本和时间线。
- 每个页面都有正常、空、忙碌或受限状态中至少两个可切换示例，所有主要按钮具有可观察结果。
- 医生工作台 A、B、C 在信息层级、布局和主要操作位置上明显不同，而不是只改变颜色或间距。
- 原型切换器更新 URL、支持左右方向键、输入聚焦时不抢键，并在生产构建中隐藏。
- 1280×800、1440×900 和 390×844 视口无文本溢出、控件遮挡或不可达操作；移动视口使用 Sheet 或纵向布局，不缩放桌面三栏。
- 所有患者、账户、机构、目录、批号、交易和审计内容均明确为合成数据，不包含参考仓真实值。
- 原型源文件和路由清楚标记为 throwaway；选型后将结论写入实现 issue，正式代码重写，原型只保留在 throwaway branch。

## Risks

内存状态无法验证真实的授权、事务、轮询和并发行为。原型只能确定信息架构与交互意图，不能作为后端可行性证据。

单患者 golden flow 容易低估密度。原型必须提供 density 切换或拥挤队列示例，选型时同时检查长姓名、长药名、多条费用和异常状态。

角色切换是评审便利，不等同生产中的登录与委托。正式实现必须使用 Better Auth 和服务端 Actor context，不能把原型的客户端角色状态迁入授权逻辑。

医生工作台可能因首个场景而过度专用。正式组件只提取被第二个真实页面复用的视觉 primitive，业务视图保持场景与岗位语义清晰。
